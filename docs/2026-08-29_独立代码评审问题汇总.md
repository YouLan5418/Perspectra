## 三、严重问题（7 项）

### S-1 🔴 Director 上下文读取全部私有作用域发言【在产信任边界】

- **证据**：`packages/application/src/context-pipeline.ts:268`
  ```ts
  const publicEvents = history.filter(event => event.eventType.startsWith('scene.') || event.eventType === 'character.speak')
  ```
  配合 `:281-284`：`value: event.data`（完整正文）、`sourceRef: eventSource(event, 'scene_public_event')`（错误标注为公开来源）。
- **可达性证据**：`packages/kernel/src/rulebook.ts:138` 证明 `character.speak` 事件携带 `scope` 与完整 `text`；`:140-143` 内核正确产出了 `observationScope`。**角色观察路径是有作用域的，Director 路径完全绕过它。**
- **当前不可达原因**：`rainy-road-pack.ts` grep `role: 'director'` **0 命中**——验收包没有 Director，canary 是盲区。
- **影响**：违反规格 §11「权限过滤先于聚合」与 §19.1 零泄漏矩阵；一旦启用 Director 即生效，且无任何测试能拦住。
- **建议**：按 `scope === 'scene_public'`（及 Director 可见策略）过滤；补 Director 方向的私密正文与跨 Scene canary。
- **交叉验证**：Qwen 判严重（对）；GLM 判中等且遗漏了同族 S2（低估）。

### S-2 🔴 玩家私语经 stimulus 注入全部被调度 NPC【在产信任边界，每轮可达】

- **证据**：`packages/application/src/context-pipeline.ts:236`
  ```ts
  stimulus: context.playerAction, stimulusHash: hashWorldJson('context-stimulus/v1', context.playerAction),
  ```
- **触发条件**：玩家使用 `scope: 'private' / 'direct'` 发言（`rulebook.ts:124-126` 要求带 `addresseeIds`）+ 场上 ≥2 个 NPC 被调度。这是**正常玩法**，非边缘场景。
- **不对称性**：同一条玩家动作，走观察路径时正确降级为 `occurrence_only`（`round-coordinator.ts:550-555`），走 stimulus 路径时**原样注入**每个角色的 `current_stimulus` 段（`context-v2.ts:373`）。
- **影响**：非目标 NPC 获得私语正文与 `addresseeIds`。
- **建议**：在 `#prepareCharacter` 中按 `playerAction.parameters.scope / addresseeIds` 对 stimulus 脱敏；非收件人降级为 occurrence-only。
- **交叉验证**：**GLM 完全漏掉此项**，Qwen 正确识别。

- **交叉验证**：**两份 8/29 报告均未覆盖**，是本次审查的独立发现。

### S-4 🔴 该缺口同时是上下文层 O(T²) 的根因【独立新增，两笔债同源】

`packages/agents/src/continuity.ts` 的 tail 重建链路：

```
:266   for (const event of this.world.readEvents(address, asOfWorldSeq))
       // ① 全量读取并反序列化整条历史（无下界参数）
:267   if (event.seq <= afterSeq) continue
       // ② afterSeq = checkpoint.sourceEndSeq，因冻结而永远停在开局
:293   blocks.slice(-maximumBlocks)
       // ③ 最终只保留 4 / 10 / 20 个块
```

**每轮每角色：全量读历史 → 丢弃绝大部分 → 只留 10~20 块。** 扫描量随历史线性增长 → 全会话 O(T²)。

这正是规格要用「Tail Block 数触发 Checkpoint 重建」阻断的东西：checkpoint 前推 → `afterSeq` 跟着走 → 扫描被约束在增量区间。

- **影响**：与 Round 决议路径的 O(T²)（见 M-1）叠加，两者同源不同层。
- **建议**：与 S-3 **同一笔修复**——补增量水位即可同时闭合长程记忆断层与上下文层 O(T²)。
- **交叉验证**：两份 8/29 报告均未识别此关联。

### S-5 🔴 `localeCompare` 进入确定性哈希链【跨环境时间炸弹】

- **证据**：`packages/agents/src/reflection.ts:268`
  ```ts
  const ordered = [...values].sort((left, right) => left.kind.localeCompare(right.kind) || left.id.localeCompare(right.id))
  return hashWorldJson('character-cognition-policy-state/v1', { records: ordered })
  ```
  该哈希 → `expectedStateHash` → Policy Receipt → 权威哈希链。
- **分布**：26 处 / 13 个生产文件（`world-spec.ts` 9、`cognition-projection.ts` 3、`round-coordinator.ts` 3、`world-store.ts` 2、`reflection.ts` 1 等）。
- **后果限定（重要）**：发散时表现为 **fail-closed 完整性错误**（`BUNDLE_HASH_MISMATCH`），不是静默数据损坏。但已提交的 Round 若在另一环境重放验证失败，会导致 `verifyBranchIntegrity` 不通过——**世界变为不可用**，故仍判严重。
- **概率**：当前 CI（Windows + Ubuntu × Node 22/24）通过，说明现有数据未触发；仅当 id 含大小写混排、重音或非 ASCII 时可能发散。
- **建议**：将 `compareText`（码元序）提到 `contracts` 作为公共原语并全局替换。见 N-C。

### S-6 🔴 `recordClarification` 无分支相位屏障

- **证据**：`packages/store-sqlite/src/world-store.ts:1077-1135` 区间内 `runtime_phase` / `branch_controls` 命中数 **0**。
- **对照**：`#forkBranch`（`:717-724`）、`#assertCommitAdmission`（`:1440-1447`）、`#assertAdmissionOpen`（`:1416-1437`）均检查相位——**只有这条写入路径没有**。
- **调用点**：`packages/application/src/world-application.ts:545-556` 裸开 `new WorldStore(...)` 直接写，位于任何 guard 之外。
- **影响**：被隔离（quarantined）或维护中的分支仍可持久写入 clarification 与审计记录，控制面违规。clarification 非权威（不建 Round、不推进 Tick），影响可控但性质明确。
- **建议**：在 `recordClarification` 内加 `#assertAdmissionOpen` 同等的相位检查，或将调用点纳入 `#durableReadGuard`。

### S-7 🔴 参与者模型调用串行【接入真实模型后成为主控项】

- **证据**：`packages/application/src/round-coordinator.ts:681` 为 `for` 循环，`:777` 在其中 `await runner.invoke(...)`。全仓库参与者冻结路径上无任何 `Promise.all`。
- **量级**：3 个参与者 × 1.5 s = 4.5 s/轮；并行化后约 1.5 s/轮。
- **为何严重**：接入真实 Provider 后这是延迟主控项，收益远超同期的计算优化。
- **⚠️ 不能简单加 `Promise.all`**：`ModelBudgetLedger` 共享，串行消费顺序决定「预算耗尽时轮到谁」。并行会破坏确定性闭环。需先把预算预扣改为**原子批量预留**。
- **建议**：先做预算预留的确定性改造，再并行化。可与缓存断点（见 O-2）叠加，两者收益相乘。

## 六、重要校准：被模型延迟稀释的性能问题

M-1（Round 决议 O(T²)）的**形状确定**（由代码结构决定），但**绝对占比需放在端到端链路里看**：

| 轮数 | 世界计算 | 模型调用（3 人 × 1.5 s） | 计算占比 |
|---:|---:|---:|---:|
| 500 | 47 ms | 4,500 ms | 1.0% |
| 1,000 | 94 ms | 4,500 ms | 2.0% |
| 3,000 | 282 ms | 4,500 ms | 5.9% |
| 10,000 | 940 ms | 4,500 ms | 17% |

**结论**：在可玩到的现实长度内是 1%~6% 的旁枝。上表 ms 数为从代码结构推出的**估算**，非实测。

**反直觉要点**：项目当前跑的是**脚本化 provider**（`mystery-demo.ts` 中 `timeoutMs: 100`、`estimatedTokens: 1`），所以 **O(T²) 恰恰在「当前无模型模式」下最明显，接入真模型后反被掩盖**。这解释了它能潜伏至今：现有测试全跑在无模型模式，且只跑几十轮——恰好落在曲线最平坦处。

**修订**：M-1 由原「严重/Top 1」下调为「中等（长会话保健项）」，让位于 S-7（串行调用）与缓存断点——后两者作用于主控项。

### O-2 云端模型缓存：无，且是有意设计；但架构「缓存就绪」

**无缓存的证据**：全仓库（排除测试/node_modules）零 `fetch(` / `node:https` / `axios` / `undici` / OpenAI / Anthropic SDK；`cacheHit?: boolean`（`provider-request.ts:52`）**从未被生产代码读取**，仅在两个测试中被赋值以验证「不进哈希」；`round-coordinator.ts:807` 硬编码 `cache: null` 与 `provider: 'scripted'`；`character-controller-cache/v1`（`phase8-registries.ts:107`）只注册未实现。

**这是符合 `AGENTS.md:8`（Phase 0 仅允许 cordis；远程须经 Bridge）的正确状态，不是遗漏。**

**但架构恰好缓存友好**：前四段在同一 world+branch+manifest 下逐字节稳定——`host_protocol` / `controller_contract` 是代码常量，`world_public_anchor` / `character_anchor` 绑定 `manifestHash`（`context-v2.ts:343-345`）。ADR-0068 `:28` 亦明确「Cache key 可以因布局变化失效而不改变语义身份」，规格 `:654` 有「Alice/Bob 的缓存前缀按 Checkpoint/Tail 规则稳定」。

**建议断点打在 `character_anchor`（第 4 段）之后**。接入时注意五个坑：① 断点无字段可标，`ExactProviderRequest`（`provider-request.ts:56-63`）无 `cache_control`，扩契约会改 `providerRequestHash`，**按 `AGENTS.md:3` 属 ADR 级变更**；② `continuity_checkpoint` 排第 5 位会周期性变动，断点须在其之前；③ 若将来动态调整 `sampling` 会清零命中率；④ `canonicalizeWorldJson` 会按键名排序（`world-json.ts:70`），别把哈希字节流当传输字节流；⑤ 隐私优先导致**每个角色前缀不同，缓存无法跨参与者共享**——收益来自同角色跨轮次复用，而非多角色共享，与并行化不叠加预热。
