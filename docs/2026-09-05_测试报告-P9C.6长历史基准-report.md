# P9C.6 长历史基准：先测量，不改生产逻辑

> **结论：长历史成本明确增长，P9C.6 性能门槛未闭合。** 本轮没有优化内核、放宽校验或调用外部模型。以下是单机诊断结果，不是跨平台 SLA，也不是十万轮真实聊天的验收。

## 测了什么

环境为 Windows / Node 24.14.1。使用 [measure-reaction-history.ts](../tools/measure-reaction-history.ts) 激活正式 v5 Manifest，随后通过带 Writer Fence 的 `WorldStore.commitRound` 每批提交 1,000 条合法 `character.speak` 事件，生成零、一万、十万条附加历史。生成前后均使用正式数据库与 Hash，不直接 SQL 灌入假 Hash。

这是 **Store 级对白日志负载**：历史事件不附带 Observation、Memory 或 Outbox，也不经过玩家 Authority 管线，故只用于隔离日志体积成本，不能代表完整长期聊天。新增的一次玩家输入和 NPC wave 才经过完整 WorldApplication、Context、Memory 和 Provider 生命周期。两名 Scripted NPC 即时 abstain，消除网络与模型推理时间。

`root-cold-mount` 指关闭初始化应用后重新挂载；不是操作系统冷缓存。建库仍在同一进程，RSS 包含建库残留和尚未回收对象，不是独立的运行时峰值或泄漏证据。

## 结果

| 附加历史事件 | 玩家输入（含重新挂载） | NPC wave | wave 结束 RSS（首次无 CPU 采样） |
| --- | ---: | ---: | ---: |
| 0 | 137 ms | 63 ms | 约 93 MiB |
| 10,000 | 710 ms；复测 718 ms | 428 ms；复测 438 ms | 约 262 MiB |
| 100,000 | 5,667 ms；范围计数复测 5,622 ms | 3,875 ms；范围计数复测 3,866 ms | 约 873 MiB |

十万条另外两次 CPU 采样运行，wave 均约 3,964～3,965 ms；有采样开销，不与无采样数据混为统计分位数。本轮样本不足以报告 P95。

所有合法负载运行的正式 wave 都执行了两次 Provider 调用并正常提交。随后同键重放不读取历史、不再次调用 Provider，约 0.36～0.44 ms；前后 `verifyBranchIntegrity` 均通过。十万条运行最终 `headSeq=100018`、`tick=102`、`roundCount=103`。

不同新建库 Root bundleHash 可包含不同的耐久运行时决策；本测试只断言同库幂等，不宣称不同墙钟运行的整个 Root Bundle 全等。

## Evidence → Finding → Path

### Evidence

- **E-001**：基准脚本和逐阶段 JSON 输出。首次日志在本机 `.tmp/p9-history-zero.log`、`.tmp/p9-history-10k-speech.log`、`.tmp/p9-history-100k-speech.log`；这些本机产物不进入 Git，下面命令可重建。
- **E-002**：十万条范围计数运行 `.tmp/p9-history-100k-range.log`：wave 的 `readEvents` 调用 1 次、返回 100,015 行、耗时约 527 ms；`readEventsRange` 调用 18 次、累计返回 400,050 行、耗时约 2,872 ms。返回行数包含重复读取，不是 SQL 扫描行数；方法时间为 inclusive，不应当作互斥 CPU 时间相加。
- **E-003**：仅 wave 的 CPU 采样 `.tmp/p9-history-100k-wave/wave.cpuprofile`。SQLite `all` 自耗时样本约 1,374 ms，序列化约 479 ms，GC 约 304 ms。`all` 的调用链落在 `readEventsRange → rebuildAt → catchUp`、`historyAt → rebuildCharacterAt`、`catchUpV2 → catchUpWithContext` 等多条路径；不只 Scheduler 的直接 `readEvents`。
- **E-004**：初次用重复 `scene.upsert` 造历史被 Scene v2 以“不能重新定义 Scene”拒绝。此失败是无效 Fixture，已改为合法对白日志，未绕过校验；失败样本不进入性能结果。

### Finding

- **F-001（E-001/E-002）**：即便没有大规模认知状态、没有模型推理，十万条历史仍给一轮 NPC 反应带来约四秒本机成本，不能宣称长会话已流畅。
- **F-002（E-002/E-003）**：重复历史读取、对象构造、Canonical 序列化及校验共同构成优化目标。仅优化一次 `ReactionScheduler.readEvents` 无法消除其余 Context / Memory / Projection 路径。
- **F-003（E-001）**：同库耐久幂等短路有效，当前测得的增长集中在新执行路径，不是每次重复请求都重跑历史。

### Path

下一步先列出同一 `(address, asOfSeq)` 在单次 wave 内的重建与读取调用，评估可以安全共享的已验证输入；任何复用都必须保留 Branch、角色权限和精确水位边界。随后才实施最小优化，并对旧新实现进行 Event/Authority/Context Hash、重启、fork、future canary 对照。不采用最近 N 条截断、不跳过来源校验、不先建一个跨轮全局缓存。

完整聊天的 Observation / Memory 增长、多分支 256 pending Job、查询计划、十万事件 / 128 Branch 混合压力和跨平台时限仍未完成。

## 如何复现

仓库根目录执行，输出目录必须不存在；数据库保留供复核，不覆盖现有目录：

```powershell
node --import tsx tools/measure-reaction-history.ts .tmp/history-baseline-new 0
node --import tsx tools/measure-reaction-history.ts .tmp/history-10k-new 10000
node --import tsx tools/measure-reaction-history.ts .tmp/history-100k-new 100000
$env:P9_PROFILE_WAVE='1'
node --import tsx tools/measure-reaction-history.ts .tmp/history-wave-profile-new 100000
Remove-Item Env:P9_PROFILE_WAVE
```

最后一次会在新目录生成 `wave.cpuprofile`，可用 CPU Profile 查看器打开。脚本输出耗时、公开读取次数/行数、RSS、提交结果与完整性摘要；没有 Secret 或真实模型响应。报告采用 docs-generator 的方法限制与 Evidence → Finding → Path 结构。
