## 3. 剩余拒绝的真正原因（第一次被看到）

修复说明的"保存被拒原文"生效后，首次拿到被拒输出。DeepSeek 那 1 次拒绝：

```
validationError: step manifestation contains missing or unknown fields
participant: agent:claude   renderer: grouped-playtest/v2
rawOutput: …,{"actionType":"interact",…,"manifestation":{"independent":["nod"]}}
```

**`manifestation` 只有 `independent`，漏掉必需的 `onSuccess`。**

同一形态在修复后的 Ollama 世界是**系统性**的：4 份被拒输出共 8 个 `manifestation` 对象，`onSuccess` 出现 **0 次**。

对照修复前：重放旧请求记录得到的 3 份 qwen 输出和 2 份 DeepSeek 输出，`independent` 与 `onSuccess` **两个键都在**。也就是说，"漏 `onSuccess`"是**修复引入的新形态**。

## 4. 定位到具体构造：`anyOf`/`allOf` 块是净负面

修复为表达"合计至少一码""跨数组不重复"新增了 `anyOf`（任一数组 `minItems: 1`）与 `allOf`（每个码一条 `not{contains}`）。做了一次 A/B：取修复后的同一份请求记录，**只把 `format` schema 里的 `anyOf`/`allOf`/`not`/`contains` 去掉**（枚举收窄、`required`、`maxItems`、`uniqueItems` 全部保留，消息与文案一字不动）：

| 条件 | 结果 |
| --- | --- |
| 修复后 schema（含组合子） | 4/4 被拒，8/8 个表现对象漏 `onSuccess` |
| 去掉组合子后 | **2/2 被接受**，每次都写出 `onSuccess` |

因此：**枚举收窄是有效的那一半**（它正是修复前被证明存在的问题），**组合子块是有害的那一半**。最可能的机制是 `anyOf` 里出现 `onSuccess`，被读成"两个数组二选一即可选填"，与同一个 schema 里的 `required: ['independent','onSuccess']` 语义打架。

注意这条不能只用"语法转换不支持"解释：DeepSeek 路径**没有任何 schema 强制**（只发 `response_format: json_object`），却出现了同一个漏字段。所以更像"schema 语义本身被误读"，两个 Provider 都会中招。

## 5. 对穷举一致性测试的限定

`grouped-playtest.test.ts` 新增的 3⁸ 组合对照（39366 组）用 **Ajv** 判定 schema 侧，与正式校验器比对，测试本身是严谨的、正是需要的形态。但它的结论**只覆盖 Ajv 的语义**：本次实测说明运行时（Ollama 的 `format` 转换）对同一份 schema 给出的是另一套语义。所以该测试可以全绿而真实模型仍然踩坑——**测试验证的是一个运行时并不遵守的假设**。

## 8. 建议

1. **保留枚举收窄与 `required`，去掉 `anyOf`/`allOf`/`not`/`contains`。** 这是本次数据支持的最小修正：有效的那半留下，有害的那半拿掉。
2. "合计至少一码""跨数组不重复"改为**只在正式校验器层保证**（现语义即如此），或只写进文案；不要用运行时可能不遵守的组合子表达。
3. 若坚持用组合子，需要先加一条**运行时级**验证（真实 Ollama 语法转换下的接受率），而不是只与 Ajv 比对。
4. 保留"被拒原文 + 精确校验原因"：本次剩余原因的定性完全依赖它。
