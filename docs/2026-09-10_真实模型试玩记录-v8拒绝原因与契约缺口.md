# 2026-09-10 真实模型试玩记录：v8 被拒输出的原因分层与契约缺口

> 修订说明：本文件已按评审意见修订。**第一版把"重放复现的失败原因"当成了"线上每次失败的原因"，这是错的**；同时把契约缺口列得过窄。下面把「线上耐久记录能证明什么」与「重放能证明什么」分开陈述，并给出完整的校验器规则 ↔ schema 表达力对照。

## 1. 结论

按[创作者 World Pack 与真实模型试玩指南](CREATOR-PLAYTEST-RUNBOOK.md) 推荐的 **`worldpack-source/v4` Pack + `--interactions`** 路径试玩示例包《一觉醒来，我的大模型们都变成了美少女》时，一部分角色输出被整条丢弃、该轮沉默。实测存在**两类互不相同的拒绝**：

| 类别 | 证据来源 | 是否由"schema 过松"造成 | 可否靠收窄 schema 修掉 |
| --- | --- | --- | --- |
| **甲类**：根对象字段集不符 | 线上耐久记录（10/10 次拒绝都是这一类） | **否**——根对象允许字段与 schema 完全一致 | **不能** |
| **乙类**：表现码与动作绑定的组合违规 | 仅重放复现（线上记录无法证明） | **是**——schema 许可、校验器必拒 | 能，但只能覆盖乙类的一部分规则 |

两类混在同一句"代码问题"里是错的，故第一版的定性作废。可确立的是：**乙类是真实的代码缺陷**（schema 与校验器不一致）；**甲类不是**，甲类的成因在耐久记录里无法判定，必须先补上"保存被拒原始输出"才有定论。

按用户要求：**只记录，不改代码**。

## 3. 线上观测（耐久记录，权威）

| Provider / 模型 | Provider 调用 | `committed` | `invalid_response` |
| --- | --- | --- | --- |
| ollama / `qwen3.5:4b` | 4 | 0 | 4 |
| deepseek / `deepseek-v4-flash` | 13 | 7 | 6 |

DeepSeek 世界逐角色：`agent:deepseek` 4 次调用 0 次成功（该角色整场没说出一句话）；`agent:claude` 3/4；`agent:gpt` 3/4；`agent:glm` 1/1。

**10 次拒绝的 `provider_calls.terminal_json` 原因串完全相同**：

```
WorldError: submit_actions contains missing or unknown fields
```

这条消息在 `packages/agents/src/submit-actions.ts` 里只可能由四处抛出，路径分别是 `submit_actions`（根）、`actions[i]`、`step manifestation`、`submit_actions.reflection`。带 `WorldError:` 前缀的是 `#validateGroup` 的失败路径，而消息里**只有根级那一条路径不带后缀**，因此这 10 次全部是**根对象字段集不符**（`exactWithOptional(root, ['schemaVersion','decision','actions'], ['reflection'], 'submit_actions')`）。

关键推论：**schema 的根 `properties` 与校验器的根允许字段完全相同**（都是 `schemaVersion` / `decision` / `actions` + 可选 `reflection`）。所以这一类拒绝**不可能**由 schema 过松解释——模型给出了 schema 明文禁止的根字段，或漏了必需的根字段，而运行时没有拦住。至于是哪一个字段，**耐久记录无法判定**（见 §5）。

## 4. 重放复现（证明缺陷存在，不等于历史原因）

`*.invalid.json` 不保留被拒原文，故用 `*.request.json`（含 `messages` 与 `schema`）原样重放。**重建的请求体与线上逐字节一致**——4 份 Ollama 请求的 `wireBodyHash` 全部相同（如 `sha256:fee3ce9adb63…`）：

```
rebuilt wireBodyHash: sha256:fee3ce9adb6325b99e652b0929d7052e5dcd5437268902546bd7244183877a9b  (identical: true)
```

即：**同模型、同消息、同 schema、同 `temperature 0.3` / `seed 42` / `num_predict 2048`，重放仍得到与线上不同的结果**。因此：

- 重放**能**证明"存在一类 schema 许可但校验器必拒的写法"；
- 重放**不能**确定历史上每一次拒绝的具体原因；
- §3 的 `invalid_response` 计数与本节重放样例必须分开看待，不能互相佐证。

## 5. 诊断缺口（必须与修复项一起做）

`provider_calls` 只留了 `terminal_json` 里的原因串（粒度到路径），`*.invalid.json` 只留 `reasonCode`（粒度到类别），**两者都不含被拒原文**；无效调用时 `response_json` 存的是脱敏替身：

```json
{"actions":[],"decision":"abstain","invalidModelOutput":true,"schemaVersion":5}
```

后果：**甲类到底错在哪个字段，今天就查不出来**。这直接决定了修复优先级——在补上证据留存之前，任何针对甲类的修复都是在猜。

## 6. 甲类与乙类的分界（为什么不能合并成一句"代码问题"）

- 甲类：模型输出**违反了自己收到的 schema**（根字段集不符）。schema 是正确且够严的，运行时没有拦住它。这属于 Provider 侧强制力/合规问题，不属于"schema 太松"。
- 乙类：模型输出**完全符合自己收到的 schema**，但不符合校验器。schema 与校验器不一致，是真实代码缺陷。

两者用同一条错误串出口，只靠 `reasonCode` 分不开；这也是 §5 那条缺口为什么值得单列。

## 7. 校验器规则 ↔ schema 表达力完整对照（乙类的边界）

来源：`packages/agents/src/submit-actions.ts` `#validateGroup` 与 `actions()`；`packages/contracts/src/action-group.ts` 的 `ACTION_GROUP_CUES`；试玩实际下发的 schema 由 `tests/experiments/grouped-playtest.ts` 的 `groupedPlaytestRequest()` 生成。

| # | 校验器规则 | schema 是否已表达 | 说明 |
| --- | --- | --- | --- |
| R1 | 根对象、字段集 `{schemaVersion,decision,actions}` + 可选 `reflection` | ✅ | `additionalProperties:false` + `required` |
| R2 | `schemaVersion === 版本` | ✅ | `const` |
| R3 | `decision ∈ {act,abstain}` | ✅ | `enum` |
| R4 | `actions` 为数组、≤2 项 | ✅ | `maxItems:2` |
| R5 | 每步字段集 `{actionId,actorId,actionType,actionVersion,parameters}` + 可选 `manifestation` | ✅ | 同上 |
| R6 | `actionId` 非空 | ✅ | `minLength:1` |
| R7 | `actionId` 在本次输出内唯一 | ❌ **G7** | 跨数组项唯一性无标准关键字 |
| R8 | `actorId === 本角色` | ✅ | `const` |
| R9 | `actionType` 属于 `speak/move/interact` | ✅ | `oneOf` 分支 `const` |
| R10 | `actionVersion === 1` | ✅ | `const` |
| R11 | 表现对象字段集恰为 `{independent,onSuccess}` | ✅ | `required` + `additionalProperties:false` |
| R12 | 每个码 ∈ 码表 | ✅ | `enum`（但未按动作收窄 → **G1**） |
| R13 | 绑定码必须在 `onSuccess`，且动作类型匹配（声音↔speak、步态↔move） | ❌ **G1** | 现在两个数组对每个步骤都枚举全部 8 码 |
| R14 | `independent + onSuccess` 合计非空 | ❌ **G3** | 两数组各 `maxItems`，无"合计≥1" |
| R15 | 合计 ≤8 | ❌ **G4** | 数组长度之和无法表达（各数组 8 已表达） |
| R16 | 合计内无重复（含跨数组） | ❌ **G2** | `uniqueItems` 只作用于单个数组 |
| R17 | 每步数组各自 ≤8 | ✅ | `maxItems:8` |
| R18 | `decision === 'act'` ⟺ `actions` 非空 | ❌ **G5** | 无 `if/then` |
| R19 | 两步必须恰好一次 `speak` | ❌ **G6** | 现仅限制 ≤2 项与每项类型 |
| R20 | `parameters` 为规范 JSON | n/a | JSON 解码值天然满足 |
| R21 | `parameters` 形状（`text` 长度、`locationId` 枚举等） | ✅（偏严） | 校验器在此层不查；最终由内核 Rulebook 裁决，方向安全 |
| R22 | `reflection` 字段集 `{operations}`、≤ `maxReflectionOperations` | ✅ | reaction 调用直接不下发 `reflection` |

**表达力结论（对"收窄枚举 + 补互斥文案"的直接回答）**：

1. **G1 可表达且是主要收益**：按 `actionType` 收窄 `onSuccess` 枚举、把 `independent` 固定为 5 个无绑定码，可同时消掉"声音码进 independent""步态码进 speak 步"两种子情形。
2. **G2 不是一等关键字**：标准 JSON Schema 无法直接表达"两数组互斥"，只能对每个码各加一条 `allOf` + `not` + `contains`（共 8 条）。**该写法能否被本机运行时的语法转换支持尚未验证**，需先做实验。
3. **G3 不能写成"两个数组都 `minItems:1`"**：`independent: []` 是**合法**的（现有测试 `grouped-playtest.test.ts:67` 就是 `{independent: [], onSuccess: ['slow_walk']}`）。正确写法是 `anyOf`（任一数组 ≥1 项）。
4. **G4 不可表达**：没有"数组长度之和"关键字，只能靠 G1/G2 收窄后压低概率，或在别处容忍。
5. **G5 / G6 可表达但被漏掉**：`decision` 与 `actions` 的对应、两步"恰好一次 speak"都属 GPT 指出的"动作组合与 decision 对应"规则，`if/then` 与 `contains`+`minContains/maxContains` 可以覆盖。
6. **G7 不可表达**。
7. 因此目标必须降级为"**schema 合法 ⇒ 校验器合法，除 G2/G4/G7 三条残余**"，而不是最初写的"完全等价"。

## 8. Provider 强制力不对称（决定修复上限）

| Provider | 下发的约束 | 强制力 |
| --- | --- | --- |
| ollama | `format: <JSON Schema>`（抽查自 `playtest-runtime.ts:250`） | 由运行时转成语法约束；**是否密不透风存疑**（甲类即证据：根字段集 schema 与校验器一致，模型却越界） |
| deepseek | 仅 `response_format: {type:'json_object'}`（`playtest-runtime.ts:253`），**不带 schema** | 只保证"是 JSON"，不保证"符合 schema" |

结论：**对 DeepSeek 路径，"schema 合法 ⇒ 校验器合法"在结构上不可达**，收窄 schema 只是提示词级的概率改善。这条路径恰恰是用户要用的那条，所以乙类修复（收窄枚举等）不足以单独收口；甲类更需要 Provider 侧强制或"被拒后可控重试/降级"，而不是改 schema。

## 9. 影响与边界（含第一版需修正的一处）

- 失败是**整条提议**被丢弃：台词、动作、表现一起作废，角色该轮沉默，页面只提示 `一个角色返回了无效动作格式；本次输出已忽略，角色可在后续轮次重试。`
- **第一版写"不会熔断"不准确**。`world.sqlite` 的 `character_runtime_availability` 确实仍为 `ready`（会话级不可用没有发生），但 `context.sqlite` 的 `provider_quality_state` 在累计无效输出：本次 `agent:deepseek` 的 `response_invalid_streak = 2`，`response_backoff_level = 0`。阈值来自 `PHASE8_PROVIDER_QUALITY_PROFILE`：`invalidResponseThreshold = 3`，退避梯度 `probeBackoffEligibleTicks = [1,2,4,8]`。即 **streak 达到 3 就开始按 1/2/4/8 个 eligible tick 退避**，长会话里反复无效会让该角色参与度阶梯式下降。所以"沉默"不是无代价的。
- 与 Pack 内容无关：表现码表与协议在协议层，创作者无法通过改 Pack 规避。
- 世界本体是好的：GLM 首轮成功提交 `speak + move` 两步组并真的换了场景；玩家 `/interact entity:phone core:take` 正常产出 `entity.transferred`（seq 154，`toHolderId: character:player`），NPC 随后对该动作作出场景内反应。

## 10. 对被评审修复方案的评价（未实施）

方案四项与本记录的对应关系：

| 方案项 | 评价 |
| --- | --- |
| ① 从同一码表派生契约、试玩 schema 与上下文描述共用 | 正确，且是消掉 G1 的前提。注意它**触及生产 src**：`context-pipeline.ts` 的 `actionGroupTool`/`interactionTool`（生产包要求逐文件 100% 覆盖），派生函数若也放 `packages/contracts` 同样受此约束，需一并补测试 |
| ② schema 内表达跨数组不重复、表现非空；无表现时省略 `manifestation` | 方向正确但**不足以兑现"schema 合法即校验器合法"**：G2 需 8 条 `not`+`contains` 且运行时支持待验证；G3 必须用 `anyOf` 而非两个 `minItems:1`；G4/G7 不可表达；**G5/G6 未列入但同样必要**（GPT 指出的动作组合与 decision 对应）。另外 ② 只对 Ollama 那条路径有强制力，DeepSeek 无（见 §8） |
| ③ 契约定性测试覆盖每个码、每类动作、重复、空数组 | 正确且必要。建议再加一条"**schema 表达力对照**"测试：逐条断言 R1～R22 里可表达的规则确实被 schema 表达，不可表达的显式登记为已知残余，避免下次又靠人工比对 |
| ④ 保存被拒原始响应及具体校验原因 | **优先级最高**。它是甲类定性的前提（§5），也是本记录第一版出错的直接原因。落点：试玩侧 `playtest-runtime.ts` 写 `invalid.json` 时补被拒原文与校验消息；生产侧 `provider_calls.response_json` 同样只存了脱敏替身，需一并核对。注意原文属角色私有上下文，证据目录本就地保存完整请求，隐私面不新增 |

补充：若希望"单条错码不致整轮沉默"，那是改校验器失败语义（ADR-0085 的"先成功不因后续拒绝撤回"之外的"局部降级"），属方向变化，须走新的 superseding ADR，不应顺手改。
