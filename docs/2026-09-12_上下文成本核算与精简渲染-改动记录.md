# 上下文成本核算与精简渲染：改动记录

- 日期：2026-09-12
- 分支：`feat/summary-digest`
- 范围：**全部落在实验侧**（`tests/experiments`）。生产契约、注册表锁、世界包格式一个字都没动。

---

## 1. 起因：成本是"每次调用 × 每次上下文的 token"

代码里的上限是**一次行动最多 8 次 NPC 调用**（`RESPONSIVE_V1_MAX_NPC_CALLS = 8`，最多 3 波、每角色最多 2 次），这还没算玩家轮本身的调用。所以省钱的单位不是"每轮省多少"，而是"每次调用省多少 × 8"。

而实测出来的账是这样（60 轮世界）：

| 观测项 | 数值 |
| --- | --- |
| 调用次数 | 60 |
| 总输入 token | 787,307 |
| 缓存命中 token | 40,854（**5.19%**） |
| 中位数每轮新增 token | **21** |
| 检查点重建次数 | 49（60 轮里） |

**每轮真正新增 21 个 token，却要按 17,242 个 token 付费**——99.8% 是每轮重复发送同一批旧内容。

## 2. 成本核算组件

`tests/experiments/context-cost.ts`。每次调用记录你关心的那七项：

总输入 Token / 缓存命中 Token / 未命中 Token / 缓存命中率 / **缓存断点落在哪一段** / 本轮新增 Token / **是否发生检查点重建**。

要点：

- **按角色分别记账**。同一轮里 Alice 和 Bob 的上下文不同，可复用的是"该角色上一次调用"的前缀，不能跨角色算。
- **断点用逐条比对定位**：从上一次同角色的消息列表起，第一条字节不同的消息就是断点，它之前的全部可复用。顺带输出它属于哪一段（`continuity_checkpoint` 这类名字）。
- **检查点重建**从第 5 段的水位直接读出来，不需要生产代码暴露任何东西。
- **token 是估算**：仓库里没有 DeepSeek 的分词器，中日韩字符按 0.65、其他字符按 0.28 折算（系数在文件顶部两个常量里）。用途是横向比较与定位，不是报销；要精确到分得接 Provider 的 `usage`。
- 附带 `estimateCostCny()`，按 DeepSeek Flash 的价格（未命中 2 元、命中 0.04、输出 8 元、空闲半价）折算。

**它立刻验证了两件事**：断点确实钉在第 5 段（连续性），命中率 5.19%；以及基线**几乎每轮都在前移**（60 轮里 49 次）——这正是第 5 段每轮都变的直接原因。

## 3. 精简渲染：按段投影，而不是删固定的几个键

试玩现在的精简规则有个漏洞：它维护一份"机器字段"清单，但把 `content` 当作叙述载荷整个放行。而观察记录恰好藏在两层 `content` 里，于是下面这些全都进了提示词：

```
actionId、observationId、status、reason: null、transactionId、roundId、
blockHash、authorityHash、sourceRef{sourceHash: sha256(64 位)...}、stateHash、schemaVersion
```

`tests/experiments/lean-context.ts` 改成**每段一个投影**：投影器看见段的 content，返回"角色能被告知的东西"，没点到的一律不进提示词。两条固定契约（主机协议、控制器契约）原样通过——它们本来就是写给模型看的。

几个关键投影：

| 段 | 留下的 | 丢掉的 |
| --- | --- | --- |
| 近期对话 | 每轮一条 `{round, lines:[{speaker, text, scope?}]}` | 动作 id、观察 id、状态、空字段、块哈希、事务 id、来源引用 |
| 连续性 | `earlierRounds`（摘要正文，已是散文）+ `holds`（认知记录去掉来源与机器键） | 摘要 id/范围/校验值、`summaryRefs`、地址、水位、epoch |
| 自身状态 | `knows`（意识内）与 `unacknowledged`（没意识到的倾向）分开 | `id`、`stateHash`、`basisRefs`、`source` |
| 场景 | `scene`、`present`、`observing`（`character:` 前缀去掉） | `decisionHash`、`asOfSeq`、调度名单、可行动作名单 |
| 召回 | `{kind, text}` | memory id、捕获哈希、来源 |
| 可行动作 | `["move","speak"]` | `actionVersion` |

还有一条硬约束写进了测试：**机器标识与作者秘密一律不得出现在提示词里**（测试会对 `sha256:`、`stateHash`、`AUTHOR_SECRET_CANARY` 这类串做全量否定断言）。

## 5. 怎么用

```bash
# 三档对比（读一次已有的上下文记录）
node --import tsx tests/experiments/compare-prompt-size.ts <含 final-context.json 的目录>

# 边跑边出成本：七项明细 + 整轮汇总
node --import tsx tests/experiments/measure-context-compression.ts <新目录> 60

# 用精简投影起试玩（实验入口，不影响生产）
node --import tsx tests/experiments/playtest-web-entry.ts --lean-prompt ...
```

试玩开关：`--lean-prompt`（环境变量入口 `HCW_PLAYTEST_*` 那套不变）。默认仍是 `compact`，**没有把任何人的默认行为改掉**。

## 6. 这一批明确没做

- **没有改生产渲染器**。它才是角色控制器真正用的那条路径，改它会动 `providerRequestHash` 与渲染器版本锁（注册表是全局精确匹配，动锁会拒绝所有已编译世界包）。要动它得先解决"注册表版本策略"，那是更大的一件事。
- **没有做缓存优化**。让前缀真正能被复用需要两处结构性改动：历史只追加（Tail 不再滑动、摘要只往后加）与每轮必变的内容（认知、场景、刺激）挪到段末。这两件是本批之后最该做的事。
- **没有接真实 `usage`**。估算值够用来定位"谁在吃钱"，但报销级别的数字要接 Provider 返回。

---

## 7. 下一步建议

按收益排序：

1. **让缓存生效**（历史只追加 + 每轮变的内容后置）。命中率从 5% 提到 90% 以上，按现在的价能再省数倍，且不减少任何信息。
2. **基线不要每轮前移**（比如每 4 轮一次、与摘要分组对齐）。断点会从第 5 段往后挪，中间几轮可复用。
3. **按调用类型分级给上下文**：一轮 8 次调用里，反应波那几次用不上完整历史，但它们现在付的是同一个档位的钱。
4. 压缩阈值等前三件落地、拿到真实 token 曲线之后再定。
