## 3. 绑定、可见性与事实边界

`player-provisional-resolution/v1` 绑定 S0 head、显式 Action、Host 派生的 player/manual_player_immediate、裁决状态、原因、观察范围和规则结果摘要。每个事件使用 `player-provisional-event/v1` 对 `{actionId, draftOrdinal, event}` 哈希。绑定经深拷贝脱离 Resolver 可变引用；最终 phase 0 结果必须重算一致，否则 `BUNDLE_HASH_MISMATCH`，不提交世界效果。

原有 `world-player-candidate-s1` 加入候选 Resolution Hash。Character ContextReceipt 使用既有 `round_stimulus` SourceRef 保存候选与裁剪视图 Hash，并绑定 S1 affordanceHash；Director 通过既有 `director_visible` 条目绑定裁剪视图及其候选 Hash。不新增 Receipt DDL，也不伪造已提交 Event seq：历史、Projection、Checkpoint 与 as-of 仍锚定 S0，候选效果单独标识。

完整视图含领域效果与脱敏关系观察；occurrence_only 仅表示私密交互发生；none 仅保留不含正文的绑定标识。relationId 不在公共关系观察中出现，只通过参与者的可执行 Affordance 提供。Recall 与 ProviderContext 包装层也使用裁剪后的刺激，不旁路传递原始参数。

玩家公开移动将 S0/S1 观察者合并，用于候选与正式 Observation；各完整可见 Agent 的场景元数据和 Affordance 由 S1 计算。历史 Memory 不预写候选，后续 Reaction 仍读取正式提交事实。

## 4. 失效、排序与协议决策

同一 S0、Action、Authority 的玩家结果字节变化属于完整性失败。NPC 在共同候选 S1 上提出动作后，若此前合法的 phase 1 动作改变了资源状态，其动作按实际候选前缀正常 rejected；已经合法成立的玩家效果不回滚。Head/fence 竞争继续由既有耐久并发边界处理。

Provider 仍按规范参与者排序依次调用，没有新增并行调度。NPC ActionGroup 仍按现有稳定顺序裁决，不能插入玩家 phase 0。此次测试不等同于新增并行乱序完成矩阵。

`submit_actions/v5` 已能表达 relation target，C2 无需 v6。两步 NPC 组仍只能是一个 speak 加一个世界操作；没有将 move + release 放宽为合法两步组。玩家仍走当前显式单 Action 入口，双步 PlayerSubmission 属于 C3。
