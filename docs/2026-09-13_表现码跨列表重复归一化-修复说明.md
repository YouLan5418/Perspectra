## 1. 29.2% 无效率的全部来源

C0 门禁首次运行（`deepseek / deepseek-flash`，24 次调用）的 7 条无效输出，逐条解析被拒原文后只有两种形态：

| 形态 | 条数 | 被拒原因 |
|---|---:|---|
| 同一个通用码同时出现在 `independent` 与 `onSuccess` | 6 | `invalid or duplicate step cues` |
| 两个列表都为空 | 1 | 同上 |

其中 6 条的原文形如 `{"independent":["smile"],"onSuccess":["smile"]}`，逐条核对确认跨列表确有重复。

## 2. 为什么这不是"模型不听话"

发给模型的 JSON Schema **无法表达**"两个列表合起来不得重复"：`uniqueItems` 只约束单个列表内部，而 `onSuccess` 的码表是 `independent` 的超集（`packages/contracts/src/action-group.ts:20-21`，`independent` 只含 `actionType === null` 的通用码），所以 `{independent:["smile"],onSuccess:["smile"]}` 对 schema 完全合法。

更关键的是：**生产路径没有给模型任何文字提示**。`createStepManifestationSchema` 生成的 schema 一个 `description` 都没有，角色 Context 的 `host_protocol` 与 `controller_contract` 两段也只是 `{protocol:'proposal_only'}` / `{controller:'character'}` 这样的枚举。唯一一句"不得重复"的 prose 只存在于试玩脚本的契约文本里（`tests/experiments/grouped-playtest.ts:27`）——也就是说门禁的 29.2% 是在**带着一句生产没有的提醒**的情况下测出来的。

结论：schema 允许、生产提示缺失、校验器拒绝。模型输出与 schema 一致，是校验器比 schema 更严。

## 3. 修法：在校验器入口做归并，而不是丢弃整步

`packages/agents/src/submit-actions.ts` 的 `#validateGroup` 内，原来把两个列表拼接后整体查重：

```ts
const all = [...independent, ...onSuccess]
if (all.length === 0 || all.length > 8 || new Set(all).size !== all.length) throw new TypeError('invalid or duplicate step cues')
manifestation = { independent, onSuccess }
```

改为按两种情况归并：

```ts
const alwaysOn = new Set(independent)
const distinctOnSuccess = onSuccess.filter(cue => !alwaysOn.has(cue))
if (independent.length === 0 && distinctOnSuccess.length === 0) {
  manifestation = null
} else {
  const all = [...independent, ...distinctOnSuccess]
  if (all.length > 8 || new Set(all).size !== all.length) throw new TypeError('invalid or duplicate step cues')
  manifestation = { independent, onSuccess: distinctOnSuccess }
}
```

两个归并方向各自的理由：

- **跨列表重复只保留 `independent`**。`independent` 的语义是"无论成败都发生"，已经蕴含成功的情况；而 `independent` 的码表只含通用码，所以唯一可能重复的就是通用码。它在 `onSuccess` 里的那一份不增加任何表达力。反方向（只留 `onSuccess`）会丢掉"失败时也发生"，是错的。
- **两列表都空归并为 `null`**，而不是接受空对象。消费端本来就把空读成"没有表现"（`packages/application/src/action-groups.ts:26` 的 `if (codes.length === 0) return undefined`），归并为 `null` 还能让 Round Authority 的字节与修复前完全一致，不留形状漂移。
- **单个列表内部的重复仍然使输出无效**。`uniqueItems` 是 schema 的机器半边，模型违反它是真实违约，不能顺手放宽；因此查重从"合并后查"变成"列表内查"，错误串保持 `invalid or duplicate step cues`。
- **`all.length > 8` 原样保留**。`parse` 已把每个列表限长 8，词表只有 8 个码，所以它当前不可达；保留是因为词表增长后它是真实护栏，且与可达的列表内查重共用一个 `if`，不影响逐文件分支覆盖。

## 4. 为什么这个改动安全

- **schema 一个字没改**，注册表锁、`specHash`、`toolSchemaHash`、任何世界包都不受影响。
- **对修复前能通过的输入，输出逐字节相同**：能通过就说明没有跨列表重复、`all` 非空，此时 `distinctOnSuccess` 与 `onSuccess` 相等，`all` 与修复前一致，赋值结果也一致。因此既有的耐久数据、Authority Hash、rule trace 全部不变。
- **只接受 schema 已经接受的东西**。`tests/experiments/grouped-playtest.test.ts` 原有的不变式"host 接受 ⟹ schema 接受"继续成立；修复后更强——两侧在整条轴上完全一致。这保证本次改动不会重新引入 C0 当初移除组合子所要防的那类"schema 太松"问题。
- **生产路径确实采用归一化结果**：`packages/application/src/round-coordinator.ts:1320` 与 `packages/application/src/reaction-scheduler.ts:542` 使用的都是校验器返回的 `validated.proposal`，而不是模型原文。模型原文仍完整保存在 Provider 调用证据里。

## 5. 唯一的取舍

修复前，同一码出现在两个列表时，它会在该步 accepted 时被演两次（presenter 按 `，` 连接、记忆按 `；` 连接），rejected 时演一次。修复后统一演一次。

这是一个语义选择，记录在此：一个 cue 表达的是"是否出现"而不是"出现几次"——`cueId` 是位置索引（`cue:0`、`cue:1`），全系统没有任何多重性语义。因此把重复视为**同一件事的重复陈述**并折叠为一次，比"演两遍"更符合模型的原意。代价是：如果将来真的需要"同一码演两次"，本设计不提供该能力，需要新的协议表达。

## 6. 评估过并否决的方案

**把两个列表改成"码 → 步"的对象图**。这是唯一能**结构性**关闭该缺口的设计：

```json
"manifestation": { "smile": "independent", "quiet_voice": "on_success" }
```

码作为键，天然只能出现一次。否决理由：

- 平铺数组（`{cue, step}`）**关不掉**这个缺口——`uniqueItems` 比较整项，`{smile,independent}` 与 `{smile,on_success}` 是不同项，照样放行。所以能关闭缺口的是对象图，不是数组改造。
- 代价：新 `submit_actions/v6` id、`bounded-action-group` 绑定版本切分与双版本读取、模型侧契约改写（本身可能引入新的无效形态）、宽测试改动。
- 真实耐久隐患：schema 经 `toolSchemaHash → providerRequestHash → provider-call-intent` 进入 append-once 身份（`packages/agents/src/provider-request.ts:193-194`、`packages/agents/src/provider-call.ts:140-142`），改形状而不升 id 会让"同一 round/participant 重新准备"撞 `BUNDLE_HASH_MISMATCH`。

**把两个码表改成不相交**（让 `onSuccess` 不含通用码）。否决理由：`independent` 本来就是 `onSuccess` 的子集，这个重叠是契约要求的，去掉会让"通用码只在成功时发生"无法表达，是语义损失。该方案在设计阶段就被排除，未进入实现。

**接受重复并原样保留**。会让重复的 cue 真的播放两次，严格劣于归并。

### 结果的边界

- 这是**一次达到预声明最低样本量（20 次）的运行**，不是无效率的分布证明。0/20 只能说明本次样本内该形态不再出现，不能声称该形态已永久消失。要收紧结论需要按 C0 的固定语料继续累积多次运行。
- 修复前的 29.2% 与 09-10 记录里的 5.9% **不是同模型对比**：那次用的是 `deepseek-v4-flash`，而当前账号可用的是 `deepseek-flash`（见 §8）。因此不能把差异整体归因于代码回归。
- 归并只覆盖 schema 允许的那条轴。若模型在**其他**轴上系统性违约，无效率仍会上升；本次运行没有出现其他形态。
