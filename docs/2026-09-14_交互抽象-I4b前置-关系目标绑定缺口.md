# 交互抽象 I4-b 前置：关系目标无法被作者绑定

| 属性 | 值 |
|---|---|
| 日期 | 2026-09-14 |
| 工作树 / 分支 | harness-cordis-world-v0-merged / fix/step-cue-normalization |
| 基线 | `04fa670`（I4-a） |

| 影响 | 冻结路径无法提供 `base:end-contact`；`I3 Gate` 的"目标可同轮解除"在新路径上没有落点 |

## 1. 缺口

`base:end-contact` 的主目标是**关系实例**：

```ts
const contactRole: InteractionRole = { name: 'contact', kind: 'relation', source: { kind: 'primaryTarget' }, distinctFrom: [] }
```

运行时的检索条件是"请求的 `targetRef` 必须与该绑定的 `targetRef` 完全一致"（`registry.ts` 的
`request does not match enabled binding`）。也就是说，**要解除一条关系，必须有一条把它指名绑好的绑定**。

但编译/作者路径**只能绑定实体和角色**：

- `compileInteractionCatalog` 的绑定循环只有两个来源：`entities[].interactionBindings` 与 `characters[].interactionBindings`（`world-pack/src/schema.ts`）。世界选择文件 `worldpack-interactions/v1` 只有 `packages` 和 `definitions`，没有任何关系绑定字段。
- `validateInteractionTargets` 对 `relation` 目标一律失败关闭（`compiler.ts`）：`declared === undefined` 时抛 "names an unknown relation target"。
- 这一点在 I2-a 就已存在，`compiler-v5.test.ts` 里那句注释写得很直白：*"A relation target has no declared set of its own in this slice, so it fails closed too."*

关系实例的身份是**运行期从来源 Action 派生**的（`deterministicId('relation', {...address, sourceActionId, relationKind, initiatorId, targetId})`），静态 Manifest 不可能预先枚举。所以这不是"暂时没实现"，而是当前绑定模型**在结构上无法表达**这类定义。

## 2. 为什么到现在才浮出来

I3-a 验证 `end-contact` 时，是**手工构造选择**的：

```ts
// packages/interaction-runtime/src/contact.test.ts
const shared = { kind: 'relation', id: 'relation:held' } as const
{ bindingId: 'binding:held-release', targetRef: shared, definitionRef: ref('base:end-contact'), config: {} }
```

测试自己发明了 `relation:held` 这个 id，于是"绑定关系目标"看起来是通的。运行时确实支持——**运行时不是缺口，作者路径才是**。I3 的三条主张（C2/C6/`contact:participant`）都因此成立而无误，但它们的**可达性**从未被验证，因为唯一的生产入口（编译目录）根本产生不了这种绑定。

换句话说：I3 的"目标可同轮解除"证明的是"给定一条指名绑定，解除成立"，而不是"世界能声明出这条绑定"。I4 要给 `end-contact` 接生产入口，第二步就缺了。

## 3. 如果不管它会怎样

v10 世界只能用冻结路径提供首批五类动作里的四类（take / drop / give / hold-hand）。`end-contact` 无法向模型提供，`hold-hand` 建立的关系只能靠 move 的 `contact:end-on-move` 收尾：

- `I3 Gate` 的"目标可同轮解除"在新路径上**不成立**——机制在，入口不在；
- 玩家会看到"牵了手但松不开"，只能走到别处触发失效；
- V0.3 §10.1 的本次 I4 边界里，"新路径 move 经统一生命周期收尾"能成立，但验收矩阵里"接触与电话同时存在，move 只按各定义结束应结束的实例"这类条目仍缺一半对手方。

## 4. 三个可选解法

**案一：绑定改为"关系类"，请求仍指名实例。**
绑定写成 `targetRef: { kind: 'relation', id: '<产生它的定义 id>' }`，语义是"由该定义创建的活跃关系类"；请求仍带具体 `relationId`，绑定匹配从"实例相等"放宽为"实例属于该类"。

- 优点：与规格 §2 的表格一致（`contact` 仍是主目标）；与 I3 收尾的处理器作用域**语义相同**（那里已经用"定义 id"作关系实例的范围键）；不需要新定义版本。
- 代价：`InteractionBindingV3` 对 `relation` 的 `id` 含义变了（类而非实例），`registry.ts` 的精确匹配规则要放宽——这是一处冻结契约的语义变更，必须单独记录（新增 ADR 或 superseding 说明），不能顺手改。

**案二：把 `end-contact` 改成角色主目标 + 派生关系。**
新增 `base:end-contact@2`：主目标是对方**角色**，`contact` 改为 `derived`（解析器找"actor 与 target 之间的活跃关系"）。

- 优点：不动绑定匹配规则，不动 `InteractionBindingV3`；关系仍由 Host 放进快照，派生角色只读快照（I3-a 已确立的语义）。
- 代价：与规格 §2 表格（"contact 为主目标"）不符，需要改规格；`base:end-contact@1` 与 `@2` 长期并存；"解除"的地址从关系变成"人"，与 `contact:end-on-move` 的"按实例收尾"不再同构。

**案三：v10 首批不含 `end-contact`，留到后续版本。**
明确把"新路径的解除"推迟，v10 只提供四类动作。

- 优点：不动任何冻结契约，最快。
- 代价：`I3 Gate` 与 V0.3 §10.1 的边界要相应改写；"牵手松开"在新路径上继续依赖 move；这是一个**对外可见的功能缺口**，不是内部欠账。

## 5. 我的建议

**案一**。理由：它不改已有的事件、定义与处理器语义，只补上"关系类"这一层寻址，而这层寻址在 `consumes` 里已经存在；案二为了绕开一处匹配规则去改定义版本，代价比它解决的问题大；案三会把 I3 的 Gate 永久打折。

但这条选择有产品含义（**"松开对方的手"在模型侧是"选一条关系"还是"选一个人"**），且案一要改一处冻结契约的语义，所以我停在这里等裁定，没有自行选定。

## 6. 已经写好、等裁定后可立即接上的部分

I4-b 的运行时部分已经成型（本工作树已回退，草稿留在 `.workbuddy/i4b-wip/`，未提交）：

- `interactionHostSnapshot`：把候选前缀投影成 `{ref, state}` 并与授权集合分离——角色带 lifecycle / locationId / sceneIds，实体带 locationId / holderId / kind，关系带 interactionId / initiatorId / targetId / active；授权集合是 Host 自己的可达判断（同地点或共 Scene 的角色、手持或同地点未持的实体、本人参与的关系），规则仍逐条复验。
- `FrozenInteractionRulebook`：一个注册表 + 按 manifestHash 缓存的世界；`interact` 走 `resolve()`（fold 在它内部），`move` 走共享 Rulebook + `fold()`——两者都是"每个动作恰好 fold 一次"，且 v10 下不再调用 `endCharacterRelations`。
- 注册表派发与 `createCoreRulebookRegistry({ interactionPackages })`，受信任包由 Host 注入。

未写的是测试与覆盖率，以及应用层调用点补 `manifestHash` / `asOfWorldSeq`。**关系绑定的裁定会改动 `frozenRequest` 的匹配规则与视图选项的构造，所以这部分等裁定再落**，否则要改两遍。

## 7. Evidence → Finding → Path

E1：`compileInteractionCatalog` 的绑定来源只有 entities / characters。F1：`kind: 'relation'` 的主目标定义在作者路径上无法被绑定。P1：裁定 §4 三案之一（建议案一）。
E2：`contact.test.ts` 手工发明 `relation:held` 并绑定成功。F2：I3 验证的是"给定指名绑定，解除成立"，不是"世界能声明出这条绑定"；可达性从未被验证。P2：把"可达性"作为 I4 的独立验收项，不再用运行时单测代替。
E3：I4-a 已让 v10 的存储侧重读对 `relation` 绑定目标失败关闭。F3：该失败关闭是对的（静态 Manifest 不能指名实例），但它现在是唯一行为——没有合法表达方式。P3：若采纳案一，失败关闭的判据要从"kind 是 relation"改为"id 不是已启用的定义 id"。
