## 1. 补的是哪一条

第三片把"为什么这个角色被称重"落成了耐久证据，但只覆盖第一波：**反应回合不给自己这一波的观察者分类**，波形产生的下一轮刺激不带证据，顺序退回按角色 ID。第三片当时写好的调度器侧分类因为**用例产不出候选**而撤掉，缺口写进了记录。

这一片把它补上，并且先造出用例——一个真的能产出下一轮候选的世界——再动实现。用例一跑就撞出一个更严重的问题（§3），它比原缺口更值得单独记。

**（状态更正）** 本片提交时曾在记录、`docs/README.md` 与 V0.3 §10 里写"I4 的 Gate 随之关闭"。那句话是错的：V0.3 §10.1 第三条把 Root、Reaction、显式玩家与 **Player Intent** 四个入口一并列入本次验收边界，而本片只补了 Reaction 入口。缺 Player Intent 在 v10 世界下的提交、Authority 6、恢复与重放样本之前，I4 仍是进行中。三处声明先改回；**（同日补记）** 该缺口随后由[审查修复记录 §4](2026-09-14_审查修复记录-反应证据边界与失败观察.md) 补齐——Player Intent 在 v10 下现在有提交、Authority 6、恢复与重放样本，I4 第三条边界随之成立。本片其余结论不受影响。

## 3. 用例撞出来的缺陷：读回顺序把类丢了

`readReactionCycle` 读 Job 行时按 `(wave, character_id, stimulus_hash, job_id)` 排序，然后**按下标**把 `wave.budgetPlan.decisions[index]` 与 `waveJobs[index]` 对上，不一致就抛 `Reaction Job diverges from its frozen budget decision`。

这等于假设"计划的顺序等于角色 ID 的顺序"。`planStableCallBudget` 的比较器是 `wave | classRank | characterId | stimulusHash | jobId`——**类排在最前面**（ADR-0096）。所以只要一个波里的候选分属不同类且类序与 ID 序相反，这个假设就不成立。

第三片没有暴露它，是因为三个用例恰好都不经过这条路：读证据的用例（`records why each observer was weighed`）从不处理周期，而它唯一那个类序与 ID 序相反的周期**恰好是最后一次提交打开的**——每次提交会读回上一个还活着的周期，前两次读到的都是顺序退化的那个；打开 v10 周期的用例用的是 `responsive/v1`，类序同样退化；反应调度器的单测也都在 v1 上。**没有任何一个用例把一个 v2 周期真正跑起来并读回来**——所以我补的用例一跑就红了。

这一轮把它按两个头一起看清：

1. **位置对齐**：读回的 Job 顺序若与计划不同，第一个 `decisions[index]` 就对不上，周期直接不可读。
2. **更重的一头**：`hashReactionCycleAuthority` 按数组顺序哈希第一波的 Job 行，而这个哈希随提交写进那一轮的 `bundle_hash`。读回时若用 ID 序重算，`committedRound` 会判定 `committed Round bundle hash is divergent`。

第二头不是只在测试里可见。把"只改位置对齐、保留 ID 序"这条更弱的修法单独试一次，红的是**生产路径**：

```
WorldError: committed Round bundle hash is divergent
 ❯ WorldStore.committedRound packages/store-sqlite/src/world-store.ts:1704
 ❯ InteractionTailBuilder.#blocksAt packages/agents/src/continuity.ts:331
 ❯ Phase8ContextPipeline.#prepareReactionCharacter packages/application/src/context-pipeline.ts
```

也就是说：一个 v2 世界的推理上下文根本拼不出来。所以修法不是"按 jobId 找对应项"（那只治第一头），而是**让读回复现写入时的顺序**——Job 的位置由它的冻结预算决定给出，因为**计划才是预约调用、并被哈希进周期权威的那一个顺序**。改完之后 `bundle.jobs` 的读写顺序与 `bundleHash` 也一致了，而 v1 世界与同类波形的顺序本来就是 ID 序，逐字节不变。

一个计划从未命名过的 Job 行现在会在排序阶段就被拒绝。这条分支要有世界能走到才留（仓库规矩），所以篡改用例里加了第三种模式：删掉该 Job 的刺激行、把 `job_id` 改成孤儿 id、重算 Job 自己的两个哈希——除"计划没放它"之外一切完好，读回必须拒绝它。

## 4. 用例：为什么两个角色要互相点名

要让"类序 ≠ ID 序"可观测，两个**类**必须不同，且顺序与 ID 序相反。这个包里能当旁观者的只有同行者与候车的人（玩家是 manual，不是反应参与者），所以两个角色各说一句：

- 同行者 `scope: direct` 点名候车的人 → 候车的人是 **addressee**（rank 1）；
- 候车的人公开说一句 → 同行者是 **witness**（rank 2）。

`character:companion` 的 ID 序在前，`character:friend` 的类序在前——**顺序正好相反**。而第一波两个人是同一句公开发言的 witness，类序并列、退回 ID 序，于是同一个世界里两波给出**两种顺序**：顺序只可能来自类。

断言落在耐久事实上：

- 恰有两波，没有第三波（到那时每人已经用完了冻结的每角色调用额度）；
- 两波的每条刺激都有证据，且 `observerCharacterId` 与 Job 的角色一致；
- 言语不由定义裁决，所以证据的入口身份是动作本身（`{kind: 'action', actionType: 'speak', actionVersion: 1}`）；
- `budget_ordinal` 的顺序：第一波 `[companion, friend]`，第二波 `[friend, companion]`。

## 5. 反应波提交窗口的第一个 v10 样本

I4 的第三条验收边界把四入口（Root / Reaction / 显式玩家 / Player Intent）与恢复接线算在本次范围内，而反应波的提交窗口此前**只在 store 层用手搭的 v1 夹具**覆盖过（`rolls back a complete Reaction Round when killed after Wave settlement but before commit` 那两条）。v10 的反应波多写三样东西：Authority 6、冻结 fold 产出的候选事件、以及这个档案下延续刺激里的证据。所以补一个走完整链路、在进程被硬杀时中断的样本。

装置复用既有的：worker 加 `frozen-reaction` 模式，两个中止点 `store.before-commit` / `store.after-commit`。

**这里踩到的一件事值得写下来。** 第一版我给这个模式同时装了根回合参与者（沿用了别的模式的写法），结果仓库里的耐久事件直接说明问题：根回合多出一条 `round.participant-terminal ... agent:group status schema_invalid`，而第一波的候选**只剩 `character:bob`**——本该回答的那位被排除在周期之外了。原因是根回合参与者在本回合已经算"正在反应"，不该再作为它自己回合的观察者被称重。把参与者去掉之后，候选才是 `[npc, bob]`，npc 拿起了杯子。这条不变量写进了 worker 的注释，因为"多给一个参与者"看起来更周全，实际会让世界少一个候选人。

这一波的世界是用例自己的内容：

- 根回合：玩家牵住同行者的手 → 一条关系，两个候选（同行者是 `direct`、候车的人是 `witness`），两条刺激各带 v2 证据；
- 第一波：同行者拿走杯子（`entity.transferred`）、候车的人弃权；
- 第二波：只剩候车的人（拿杯子的那位是自己动作的 actor），它的刺激正是**上一波产生的延续行**，证据入口指向 `base:take`；
- 之后周期终止。

断言：`character.relation-started` 恒为 1（根回合在暂停布防前就已提交）；杯子转移在提交前中止时 0 条、提交后中止时 1 条；那一波的状态相应为 `frozen` / `committed`；等租约过期、重启恢复之后——**provider 不再被问一次**（`calls === 0`，回放的是已记录的答复），周期走到终止，杯子**恰好**转移一次。

## 6. 证伪

把一个改动拆成两半、每条单独回退，用例必须红。逐条跑过：

| 回退 | 结果 |
|---|---|
| R1 调度器不再分类（刺激不带证据/类） | 红：新用例（证据为 null） |
| R1b 调度器带证据但不给规划器类 | 红：新用例（顺序断言） |
| R2 store 不落库延续证据 | 红：新用例（`expected null not to be null`） |
| R3 store 权威计划不带类 | 红：新用例（顺序断言） |
| R4 读回改回 ID 序（位置对齐） | 红 ×2：既有读证据用例与新用例，`Reaction Job diverges from its frozen budget decision` |
| R5 读回保留 ID 序、只把位置对齐换成按 jobId 查 | 红 ×2：`committed Round bundle hash is divergent`，其中一次由 `Phase8ContextPipeline.#prepareReactionCharacter` 抛出 |

R5 是这一片最该留下的一条：它证明"看起来够用"的修法是错的，而且错在生产路径上。

新的硬终止用例不需要单独证伪：它的装置本身就要求 worker 死在故障点上（`hardKillAt` 在 worker 正常退出时会直接判失败），而恢复段里"周期到达终止、杯子恰好转移一次"两条断言要求恢复真的把那一波跑完——什么都没做的话周期仍是 active。

## 8. Evidence → Finding → Path

E1：第三片 §5 明写反应回合不给自己这一波的观察者分类，wave ≥ 2 的顺序退回角色 ID；当时的调度器侧实现因为用例产不出候选而撤掉。F1：规格 §5 的证据契约只覆盖第一波，顺序在第二波起失去依据。P1：先造出能产出下一轮候选的世界，再按根回合同样的两个函数分类（§2、§4）。
E2：补的用例第一次运行即红，报 `Reaction Job diverges from its frozen budget decision`。F2：读回按 ID 序排列 Job 行、按下标与冻结计划对齐，而计划从 ADR-0096 起就把类排在最前——两个头，第二个头会让 v2 世界的推理上下文拼不出来。P2：读回复现写入顺序，并把"孤儿 Job 行"钉成篡改用例（§3、§6）。
E3：`reaction-evidence.ts` 的注释声称两个写入者都调用分类函数，而实现里只有一个。F3：注释描述了一个不存在的实现，读者会以为缺口已补。P3：补上第二个写入者，使注释成立（§2）。
E4：I4 第三条验收边界把反应入口的恢复算在范围内，而反应波的提交窗口只有 store 层的手搭 v1 夹具。F4：v10 反应波多写的 Authority 6、fold 候选事件与延续证据从未被进程级中断检验过。P4：worker 加 `frozen-reaction` 模式与两个中止点，并把这轮踩到的"根回合参与者会挤掉本该回答的候选"写进注释（§5）。
