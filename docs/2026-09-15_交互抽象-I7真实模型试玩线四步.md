## 1. 生产 Provider 适配器（新包 `@harness-world/provider-chat`）

此前"把 Host 的 `tools` 描述渲染成端点能绑定的 JSON Schema"这段映射只存在于 `tests/experiments/v10-provider-gate.ts`（一个实验脚本）。现在它是生产包，被测例覆盖（逐文件四项 100%），并被网页入口与两个真机脚本共同使用——**一份映射，不是两份手工保持同步的副本**。

| 位置 | 内容 |
|---|---|
| `wire.ts` | `chatMessages`（`developer` → `system`，其余逐字节透传）、`actionGroupWireSchema`（从 Host 的 `tools` 描述派生 wire schema）、`actionGroupDescription`（把组策略里声明的上限与失败语义讲给模型）、`intentCall`（解释请求渲染成消息，schema 原样交回） |
| `provider.ts` | `createChatProvider`：`propose`（角色调用）与 `dispatch`（解释调用），两种风格（`tool` 强制工具调用 / `format` 本地端点输出格式），注入式 `fetch`、可注入的调用遥测（只有耗时与状态，**不含内容**） |

**推广时暴露并修掉的三处缺陷。**

| 缺陷 | 证据 | 修复 |
|---|---|---|
| 原脚本的 wire schema **漏掉了 `move`** | `variants = [speak, interactStep]`，而组的 `allowedActionTypes` 里有 `move` | 按组声明的 `allowedActionTypes` 渲染，且只渲染协议定义了请求形状的动作类型 |
| 世界没有可交互选项时渲染出 `oneOf: []` | Ajv 直接报 `must NOT have fewer than 1 items`——**那不是合法的 JSON Schema** | 没有选项的动作类型不进 `oneOf`；一个都不剩时渲染成 `maxItems: 0` |
| 演员身份取自 `tools.actorId` | 生产的 `tools` 里**没有**这个字段（它只是脚本里的防御性读取） | 从 `character_anchor` 段读 `characterId` 并作为 `const` |

**真机又抓到一处**：端点回 `400 Thinking mode does not support this tool_choice`——强制工具调用与推理模式互斥。适配器现在默认在 `tool` 风格下声明 `thinking: {type:'disabled'}`，并把它做成可覆盖的选项；端点的错误正文也随失败一起抛出（此前只有状态码，运维没有任何线索）。

## 2. v10 网页入口

`tests/experiments/playtest-frozen-runtime.ts`：与旧线**共用同一个页面与服务器**（`PlaytestRuntime` 接口），但世界侧完全走冻结路径——Host 自己装配的请求直接发给模型，模型回什么由世界的校验器判定，转录由 `playerTranscript` 从玩家的观察事实里重建（它本来就会渲染 `manifestation.cues` 与 `interaction`）。

入口 `playtest-web-entry.ts` 自动识别：Pack 目录的 `worldpack.source.json` 是 `worldpack-source/v5` → 冻结运行时；否则保持旧线（旧线自己的渲染器与工具解释器一行未动）。

试玩接线时又发现一处**配置契约**：世界把解释器挡在门外——`modelBudgetTokens: 64` 小于解释档案的 `maxOutputTokens`，于是 `budget_exhausted`，一次 provider 都没调。运行时的模型预算现在按解释器的输出上限配（8 192），档案的 `timeoutMs` 也夹在契约上限（60 秒）内。

## 3. Player Intent Provider

解释器由**生产适配器**驱动，`playerIntent.dispatch` 就是它的 `dispatch`。这一条还牵出两处**作者面**的缺口，都已补：

| 缺口 | 证据 | 修复 |
|---|---|---|
| 世界无法声明玩家输入走哪条解释线 | 编译器把 `playerInputPolicy` **硬编码**成 `legacy-speech/v1`；作者写 `player-intent/v1` 会被 `exactKeys` 拒绝 | 源世界文档新增可选 `playerInputPolicy`（闭集校验，未知版本拒绝而不是回落到旧路线），编译器落进 Manifest 并进 `specHash`；`hand-in-hand` 示例包声明 `player-intent/v1` |
| 契约没讲清楚解释器会被世界拒的规则 | 真机第一轮：模型给 `move` 标了 `kind: "speech"`、span 的 `endUtf16` 越界 | 契约文本写明三条世界真正执行的规则（UTF-16 偏移、`endUtf16 - startUtf16` 等于 `text` 长度、`kind` 只对说话是 `speech`、表现只取选项列出的 cue） |

`player-submission/v2` 与 `interact@2` 的形状都没变：玩家的表现仍是冻结请求的第五个键，解释协议是 `player-intent-request/v2` + `candidate/v2`。

## 4. 真实模型试玩与重启验收

两次真机运行都通过生产适配器，key 只走 `DEEPSEEK_API_KEY`，从不落盘。

**门禁**（`v10-provider-gate.ts`，改用生产适配器）：4 次调用、**0 次失败**、763/1017/824/1018 ms，3 个 `interact@2` 步骤被接受，**4 条表现事实**（`移开视线`/`说话声音很轻`/`微微一笑`/`点了点头`），伞从玩家 → 同行者 → **候车的人**——模型听懂了"递给那边等车的人"，那正是这条线要证明的事。

**连续试玩与重启**（`frozen-playtest-drive.ts`，走网页运行时本身）：玩家说"我把共用的伞拿起来"，世界落事实，两个 NPC 各自用真模型演出对白与外显表现；**关闭进程、用同一个数据目录重新打开**，世界从 `headSeq=40` 继续，下一轮（牵住同行者的手）NPC 继续回应。重启后 `playerInputMode` 仍是 `interpreted-free-text`。

## 5. 实测出的残余：解释器的 span 精度

四轮里通常有一到两轮以 `candidate_validation_failed` 收场，玩家收到的是耐久澄清（"换一种说法，或用 /act 显式命令"）。逐条查耐久记录，原因是**模型自己的转写错误**：声明的 `text` 比它给的 `[startUtf16, endUtf16)` 多含一个标点，或 `kind` 给错。世界的拒绝是**正确**的——一个偏移对不上的 span 会让"玩家到底说了什么"变成猜测。

我试过两轮契约措辞收紧（加规则、加偏移恒等式），失败率在轮次间仍有波动，所以我停手并把结论记在这里：**这是解释线自己的课题**（契约/提示词/候选后处理），不是世界边界的缺陷，也不该用放宽 span 校验来解决。可考虑的下一步：候选里省略 `text`、只给两个偏移由宿主切原文；或对唯一动作的候选允许宿主自行取连续原文段。两者都要动 `player-intent-candidate`，属同一批。
