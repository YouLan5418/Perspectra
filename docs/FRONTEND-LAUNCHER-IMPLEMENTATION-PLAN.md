# Windows 前端与启动器实施方案

状态：首版开发机实现已落地（2026-09-29）。下文保留原阶段目标；具体验收边界以本段为准。A、B 已通过子进程和存档集成检查；D 已接入候选显示与结构化提交，但显示文案仍需完善；C 已支持世界包自定义完整游戏页，未提供时沿用原型页；真实模型连续试玩待做；E 已生成并冒烟验证本机 Windows 免安装目录，干净机器验证待做。

## 1. 已确认与默认选择

| 属性 | 决定 |
| --- | --- |
| 交付形态 | Windows 启动器窗口负责启动和停止；游戏界面由宿主默认浏览器打开 |
| 第一步范围 | 本机单用户、一个正在运行的世界、文字交互；先做开发环境可用版本 |
| 桌面容器 | 建议 Electron。主进程管理窗口和后端子进程；渲染进程只做界面。沿用项目 TypeScript/Node，避免为首版另引 Rust 构建链 |
| 后端 | 保留现有 `FrozenWorldPlaytestRuntime`、`WorldApplication`、Rulebook 和 Event Log；桌面层不复制游戏规则 |
| 存档 | 新实验使用应用管理的新目录；`D:/worlds` 历史存档默认只读，不自动导入或修改 |
| 分发 | 第一阶段要求在开发机运行；免安装版或安装器在通过打包验证后选择 |

Electron 只负责启动器窗口、受限 IPC、进程生命周期和调用默认浏览器。其渲染进程不直接获得文件系统、模型密钥或世界存储权限。开发时后端可沿用仓库要求的 Node 22.19+ 或 24+；打包前必须验证内置/随包 Node 运行时支持 `node:sqlite` 和当前 ESM/`.ts` 构建产物，不能假设 Electron 自带 Node 与开发机等价。

## 2. 调用边界

```text
桌面窗口：启动页 ──受限 IPC──► Electron 主进程
                                ├─ 列出管理目录中的世界包、存档、非秘密模型配置
                                └─ 启停一个游戏后端进程
宿主默认浏览器：游戏页 ──本机 HTTP──► 现有试玩服务 ─► Application/Rulebook/Event Log
```

启动器 IPC 只提供选择、启动、停止和状态，不转发游戏回合。游戏页复用 `GET /api/state`、`POST /api/submit`、`POST /api/pause`、`POST /api/resume`，并已接入 `POST /api/perform`；候选随 `GET /api/state` 返回。新增玩法不增加专属 HTTP 路由；由世界包绑定和受信任交互实现提供候选，规则在提交时重验。

## 3. 实施顺序与阶段门槛

### A. 抽出可启动的后端入口

从 `tests/experiments/playtest-web-entry.ts` 抽出可由桌面主进程调用的启动参数与就绪/关闭结果；保留当前 `experience:web` 命令作为冒烟入口。后端仍随机选本机端口、生成令牌、调用同一个 `createPlaytestServer`。启动错误返回可读类别，不把密钥或私密模型上下文写入窗口日志。

**通过条件：** 旧命令行为保持；桌面层能知道“已就绪、地址、退出原因”；正常关闭后同一存档可续玩。

### B. 最小 Windows 启动器

新增一个桌面入口和启动页。主进程负责目录选择、世界包校验、存档识别、模型配置和单实例后端进程。启动页显示世界包、存档、Provider/模型、启动与停止状态；成功后调用宿主默认浏览器打开游戏，启动器窗口留在原处管理进程。第一版模型密钥只从启动器进程环境传给后端进程；窗口可选择 Provider、模型名和端点，但不提供密钥输入或展示。密钥不保存到世界包或存档。

存档预检直接读取现有 `world.sqlite` 的 Manifest/Pack 身份。当前网页运行时从 `packHash` 派生 `worldId`；仅检查目录是否存在不足以确认“续玩”。若所选 Pack 与存档身份不符，启动器给出明确错误或引导新建独立目录，不能在旧目录里静默激活另一世界。现有应用只对同一 `packId`/`packVersion` 的 Hash 分歧做特定拒绝；启动器需要补齐更宽的“所选存档是否就是此世界”检查。

**通过条件：** 新建、续玩、错包拒绝、后端启动失败、关闭后重启五条本机路径可复现；`D:/worlds` 不发生写入。

### C. 替换试玩页为正式游戏界面

先沿用现有玩家状态接口，做场景、转录、输入、忙碌、暂停和错误反馈。普通文本保持发言；显式命令保持当前受控操作语义。HTTP 连接继续仅限回环地址和当前会话令牌。将诊断信息与玩家视图分开呈现，避免把 `debug` 直接当成正式产品数据。

**通过条件：** 使用真实模型完成短场景连续试玩；核对 NPC 可见性、命令执行结果、失败反馈和重开续玩。自动化测试只验证程序路径，不代替体验观察。

### D. 当前可尝试交互与结构化操作

在玩家授权视图上复用 `FrozenInteractionRulebook.affordances()` 的候选计算，补齐显示名、目标名和参数说明，再提供“读取当前选项”的游戏接口。之后加一个结构化提交入口，把用户选定的选项转换为现有 Application 提案；Rulebook 根据最新世界状态重新裁定。前端不长期拼接 `/act` 内部 JSON，也不读取 NPC 的交互视图。

**通过条件：** 同一 UI 能呈现至少两个世界包的不同交互；旧候选在世界变化后被拒绝或按新状态裁定；玩家无法从接口读到 NPC 私密信息，文本不能直接改写物品归属或位置。

### E. 打包与运行检查

在 A–D 稳定后，制作 Windows 开发分发包。验证打包 Node 对 `node:sqlite`、ESM 和本地导入的支持；验证 Pack、存档和配置路径不依赖仓库工作目录。再决定免安装版或安装器，不以打包方案倒推运行时重构。

**通过条件：** 干净 Windows 环境可启动、创建存档、玩一轮、退出并续玩；关闭窗口能有序关闭后端和 SQLite 连接。

## 4. 验证范围与已接受限制

- A、B：类型检查、启动器/存档预检相关测试、真实子进程启停与重开集成场景。
- C、D：相关接口与权限测试，加真实模型短场景试玩；重点看角色自然度、观察隔离和权威状态一致性。
- E：独立 Windows 打包环境的端到端检查。只有实际改动事务或中断恢复边界时，才增加对应硬崩溃测试。
- 首版只管理一个游戏进程，不实现多用户远程访问、历史存档自动迁移、存档删除、插件市场或任意第三方脚本执行。

## 5. 开工时再定的非阻塞选项

游戏界面的视觉风格和组件库、安装包形式、模型密钥是否需要跨次启动保存。前两项不影响 A/B 的接口边界；第三项默认不持久化密钥。
