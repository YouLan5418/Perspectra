## 2. 三条可判定的规则

**一、交互步骤不能承载声音或步态。** 冻结的八码表里 `quiet_voice`/`trembling_voice` 绑 speak、`slow_walk` 绑 move（`ACTION_GROUP_CUES[cue].actionType !== null`）。交互是另一种动作，所以任何在交互策略里声明这三者之一的包都会在**安装期**被拒绝，而不是留到运行时。规格那句"声音属于 speak，步态属于 move"因此是结构性成立的，不是靠约定。

**二、cue 必须在定义声明的策略内、且在允许的位置上。** 越界即**整份提案失败**，不静默丢弃——静默丢弃会向世界报告一次并未发生的表现。这条与仓库既有的"不因表现字段宽松而吞掉语义"一致。

**三、cue 引用的角色必须是定义声明过的参与者角色。** `requiresRole` 非 null 时，定义必须真的声明该角色槽，否则**激活期**拒绝。这是"握杯子的手发抖"那类表述的入口：它需要一份已建立的持有事实，而持有事实只能来自被解析并在候选快照中验证过的角色。凭空引用一个角色是表现暗示未建立事实的路径，所以它在激活期就被挡掉。

## 3. 表现不产生事件：这是"单一来源"在交互路径上的实现

**执行上下文故意不包含 `performance`。** 效果构造器拿到的是 `{ host, definition, binding, arguments, roles }`——没有表现字段。测试断言**带表现与不带表现的事件逐字节相同**。因此表现无法影响任何世界状态，持续可见状态仍然只由已注册效果声明的正式事件产生，交互路径不会冒出第二个事实来源。

同时，表现**仍然是可记忆的观察事实**（规格原话"表现自身也是可记住的观察事实"）。把它转成观察事实是 Host 的职责，与既有 action-group 路径同构：`stepManifestation()` 在 application 层把被接受的表现变成 `character.manifested` 观察，运行时本身不合成事件。本轮的裁定结果里带上 `performance`，就是给 Host 留的那个接口。**接线属 I3/I4**，本轮只交付契约与运行时的校验。

跨列表重复的 cue 视为同一句自我表达的复述、只播放一次——与冻结的步骤归一化规则逐字一致，不另立一套。

## 4. 验证范围

七组新增断言（视图套件共 24 项）：

- 声明内的 cue 被接受并回显在裁定结果里；**带与不带表现的事件完全相同**；`ruleTraceHash` 因请求内容不同而改变。
- 位置不符、cue 不在策略内、空策略收到表现：三种都整份提案失败。空策略（首批 take/drop/give 的形态）收到表现同样失败。
- 跨列表重复折叠为一次；同列表重复拒绝；空表现对等价于不带表现。
- 安装期拒绝：`quiet_voice`/`slow_walk`/`trembling_voice`、未知 cue、重复 cue、非法位置。
- 激活期拒绝：`requiresRole` 指向未声明角色；指向已声明的 `item` 角色则通过。
- 策略进包锁：改策略会改变 `interactionPackageHash`，且重排组件不改变它。
- 定义引用的策略未被选中时，`freeze()` 以"performance policy missing"拒绝。

## 6. Evidence → Finding → Path

E1：规格 §5 要求"声音绑定 speak，步态绑定 move"，而八码表已经编码了这件事。F1：若只在文档里说，包可以声明一个交互步骤上的步态。P1：安装期按 `actionType !== null` 拒绝，规则从既有表派生而不是新写一张。
E2：规格 §10.3 要求"表现不能虚构持有、支撑"。F2：`requiresRole` 若可指向任意字符串，表现就能暗示一份没人建立过的持有事实。P2：激活期要求该角色确实是定义的参与者角色，而参与者角色在每次裁定中都对候选快照验证过。
E3：规格 §10.3 要求"持续可见状态单一来源、复用现有 visible-state 路径"。F3：表现若进入效果上下文，就能塑造事件。P3：执行上下文不含表现，并有"带/不带表现事件相同"的断言。
E4：规格 §10.3 说"表现自身也是可记住的观察事实"。F4：完全不产生观察会让表现变成无效字段。P4：裁定结果回传被接受的表现，由 Host 走既有观察路径转换成事实（I3/I4）。
