## 3. 我主动标出的可质疑点

以下是**判断**而非事实，请优先质疑这几处。

**Q1 退出选项优先保留与容量失败完全没实现。** 规格 §6.2 要求"自己的解除、撤回等恢复选项优先保留；必需选项自身超过预算时返回明确容量失败，不能通过丢掉全部退出选项继续运行"。我给的理由是：首批五个定义（take/drop/give）里没有任何一个产生恢复类选项，而标记"哪些定义是恢复入口"的声明应当与真正需要它的定义（I3 的 `end-contact`）一起定义，否则会造出一个无法验证的开关。**这是一个可以用"契约先行"反驳的判断**——也可以主张该声明属于 I0-B 的契约冻结范围，本应在 I2 之前就定下来。

**Q2 表现不参与视图枚举，是一个未在规格中明写的分层。** 视图只列交互选项，表现是选中选项之后在请求里附带的。理由是若把表现变体并入选项，`independent`/`onSuccess` 的组合会把 128 的预算瞬间吃光。规格没有明说该分层，值得审：模型是否因此"看不到自己能做的全部事情"。

**Q3 `interactionPackageHash` 变了。** `performances` 成为受锁组件后哈希输入增加，任何先前钉住该哈希的制品都会失效。我确认仓库内没有外部钉子，但这是契约演进的信号，审查者应确认外部使用方是否受影响。

**Q4 为什么先做 `performancePolicyRef` 而 `observationPolicyRef`/`presentationInputSchemaRef`/`lifecycleRefs` 仍未实现。** 选择标准是"I2 Gate 里点名的那条"——"表现不能虚构持有/接触/支撑"直接对应 §5。其余字段属 I3/I4。审查者可以主张字段实现顺序不合理。

**Q5 自由字符串的 Schema 是宽松侧。** Host 按 UTF-8 字节限长，JSON Schema 的 `maxLength` 数码点，所以取字节上界意味着"Schema 接受但 Host 拒绝"是可能的。这保住了"Host 接受 ⟹ Schema 接受"，但代价是模型可能提交一个必然被拒的请求。规格 §7.3 把这类归为"提案失败、整份按协议拒绝"，所以我认为可接受，**但这是判断**。

**Q6 `requiresRole` 只校验"该角色被声明过"，不校验"该 cue 的语义真的依赖该角色状态"。** 由于八码表的 cue 全是自我指向的（facial/gesture/gaze），今天无法表达"对象细节"，所以这条约束是"为未来预留但当前无法被违反"。**它可能是一个没有实际防护力的检查。** 见 §4 的 A8。

**Q7 "模板展开"未实现。** 规格 §5.1 提到"可复用物品 / 角色模板展开成显式绑定"，但当前源格式里根本没有模板构造，我把它当成了逐目标显式绑定。如果审查认为模板是 I2 的交付项，那这一项是缺的。

**Q8 world-pack 与 interaction-runtime 各有一份 config 校验实现**，读同一份 `bindingConfigSchema`。运行时的 `parameters()` 是激活期权威，world-pack 的 `bindingConfig()` 是编译期诊断（错误信息带 JSON 路径）。缓解措施是 §4 的 A9 那条跨包一致性测试。我在 I2-a 记录里说过"应把这段校验收敛到 contracts 一份实现"，**本轮没有做**，因为改动会牵动 I1 与全部既有测试。

## 4. 建议的攻击面

按"如果我是审查者会先打哪里"排序。前四条我认为最可能出问题。

**A1 目标 kind 的边界。** 试着把 `base:take`（entity 主目标）绑到一个 character 目标，再把 `base:give` 的 `recipientId` 指向一个 entity。前者应在编译期拒绝，后者应在参数域枚举时就取不到值。相关：C2、C5。

**A2 效果的事件闭包。** `install()` 只拒绝 `character.moved`（"交互不能拥有位移"）。试着让一个交互效果声明 `character.visible-state-upserted` 或 `character.manifested`，看会发生什么——**我认为当前是允许的**。规格 §10.3 说"坐下、靠墙、站在某人身旁若建立持续关系，须通过正式交互或 move 及受控状态表达"，所以允许可能是对的；但"不新建与已有 visible-state 并行的事实库"这条是否被这条路径破坏，值得审查者判断。**这是我列出的最可能被判定为缺口的一处。**

**A3 视图与裁定的分歧。** `view()` 用 `#plan()` 过滤，`resolve()` 也用它，但两者的输入构造不同（视图用 `action:affordance-only` 占位 actionId）。试着构造一个让"视图列出但裁定拒绝"或反之的场景。相关：C4。

**A4 表现的归一化语义。** 跨列表重复被折叠为一次（`independent:['smile'], onSuccess:['smile']` → 只播放一次）。这与冻结的步骤归一化规则（`docs/spec/bounded-action-groups-v0.1.md` §2）逐字一致，但**它是一个语义选择**：也可以主张重复应当整份拒绝。相关：C10 的边界。

**A5 预算与域上限的相互作用。** 单绑定组合上限 64 低于单角色选项上限 128，所以"128 项被裁剪"与"某个绑定超 64 抛错"是两种不同的失败。试着构造只有 65 个授权角色、没有其他绑定的世界，看它是否抛错而不是给出 65 个选项。相关：C7。

**A6 依赖闭包与循环。** `performancePolicyRef` 现在进入 `definitionDependencies()`。试着让一个策略的 `dependencies` 指回定义自身，看 `freeze()` 是否以 cycle 拒绝。

**A7 篡改编译产物。** 手改 `worldpack/v5` 的 `interactions` 段并重算 `packHash`，看 `validateInteractionTargets()` 是否拦下未知目标、目录外定义、relation 目标。相关：C1。

**A8 `requiresRole` 的实际防护力。** 见 Q6。试着构造一个"描述对象的 cue"看能否绕过——如果绕不过只是因为词表里没有这样的 cue，那这条约束应被标注为"当前不可违反、未来才生效"，而不是"已防护虚构持有"。

**A9 跨实现一致性。** 构造一个 world-pack 编译期接受、运行时 `freeze()` 拒绝的 config，或者反过来。这是 Q8 那个漂移风险的直接检验。
