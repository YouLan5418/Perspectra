## 2. 派生角色：本轮的核心

`derived` 是**唯一请求无法指名的角色来源**。关系目标本身就带着参与者，所以定义可以绑定"另一方"，而不需要模型去识别他。两个解析器（`contact:initiator`、`contact:target`）从 Host 已提供的关系状态里读出参与者。

**解析分两趟**：先解析 hostActor / primaryTarget / argument，再按声明顺序解析 derived。这样解析器只看到已经绑定的角色，**确定性由构造保证，不需要环检测**。解析器返回 `null` 表示该角色无法成立，整份提案按 `PARTICIPANT_NOT_AUTHORIZED` 拒绝。

**一处语义决定值得单独说明**：派生角色只要求出现在候选快照里，**不要求出现在 `authorizedTargets` 里**。理由是派生角色来自 Host 已经放进快照的关系事实，不是请求指名的目标；而 `authorizedTargets` 说的是"Host 授权请求可以去碰哪些目标"。更实际的是：`end-contact` 的 `initiator` 往往就是 actor 自己，而 Host 从不把 actor 列进它授权的目标集合里——若要求授权，这条路径就永远走不通。关系目标本身仍需被授权（它是 primaryTarget），这才是真正的控制点。

## 3. 两个接触定义

**`base:hold-hand`**（actor + target，target 为主目标角色）：权限是 `base:player-immediate`——只有 Host 证明的人工玩家能建立接触，authority 从上下文来，请求无法声明。前置检查同地点、同 Scene、该对尚未在关系中。

**`base:end-contact`**（actor + contact 关系主目标 + initiator/target 派生）：任一参与者可自发解除。

两条设计决定：

**关系身份是派生的。** `relationId` 从 WorldAddress、来源 actionId、定义与双方派生，所以同一 Action 重放会铸出同一个关系而不是第二个。测试断言同参数两次裁定的事件完全相同，换个 actionId 才不同。

**自指由结构拦下，不由规则拦下。** target 角色声明 `distinctFrom: ['actor']`，别名检查在任何规则之前就拒绝。因此 `contact:unpaired` 里那条 SELF 分支被删掉了——它是死代码，留着只会永远无法被覆盖、也永远无法被验证。同理把 `base:actor-active` 从 `end-contact` 的前置里去掉，它已经是 `authorityPolicyRef`，重复只会让 trace 出现两次同名规则。

**"同意"不是接触事件的含义。** 接触事件只表示关系存在、任一方可结束。定义不问模型对方是否同意，规则也不检查对方的意愿——规格 §4 那句"同意、喜欢、顺从、无法反抗都不是 contact Event 的含义"在代码里就是"没有任何字段或检查表达它们"。

## 4. 验证范围

十二项针对性测试（`packages/interaction-runtime/src/contact.test.ts`）：

- 建立关系：单个 `character.relation-started`、字段完整、同参数重放事件相同、换 actionId 事件不同。
- 权限：agent authority 被 `HOLD_HAND_REQUIRES_MANUAL_PLAYER_IMMEDIATE` 拒绝且不产生事件；任一参与者可解除，解除事件的数据形状固定。
- 拒绝面：自指（结构拒绝 `PARTICIPANT_ALIAS_FORBIDDEN`）、该对已激活（含反向记录的 initiator）、同地点不满足、非同场景、非参与者解除、快照外的派生目标、快照缺参与者字段。
- 派生角色证据：解除请求**不含** initiator/target 任何字段，而读取它们的规则全部执行且通过。
- 视图：`hold-hand` 只对有玩家即时权限的角色出现；同一角色换成 agent 权限后只剩 `take`。
- 效果守卫：长度、参与者不匹配、自指、非参与者解除四个分支各自直接调用验证。
- 包契约：不装解析器（锁漂移）、装了但没有解析器实现、包未安装三种情形分别拒绝。

## 6. Evidence → Finding → Path

E1：I1 契约写明"关系派生槽位留待 I3"，`resolve()` 对 `derived` 直接抛错。F1：关系类定义无法表达"另一方"。P1：新增 `derived` 来源与注册解析器，两趟解析保证确定性。
