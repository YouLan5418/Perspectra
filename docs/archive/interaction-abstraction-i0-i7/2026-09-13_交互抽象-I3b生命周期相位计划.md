## 2. 三条约束各自的落点

**反向依赖在激活期拒绝。** 冻结顺序是"相位优先、相位内按精确 ID"。`freeze()` 先算出这个全局顺序，再检查每个处理器的每条依赖是否出现在它**之前**；否则以 `lifecycle order is unachievable` 拒绝。这一条同时覆盖了跨相位反向（spatial 依赖 observation）和**同相位但逆 ID 序**两种情形——后者是只检查相位会漏掉的。

**每个处理器单次 fold 至多执行一次，由构造保证。** 计划是定义 `lifecycleRefs` 经**处理器依赖闭包**后的有序列表（注意：闭包只沿处理器走，规则/效果引用不算 fold 步骤），每个处理器只出现一次。因此不需要 visited 集合，"至多一次"不是靠运行时去重，而是计划本身的性质。

**上限整组失败。** fold 步骤数超过冻结的 256 直接抛错，与"不能截断尾部后提交"一致。

每个处理器的产出都按它自己声明的 `eventTypes` 校验，并用 `limits.maximumEvents` 限长——与效果同一套闭合规则，包无法借 fold 越出状态域。

## 3. 验证范围

九项测试（`packages/interaction-runtime/src/lifecycle.test.ts`）：

- 声明顺序打乱时仍按相位执行；同相位内按精确 ID 破同序（`fixture:alpha` 先于 `fixture:zeta`）。
- 定义只引用链尾时，依赖闭包把整条链纳入 fold 步骤。
- 反向依赖与同相位逆序两种不可达顺序各自在激活期拒绝。
- 定义引用了包没提供的处理器 → `lifecycle handler missing`。
- 越出事件闭包、超出单步事件上限、未知相位、fold 步骤声明 `character.moved`、处理器缺少 `build`，各自拒绝或抛错。
- 处理器返回空数组时不改动候选事件；依赖指向非处理器节点时忽略。
- **fold 预算**：五个包串成 260 步的依赖链（单包上限 64，所以必须跨包），超出 256 时整组失败。这条不能用单包夹具覆盖，也正因为如此才有存在意义。

## 5. Evidence → Finding → Path

E1：规格 §4 给出五段相位与三条约束。F1：没有计划执行器时，"顺序稳定"无法被验证，只能靠约定。P1：相位常量 + 激活期可达顺序校验 + 确定性的 fold。
E2：规格要求"反向依赖、环或重复注册在激活时拒绝"。F2：只有相位检查会漏掉同相位逆 ID 序。P2：校验做在完整的冻结顺序上，一次覆盖两种。
E3：规格要求"每个处理器至多执行一次"。F3：靠运行时去重会引入额外状态与失败模式。P3：计划由构造保证唯一，无需去重。
E4：`end-on-move` 的真正触发者是 move，而位移归 move、不归交互。F4：在交互运行时里伪造一个触发器只会做出无法验证的机制。P4：如实记录，接线属 I3-c。
