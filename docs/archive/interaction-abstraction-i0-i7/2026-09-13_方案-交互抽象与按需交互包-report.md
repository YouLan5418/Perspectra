## 1. 目标与决策摘要

目标是让新增交互有完整的落点：交互包定义行为，目标声明能力，Rulebook 统一裁定。新增物品只需内容配置；新增行为只需受信任扩展及其契约，不再给通用运行链路增加动作名分支。

顶层行动入口保持：

~~~text
Action
├─ speak：发言，保留专用参数与可见性
├─ move：移动，保留地点与 Scene 迁移语义
└─ interact：一次具体交互
   ├─ 拿起 / 放下 / 递交
   ├─ 牵手 / 拥抱 / 解除
   ├─ 待签收递交 / 签收 / 撤回递交
   └─ 其他已启用交互包提供的动作
~~~

“子动作”指交互定义，不表示一个 interact 可以嵌套任意 Action 数组。一次签收可以原子产生多个属于该交互的事件，但不能借此顺便移动、发言或执行无关世界操作。

上图只展示用法，不限定动作种类。基础包是可持续增加定义的通用交互集合，具体清单由场景需求与完整语义决定；某个世界激活后使用的精确集合仍须冻结。设计时可扩展与运行时可重放并不冲突。

| ID | 提议决定 |
|---|---|
| D-001 | speak、move 为同级专用入口，interact 通过精确版本化定义调度 |
| D-002 | 基础交互与第三方交互实现同一契约；基础包内容不以本文示例穷举，不享有跳过验证的特殊路径 |
| D-003 | 新作者格式直接在角色、物品文件声明交互绑定，编译后形成统一目录 |
| D-004 | 动作声明规则引用、参数契约、效果与生命周期；Rulebook 执行检查并掌握提交权 |
| D-005 | 当前交互选项属于指定角色的可重建授权视图，最终执行重验最新候选前缀 |
| D-006 | Host 安装、世界启用、目标绑定、角色当前可尝试是四个不同条件 |
| D-007 | 可见目标与可尝试动作分开；场景过滤只能缩小授权范围 |
| D-008 | 持续关系及待签收记录由事件重建，并提供解除或终止路径 |
| D-009 | 新协议从冻结定义派生 Schema 与校验；旧协议继续使用原契约 |
| D-010 | Memory 继续消费授权 Observation，不按每个交互种类增加捕获分支 |

## 3. 抽象与职责

### 3.1 三类身份

| 身份 | 示例 | 归属 |
|---|---|---|
| InteractionDefinition | base:take@1 | 受信任包提供的确定性行为 |
| InteractionBinding | binding:cup-take | 目标上的一个配置实例，可带经过验证的固定参数 |
| InteractionRequest | 某角色对杯子调用该 binding | 不可信提案，actor 与裁定权限由 Host 确定 |

定义身份与绑定身份分离。同一动作可以被多个物品使用；同一物品也可以绑定同一定义的多个明确配置。显示名称不参与动作身份解析。

### 3.2 InteractionDefinition 候选契约

首版用 TypeScript 模块提供定义，数据描述必须可 Canonical JSON 序列化；函数实现由精确版本的宿主注册表解析。

| 字段 / 能力 | 责任 |
|---|---|
| id、version、definitionHash | 唯一身份与定义锁 |
| targetKinds | 允许 entity、character 或对应运行时实例目标 |
| argumentSchema、bindingConfigSchema | 调用参数和作者可配置字段的严格闭合契约 |
| requiredCapabilities、authorityPolicyRef | 发起者资格与 Host 权限策略 |
| parameterDomains | 从受限视图枚举目标、收件人、待签收记录等参数域 |
| preconditions | 按稳定顺序引用具名、版本化规则及参数 |
| effectBuilderRef | 构造本动作的候选事件，声明允许输出的事件类型 |
| observationPolicyRef | 本动作观察范围上限与结构化内容 |
| presentationInputSchemaRef | 允许显示的字段，避免模板读取隐藏状态 |
| lifecycleRefs | 持续关系、待签收记录的状态与收尾规则 |
| executionClass、limits | 行动组分类与单次事件、规则执行预算 |
| dependencyRefs | 所需规则、事件、Reducer、模板、能力的精确依赖 |

ActionRequest 外层仍回答“谁提出了哪类行动”。speak、move 可以使用同一裁定上下文和公共规则，但保留专用处理器，不强迫它们伪装成目标绑定的 interact。

### 3.3 规则声明的边界

例如，拿起定义声明依次检查目标类型、行动资格、目标无人持有和同地点，成功调用实体转移效果构造器。重复使用的规则由基础规则库提供，特殊规则由所属包提供。

规则引用不是自然语言指令。首版只允许已注册规则与类型化参数，禁止 Pack 写 JavaScript、表达式字符串、任意 Event 模板、递归规则或外部路径。固定参数只能使用该定义的 bindingConfigSchema 允许字段。

受信任规则是同步纯函数，输入为不可变候选快照及 Host 上下文，输出为结果与结构化 trace；不传递数据库句柄、Provider、文件或网络能力。这是宿主扩展的工程契约，不宣称构成不受信任代码沙箱。

## 4. 包、依赖与按需启用

### 4.1 包组织

建议新增两个 workspace 包；以下名称为候选：

| 包 | 责任 |
|---|---|
| @harness-world/interaction-runtime | 注册、依赖闭包、目标绑定编译、候选枚举、通用规则与生命周期执行 |
| @harness-world/interactions-basic | 按场景选定的通用交互定义、规则、事件契约、Reducer、观察与模板；内容可随明确版本演进 |

interfaces / 纯数据契约归 contracts。interaction-runtime 依赖 contracts；基础包依赖 contracts 与运行时的定义接口；Kernel 消费运行时接口；Application 组合根显式安装基础包。基础包不依赖 Application、Store 或 Memory。

speak、move 的现有处理器通过 Rulebook 接入同一执行环境。通用 Kernel 不导入基础包中的动作常量，不按具体 interactionId 分支。

后续调查、交易、物品使用等包采用相同注册方式。数据形态类似并不自动共享语义；新世界状态必须由所属包提供完整契约。

### 4.2 启用层次

~~~text
Host 已安装且允许
  → 世界显式选择包与定义
  → 目标绑定具体定义
  → 当前角色满足可公开检查的适用条件
  → 向该角色暴露可尝试选项
~~~

新世界默认模板可以选择基础包，但必须把选择写入 Manifest，不能依赖“程序启动时碰巧注册过”。可选包只在世界明确引用时参与新动作裁定；未启用包不向模型提供能力。

包必须完整声明传递依赖，激活前验证身份唯一、无依赖环、版本精确、契约与实现锁一致。缺失、重复、Hash 漂移立即拒绝，禁止就近版本替换。

首版只支持新世界激活时选择包，不实现运行中热插拔。后续通过维护屏障与新 Manifest Epoch 改变启用集合；新定义不能影响旧 Epoch。

停止接受某包的新动作，不代表可以卸载历史所需实现。已有 active 关系、pending 递交以及历史 Replay 所需依赖必须保留；无法安全完成生命周期时拒绝停用。旧世界不能静默加载替代实现。

### 4.3 资源与生命周期

规则注册在启动期组装，世界 Registry 冻结后不可变。Branch 的执行状态与缓存归所属 Fiber 清理，跨 Branch 保持显式地址过滤。

编译计划与缓存键至少覆盖 WorldAddress、ManifestHash、definitionSetHash、字符身份、视图水位和相关 policy 版本。缓存不能代替耐久幂等或来源校验。

## 5. 让物品和角色声明交互

### 5.1 作者源文件

新源格式在物品、角色定义中加入 interactionBindings。以下 JSON 是候选物品片段，省略已有身份以外的普通物品字段：

~~~json
{
  "entityId": "entity:cup",
  "interactionBindings": [
    {
      "bindingId": "binding:cup-take",
      "definition": { "id": "base:take", "version": 1 },
      "config": {}
    },
    {
      "bindingId": "binding:cup-drop",
      "definition": { "id": "base:drop", "version": 1 },
      "config": {}
    },
    {
      "bindingId": "binding:cup-give",
      "definition": { "id": "base:give", "version": 1 },
      "config": {}
    }
  ]
}
~~~

角色用相同的绑定结构引用 base:hug、base:hold-hand；包裹引用签收相关定义。bindingId 在编译世界内唯一，解析必须同时核对目标身份和定义版本。

目标声明“提供什么”，不声明哪个模型能代替谁行动。配置不能写 privileged、actorId、任意观察者列表或世界效果。允许的参数只能在实现声明的范围内缩小能力。

可复用物品 / 角色模板展开成显式绑定；模板合并冲突和重复身份在编译期拒绝，不采用最后一个覆盖前一个。

### 5.2 编译结果与旧目录

作者源内的绑定归物品或角色所有；编译结果统一收敛为 definitions、bindings、definitionLocks 与依赖闭包，运行时无需遍历源文件。

旧 object-interactions/v1 与 interaction-catalog/v2 保留原始解析与 Hash。可以提供一次性作者转换工具生成新版本源文件，但不在读取旧世界时自动转换。

中文 label 的修改只影响版本化呈现。进入 Observation / Memory 的权威语义由受信任定义生成，不能由作者标签替换；标签“拥抱”配牵手定义仍不会生成拥抱事实。

### 5.3 场景的角色

Scene 决定可见性、成员范围和已注册的 affordance filter；它只能收窄包、目标和 Host 允许的能力。多个适用过滤器按冻结策略取交集，不能取并集扩权。

第一阶段覆盖角色、物品、由动作生成的关系和递交实例。地点自身作为新 interact target、容器嵌套和场景脚本行为另行扩展，move 继续处理地点转换。

## 6. “当前场景谁、什么物品、能做什么”

### 6.1 每角色交互视图

每个视图绑定 WorldAddress、characterId、asOfWorldSeq、ManifestHash 和 viewPolicyHash。人物清单、物品清单、动作选项是三个独立集合；可见但无交互的目标仍可显示。

~~~text
玩家可见场景
  Alice：可尝试拥抱
  Bob：当前无角色目标交互
  桌上杯子：可尝试拿起
  固定柜台：可见，无交互
自己的持有物
  包裹：可尝试放下、递交待签收
自己的运行时实例
  与 Alice 的拥抱关系：可解除
  发给自己的待签收包裹：可签收
~~~

“可尝试”表示符合当前授权与可公开判断的前置条件，不是未来执行成功的承诺。若规则依赖隐藏状态，选项生成不能用隐藏拒绝原因泄漏秘密；可以公开的尝试保留到正式裁定，由观察策略裁剪失败反馈。

场景里的其他人分别能做什么，属于作者诊断视图或各角色自己的能力视图。玩家/NPC 不自动获得其他角色全部私有能力、待签收记录或关系句柄。

### 6.2 参数域与可执行授权

对 give 枚举合法可见收件人；对签收枚举仅自己能处理的 pending delivery；对解除只暴露本人参与的 active relation。参数必须与目标和 binding 组成精确合法组合，不能把各字段独立 enum 后允许任意笛卡尔积。

候选枚举复用同一 precondition 计划的可公开检查部分，不调用效果构造器、不写状态、不生成真实关系身份。正式裁定执行完整计划。

所有选项以稳定定义身份、目标身份、绑定身份、参数 Canonical bytes 排序。超限按冻结配额整项选择，记录候选数量、被裁剪项和 selectedAffordanceHash；不因截断改变权限。

自己的解除、撤回等恢复选项优先保留。必需选项自身超过预算时返回明确容量失败，不能通过丢掉全部退出选项继续运行。I0 冻结每类数量与字节上限，I5 用负载验证；当前没有实测容量承诺。

## 7. Rulebook 的统一裁定

### 7.1 两层约束

| 系统不可取消的约束 | 定义拥有的规则 |
|---|---|
| WorldAddress、Principal/participant、Host resolutionAuthority | 目标类型、距离、持有状态、交互专用资格 |
| 已启用包、精确版本与依赖锁 | 参数与作者固定配置 |
| ActionOrderKey、行动组边界和调用预算 | 本动作允许的事件与生命周期 |
| Canonical JSON、来源水位、Event/Reducer 不变量 | 观察内容与权限上限 |
| Writer Fence、事务、耐久幂等、Hash | 具名规则检查的顺序和结果 |

动作不能通过声明优先级或来源角色抢占玩家阶段。定义可以声明受限的执行类别，最终顺序与预算由锁定的系统策略决定。

### 7.2 确定性流水线

1. 验证请求外层、Host 身份、Manifest 与已启用定义；未知定义拒绝。
2. 精确解析目标及 binding，验证 argumentSchema、固定参数和额外字段。
3. 在当前候选前缀检查系统授权与动作规则；保存稳定的结果和拒绝原因。
4. 全部检查通过后，effectBuilder 在临时子 Candidate 生成本动作事件。
5. 应用事件 Schema、纯 Reducer 和生命周期阶段，计算空间、关系、递交等派生收尾。
6. 验证完整候选状态不变量、事件集合上限、观察权限与 trace。
7. 正常领域拒绝舍弃本动作候选效果；成功则采用。Schema、Reducer 或不变量错误进入完整性失败，不伪装成普通拒绝。
8. 按现有玩家组 / NPC 组顺序继续。最终 Root Round 的 Event、Authority、Head、Outbox 原子提交。

SQLite 事务内不等待 Provider、Memory 或其他异步 I/O。裁定不能嵌套调用新 Action、等待对方模型或递归调度 Reaction。

### 7.3 Trace 与失败分类

trace 至少覆盖 definitionRef、bindingHash、输入 Canonical Hash、候选前缀标识、resolutionAuthority、规则身份与按序结果、effectHash、生命周期计划身份和输出事件 Hash。

诊断 trace 可以含宿主检查依据，但面向角色的拒绝反馈必须经过观察裁剪。模型不得看到完整私有 trace。

候选错误分类：

| 类别 | 示例 | 处理 |
|---|---|---|
| 激活失败 | 包未安装、依赖不闭合、定义 Hash 不同 | Writer Lease / 入站受理前拒绝 |
| 提案失败 | 额外字段、目标类型不符、未提供的参数组合 | 整份提案按协议拒绝 |
| 领域拒绝 | 物品被先拿走、关系已结束、递交被撤回 | 自我反馈；行动组按现有规则停止后续步骤 |
| 完整性失败 | 同输入产生不同事件、非法 Reducer 转移 | 整轮不提交，按既有 quarantine / recovery 契约处理 |

## 8. 持续效果与跨包联动

### 8.1 关系由定义拥有

关系必须保存 relationId、kind/version、创建定义身份、参与者、来源 Action 和生命周期状态。kind 为精确注册的语义引用，不改成任意字符串后直接接受。

关系定义提供 start/end Schema、Reducer、冲突键、解除动作、观察、对移动和生命周期变化的响应。运行时只理解“已注册关系实例”，不判断 hand_hold 或 hug 字符串。

基本接触关系首版采用无方向的参与者对作为冲突域，同一对角色最多一个基础接触关系；牵手与拥抱之间的切换先解除再建立，避免在首版引入组合姿态。该规则属于基础包，不限制未来其他关系域。

每个受影响参与者都有独立解除路径；关系句柄不是 capability，猜中身份也必须重验参与者资格。

### 8.2 移动不依赖具体接触包

move 产生位置变化后，统一阶段计划先完成空间 / Scene 迁移，再由已启用关系定义处理失效，最后生成 Observation。牵手和拥抱定义声明参与者成功移动或离场时解除；基本接触不阻止移动。

生命周期只参与本动作的候选事件闭包，不成为新的自主行动。规则声明 consumes / produces 的事件阶段与预算，激活时构建确定性有向无环计划，拒绝反向依赖和环路。同一规则 / 实例 / 来源事件在本次候选 fold 中至多运行一次；耗尽上限是完整性失败，不能截断提交半个效果。

该 fold 内的访问集合不是耐久幂等。持久身份、幂等与恢复仍由 Action/事件/Authority 账本负责。

## 9. 基础包范围与代表性案例

### 9.1 能力覆盖与动作选择

基础包负责跨题材复用的常用交互，不把某组示例当成永久动作全集。首批目录依据实际场景确认，扩展时增加定义与包版本，无需修改通用 operation 枚举。

选择动作时至少区分：瞬时可观察行为、已有状态迁移、持续关系、具有跨轮生命周期的交接。纯瞬时行为不应被迫建立假关系；确实改变持有、位置、认知等状态的行为也不能伪装成无效果文本。单纯语气和表情仍由表现契约处理，不因交互抽象而自动成为世界操作。

纳入基础包的判据是：跨题材复用、事实效果明确、权限可检查、能完整重放、涉及持续状态时具有终止语义。题材专属规则进入可选包。复杂度和能否写一句自然语言标签都不是动作分类依据。

下表是检验抽象的代表性案例，不是已经确认的动作目录，也不是要求全部首批实现。既有动作的兼容迁移与新增动作的选择分别验收。

| 候选定义 | 目标 | 前置条件与效果 | 发起策略 |
|---|---|---|---|
| base:take@1 | 物品 | 无人持有、同地点；改变持有者为 actor | 玩家 / NPC 按能力 |
| base:drop@1 | 物品 | 自己持有；放到当前位置 | 玩家 / NPC 按能力 |
| base:give@1 | 物品 | 自己持有，合法收件人可交互；直接转移持有权 | 保留现有即时递交语义 |
| base:hold-hand@1 | 角色 | 同地点 / Scene、有效参与者、无冲突；建立牵手关系 | 保留 Host 证明的人工玩家即时策略 |
| base:hug@1 | 角色 | 同地点 / Scene、有效参与者、无冲突；建立可解除拥抱关系 | 提议首版沿用同一人工玩家策略 |
| base:end-contact@1 | 关系 | actor 为 active 关系参与者；结束该关系 | 每个参与者均可调用 |
| base:offer-delivery@1 | 物品 | 自己持有，收件人可交互；建立待签收递交 | 玩家 / NPC 按能力 |
| base:accept-delivery@1 | 物品＋deliveryId 参数 | actor 是指定收件人；转移持有权并记录签收 | 收件角色自身调用 |
| base:withdraw-delivery@1 | 物品＋deliveryId 参数 | actor 是递交发起人；结束 pending 记录 | 发起角色自身调用 |

无论最终选择哪些动作，基础包都允许模板只选择所需定义，依赖闭包强制补全生命周期实现；缺少必需解除/撤回实现时禁止激活。物品绑定决定具体提供哪组动作。

拥抱定义只描述当前外部接触，不产生同意、喜欢、信任、失能或“无法反抗”。目标可以同轮解除、发言、移动或不响应。NPC 主动发起拥抱的请求策略不在首版开放，后续必须通过新的已注册权限与关系语义增加。

### 9.2 签收案例：接收并确认

对于签收这个示例，用户已明确选择“从递交方接收物品，同时记录确认”。若基础包或可选包纳入该动作，建议使用如下最小耐久流程；它用来验证抽象能承载跨轮交接，不作为整个抽象落地的前置功能要求：

~~~text
递交方执行 offer-delivery
  → pending 递交记录；物品仍由递交方持有
  → 收件人获得获授权的待签收选项
收件人执行 accept-delivery
  → 同一 Action 候选中：
       物品转移给收件人
       递交记录变为 accepted，并记录签收来源
  → 完整验证后与本 Round 一起原子提交
~~~

这需要两个角色分别提出行动，但不要求同一轮等待。签收动作本身同时完成接收和确认。

Delivery 状态至少包含 deliveryId、entityId、senderId、recipientId、创建 Action、交付定义身份、pending/accepted/withdrawn/invalidated。deliveryId 从 WorldAddress 与来源 Action 派生；同一 Action 重放不生成第二份记录。每件物品首版最多一条 pending 递交。

签收必须重验：记录 pending、actor 是 recipient、物品仍由 sender 持有、双方可交互且 lifecycle 有效。请求不能自填发起方授权，也不能将旁人持有的物品直接签到自己名下。

签收事件记录谁、何时的世界 Tick、签收哪个 delivery、来源 Action；不表示已经阅读、检查无误、支付或接受额外条款。签收事实不会抹掉递交前历史。

withdraw 由 sender 显式提出。持有权改变、任一方失去可交互空间范围或不再有效，会由生命周期规则使 pending 递交失效；它不锁住物品，也不阻止移动。首版无墙钟超时，未来若需到期，使用版本化世界 Tick 策略。

接受动作先在子 Candidate 完成 transfer 与 accepted 记录，再执行递交收尾；同一成功签收不能被其自身转移事件误判为 invalidated。任一内部校验失败时两项效果都不采用。

重复 idempotency key 返回同一结果；新 key 再签同一 delivery 得到领域拒绝。跨 Branch、未来 delivery 或伪造收件人均拒绝。

## 10. 模型、玩家输入与表现字段

### 10.1 顶层协议与交互参数

保留 actionType 为 speak / move / interact。新 interact 参数建议含 targetRef、bindingId、definitionRef 和 arguments；动态关系的 binding 由关系定义生成并记录来源，不能由 Pack 伪造。

这是新协议候选，不直接改变现有 interact@1。I0 冻结其版本、旧 interactionId 映射、新 PlayerSubmission / Provider 契约的演进范围。

新 Schema 编译器消费同一个冻结定义描述，生成参数验证计划与模型 Schema。用判别分支约束 definition、target、binding 和参数域的配对；Host 仍重验权威状态。Schema 合法不等于领域执行必定成功。

### 10.2 接入四条路径

| 路径 | 要求 |
|---|---|
| 显式玩家输入 | speak/move 保留专用入口；interact 使用当前绑定和精确参数 |
| Player Intent | 仅选择耐久准备阶段提供的 Affordance；保留原文 span 与解释终态 |
| Root NPC | 基于按角色裁剪的玩家候选 S1 生成新选项 |
| Reaction NPC | 以当前已提交 wave 前缀生成选项，保持 NPC-only Round |

所有路径调用同一注册表与裁定计划，不分别维护基础动作白名单。speak、move、interact 顶层闭集是明确产品边界，可以保留；具体交互名不再写入通用校验分支。

每次最多两步且至多一条 speak；两步仍是一条 speak 加一条 move/interact。保持玩家优先、组内不可插入、失败后续 skipped，以及 3 waves / 8 calls / 每角色 2 calls。新增定义不能通过 effects 或 executionClass 绕过这些上限。

S1、Provisional Observation、Affordance 与最终裁定绑定相同 definitionSetHash 和候选依据；同冻结输入的 provisional/final 不一致时整轮失败。

### 10.3 表现与事实

本工作流不把 manifestation 升级为自由叙述，也不把八个 cue 当作交互实现。已有表现归一化行为保持。

动作定义提供可观察的结构语义；纯呈现文案通过受限 Presentation 模板生成。未来表现目录扩展单独版本化，并与成功动作绑定。未经裁定的玩家原文、作者标签和模型描述不能直接写入 Event、Observation 或 Memory。

## 11. 持久化、Context 与 Memory

Manifest 必须锁定所选包、定义集合、事件/规则/Reducer 契约、绑定、观察/呈现策略及生命周期计划。使用精确版本和规范化 Hash；代码实现锁不能仅靠函数名，需宿主验证包构建内容与可序列化描述对应。

Round Authority 保存实际所用定义、binding 与规则计划身份，或可从不可变 Manifest 唯一还原的引用，并覆盖 traceHash。签收与关系新状态通过 Event 重建；Snapshot 只是加速器，不建第二个事实库。

ContextReceipt 至少绑定源前缀、definitionSetHash、参数域 / affordanceHash、裁剪策略、选择结果和 provisionalHash。动态选项放在本轮变化区域，稳定包契约与当前角色公开能力可以按现有缓存布局分区；不能为缓存保留过期选项。

Memory 继续读取已提交授权 Observation 和 source refs。结构化签收、关系变化进入现有 episodic 捕获路径；若通用 Observation 格式确需增加字段，集中版本化一次，不给 take/hug/sign 各写一套 Memory 分支。

摘要、Recall、Epoch 缓存不能扩大交互权限，不能从“拥抱发生”推导“双方喜欢”，也不能从“签收”推导“认可所有内容”。保持角色、Branch、as-of、来源 Hash 校验。

此次不合并世界级 Memory Profile 改造。它与本方案只协调 Manifest 版本分配，避免两个工作流各自占用同一新版本号。

## 14. 实施阶段与验收

### I0：冻结契约与兼容基线

产出：superseding ADR 草案、定义/绑定/视图 Schema、状态机、版本分配表、稳定排序和资源上限、迁移与重放矩阵。

Gate：用瞬时行为、状态迁移、持续关系、跨轮交接等代表性语义推演接口，拿起/拥抱/签收仅是可选推演案例；确认第一批基础包目录；确定拒绝分类和包间生命周期 DAG；冻结旧版本黄金数据，不能从重构结果反推 expected。

### I1：打通最小注册与已有物品闭环

产出：contracts、interaction-runtime、基础包中的 take/drop/give，新路径 Registry 调度；旧路径原样保留。

Gate：未注册/未启用/Hash 漂移/重复注册全部拒绝；一个物品完成 take → give → drop → take。通用 Kernel 不出现这三个交互名分支。对于承诺保持的旧路径，Resolution、Event、Authority、Bundle Hash 黄金全等。

### I2：作者声明与每角色视图

产出：新源格式、模板展开、物品/角色绑定编译、可见目标清单、参数域和模型契约。

Gate：只修改内容文件即可加入新的可交互物品；角色/Scene/Branch 隔离、隐藏条件、持有物、精确参数组合、预算裁剪与 as-of 重建全部通过。Schema 与 Host 结构校验进行机械一致性检查。

### I3：持续状态与选定的新交互

产出：通用关系状态与收尾计划，迁入既有牵手/解除；实现 I0 选定的新增基础动作。拥抱和签收可作为代表性 fixture 检验设计，但是否作为生产动作交付由基础包目录决定。

Gate：目标可同轮解除；move 无接触名分支；选定动作各有完整参数、权限、效果、观察和恢复测试。如果交付签收，则接收与确认必须原子成立，withdraw、invalidated、重复签收、非收件人和并发竞争均有明确结果，成功签收不得自我失效。未纳入本批的案例不得标记为已实现。

### I4：Root / Reaction / Player Intent 与恢复

产出：四入口统一接线，S1/最终绑定，Authority、ContextReceipt、Snapshot、fork、导入导出和备份恢复。

Gate：不扩大预算、不改变排序；异步 Provider 超时不占事务；耐久 validated 结果恢复不重发模型调用；公开/私有 Observation 与 Memory 来源闭包一致。

### I5：独立扩展验收与真实模型试玩

产出：一个独立的 fixture 交互包、工程门禁和预声明语料的实际运行记录。

独立包建议提供“打开/关闭机关”：有自己的状态、规则、Event、Reducer 和观察，能验证超出物品转移与角色关系的新语义。它只作为扩展验收包，不默认加入基础包。

Gate：新增包与组合根注册、内容绑定即可运行；不修改通用 Kernel、Application、Agents、Memory 中的动作名判断。禁用后从模型与当前选项消失；历史所需依赖仍可重放。

在此基础上执行生产代码对应测试、全量 check、性能与硬终止矩阵，以及真实模型混合试玩。既有 C0 成绩不替代新协议成绩。发布前单列尚未关闭的原 C3 生产入口 / C4 长程门禁，不因本方案门禁通过就自动勾选。

### 14.1 必测矩阵

下表按能力分类。涉及具体新增动作的行，在该动作进入交付清单时成为它的门禁；未选中的动作不因此被加入范围。抽象本身仍需通过覆盖相应机制的代表性 fixture，不能以暂不实现某个示例为由跳过生命周期或原子性验证。

| 类别 | 核心场景 |
|---|---|
| 作者 / 编译 | 同 ID、跨目标错误绑定、未知字段、包未启用、缺依赖、模板冲突、Hash 漂移 |
| 规则 / 模型 | 同定义派生 Schema 与校验；额外参数、非法组合、伪造 actor/authority |
| 物品 | 同物竞争拿取、别人持有、给不可见或无效角色、过期选项 |
| 接触 | 牵手/拥抱冲突、第三方猜句柄、双方解除、移动/离场自动结束 |
| 签收 | 无待签收记录、非收件人、sender 不再持有、重复 key、新 key 重签、撤回与接受竞争 |
| 可见性 | 同地点不同 Scene、隐藏条件、第三方 occurrence-only、私有 delivery 泄漏 canary |
| 顺序 | 玩家 S1 / 最终相同、NPC 看见正确解除选项、前步拒绝后 skipped、生命周期稳定排序 |
| Memory | 只记已提交接触与签收；无未来来源、无伪造目标意愿，Recall 与 Context 包含分别测量 |
| 恢复 | full / snapshot / restart 等价、fork 父未来隔离、逻辑传输、备份恢复依赖预检 |
| 扩展 | 新包带全新事件与状态、缺包 fail-closed、卸载检查、通用模块无新动作分支 |

高风险窗口至少包括：多事件交互的两个事件写入之间、最后一个事件写入后但 COMMIT 前、COMMIT 后 receipt 前；接触与移动收尾之间；Provider 响应耐久后但 Round 提交前。若实现签收，则必须覆盖 transfer 与确认之间。使用真实子进程硬终止，重启后只能观察到整组提交或整组未提交。
