## 2. Host 事实投影

`interactionHostSnapshot(manifest, events, actorId)` 把一段候选前缀投影成冻结运行时需要的两样东西：

**目标快照**（`{ref, state}`，与授权集合分离）：

| kind | state |
|---|---|
| character | `lifecycle`、`locationId`、`sceneIds`（**全部活跃 Scene**，按 id 排序） |
| entity | `locationId`、`holderId`、`kind` |
| relation | `interactionId`、`initiatorId`、`targetId`、`active` |

**授权集合**是 Host 自己的可达判断，不是规则的第二份拷贝：同地点或共 Scene 且活跃的角色、本人手持或同地点未持的实体、本人参与的关系。

两点刻意的选择：

1. **关系前缀读取复用 `currentCharacterRelations`，不另写一份。** 两份校验器可能对"什么算良构关系前缀"给出不同答案，那比复用更糟。运行时的**语义**里仍然没有任何关系种类分支——投影只搬运事实，判断留给定义声明的处理器。
2. **授权集合宁可宽一分，也不重复规则。** 同地点但无共 Scene 的角色仍在授权集合里，因为"可达"是可达，而"这条定义要不要求共 Scene"是规则的事。安全边界由规则逐条复验，加上这里的"猜中 id 也不在集合里"。

## 3. 单一 fold 位置

这是 V0.3 §10.1 的第二条验收边界的落点：

| 动作 | 谁 fold | 看到的状态 |
|---|---|---|
| `interact` | `FrozenInteractionWorld.resolve()` 内部（I3-b 起就在那里） | 请求被裁定的那段前缀；fold 期间只有候选事件增长 |
| `move`（v10） | `FrozenInteractionRulebook.resolve()` 在共享 Rulebook 产出移动之后调用 `world.fold()` | **移动之后**的前缀 |

两者都是"每个动作恰好 fold 一次"，且 `move` 在 v10 下**不再调用 `endCharacterRelations`**——`manifestUsesCharacterInteractions` 仍是 `9` only，Kernel 侧的关系语义在新路径上没有回退可走。

`move` 的 fold 之所以必须看**移动之后**的状态：移动本身才是改变可达性的那件事。这是与 `interact` 不对称的地方，代码里写明了理由。

被验证的边界：一条 `interactionId` 不在任何处理器 `consumes` 范围内的活跃关系，即使已经不可达，`move` 也不会结束它（用例外显式断言）——这正是 V0.3 §7 禁止的"扫描全部 active relation"。
