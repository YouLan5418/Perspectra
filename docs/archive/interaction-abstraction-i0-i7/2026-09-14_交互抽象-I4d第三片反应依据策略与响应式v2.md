## 2. 分类与证据

`direct` 按 ADR-0096 从定义的受锁策略读：策略声明受影响角色槽 → Host 解析到实际角色 → 核对那条角色有对应的耐久 Observation。空列表是真实答案（`take`/`drop` 唯一角色是 actor，actor 在任何槽被查之前已是 `self`）。

**失败不落在任何人身上**：只有成功的动作才有"效果落在谁身上"，这正是规格"仅观察到失败尝试的旁观者不得标为 direct"的另一面（该守卫在上一片已单独证伪过）。

证据的入口身份按事实取：定义裁决的动作记定义锁，`speak`/`move` 记动作身份。

## 3. 排序落在预算规划器里，不在草案里

第一版我把候选在草案里排序，端到端用例**绿着**——但把方案改成"只按角色 ID"重跑，**它还是绿的**。查下来两件事：

1. 我的排序断言恰好与字母序一致（`character:companion` 排在 `character:friend` 前），是**假绿**；
2. 真正决定耐久顺序的是 `planStableCallBudget`，它按 `(wave, characterId, stimulusHash, jobId)` 重排——**草案里的顺序会被它覆盖**。

所以：把 `roleClass` 交给规划器，由它持有完整顺序；用例改成把伞递给**id 靠后**的那个角色，让类顺序与 id 顺序相反；再证伪——**把类序中性化，用例当场红**。草案里的那次排序被删掉了，因为它不生效。

## 4. 我留下的与删掉的死分支

- 删：`strongestRoleClass` 里的 `?? 'witness'`、草案排序内联的比较器闭包（单元素列表不会调用排序器 → 只等到第二个角色出现才跑的未测代码）。
- 删：`prepareContinuationStimuli` 里的证据 spread。理由不是"省事"，见 §5。
- 保留并解释：`affectedCharacters` 里不做形状检查——策略槽在激活时被校验为角色类、已接受的计划绑完了所有声明角色、计划只接受快照中的引用，所以再问一次是没有世界能走到的分支。
