## 1. 补的是哪一条

规格 §6.2 的两行从 I2 起就挂着：

| 资源 | 上限与失败处理 |
|---|---|
| 单角色公开选项 / 每绑定参数组合 | 128 / 64；**稳定排序并保留本人解除入口** |
| 必须保留的退出选项超过视图预算 | **明确失败，不静默删除**；限制激活内容或当前实例数量 |

实现里只有前半句：`view()` 一直是 `ordered.slice(0, 128)`——**静默截断**。第二批（I2-d / I3）的审查记录都把它列为未实现，落点是"首批定义里没有恢复类入口，该声明应与 I3 的 `end-contact` 一起定义"。现在 `end-contact` 与关系类绑定都在，落点具备。

## 2. 实现

`view()` 的选项预算分两步：

```ts
const ordered = [...candidates].sort(compareViewOptions)
const exits = ordered.filter(option => option.targetRef.kind === 'relation')
if (exits.length > MAXIMUM_VIEW_OPTIONS) throw new TypeError('the required exit options exceed the view budget')
const remainder = ordered.filter(option => option.targetRef.kind !== 'relation')
const options = [...exits, ...remainder.slice(0, MAXIMUM_VIEW_OPTIONS - exits.length)].sort(compareViewOptions)
```

三点理由写在代码注释里，也在这里：

1. **什么算"退出选项"由结构定义，不由名字定义。** 目标是关系实例的选项就是"本人解除入口"——关系类绑定只能寻址本人参与的关系（授权集合已经这样限定），所以这个判据不需要运行时认识任何定义名。
2. **排序不能是保留它的原因。** 当前 `base:end-contact` 恰好按 id 排在 `base:take` 之前，所以"排序在前 128"眼下也能保住它；这不是契约，改一个字就没了。先把 exits 摘出来，才与顺序无关。
3. **超限是失败而不是截断。** 退出入口放不下时不静默删一个，视图直接失败——调用方要么限制内容要么限制当前实例数，正如规格所写。

## 3. 用例与证伪

`contact.test.ts` 新用例构造 130 个可拿物品 + 若干条活跃关系：

- **132 条候选、3 条退出、预算 128**：返回恰好 128 个选项，其中**三条退出全在**，`candidateCount` 为 133（总数照实报告）。
- **退出自己就有 132 条**：抛出 `the required exit options exceed the view budget`。

**证伪：** 把 `view()` 换回 `ordered.slice(0, MAXIMUM_VIEW_OPTIONS)`，该用例失败（`expected [Function] to throw an error`）。也就是这一条不是"跑通了"，是"不修就红"。

## 4. 影响面

只影响冻结路径的 `view()`：v9 及更早的选项枚举走 `availableInteractions`，与这里无关。既有 `view.test.ts` 全部保持通过，说明未超预算时的返回集合没有变化。
