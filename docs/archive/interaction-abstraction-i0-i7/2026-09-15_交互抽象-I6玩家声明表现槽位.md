## 1. 缺口在哪：先纠正上一轮的一句结论

上一轮的产品评估里我写过"v10 世界里玩家无法声明表现"。**那句话说得太宽了**，探针核对后要分开讲：

| 玩家路径 | 本轮之前 | 证据 |
|---|---|---|
| **显式命令** `/act interact {...}` | **已经能用** | 冻结请求从 I4-e 起就接受可选的第五个键 `performance`；`records an accepted step as an observation fact` 走的正是 `app.submit` + `parameters.performance`，它是绿的——上一轮的 F2 证伪把它精确变红，说明它确实在跑这条路径 |
| **自由文本（Player Intent）** | **没有位置** | 解释器输出 schema（`player-intent-candidate/v1`）每个动作只有 `{key, affordanceId}`；参数由宿主声明的 affordance 给出，而 `interactParameters(2, …)` 是精确键。玩家说"我皱着眉把杯子递过去"，"皱着眉"无处可放 |
| **模型** | 能用 | v7 工具的 `action.manifestation`，由宿主桥接进同一个 `performance` 键 |

所以这一片做的是**解释路径**，外加把两条路径都写进作者文档。附带一个可发现性问题：模型那边能看到"每条定义接受什么"（`affordances.performances`），玩家这条线上没有对等物。

## 2. 落地内容

| 位置 | 改动 |
|---|---|
| [contracts/player-submission.ts](../../../packages/contracts/src/player-submission.ts) | `createPlayerIntentCandidateSchema()` 升 `player-intent-candidate/v2`：每个动作多一个可选 `performance`，其 schema **直接复用** `createStepManifestationSchema('interact')`——模型那一步与玩家这一步共用同一份映射，不会各自漂移 |
| 同上 | `PlayerIntentAffordance` 新增可选 `performances: readonly ActionGroupCue[]`：这个选择接受哪些 cue。**没有字段 ≠ 空数组**：不接受任何 cue 的选择不出现这个字段，调用方看到"没有清单"就知道不要声明 |
| 同上 | `bindPlayerIntentCandidate` 校验：cue 列表的形状（闭集词表、不含声音/步态、单列不重复、≤8）与**归属**（每个 cue 必须在该选择的接受清单里）；通过后把 `performance` 并进该动作的 `parameters`——也就是冻结请求本来就接受的那个键 |
| 同上 | 清单外 → `clarification_required / not_afforded`（**不静默丢弃**，也不连累整条动作）；形状违规（词表外、声音/步态、重复、多字段）→ 抛错，因为那是无视了它所收到的 schema |
| 同上 | 只解析 v2：宿主把这份 schema 放进它要派发、并参与哈希的请求里，所以 v1 候选是"无视契约的调用方"，而不是要容忍的旧对端 |
| [kernel/rulebook-registry.ts](../../../packages/kernel/src/rulebook-registry.ts) | `ActionAffordance` 补上可选 `performances`：冻结规则书本来就返回它（I4-f 加的），但 resolver 接口没有声明，所以准备层看不到 |
| [application/player-intent-preparation.ts](../../../packages/application/src/player-intent-preparation.ts) | 每个交互选择带上它定义接受的 cue；解释请求升 `player-intent-request/v2`（affordance 结构变了，版本要跟着说实话）；契约文案告诉解释器"只在玩家的话点名时才声明，且只从该选择接受的 cue 里挑" |
| [agents/player-intent-call.ts](../../../packages/agents/src/player-intent-call.ts)、[application/player-intent-worker.ts](../../../packages/application/src/player-intent-worker.ts) | 请求哈希的版本标签跟着升 v2（写入端与校验端两处，一致） |

**没变的东西也要说清楚**：`interact@2` 的请求形状没有变，`player-submission/v2` 没有变。规格 §7 登记过
`player-submission/v3`，这一片**没有用它**——提交体的结构确实没动，变的只是解释协议。这条写进规格表下的
补充说明，免得以后有人照着登记表去找一个不存在的 v3。

## 3. 三条边界各自证伪（改回一半就变红）

| 号 | 回退了什么 | 结果 | 红在哪条断言 |
|---|---|---|---|
| F-P1 | 宿主侧的接受清单校验 | 红（2 处） | 端到端从 `clarification_required` 变成 **`submitted`**——没有这道校验，玩家的**整条动作**会进世界、在那里被 `PERFORMANCE_NOT_ACCEPTED` 拒掉，而不是被重新询问；契约层那条澄清断言同时红 |
| F-P2 | 把 `performance` 并进请求参数 | 红（2 处） | 端到端的 `character.manifested` 从 `[['微微皱眉','微微一笑']]` 变成 **`[]`**——步骤根本没有到达定义；契约层的参数断言同时红 |
| F-P3 | 准备层带上接受清单 | 红 | 端到端 `expected 'clarification_required' to be 'submitted'`——没有清单，玩家的步骤会被自己宿主拒掉，递交这一步根本发生不了 |

F-P1 那一行是这一片最值得记的对比：**同一句玩家的话，两条兜底路径的语义不同**——模型越界是"提案被世界拒"
（它被告知过清单，是有意越界），玩家越界是"请换一种说法"（那句话是玩家的原话，不该被整个否掉）。

## 4. 明确没做

| 项 | 说明 | 为什么 |
|---|---|---|
| **speak/move 的玩家步骤** | 模型可以对说话与移动声明表现（`schemasByAction` 三类都有；`speak` 的 onSuccess 还多两个声音 cue），玩家不行 | `ActionRequest` 没有动作级步骤字段，而 `speak` 的请求形状就是 `{text}`，没有位置放 cue。对齐要给玩家提交新增载体（或新版本），是一次真正的协议增量——用户 2026-09-15 裁定本次不做 |
| **Player Intent 的生产 Provider** | `WorldApplication` 只留了 `playerIntent.dispatch` 接线点，Creator 的 v9 入口仍未启用自然语言解释 | 所以自由文本那条路的端到端证据目前由仓库测试里的脚本解释器提供；显式命令那条不需要 Provider |
| **`player-submission/v3`** | 规格登记过，本次未用（理由见 §2） | 结构确实没变，不用就不是"欠账"而是"不需要" |

## 6. Evidence → Finding → Path

| Evidence | Finding | Path |
|---|---|---|
| 探针：`app.submit` + `parameters.performance` 的用例本来就是绿的 | 上一轮"玩家无法声明"的结论过宽，真正的缺口在解释路径 | 先纠正结论，再只补解释路径（§1） |
