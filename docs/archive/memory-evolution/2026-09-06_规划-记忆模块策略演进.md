# 记忆模块规划：模块边界与长期召回策略演进

- 日期：2026-09-06
- 调研基线：当前仓库 `a2cc212`，根包版本 `0.3.1`；版本号不代表所有后续工作均未实现
- 工作流名称：Memory Evolution（M0～M4），不占用或重排现有 Phase 编号
- 状态：Proposed；规划与实施设计已形成，尚未实现或完成性能验收
- 配套规格：[记忆模块实施规格](../../spec/memory-evolution-implementation-v0.1.md)

> **权威边界：** World Event Log 记录客观事件与已接受的认知事实。Memory 是可重建的派生检索层；它不能直接修改 Claim、关系、情绪、承诺或世界状态。

> **兼容边界：** 本文不修改 Accepted ADR、不隐式升级已激活 Manifest，也不改变现有 FTS、Summary、Context 和 Receipt 的版本含义。新增行为通过新的版本化契约交付。

## 1. 目标

在保持来源完整性、耐久恢复和角色隔离的前提下，让角色在长历史中能够根据当前人物、地点、目标和未完成事项，找回相关经历。工作主体放在 `packages/memory`，跨包修改集中于契约和 Context 接入，不发起全项目重构。

本工作流回答三个问题：

1. Memory 的召回与经历整理策略能否独立替换、比较和验证；
2. 角色是否能在百轮以后找回承诺、人物旧事以及信念形成依据；
3. 新策略能否保持 restart、fork、as-of、来源 Hash 与精确模型输入重建。

## 2. 当前模块化判断

| 观察 | 当前代码 | 对实施的影响 |
|---|---|---|
| Memory 独立 workspace 包，仅依赖 contracts / store-sqlite | `packages/memory/package.json` | 能作为独立工作流推进 |
| Application 集中创建 CognitiveMemoryService | `packages/application/src/world-application.ts` | 组合入口有限，但依赖具体类 |
| Agent 消费 RecallQueryPlan / CognitiveRecallResult | `packages/agents/src/context-v2.ts` | 算法升级需要公共契约配套 |
| LocalMemoryStore 集中 SQL、捕获、校验、水位、召回与 L1 | `packages/memory/src/local-memory.ts` | 先抽取策略边界，避免混改持久化逻辑 |
| Memory 内仍有 KnowledgeRule / CharacterReflectRule | `packages/memory/src/cognition.ts` | 暂保留兼容导出；不把认知规则调整混入检索重构 |
| Checkpoint、Tail、Context 容量位于消费侧 | `packages/agents/src/context-v2.ts`、`packages/application/src/context-pipeline.ts` | 必须区分检索命中与最终上下文包含 |

结论：包级分层足以支撑集中调整，内部策略可替换性仍需补齐。无需把 Memory 拆成多个 workspace 包，也无需引入独立服务或网络接口。

## 3. 产品行为范围

| 行为 | 本次安排 |
|---|---|
| 当前可见人物触发相关旧经历 | M2 实现实体召回 |
| active Goal / Commitment / OpenLoop 关联原始依据 | M2 实现来源关联召回；当前状态继续由 Cognition 提供 |
| 中文查询、同一实体的已授权别名 | M1 固定基线，M2 增加确定性查询规划 |
| 多轮对话按经历组织、按预算展开原文 | M3 实现来源分组与展开，不生成第二套摘要 |
| 重要旧经历保留召回机会 | M2 使用独立通道配额；更复杂显著性与衰减留待数据验证 |
| 修改信念、关系或承诺状态 | 不纳入，继续走既有 Reflection / Rulebook |
| 向量数据库、远程 Provider、模型总结 | 不纳入首轮交付 |
| 长期“遗忘”导致权威认知变化 | 不纳入；检索降权不等于角色失忆事件 |

例：Alice 看到 Bob 进入房间时，系统可以依据 Bob 的实体 ID 找回 Alice 亲历的旧事。若 Alice 只听说过某段传闻，返回内容仍标记为 reported speech，并保留说话者与来源；不能替她确认传闻真值。

## 4. 实施顺序

| 阶段 | 交付 | 通过条件 |
|---|---|---|
| M0：边界整理 | 抽取内部存储与召回职责，保留 Service 门面和旧实现 | 旧行为、Golden Hash、Receipt、故障恢复保持一致 |
| M1：基线评测 | 固定长历史数据集、质量分层指标、性能报告 | 数据、查询、期望来源和基线结果可以复跑 |
| M2：多路召回 | 版本化文本 / 实体 / 未完成事项通道、稳定融合、解释回执 | 强制案例通过，权限零泄漏，整体指标满足规格 |
| M3：经历组织 | 确定性经历分组、来源去重与受预算约束的展开 | 不产生第二套摘要，不借分组泄露未授权信息 |
| M4：集成与交付 | Manifest / Context / migration / backup 集成、故障和性能验收 | 完整 check、硬终止矩阵和交付证据齐备 |

M0 不改策略，M2 不与数据库重构揉成一个提交。M3 不能成为 M2 文本与实体检索交付的隐性前置。日历工期在 M1 的数据规模、耗时与契约差异明确后估算，不用未测量的吞吐假设承诺时间。

## 5. 跨包预算

| 包 | 允许的联动 | 避免扩展的方向 |
|---|---|---|
| memory | 来源验证、捕获、检索、经历索引、Receipt、SQLite migration | 直接提交认知或客观事件 |
| contracts | 新 Plan / Receipt / Profile 与必要的分组类型 | 改写旧版本字段含义 |
| agents | 验证新 Recall 结果、预算裁剪、展开来源进入 ContextReceipt | 把安全校验交给模型 |
| application | 门面注入、策略选择、恢复与已授权情境输入 | 改变 Round / Cycle 权威顺序 |
| world-pack / kernel | 必要的显式策略版本锁定与校验 | 作者提供任意 SQL、脚本或索引正文 |
| operations | Memory Schema 与部署恢复集合兼容 | 自动重建并掩盖待恢复的历史输入缺失 |

生产代码更新必须同时更新测试。最终 cross-package 范围以 M1 契约差异表为准；不得以“单独改 Memory”为理由跳过消费侧验证。

## 6. 设计决策安排

1. 行为不变的 M0 不需要 supersede 现有 ADR，记录拆分前后的等价证据。
2. M2 为新召回计划、算法选择、Receipt 和 Manifest 锁定新增 ADR；不预占 ADR 编号，创建时核对最新索引。
3. M3 的纯来源分组扩展 ADR-0067 / 0068；如后续改变 L1 算法或引入生成式摘要，必须单独创建明确 superseding 范围的 ADR，不能塞进分组工作。
4. 文档的 Proposed 状态标记设计成熟度，不额外引入逐步用户确认流程；实施时按项目既有 ADR 与验证规则推进。

## 7. 验收与风险

首要验收不是模型输出是否“看起来记得”，而是目标来源是否进入候选、是否进入最终 Context、模型是否正确使用，三者分别报告。

主要风险包括：实体标签来自全知资料、FTS 统计受其他 namespace 影响、Receipt 被索引刷新改变、旧 Claim 被当作当前信念、经历展开绕过 Context 预算、备份恢复后丢失精确历史输入。逐项控制与测试见配套规格 §5～§12。

首轮交付不启用检索次数强化。否则同一角色被调用次数可能反过来改变排名，需要新增耐久历史状态与 as-of 语义。显著性、衰减和语义召回仅在 M1 / M2 证明具体缺口后立项。
