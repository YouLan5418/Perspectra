## 1. 起因：两个根因

### 根因一：可用性状态只写不恢复

角色参与一轮模型提案前要先"准备上下文"。准备失败时，代码会把角色的运行可用性写成 `session_lag`（会话/记忆落后）。问题是**没有任何路径把这个状态改回去**：

- 场景决策的调度名单只收 `ready` 的角色，所以掉线角色下轮连候选都进不去；
- 回合协调器的尝试闸门要求 `ready`，所以即使进了名单也会被跳过；
- 恢复只处理了一种状态（非法输出），且只在准备成功时才触发——可掉线角色根本走不到那一步。

结果是：一次体积溢出或一次提供方故障，就把角色从世界里摘掉，直到管理员手动重置。而规格（`docs/spec/implementation-v0.2.md` 6.3 节、Phase 8 规格）承诺的一直只是"**本轮** unavailable"。

### 根因二：裁剪只按条数，不按体积

冻结的裁剪优先级有四级：

1. 不可删除（身份、水位、当前刺激、可行动作、输出契约）
2. 核心（Scene 成员、观察者等）
3. 近期（完整 InteractionBlock、Scene 次要细节）
4. 长期（Recall 记忆、低相关历史摘要）

而实现里只有"按条数截断"：对话块保留 4/10/20 块，召回保留 10 条。**单个对话块的字节数完全没有上限**——说话文本只校验非空（`packages/kernel/src/rulebook.ts`）。所以块数一次没超、体积却能顶爆，然后直接抛出 `CONTEXT_WINDOW_EXCEEDED` 让角色掉线。

这也解释了最初的疑问：掉线的驱动因素往往**不是长期记忆条数多**，而是一条条很长的对话历史。

## 3. 逐条改动

### 3.1 `7f7a149` 掉线的角色能自己回来

把运行可用性状态按"谁来解除"分成两类：

| 类别 | 状态 | 行为 |
| --- | --- | --- |
| 自愈类 | `ready`、`session_lag`、`budget_unavailable` | 保留调度资格，每轮都重试；准备成功即回到 `ready` |
| 提供方质量类 | `provider_output_invalid`、`model_unavailable` | 也允许重试，但只在质量退避允许时（避免持续坏掉的提供方被每轮重复调用） |
| Host 设定类 | `provisioning`、`offline`、`disabled` | 继续拦住，不会被自动恢复 |

实现放在新文件 `packages/application/src/runtime-availability.ts`，导出三个判定：

- `SCHEDULABLE_AVAILABILITY_STATES`：场景决策可以排进调度名单的状态；
- `alwaysRetryableAvailability(state)`：不需要额外信号就能重试（自愈类）；
- `retryableAvailability(state, hasProviderQuality)`：回合路径用，能读到质量退避；
- `availabilityRecovery(state)`：准备成功时返回"改回 ready"的转换，已经是 ready 则返回 `undefined`。

改动的三个点：`scene-decision.ts`（两处调度名单）、`round-coordinator.ts`（尝试闸门 + 成功时恢复）。失败路径一字未改——仍然写落后状态、仍然记一条 `runtime_unavailable`、仍然不阻塞玩家回合。

### 3.2 `f434065` 反应波路径对齐

反应波（Reaction Wave）的准备闸门之前是**字面判断 `ready`**，比回合路径更严：回合路径已经会重试的角色，在同一个反应周期里的每一波仍然被跳过，而且反应路径从不写可用性，自然也解不开这个状态。

现在两个路径共用同一个模块。区别是反应波**只用 `alwaysRetryableAvailability`**（更窄的那条规则）：反应波没有质量退避信号，若把"输出非法"也放进来，会在没有退避的情况下每波都重调一个持续出错的提供方。

### 3.3 `69c68da` 模型不可用 / 预算不可用也能恢复

这两个状态原本同样没有恢复路径。其中预算那个最说不过去：**模型预算账本是每一轮、每一波重建的**，也就是说这一轮抢不到额度，下一轮本来就有额度，可角色永远回不来了。

- `budget_unavailable` 加入"所有路径都能重试"的组；
- `model_unavailable` 加入提供方质量组（退避允许才重试）；
- 同时把**提供方故障计入响应退避**（`recordResponse(..., 'invalid')`）。不做这步的话，"让状态可重试"会变成"每轮重调一个坏掉的提供方"，而退避永远不升级。故障的确切内容仍由 Provider 调用账本记录，这里只影响重试节奏。

### 3.4 `7d19631` 体积驱动的三级/四级裁剪

新增 `packages/agents/src/context-budget.ts` 的 `CharacterContextBudgetPlanner`：

```
先按"不额外裁剪"组装并渲染  ──成功──▶ 直接返回（与改动前逐字节一致）
        │
        └─抛出 CONTEXT_WINDOW_EXCEEDED──▶ 多砍一项重来
                                        顺序：先 Recall 里排位最低的，再最老的整块对话
                                        砍完仍放不下 ──▶ 保留原始错误，fail closed
```

要点：

- **最常见路径零变化**：不需要裁剪时走的就是原来那条渲染路径，字节完全相同，历史哈希与既有测试不受影响。
- **只认一种错误才裁剪**：`WorldError`、类别 `provider`、错误码 `CONTEXT_WINDOW_EXCEEDED`。其他错误原样抛出。
- **块内绝不截断**：只整块丢，不切问题/回答（ADR-0064 第 4 条）。
- **每次丢弃都记账**：组装请求新增可选字段 `budgetTrim: { tailBlocks, recallItems }`（agents 包内部类型，不影响契约），被体积砍掉的记 `budget_trimmed`，被配置档条数砍掉的记 `profile_capacity`。`budget_trimmed` 在契约里早就定义好了，生产代码此前从未发出过。
- **最坏代价**：记忆 10 条 + 对话 20 块 = 最多 31 次组装渲染；由于丢得越多体积只会越小（单调），第一次放得下就是砍得最少的答案。
- 回合角色路径与反应角色路径都改走这个编排函数；Director 路径不动。

### 3.5 `67f06ce` 裁剪不碰世界，且可重建

"裁剪只改变给模型看的内容"这句话需要有测试而不是论证。新增用例：造一个唯一一条召回记忆也放不进 32 KiB 预算的世界，断言

1. 裁剪确实发生了；
2. 世界事件日志与 head 与准备前**完全一致**；
3. 用同一批耐久文件重开流水线，重启后收据字节与丢弃集合完全相同。

第 3 点由代码强制而非仅靠观察：`ContextReceiptStore.append` 会对同一确定性身份重读已存收据，一旦身份不一致就 fail closed 报 `CONTEXT_REBUILD_DIVERGED`。也就是说，不确定的裁剪会以完整性错误暴露，而不是悄悄降级。

### 3.6 `e359ef5` 召回候选只读诊断

**为什么需要**：召回条数上限是在 SQL 里截断的，发生在任何收据存在之前，所以"这次召回漏掉了多少候选"没有任何耐久记录，收据里的 `exclusionReasons` 结构上也永远填不上这一项。

**做了什么**：不假装记账，而是给出测量——同一条查询、同一个 as-of 下、在条数上限之前匹配到多少候选：

```ts
const diagnostics = await demo.diagnoseRecall('character:lin', '钥匙', asOfWorldSeq)
// {
//   schemaVersion: 'recall-candidates/v1',
//   address, characterId, asOfWorldSeq, query,
//   matchedCount: 37,   // 上限之前匹配到的候选数
//   limit: 10,
// }
```

对外入口：`WorldApplication.diagnoseMemoryRecall(address, characterId, query, asOfWorldSeq?)`，悬疑 Demo 上是 `MysteryDemo.diagnoseRecall(characterId, query, asOfWorldSeq?)`。

**保证**：

- 召回与计数**共用同一个 MATCH 表达式构造器和同一个查询计划构造器**，所以"计数的集合"不可能和"排序取前 N 的集合"漂移；
- 生产用条数上限统一为 `DEFAULT_RECALL_LIMIT = 10`；
- v1 与 v2 两代记忆都支持（内置 Demo 世界跑的是 v1，编译出的 World Pack 跑 v2）；
- 计数**不写任何** Recall、Receipt、Context 记录，因此不可能改变它们的存储内容。它是调参用的观测面，不是审计流水。

## 7. 后续两件事（都需要先立 ADR-0088）

这两件都要动记忆层的**耐久契约**，建议用一份 ADR 一次定清楚，而不是分两次改同一套表。

### 第 2 件：记忆库有上限与"退休"通道

现状：`cognitive_memory_v2_sources` 与 `_summaries` 两张表只增不减，没有任何单条退休机制；`forget` 只作用于 v1 的表；唯一能瘦身的是 `resetCognitiveNamespace`，而它会提升 `memoryEpoch`，导致既有收据与检查点全部失效——属于"推倒重来"，不是日常维护手段。

需要定的是：容量上限怎么设、按什么顺序退休、退休后既有 as-of 召回与已签发收据如何保持可重建。契约里已经预留了 `retention_ineligible` 这个排除原因，可以用上。

### 第 3 件：真正的长期记忆压缩 + 摘要正文进模型

现状：L1 摘要（每 8 条一条、`deterministic-extractive-l1/v1`）的正文 `extracts` 是**死数据**——只有 id、序号、哈希进入检查点，压缩出来的文字从来没有到过模型眼前。

要打通它，就必须改 `contextHash` 的语义（摘要正文一旦进上下文，哈希必须覆盖它），因此要同时给上下文与收据升版本，并推翻"只有单一 L1 算法"的既有决定。

### 为什么必须先立 ADR

上面两件都会改变 Recall 计划/收据的版本、排除原因的封闭集合、以及记忆表的保留策略。按仓库规则，方向变化必须新增 superseding ADR（下一个空号是 **ADR-0088**），并在 `docs/adr/README.md` 追加一行，先提交文档再动实现。

## 8. 现在就能用的观测入口

// 一次召回在条数上限之外漏掉了多少候选（只读，不写任何记录）
