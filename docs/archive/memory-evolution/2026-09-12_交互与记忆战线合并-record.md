## 1. 为什么需要这次合并

交互线（C1～C4，5 个提交）与记忆/压缩线（28 个提交）**都从 `b30e479` 分叉**，没有任何一方包含另一方。两者各自新增了持久化版本号、Manifest 能力和 Context 行为，但从未在同一棵树上编译或测试过。在继续任何一条战线之前，必须先把它们合成一棵可验证的树。

## 2. 双 v6 碰撞：本次合并的实质问题

两条线**各自独立地**把 Context schema 从 5 推进到 6，迁移体却不同：

| 来源 | 版本 6 的迁移体 |
|---|---|
| 交互线 | `PROVIDER_CALL_V2_SCHEMA`：重建 `provider_calls`，新增 `purpose` / `work_id` / `request_json`，并建 `player_intent_late_responses` |
| 记忆线 | `CONTINUITY_DIGEST_SCHEMA`：`DELETE FROM continuity_checkpoints` |

危险在于迁移器的形状。`packages/store-sqlite/src/sqlite.ts` 的 `openMigratedDatabase` 走**单一 `user_version` 轴**：

```ts
for (const migration of migrations) {
  if (migration.version <= existingVersion) continue
  db.exec(migration.sql)
  db.exec(`PRAGMA user_version = ${migration.version}`)
}
```

任何版本号小于等于已存版本的迁移都被**静默跳过**，不报错。因此若合并后只保留一个 `{ version: 6 }`，另一条迁移就永远不会在"先被对方迁到 6"的库上执行——世界库可以正常打开，代码却在期待一个并不存在的表结构。

更糟的是它是**不可见的**：交互线那三处测试写的是硬编码字面量（`PRAGMA user_version=7`、`.toBe(6)`），在"常量保持 6"的一侧式解法下**恰好会通过**，所以整套测试会给出假绿。

### 解法

两个迁移都保留，轴移到 7：

```ts
export const CONTEXT_SCHEMA_VERSION = 7

{ version: 1, sql: CONTINUITY_SCHEMA },
{ version: 2, sql: RECEIPT_SCHEMA },
{ version: 3, sql: PROVIDER_CALL_SCHEMA },
{ version: 4, sql: QUALITY_SCHEMA },
{ version: 5, sql: COMPLETE_CONTEXT_SCHEMA },
{ version: 6, sql: PROVIDER_CALL_V2_SCHEMA },      // 交互线：重建 Provider call 账本
{ version: CONTEXT_SCHEMA_VERSION, sql: CONTINUITY_DIGEST_SCHEMA },  // 记忆线：清理连续性基线
```

两个迁移操作的是不相交的表（`provider_calls` 及其索引与附属表 / `continuity_checkpoints`），先后顺序无语义影响。选择 6 给交互线是任意的，只是因为它是较早提出的那一个。

### 让错误解法无法通过

新增测试 `still clears Continuity baselines on a database already at the Provider call version`：先造出一个已经处在**版本 6 形状**（Provider call 账本已重建）但 `continuity_checkpoints` 仍有行的库，把 `user_version` 压回 6，再打开它，断言基线被清空且版本到达 7。

这条测试经过**反向验证**：临时改回"单一 v6"的错误解法后，它和既有的 `repairs legacy component-first layouts...` 一起失败，报错正是 `expected { checkpoint_id: 'checkpoint:stale' } to be undefined`。也就是说它确实能抓住这个碰撞，而不是恰好通过。

## 7. 已知未处理项

以下都不在本次合并范围内，逐项记录以免被当作已解决：

1. **世界声明式记忆策略**：召回策略与摘要策略目前仍是应用层选项（`WorldApplicationOptions.recallTokenizer` / `recallDictionary`）与试玩开关，不是世界内容。Manifest v9 已被交互线占用且没有可扩展的策略槽（每个策略对象都是 `exactKeys` 闭集），因此这条需要在合并树上**新开 Manifest v10**，也可以顺带修掉下一条。

   **v10 的归属与容量（2026-09-13 核对，仍是待决项）**：同日入库的[交互抽象与按需交互包方案](../interaction-abstraction-i0-i7/2026-09-13_方案-交互抽象与按需交互包-report.md)同样声明"不得因为当前最新 Manifest 是 v9 就在本方案直接占用 v10"（该文档 §13.2），所以 v10 有两个需求方——本条的声明式记忆策略，与该方案的包选择与定义锁。**这两项不需要拆成两个版本号**：Manifest v9 本身就同时承载了两个互不相关的命名新增，`interactionCatalog: InteractionCatalogV2` 与可选的 `playerInputPolicy`（`packages/kernel/src/world-spec.ts:222`、`:224`），仓库里并没有"一个版本只放一个策略"的规则。真正的成本在版本守卫的枚举面：`runtimeManifestFromStored` 把版本号写成字面量 `!==` 链，`world-spec.ts` 里枚举 `9` 的位置有 13 处，另外 6 个模块按 `schemaVersion === 9 / !== 9` 分支共 14 处（`round-coordinator.ts` 5、`reaction-scheduler.ts` 4、`interactions.ts` 2、`world-application.ts`、`world-bootstrap.ts`、`world-store.ts` 各 1）。漏改其中任何一处不会报错，只会静默按旧版本门禁处理，因此 I0 的版本分配表应当同时给出这 27 处的覆盖清单，而不是只宣布一个号。

   **v10 已裁定（2026-09-13 补记）：归交互线。** I0-B 的 [交互定义规格](../../spec/interaction-definition-v0.1.md) §7 已把 Manifest v10 分配给交互包选择与定义锁，本条的世界级记忆策略则记为"后续另行版本化，本次不分配编号"。也就是说上面"两个需求方可以共用 v10"的提议没有被采用——交互线先占号，记忆策略继续等。**本条因此仍然完全未解决**，只是被明确排到了交互之后；第 2 条的 ADR-0088 背离同样继续挂着。
2. **ADR-0088 与实现的背离**：ADR-0088 §4 要求"停用是世界内容或 Manifest 的显式选择，不是运行时 Host 开关"，而实现做成了 `WorldApplication` 构造选项。同一个世界库可以在不同 Host 选项下得到不同的召回加权，只在 receipt 重放层面 fail-closed，而不是在准入层面。与第 1 条同一批处理。
