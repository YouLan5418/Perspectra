## 1. 总体结论

Phase 7 的核心主张——**创作者只修改内容目录即可编译、激活并持续运行一个角色认知互相隔离的非悬疑世界**——在代码与测试层面成立。安全边界（路径逃逸、符号链接、大小写碰撞、UTF-8、大小与预算限制、严格 JSON、未知字段、引用闭合、fail-closed Hash 校验）实现质量高，测试矩阵覆盖到位；激活幂等、重启、fork future-canary、同键重放零 Provider 调用、源目录删除后运行均有直接证据。

未发现"严重"级问题（无数据损坏、无安全突破、无权威边界违反）。发现 **5 个中等**、**8 个轻微** 问题，集中在外围契约（错误码接线、CLI 错误面、版本纪律、行为开关耦合）而非核心不变量。阶段完成度对照规格约 95%：本地门槛达成，四格 CI 与 Tag 按报告自述待办；规格 §9 声明的两个错误码与 §4.2 的版本分歧错误码未在用户可达路径上兑现。

## 3. 问题清单（按严重程度）

### 严重（0 项）

无。

### 中等（5 项）

**M1. `PACK_VERSION_DIVERGED` 未接入激活路径，`assertCompatiblePackVersion` 为生产死代码**
- 提交：`a2c83bc`（引入函数）、`7d760a5`（activate 未接线）
- 位置：`packages/world-pack/src/compiler.ts:449`；`packages/world-pack/src/creator-cli.ts:122-145`
- 规格 §4.2 要求"同 packId + packVersion 异 packHash 返回 PACK_VERSION_DIVERGED"。该函数仅被 `compiler.test.ts` 引用；`worldpack activate` 实际依赖 Store 层 `IDEMPOTENCY_KEY_CONFLICT`（`world-store.ts:527-536`）兜底，虽 fail-closed 但错误语义与规格不符，创作者看到的是 Genesis 冲突而非版本分歧提示。
- 建议：在 `activate()` 中先读取已存 Manifest 的 `contentPack` 绑定（同地址）并调用 `assertCompatiblePackVersion`，将诊断转译为 `PACK_VERSION_DIVERGED` 后再进入 Store。

**M2. worldpack CLI 进程入口硬编码错误码，丢弃结构化诊断，错误面与 worldappctl 不一致**
- 提交：`7d760a5`
- 位置：`packages/world-pack/process/cli-entry.ts:5-8`
- 所有异常（包括 Store 层 `IDEMPOTENCY_KEY_CONFLICT`、文件系统错误）一律输出 `errorCode: 'PACK_SOURCE_INVALID'`；`WorldPackContractError.diagnostics` 携带的真实代码（`PACK_REFERENCE_INVALID`/`PACK_DUPLICATE_ID`/`PACK_LIMIT_EXCEEDED` 等）与 jsonPointer 全部丢失，与 Runbook §6 承诺的诊断集合矛盾。且未复用 contracts 的 `createErrorEnvelope`，与 `worldappctl` 的 canonical ErrorEnvelope（规格 §7 要求）形成两套错误格式。
- 建议：catch 中识别 `WorldPackContractError` 并经既有 `worldPackErrorCode()` 映射输出诊断数组；其余错误走 `createErrorEnvelope`。

**M3. `worldpack/v1` envelope 新增必填字段未提升 schema 版本**
- 提交：`ffa41ab`
- 位置：`packages/world-pack/src/schema.ts`（`parseCompiledWorldPack` 的 `exactKeys` 增加 `content.entities`；`parseWorldPackSourceManifest` 增加 `entityFiles`）
- 同名 `worldpack/v1` 与 `worldpack-source/v1` 的必填字段集在阶段中途发生变化，旧编译产物在新解析器下直接失效。ADR-0061 以"尚未形成 0.2.0 候选"为由接受，属于合理的开发期决策，但与 ADR-0054 强调的版本纪律相悖，一旦 0.2.0 Tag 建立后同类变更将不可行。
- 建议：在 0.2.0 冻结前完成 envelope 字段收敛审计；未来任何 `worldpack/v1` 内的结构变更必须走 `worldpack/v2`。

**M4. RoundCoordinator 以 Manifest schemaVersion 作为行为策略开关**
- 提交：`d66e057`
- 位置：`packages/application/src/round-coordinator.ts:456`（`rulebook.version >= 4 || schemaVersion === 3` 触发公开对白 Observation）
- 把"数据格式版本（provenance 绑定）"与"行为语义（public speech）"耦合：任何 v3 Manifest 自动启用公开对白事件，即使其 rulebook 仍锁定 v2。未来非 Pack 来源的 v3 Manifest 会无意改变回合语义，且该耦合无 ADR 记录。
- 建议：改为显式能力字段（如 runtimePolicy 或 rulebook 能力声明），并为该行为开关补一条 ADR；至少在 ADR-0060 中补充说明此耦合。

**M5. kernel `runtimeManifestFromStored` 对 v3 `contentPack` 仅做浅校验**
- 提交：`4fa4ce9`
- 位置：`packages/kernel/src/world-spec.ts`（v3 分支：`compiler` 仅 `objectAt`、`pluginLocks`/`initialFacts` 仅 `arrayAt`、`presentation` 不校验内容、pluginLock 元素结构不检查）
- 与 world-pack 侧的严格解析深度不对等。虽然激活入口已严格验证且 manifestHash 绑定字节，但按项目自身的 fail-closed 深度防御姿态（AGENTS.md），从 Store 读回的信任边界应有同等校验强度。
- 建议：v3 分支复用与 `parseCompiledWorldPack` 一致的元素级校验（pluginLock 的 kind/id/version/hash 闭合、presentation 结构）。

### 轻微（8 项）

**L1. Markdown `contentHash` 从不与 `text` 复核**
- 提交：`ac05128`；位置：`packages/world-pack/src/schema.ts:463-470`（`markdownAt`）。编译时正确生成，但 `verifyCompiledWorldPack` 也不验证该冗余字段，字段可与其描述的内容不一致而验证仍通过（packHash 覆盖的是字段值本身）。建议在 `markdownAt` 中校验 `rawHash(encode(text)) === contentHash`。

**L2. `adaptToWorldSpec` 中的非空断言是 fail-open 缺口**
- 提交：`4fa4ce9`；位置：`packages/world-pack/src/compiler.ts:422`（`lifecycleByCharacter.get(characterId)!`）。当前数据流保证存在，但若 kernel 未来新增 `character.created` 事件来源，`undefined` 会被静默写入 `lifecycle-changed` 事件。建议显式判空并 `failWorldPackContract`。

**L3. `worldpack test` 无条件返回 `status: 'passed'`**
- 提交：`7d760a5`；位置：`packages/world-pack/src/tooling.ts:61`。Runner 只做编译/适配与 Hash 固化，不执行任何 acceptance assertion（Runbook §3 已如实说明）。字段名 `passed` 对创作者有误导，实义是 "compiled"。建议改为 `status: 'compiled'` 或输出 `assertionsExecuted: 0` 之类的显式声明。

**L4. chat shell 的错误包装泄漏内部信息且统一为 INVALID_REQUEST**
- 提交：`6c53a3e`；位置：`packages/operations/src/chat.ts:110-115`。`String(error)` 可能携带内部路径/堆栈文本写入 stdout；`correlationId` 用行序号而非提交键，与 durable 语义脱节。本地 stdio 场景风险低，建议收敛为按错误类型映射错误码。

**L5. `PLUGIN_NOT_REGISTERED` / `REGISTRY_HASH_MISMATCH` 声明后零使用**
- 提交：`a2c83bc`；位置：`packages/contracts/src/errors.ts:16`。规格 §9 称 Phase 7 使用这两个代码，实际生产代码无引用（grep 全仓库仅类型声明一处）。属于规格与实现的偏差；建议要么在激活路径的 pluginLock 校验失败时使用，要么从 Phase 7 冻结面移除。

**L6. `sourceFile` 的 TOCTOU 窗口与先读后限**
- 提交：`ac05128`；位置：`packages/world-pack/src/compiler.ts:135-169`。realpath→lstat→readFile 之间存在替换窗口（本地工具威胁模型内可接受）；`loadBytes` 先整读再比对上限，超大文件会先进入内存，可先 `stat` 预检。均属加固项而非缺陷。

**L7. `worldpack init --profile social` 依赖仓库相对路径复制示例**
- 提交：`7d760a5`；位置：`packages/world-pack/src/creator-cli.ts:60-62`。`../../../examples/...` 仅在仓库源码形态有效，包一旦发布即失效。当前 private 边界内可接受，发布前需内嵌模板。

**L8. 测试超时余量偏紧，完整 check 对硬件敏感**
- 提交：`fac70d4`（报告声称全绿）；本审查机（Windows/Node 24.14.1）完整 `check` 有 4 个用例在并行负载下超时（15s/20s 上限），单独复跑全部通过（`process-entry` 14.4s vs 15s 上限、tavern E2E 4.9s、archive 6.2s）。结论：报告的"通过"可信，但四格 CI（尤其慢 runner）存在超时脆弱性。建议对重 IO 用例显式放宽 timeout 或标注 `test.sequential`。

## 4. 安全与性能专项评价

**安全（总体良好）**：`normalizedSourcePath` 拒绝反斜杠/盘符/绝对路径/`..`/尾点尾空格/Windows 设备名；`realpath` + `withinRoot` 阻断符号链接逃逸（有专门测试）；大小写折叠碰撞检测保证 Windows/Linux 一致性；严格 JSON 解析器拒绝重复键、非整数、未转义控制字符、尾随内容；预算制（单文件+总量 16MB）防资源耗尽；插件 allowlist 精确锁定 id+version+hash。未发现注入或逃逸路径。

**性能（可接受）**：编译为一次性成本，排序用码元序保证跨平台确定性；`checkWorldJson` 通过 canonicalize 顺带做大小测量属 O(规模) 必要开销。运行时路径无新增热点；SQLite `synchronous=FULL` 导致测试耗时偏长（总 tests 时间 ~672s），是 L8 超时脆弱性的根因之一。

**风格与可维护性**：schema.ts 中大量单行双语句（`const at = ...; const value = ...`）在 ffa41ab 新增段延续，与 a2c83bc 原有排版尚一致但密度偏高；错误路径全部走 `failWorldPackContract` 统一抛出，诊断结构完整；`profileAt` 用 `JSON.stringify` 相等比较 PHASE7_CORE_PROFILES 依赖键序稳定（当前受控，属脆弱点）。

## 5. 结论与建议优先级

1. **0.2.0 Tag 冻结前必须处理**：M1（版本分歧检查接线）、M2（CLI 错误面统一）——两者都是创作者可直接触碰的契约面，修复成本低。
2. **冻结前应评估**：M3（envelope 字段收敛审计）、M4（行为开关与格式版本解耦，或补 ADR）。
3. **可排入 Phase 8 前置**：M5、L1～L7。
4. **CI 策略**：L8 建议在推送后首轮四格 CI 中观察慢 runner 的超时情况，必要时调整 timeout 配置而非放宽断言。

Phase 7 的工程质量在同类项目中属上乘：安全边界、确定性、fail-closed 与证据文化执行到位；主要短板集中在 CLI 边界的错误契约一致性与两处"版本号/格式承载语义"的耦合决策。建议按上述优先级修复后再申请 `v0.2.0` Tag。
