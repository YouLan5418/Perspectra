# Phase 9A 数据迁移、恢复集合与玩家抢占评审

| 属性 | 值 |
|---|---|
| 日期 | 2026-08-31 |
| 基线 | World Schema v15、`dshworld-authority/v5`、Context v5、Memory v5、Session v2 |
| 上位决策 | ADR-0077、Phase 9 实施规格 v0.1 |
| 原型证据 | ADR-0076、`prototype/reaction-cycle-p0` |
| 状态 | **Phase 9A 开工设计门禁通过** |

## 1. 结论

Phase 9A 可以开始生产实现，但不得直接复制原型的两表 Schema。

原型已经证明 NPC-only Round、同事务创建 Job、领取 fencing、提交后恢复和 UTF-16 排序可行；它没有表达正式规格需要的多 wave、刺激束、稳定预算快照、玩家抢占、完整终止原因和跨 Context ProviderCall 恢复。因此正式 v16 冻结为四张核心表：

1. `world_reaction_cycles`：Cycle 身份、冻结策略、生命周期和终止原因；
2. `world_reaction_waves`：每 wave 的 Head 基点、预算计划与 Reaction Round 关联；
3. `world_reaction_jobs`：角色级预算、租约/fence、Provider 引用和终态；
4. `world_reaction_job_stimuli`：Job 的授权 Observation 输入及稳定顺序。

此外，v16 增加 Event 类型范围索引，但不改写任何 v15 Event。Logical v6 同时携带 World Reaction Authority 与它引用的 Context Receipt / ProviderCall。四库物理备份采用“写入屏障 + 四个 SQLite 备份 + Canonical Set Manifest”，不伪称跨数据库事务。

## 2. 对原型的采用与拒绝

### 2.1 采用

- Cycle 与首 wave Job 和 Root Round 在同一个 World `BEGIN IMMEDIATE` 事务中创建；
- 每 branch 最多一个未终结 Cycle；
- Job claim 保存 owner 与 fencing token；
- 应用层按 `compareWorldText` 重排后再 Hash、领取和截断；
- Reaction Round 通过现有 `commitRound` 追加 Event、Tick、Head 与 Authority；
- 原型硬终止窗口继续作为正式 Crash Harness 的起点。

### 2.2 拒绝直接转正

原型的 `world_reaction_cycles` / `world_reaction_jobs` 不足以成为正式 v16：

- 只有 `active/completed`，不能表示 `stop_requested`；
- terminal reason 只有三个值，不覆盖 ADR-0077 闭集；
- 一个 Job 只能引用一个 Observation，不能冻结 `StimulusBundle`；
- 没有 wave Head 基点、预算 before/after、稳定 `planHash`；
- 没有 claim expiry、attempt、outcome、Context Receipt 与 ProviderCall Hash 引用；
- claimed 导出一律归一化 pending 会让已经 dispatch 的调用被错误重发；
- Logical v6 只含 World 两表，没有 Context ProviderCall，无法证明恢复安全。

## 3. 正式 World Schema v16

### 3.1 `world_reaction_cycles`

必须耐久保存：

| 字段组 | 字段 |
|---|---|
| 身份 | `cycle_id`、`address_key`、`root_round_id`、`root_transaction_id`、`created_at_seq` |
| 策略 | `policy_version`、`profile_id`、`max_waves`、`max_npc_calls`、`max_calls_per_character`、`max_actions_per_call`、`allowed_action_types_json` |
| 预算 | `initial_token_budget`、`deadline_at_ms`、`budget_hash` |
| 状态 | `status`、`stop_reason`、`terminal_reason`、`terminal_at_seq` |
| 完整性 | `cycle_hash`、`state_hash` |

状态闭集：

```text
active -> stop_requested -> terminal
active -----------------> terminal
```

检查约束：

- `active` 时 stop/terminal 字段均为 `NULL`；
- `stop_requested` 只能使用 `player_preempted`、`user_cancelled`、`administrative_stop`、`quarantined`；
- `terminal` 必须使用 ADR-0077 冻结的 terminal reason，并记录 `terminal_at_seq`；
- partial unique index `WHERE status <> 'terminal'` 保证每 branch 最多一个未终结 Cycle；
- `root_transaction_id` 唯一并外键指向 `round_commits`；
- v15 迁移后表为空，不回填历史 Cycle。

`deadline_at_ms` 是 Cycle 创建时冻结的 operational 判定输入。历史是否 deadline 终止只读取耐久 `terminal_reason`，重放不再次比较当前墙钟。

### 3.2 `world_reaction_waves`

每个 `(cycle_id, wave)` 一行：

| 字段组 | 字段 |
|---|---|
| as-of | `base_head_seq`、`base_head_hash` |
| 预算 | `calls_before`、`tokens_before`、`budget_plan_json`、`budget_plan_hash`、`reserved_calls`、`reserved_tokens` |
| 状态 | `status` (`frozen/committed/closed_without_dispatch`) |
| Round | `reaction_round_id`、`result_transaction_id`、`authority_hash` |
| 完整性 | `wave_hash`、`state_hash` |

约束：

- wave 从 1 连续增长且不超过 Cycle `max_waves`；
- `frozen` 不得带 result transaction；
- `committed` 三个 Round 引用必须齐全，并唯一映射一个 World transaction；
- `closed_without_dispatch` 只允许所有 reserved Job 均可证明未 dispatch；
- base Head 必须等于 Tx A 冻结时 branch Head；Tx B 仍执行 Head/hash 乐观校验。

### 3.3 `world_reaction_jobs`

每个候选角色每 wave 最多一行，唯一键为 `(cycle_id, wave, character_id)`。至少保存：

- `job_id`、`address_key`、`cycle_id`、`wave`、`character_id`、`stimulus_hash`；
- `status`：`pending/claimed/settled/skipped`；
- `budget_decision`、`budget_ordinal`、`reserved_tokens`；
- `claim_owner_id`、`claim_expires_at_ms`、`claim_fencing_token`、`attempt_count`；
- `outcome`：`proposed/abstained/provider_terminal/runtime_unavailable/rejected`；
- `context_receipt_id/hash`、`provider_call_id`、`provider_request_hash`；
- `proposal_hash`、`result_transaction_id`；
- `job_hash` 与 `state_hash`。

硬规则：

- 预算排除的候选直接 `skipped`，不得拥有 claim/Provider 字段；
- `claimed` 必须拥有未过期租约、fence 和 reservation；
- `settled` 保留原 owner/fence，并按 outcome 要求 Provider/transaction 引用；
- `prepared` 且可证明未 dispatch 的 ProviderCall 才能在租约过期后重新领取；
- `dispatch_started` 无响应必须收口 `provider_terminal/timed_out_ambiguous`，不得回 pending；
- Job 状态 Hash 必须覆盖所有可变权威字段。

索引：

```text
(address_key, status, wave, character_id, stimulus_hash, job_id)
(cycle_id, wave, status)
UNIQUE(provider_call_id) WHERE provider_call_id IS NOT NULL
```

SQLite 只负责缩小候选集；参与 Hash、claim 或预算截断前必须用生产 `planStableCallBudget` 在应用层按 UTF-16 重排。

### 3.4 `world_reaction_job_stimuli`

每个 Job 的输入按 `stimulus_ordinal` 存储：

- `job_id`、`address_key`、`stimulus_ordinal`；
- `observer_character_id`；
- `source_round_id`、`source_transaction_id`；
- `source_event_seq`、`source_event_ordinal`、`observation_ordinal`；
- `observation_id`、`source_event_hash`；
- `stimulus_entry_hash`。

外键 `(address_key, source_event_seq)` 指向 `events(address_key, seq)`。导入和读取时还必须验证 Event 类型为 `observation.upsert`、observer 与 Job 角色一致、来源 Round 属于本 Cycle、且 Observation 对该角色已授权。

`stimulusHash` 按以下应用层全序重算：

```text
(source_event_seq, source_event_ordinal, observation_ordinal)
```

### 3.5 额外索引与迁移纪律

v16 同时新增：

```sql
CREATE INDEX events_type_range ON events(address_key, event_type, seq);
```

迁移只执行 `CREATE TABLE/INDEX`，不重写 v15 权威行。`openMigratedDatabase` 在一个 `BEGIN IMMEDIATE` 内设置 `user_version=16`；任一 DDL 失败必须留下完整 v15。旧二进制继续因 future `user_version` 拒绝打开 v16。

## 4. Logical Authority v6

### 4.1 Envelope

v6 冻结为：

```typescript
interface LogicalAuthorityV6 {
  format: 'dshworld-authority/v6'
  data: {
    authorityVersion: 6
    worldTables: Record<string, SqlRow[]>
    contextEvidence: {
      contextReceipts: SqlRow[]
      providerCalls: SqlRow[]
    }
  }
  bundleHash: WorldHash
}
```

World 表在 v5 集合上增加四张 Reaction 表。Context evidence 只包含被 Round Authority 或 Reaction Job 引用的 Receipt / ProviderCall；Continuity Cache、Provider Quality、Memory、Session 和 operational Audit 不属于 Authority v6。

导出必须在应用级 admission barrier 下同时打开 World 与 Context `BEGIN DEFERRED` 读事务。没有 barrier 的两个独立 SQLite snapshot 不能宣称一致。

### 4.2 v5 输入兼容

- v5 导入 v16 时四张 Reaction 表与 `contextEvidence` 为空；
- v5 的 source `bundleHash` 先按 v5 字节验证，不能拿升级后的 v6 data 重算并冒充原 Hash；
- 归一化后的 v16 数据首次重新导出时生成新的 v6 Hash；
- v5 本来就不携带 Context，导入结果只能以 legacy rebuildable 模式运行，且绝不允许恢复 active Reaction Cycle。

### 4.3 v6 导入验证

除 v5 现有 Event/Head/Round/Outbox/Inbox/Failure 校验外，必须验证：

1. Cycle root transaction、created seq、policy、budget 与 Hash；
2. wave 连续性、base Head、预算 before/after、`planStableCallBudget` 复算和 result transaction；
3. Job/Stimulus Hash、Observation 类型/owner/as-of/Cycle 来源；
4. 每角色与 Cycle call limit、token limit 可从 Job 重算；
5. Reaction Round Authority 的 `origin/cycleId/rootRoundId/wave` 与 wave 行一致；
6. Context Receipt hash、ProviderCall append-once字段与 World Job 引用一致；
7. `committed` ProviderCall 的 transaction/authority hash 在 World 中双向存在；
8. active/stop-requested Cycle 唯一，且所有状态组合满足 CHECK；
9. claimed Job 不得在 authority-only import 中被无条件改回 pending；安全恢复由 ProviderCall 状态决定。

导入使用两个全新临时数据库。只有 World 与 Context 都导入、校验成功后才返回可激活结果；失败删除两个临时目标，不覆盖现存数据。

## 5. 四库一致 Backup / Restore

运行组合根实际使用四库：World v16、Session v2、Memory v5、Context v5。Projection SQLite 是可选派生工具，不在当前 Host 的恢复集合中。

### 5.1 创建流程

1. 获取 Instance Lock，关闭新 admission；
2. 停止领取新 Reaction/Cognitive/Outbox work；
3. 将已 dispatch Provider 调用收口到耐久 response/terminal，完成 post-COMMIT ProviderCall 与 Availability 对账；
4. 让当前 frozen wave 提交或证明 `closed_without_dispatch`；
5. drain Memory Job 与 Outbox，或使其状态满足冻结恢复规则；
6. 在写入完全静止后分别调用 SQLite backup；
7. 为四个文件记录 application id、schema version、byte length 与 SHA-256；
8. 计算 Cross-store Anchor，并最后以 `wx` 发布 Canonical Set Manifest；
9. 解除 barrier。

这是一致的停写快照，不是跨 SQLite COMMIT。

### 5.2 Set Manifest

`world-runtime-backup-set/v1` 至少包含：

- `setId` 与 Host 配置版本；
- World/Session/Memory/Context 四个 artifact descriptor；
- 每 branch 的 Head seq/hash/tick、active Cycle（正常发布应为 null）与最后 Round Authority Hash；
- World Outbox ↔ Session delivery verification Hash；
- World Cognitive Job ↔ Memory watermark Hash；
- World Authority/Reaction Job ↔ Context Receipt/ProviderCall Hash；
- `consistencyHash`。

Set Manifest 最后发布。中途崩溃只留下无 Manifest 的孤立临时文件，不构成可恢复集合。

### 5.3 双向验证

| 方向 | 必须成立 |
|---|---|
| World → Session | 每个 delivered Outbox 的 deliveryId/seq/payloadHash 在 Session 唯一存在；pending 可以不存在 |
| Session → World | 每个 Session delivery 都对应同一 World Outbox；禁止 Session 领先的幽灵绑定 |
| World → Memory | completed Cognitive Job 对应 namespace watermark `>= asOfSeq`；所有 Memory source ref 不晚于 branch Head |
| Memory → World | source Event/Hash/character namespace 可在有效 branch prefix 验证；future/cross-branch/cross-character 仍拒绝 |
| World → Context | Authority/Reaction Job 引用的 Receipt、ProviderCall、request/response/proposal Hash 完整存在 |
| Context → World | committed ProviderCall 的 transaction 和 authorityHash 匹配；非终态调用只能属于同一未终结 Job |

正常 backup 在 barrier 内把所有 post-COMMIT sidecar 对账完成，因此 Set Manifest 不接受“World 已提交、Context 仍 validated”或“World delivered、Session 缺 receipt”的集合。

### 5.4 Restore

- 永远恢复到四个新目标，不覆盖当前运行目录；
- 逐文件验证 identity/version/quick_check/hash；
- 执行上述双向验证与 World Authority 全量校验；
- 对可证明未 dispatch 的 claimed Job 清 claim 后恢复 pending；
- dispatch 歧义转 `provider_terminal`，不重发；
- 只有四库与 Set Manifest 全部一致时创建 activation marker；
- Windows 上不尝试逐个替换四个活跃文件；Host 下次启动显式选择完整的新 generation 目录。

## 6. 玩家抢占线性化矩阵

玩家 Inbox 与 Cycle stop request 必须在同一个 World `BEGIN IMMEDIATE` 中线性化。不能先 enqueue、再由另一个事务“尽量”停止 Cycle。

| 玩家输入到达点 | 结果 |
|---|---|
| Tx A 之前 | 入队并把 Cycle 置 `stop_requested(player_preempted)`；不得冻结新 wave |
| Tx A 已冻结、dispatch 之前 | 保留已冻结计划；若没有任何 dispatch，可 `closed_without_dispatch`；不建下一 wave |
| Provider dispatch 期间 | 命令耐久入队；当前 wave 按原 fence 收口，歧义调用不重发 |
| response 后、Tx B 前 | 当前 wave 可提交；Cycle 在同一 Tx B 终结为 `player_preempted` |
| 与 Tx B 并发 | SQLite Writer 顺序决定线性化：Tx B 先则输入随后停止下一 wave；输入先则 Tx B 只允许收口已冻结 wave |
| Tx B 后、下一 Tx A 前 | stop request 阻止下一 wave，玩家 Round 按原 Inbox FIFO 运行 |
| enqueue COMMIT 后崩溃 | 启动恢复从 World 读 stop request；命令不丢，旧 Cycle 不恢复 |

重复 idempotency key 命中同一 Inbox 项，不重复增加 stop revision。stop request 不改变 World Head，因此不会制造虚假 Head conflict；非预期 Head 变化仍 quarantine。

## 7. Migration 与 Crash Matrix

### 7.1 Migration

- fresh v16 包含四表、索引、CHECK/FK；
- v15 → v16 后历史表逐字节不变、Reaction 表为空；
- v15 → v16 DDL 中途失败回滚为可打开 v15；
- v17/future 与外来 application id 拒绝；
- v16 旧二进制拒绝；
- Schema Golden 固定 `sqlite_master` 归一化 Hash。

### 7.2 运行时硬终止点

- `reaction.after-cycle-insert`；
- `reaction.after-stimulus-insert`；
- `reaction.after-budget-freeze`；
- `reaction.after-job-claim`；
- `reaction.before-provider-dispatch`；
- `reaction.after-provider-dispatch`；
- `reaction.after-provider-response`；
- `reaction.before-world-commit`；
- 复用 `store.before-commit` / `store.after-commit`；
- `reaction.after-stop-request`；
- `backup.after-each-store`；
- `backup.before-set-manifest`；
- `restore.after-each-store`；
- `restore.before-activation-marker`。

所有故障测试必须使用独立子进程硬终止。普通 throw 仅用于事务回滚单元测试。

## 8. Evidence → Finding → Path

### Evidence

- E-001：P0 原型两表与 Crash Harness 证明单 wave 的原子创建、claim/fence、World exactly-once 可行。
- E-002：当前 `logical-transfer.ts` 已用 `BEGIN DEFERRED` 防止单 World 导出撕裂，并完整复算 Event/Head/Round/Outbox/Inbox Hash。
- E-003：当前 Host 明确使用 World、Session、Memory、Context 四个路径；ProviderCall 只在 Context，Memory 与 Session 各有独立水位/receipt。
- E-004：`planStableCallBudget` 与 10k 门槛已提供正式 Job 顺序和预算 Hash 计算。

### Finding

- F-001：原型 Schema 不能表达正式恢复责任，直接 cherry-pick 会造成 dispatch 后 claimed Job 被错误重发。
- F-002：四库一致性不能靠逐个复制文件推断，必须先停写并以最后发布的 Set Manifest 证明同一恢复集合。
- F-003：玩家抢占的线性化点必须是 Inbox enqueue 与 Cycle stop 的同一个 World 事务。

### Path

1. Phase 9A 实现 v16 migration、四表 repository、Hash/索引/claim/fence，以及包含被引用 Context Receipt / ProviderCall 的完整 logical v6；
2. 复现 P0 单 wave公开对白、私语隔离、UTF-16、硬崩溃；
3. Phase 9B 实现多 wave、stop request 和本节抢占矩阵；
4. Phase 9C 接入四库 Set Backup/Restore、API/Health/Presentation 与运行演练；
5. 每一阶段保持生产文件逐文件四项 100%，相关测试通过后独立提交。
