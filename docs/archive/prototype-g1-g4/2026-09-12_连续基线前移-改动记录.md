# 连续基线前移：让更早的历史不再是死区

- 日期：2026-09-12
- 分支：`feat/long-term-memory-compression`
- worktree：`D:\DeepSeek Harness\harness-cordis-world-v0-memory`
- 目的：把规格 §10.4 早已要求、实现为零的"Checkpoint 由 Tail Block 数触发重建"补上。它是上下文压缩的挂载点，同时闭合两笔早已记录的债。

---

## 1. 起因：两笔已经写在报告里的债

`docs/archive/v0-phase-0-6/2026-08-29_独立代码评审问题汇总.md` 的 S-3、S-4 记录过同一件事：

- **S-3 基线冻结**：`latestAt(...) ?? rebuildAt(...)` 一旦命中就永不重建，所以每个（分支, 角色）的连续性基线**只创建一次，永久停在创建时的 seq**。
- **S-4 扫描量随历史线性增长**：Tail 的重建下界就是基线来源范围的末端，基线不动，下界就不动，于是每轮每角色都要读完整条历史再丢掉绝大部分，最终只留 4/10/20 块。

规格 `docs/spec/phase-8-implementation-v0.1.md` §10.4 写的是：

> 重建只发生在 Round 边界，并由 **Tail Block 数**、规范化字节、Profile/版本变化、maintenance 或 fork 条件确定，不因每次心理变化重建。

评审给的结论是：这**不是**新方向，是实现已经 Accepted 的规格，不需要新增 ADR。所以这一批和第一批一样，是让代码追上文档。

---

## 2. 先测出来：基线冻结到底意味着什么

新增只读诊断 `tests/experiments/measure-context-compression.ts`。它在一个 60 轮的世界上跑完，然后逐段拆开角色最后一轮真正收到的上下文。改动前的数字：

| 观测项 | 改动前 |
| --- | --- |
| 上下文字节 | 35472 |
| `continuity_checkpoint` 段字节 | 5429 |
| 基线水位 `asOfWorldSeq` | **34**（世界已经走到 814） |
| 基线引用的摘要条数 | **1**（覆盖 seq 11–31） |
| `recent_interaction_tail` 保留块数 | 10（Profile 上限） |
| 第 1 轮那句重要事实还在不在 Tail 里 | 不在 |
| 最后一轮上下文里的召回段 | 空（查询与任何既往记忆都不匹配） |

也就是说：世界走了 814 个序号，角色的连续性基线停在 34；摘要通道名义上存在，实际只有 1 条、且停在开局；更早的历史既不在 Tail 里，也不在任何摘要引用覆盖的范围内。**能承载"更早"的只有一条几乎没内容的引用链。**

## 3. 改动

### 3.1 `packages/agents/src/continuity.ts`：Tail 自己报告它从哪里开始

新增 `InteractionTailBuilder.rebuildRolling(...)`，返回 `{ floor, tail }`：

- 已提交的块还放得下 Profile 的块数上限时，`floor` 就是调用方给的下界，**不动**；
- 放不下时，`floor` 前移到"最后一个被丢弃块的 `endSeq`"，Tail 只保留窗口内的那些块。

同时把构建块的逻辑抽成私有 `#blocksAt(...)`，`rebuildAt` 与 `rebuildRolling` 共用同一份读取与校验——两个方法不可能对同一段历史得出不同结论。

### 3.2 `packages/application/src/context-pipeline.ts`：两条路径共用一次解析

新增私有 `#continuity(address, characterId, asOfWorldSeq, maximumBlocks)`：

```
已有的基线 ──▶ floor = 它的来源末端
                │
                ├─ Tail 重建后 floor 没动 ──▶ 沿用已有基线（不重建）
                └─ floor 前移了 ────────────▶ 在新区间末端重建基线
```

角色路径与反应路径都改为调用它。两处原本各自写着 `latestAt(...) ?? rebuildAt(...)`，是同一份规则的两份拷贝；现在只有一份，和第一批里 `runtime-availability.ts` 的处理方式一致。

**为什么基线必须跟着 Tail 一起走**：上下文层的完整性校验要求 `tail.afterSeq === checkpoint.asOfWorldSeq`。基线不动，Tail 的扫描下界就不动；基线前移，两者才同时收窄。

## 4. 改完之后的同一组数字

| 观测项 | 改动前 | 改动后 |
| --- | --- | --- |
| 基线水位 `asOfWorldSeq` | 34 | **668** |
| 基线引用的摘要条数 | 1 | **12** |
| 摘要覆盖的序号范围 | 11–31 | **11–624** |
| Tail 扫描起点 | 34 | **668** |
| Tail 保留块数 | 10 | 10（不变） |
| 上下文总字节 | 35472 | 37564 |
| `continuity_checkpoint` 段字节 | 5429 | 7520 |

三个点值得说清楚：

1. **Tail 的内容完全没变**（仍是最近 10 块，覆盖 seq 676–798）。变的只是它从哪里开始重建：扫过的序号从 780 个降到 146 个。
2. **基线不再冻结**，摘要引用从 1 条变成 12 条，第一次覆盖到 Tail 起点之前——这正是后续把摘要正文接进上下文所需要的挂载面。
3. **上下文变大 2092 字节**，全部来自 `continuity_checkpoint` 段里多出来的 11 条摘要引用。摘要引用只带 id、序号和 Hash，对模型没有信息量；它变大是因为**引用面变宽了**，要等下一步把正文接上才产生价值。

## 5. 必须守住的不变量

| 不变量 | 保障方式 |
| --- | --- |
| 还放得下时不重建基线 | 集成测试断言第 2 轮的基线水位与第 1 轮完全相同 |
| 放不下时基线随窗口前移 | 同一测试断言最后一轮的水位严格大于第一轮 |
| Tail 永不超出 Profile 块数 | 同一测试逐轮断言块数 ≤ 4 |
| 不扫全量历史 | 既有守卫测试把 `readEvents` 换成抛错的替身，Tail 仍能构建 |
| `rebuildRolling` 与 `rebuildAt` 结论一致 | 单元测试断言 `rolling.tail` 与"从 `floor` 直接 `rebuildAt`"逐字段相等 |
| 边界与非法输入不变 | 单元测试覆盖 `maximumBlocks = 0`、负数下界、倒置水位 |
| 块内绝不截断 | 仍然只做整块丢弃，没有任何切块代码路径 |

## 7. 这一批明确没做

- **摘要正文仍然不进上下文**。ADR-0068 第 1 条明确禁止 Checkpoint 复制 L1 正文（"不临时生成自由文本"，理由是防止两套漂移的摘要事实源），要打通它必须先有一份 superseding ADR。这一批只把"能被引用的范围"铺好。
- **没有处理基线与摘要之间的小缝隙**。摘要是按记忆条数每 8 条一组，最后一组不足 2 条会被跳过，所以基线的来源末端与摘要覆盖末端之间会留几个序号（实测 624 与 668）。这是分组边界的固有结果，等下一步决定"取哪些摘要进上下文"时一并处理。
- 不改裁剪优先级、不改任何 Context Profile 数值、不改世界事件日志、不改记忆库存储结构。
