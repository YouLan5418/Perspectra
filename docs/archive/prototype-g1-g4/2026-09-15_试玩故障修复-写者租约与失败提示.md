## 1. 现象与定位

真实试玩里，玩家第一轮成功（`headSeq 145`），隔了**超过 3 分钟**再发言就整轮失败，且**一次模型调用都没有发出**。耐久记录把两件事同时钉死：

- 玩家输入 job 停在 `received`（未被丢弃，也未推进）；
- 租约表 `expires_at_ms` 已过期 **183.2 秒**（`leaseTtlMs` = 180 秒）。

机制只有一处：

| 位置 | 事实 |
|---|---|
| [writer-lease.ts](../../../packages/store-sqlite/src/writer-lease.ts) `renew` | 条件是 `expires_at_ms > now`——**租约还活着才能续**；过期再续即抛 `WRITER_LEASE_LOST`（retryable） |
| [round-coordinator.ts](../../../packages/application/src/round-coordinator.ts) `#refreshLease` | 回合路径会**先 acquire 再 renew**（418/483/509/529 行），所以回合本身不怕空闲 |
| [world-application.ts](../../../packages/application/src/world-application.ts) 玩家输入入口 | 只挂了 `renewWriterLease()`。意图 worker 把它当心跳、**在派发解释之前就先续一次**——此时租约已过期，于是整轮失败 |

**结论：宿主的玩家输入入口在空闲超过 TTL 后无法自愈。**"暂停一会儿再接着说"恰恰是试玩最正常的节奏，所以这是真实缺陷，不是玩家输入的问题。

## 2. 修法一：处理耐久玩家输入之前**确保**租约（§1 的病根）

- `RoundCoordinator` 新增公开 `refreshWriterLease()`（内部即 `#refreshLease`：acquire + renew）。
- 玩家输入入口的租约端口从 `renewWriterLease()` 改为 `refreshWriterLease()`；worker 的心跳因此变成"确保我是写者"。
- **安全性来自 `acquire` 的语义**：租约若被别人**活着**持有，`acquire` 抛 `WORLDSTORE_BUSY` 而**不会抢占**（围栏语义保留）；自己持有则沿用同一 token；只有过期才重新取号。所以这条改动不会让一个被围栏的 Host 抢回分支。

## 3. 修法二：失败提示说实话（让玩家重发才是"被切成两次"的真因）

同一场试玩里的第二个现象更值得记：玩家第一次失败后**重发**了同一句，于是世界把同一意图**做了两遍**——因为那条输入**从未被丢弃**（状态 `received`），宿主的耐久输入 FIFO 会先把前一条未完成的跑完，再处理新的一条（实测：`headSeq 145 → 201 → 260`，两条 job 都 `completed`）。

**误导来自提示语**：页面写的是"本轮失败……换一种说法"，读起来就是"这句没生效，重说一遍"。现在运行时在失败时用**自己生成的 idempotency key** 回查耐久的 `player_input_jobs`，把真实状态报给玩家：

| 真实情况 | 提示 |
|---|---|
| 世界从未受理（例如宿主已关闭） | "这条输入没有被世界受理；可以重新说一次。" |
| 已被世界记录、尚未完成 | "你的输入已被世界记录（状态 received），它会在世界能写入时完成——**请不要重发**。" |
| 已完成 | "这一轮其实已经完成了，请看转录。" |

## 4. 验证

- **成对证伪**：把修法一的那一行改回 `renewWriterLease()`，新增用例 `takes the writer lease back when the page was idle past its deadline` 立刻变红，且报出的正是真实试玩里那句 `writer lease cannot be renewed because it expired or was fenced`（即该用例是这次故障的回归测试）；改回后通过。
- 新增用例两条：空闲超期后输入仍能落（租约自愈）；未受理时提示允许重试（提示语是玩家读到的文本，钉住它）。
- `corepack pnpm@11.7.0 check` 退出码 **0**，主用例 **1440** 项 / 131 文件，崩溃套件 **55** 项，生产 `src` 逐文件四项 **100%**。

## 5. 修法三：把"能去哪里"交给模型（真机里被撞出来的第三个缺陷）

第三次试玩里，玩家让 Claude"去帮一下 GLM"，Claude 也答应了——**但它在世界里一步都没动**。日志给出的原因不是策略，而是拒绝：

```
seq 346  action.resolved  actor=claude  actionType=move  accepted=false
         reason="move target is not a manifest location"
模型提出的参数：{"locationId": "location:study"}      ← 世界只有 bedroom / living-room / workspace
```

**根因**：冻结路径的 `move` 选项里只有 `{actionType:'move', actionVersion:1}`——**没有任何"能去哪"的清单**，模型只能自己编一个像样的 id，世界再拒绝它，而那一次调用**已经付过费**。对比：**玩家**那条路（Player Intent 的准备层）会把地点逐个列出来 ✓，所以玩家能移动；**模型**这条路没有。

**修法**：让选项带上世界自己的地点，并**用移动规则本身去问**（不另写一套判据）：

| 位置 | 改动 |
|---|---|
| [frozen-interactions.ts](../../../packages/kernel/src/frozen-interactions.ts) | `move` 选项新增 `destinations`：用 `SpeakMoveRulebook` 逐个地点试解，只保留 `accepted` 的（因此"当前所在地"天然不在其中——移动到这里不是一次移动） |
| [rulebook-registry.ts](../../../packages/kernel/src/rulebook-registry.ts) | `ActionAffordance` 声明同一字段 |
| [context-pipeline.ts](../../../packages/application/src/context-pipeline.ts) | affordance 段把它一并交给模型（与 `performances` 同一条路） |
| [provider-chat/wire.ts](../../../packages/provider-chat/src/wire.ts) | `move` 的 `locationId` 渲染成**闭集**（`enum`，描述里带地点名字）；世界没给清单时保持自由字符串，**不发明** |

**真机验证（同一批轮次，`deepseek-flash`）**：

| | 修复前 | 修复后 |
|---|---|---|
| 模型提出的目标 | `location:study`（不存在） | `location:ridge-path`（真实存在） |
| 世界裁定 | `accepted=false: move target is not a manifest location` | **`accepted=true`**，`character:moved` 落库 |

`character:companion`（NPC、模型驱动）实际完成了 `ridge-shelter → ridge-path` ✓。**这同时解开了隔离测试的反方向**：只有角色能真的跨场景，才谈得上"另一个场景里的对话会不会泄漏回来"。

### 5.1 顺带记录的一条观察（非缺陷）

同一局里有一次玩家发言以 `ambiguous` 收场——那是**解释器自己**要求澄清（它不确定该怎么理解那句话），不是失败。设计允许它这么做（宁可问，不要猜），代价是那一轮不推进。

## 6. 未做 / 遗留

- **已被受理但未完成的输入如何告知**：当前只在"本轮失败"时回查一次。更完整的是把输入状态做成页面可见的队列指示（"排队中"），但那要动 `PlaytestState` 的形状，属另一批。
- **FIFO 先补前一条**这一行为本身正确（已受理的输入不该丢），**不需要改**；要改的是别诱导玩家重发（§3）。
- 修复只在应用层与试玩运行时，**没有动世界事实、协议版本或 Authority**。
