## 2. 发现 1：持久化边界不核对证据与档案

### 2.1 问题成立

[reaction-cycle.ts](../../../packages/store-sqlite/src/reaction-cycle.ts) 的首波与延续两处准备只核对刺激引用的 Observation，随后把 `evidence` 原样接收并纳入 `stimulusEntryHash`。因此同时接受过：

- 一个 `responsive/v2` 周期，候选与刺激**都没有** `roleClass`/`evidence`；
- 一个 `responsive/v1` 周期，刺激带着观察者、Observation、事件序号互相矛盾且类别冲突的证据。

两者都会进入耐久哈希，也就是"为什么这个角色被称重"可以成为**自洽但语义错误**的权威记录。

### 2.2 修法：一个共享校验，落在三个边界

新增 [contracts/reaction-evidence.ts](../../../packages/contracts/src/reaction-evidence.ts)：`REACTION_ROLE_RANK`、`strongestReactionRoleClass`、`assertReactionEvidenceBinding`。类序表从两份（`stable-call-budget.ts` 与 `application/reaction-evidence.ts` 各一份）收敛成一份，应用侧与持久化边界读同一张表。

校验按档案分支：

| 档案 | 要求 |
|---|---|
| `responsive/v2` | 候选必须有类；每条刺激必须有证据；证据的 `version`/`sourceEventOrdinal`/`observationId`/`observerCharacterId` 必须与本刺激一致；`actionId` 必须等于来源 Observation 记录的动作，完整可见的 Observation 还要与 action/definition 入口身份一致；证据的类必须是四个冻结类之一；草稿同时写出刺激类与证据类时两者必须相同；候选的类必须等于其刺激中的最强类 |
| `responsive/v1` | 候选不得有类；刺激不得有类，也不得有证据 |

证据本身按**精确键**校验（`version`、`sourceEventOrdinal`、`observationId`、`observerCharacterId`、`actionId`、`entry`、`roleClass`），`entry` 的两个变体各自精确：`{kind:'definition', definitionRef:{id,version}}` 或 `{kind:'action', actionType, actionVersion}`，`actionId`/`definitionRef.id`/`actionType` 走 `assertProtocolString`，版本为正安全整数。二次审查又补上来源事实绑定：合法字符串不等于正确动作，`actionId` 必须与来源 Observation 相同；完整内容下 action entry 的 `actionType` 也必须相同，definition entry 只能对应 `interact`。`occurrence_only` 有意隐藏动作身份，只核对仍然公开的 `actionId`，不能从隐藏内容反推类型。

边界：

1. **首波**（`prepareInitialReactionCycle`）——在任何东西被哈希之前；
2. **延续波**（`prepareReactionWaveSettlement`）——与首波同一条规则；
3. **读回**（`readReactionCycle`）——行不仅重新哈希，还重新核对。这一点是必须的：条目哈希覆盖的是**存进去的那份证据**，所以一份与自己刺激不符的记录会自洽地通过哈希。

顺带修掉一个形状认知错误：**存库的刺激不带独立的 `roleClass`**，类在证据里面。第一版校验把两者都当必填，读回时对每个 v2 刺激都误报，随即改成"草稿有两份必须一致、行只有一份"。

### 2.3 用例与证伪

`reaction-cycle.test.ts` 新增三段：

- 23 条 v2 变更用例（无类、非冻结类、无证据、类与证据冲突、证据非对象、多余字段、版本不支持、序号/Observation/观察者不符、证据里的类不合法、`actionId` 为空或指向另一动作、入口身份与来源动作不符、`entry` 类型不支持、`entry`/`definitionRef` 键不符、`definitionRef.id` 为空、版本为 0、`actionType` 为空、候选类不是最强类）；
- 3 条 v1 用例（候选带类、刺激带类、刺激带证据）；
- 一条读回篡改：把证据里的动作改成另一动作并**重算条目哈希**，使行自洽——读回必须根据来源 Observation 拒绝。

另外把既有"拒绝下一个波次候选"的表格补上两条 v1 行，并新增一条 v2 延续波用例。

逐条回退跑过，全部变红：

| 回退 | 结果 |
|---|---|
| R-A 首波不校验 | 红：变更用例整段 |
| R-B 延续波不校验 | 红：两条 v1 表格行 + 新的 v2 延续波用例（**第一次跑时这条是绿的——我自己的证伪发现了这个覆盖漏洞**） |
| R-C 读回不重新核对 | 红：自洽篡改用例 |
| R-D 去掉"最强类"规则 | 红：变更用例 |
| R-E 不把证据与刺激对齐 | 红：变更用例 + 自洽篡改用例 |
| R-F v1 不再拒绝无档案记录 | 红：v1 用例与新延续波用例 |

**一处需要说明的收紧**：读回校验意味着上一版（同分支、未发布）写下的 v2 延续刺激——当时不带证据——现在会被拒。该档案是本分支同日引入的，仓库内没有任何耐久基线含这种行，所以这是收紧而不是破坏；但它确实是"a previously accepted durable state now fails closed"，记在这里而不是埋着。

## 3. 发现 2：失败观察与 ADR-0096 §3 不一致

### 3.1 问题比描述的更严重

ADR-0096 §3 决定："失败默认可观察（与今天的硬编码行为一致），由世界声明的观察策略可关；关闭只抑制知情范围，事实层照常写入 `action.rejected`"。

核查后发现两件事：

1. 那句话里的"与今天的硬编码行为一致"**说的是非冻结路径**：`rejectRulebookResolution` 本身不带观察范围，协调器因此退回 `scene_public`，失败在今天就是可观察的；
2. 冻结路径（`043737f`，I4-b）把失败**硬编码成 `self`**，把 ADR 的前提改掉了；而交互定义契约里根本没有可声明的观察策略字段（规格 §2 的 Definition 表里列着 `observationPolicyRef`，实现里一直缺）。

所以这不是"文档与实现各说各话"，而是实现把一条已接受决定的前提推翻了：旁观者看不到失败尝试，也就不会产生规格 §5 所说的 witness 刺激。

### 3.2 修法：受锁观察策略

- [contracts](../../../packages/contracts/src/interaction-definition.ts)：新增 `InteractionObservationPolicyV1`（`onAccepted`/`onRejected` ∈ `{scene_public, self}`）与 `InteractionObservationPolicyImplementation`；`InteractionDefinitionSpec` 增加必填 `observationPolicyRef`；`InteractionPackageImplementation` 增加 `observation`；`InteractionAdjudication` 增加 `observationScope`（与 `resolvedRoles`/`affectedCharacterIds` 一样，放在被哈希载荷**之外**，所以交出去不会移动任何 trace 哈希）。
- 范围只允许 `scene_public` 与 `self`：`direct`/`private` 要点名收件人，而定义在动作提交前无从知道收件人是谁。
- [runtime](../../../packages/interaction-runtime/src/registry.ts)：安装期校验策略形状；冻结期要求每个启用定义的策略都能解析（少了就 `observation policy missing`）；`resolve()` 按状态取 `onAccepted`/`onRejected` 并交出去。
- [kernel](../../../packages/kernel/src/frozen-interactions.ts)：不再自己决定范围。**定义级拒绝**用定义的声明；**没能命名定义的请求**（`INTERACTION_NOT_BOUND`、非法参数）仍留给 actor——那条理由会点名世界的目录结构，不是定义该不该披露的问题。
- [首批包](../../../packages/interactions-basic/src/basic.ts)：两条策略。`base:public-outcome`（成功与失败都 `scene_public`）用于拿/放/递；`base:private-refusal`（成功 `scene_public`、失败 `self`）用于牵手与解除。取物被拒是场景里看得见的事，而"想牵某人手被拒绝了"不该由场景替当事双方宣布。事实层两种情形都照常写 `action.rejected`。

### 3.3 用例与证伪

- 单元：被拒的取物 `scene_public`、被拒的牵手 `self`、未能命名定义的请求 `self`，且每种情形都写出 `action.rejected`；
- 端到端：同一世界里两次同形拒绝——杯子已被拿走、两人已牵着手——旁观者只收到前者的 Observation，后者只有 actor 自己；
- 运行时：策略不在选择内、版本不支持、范围写了 `private` 三种拒绝，以及组件参与包锁（数组顺序无关）。

四条回退全部变红：R-A kernel 自己决定范围、R-B runtime 两种状态报同一个范围、R-C 去掉冻结期检查、R-D 去掉范围校验。

### 3.4 ADR 的一处事实更正

ADR-0096 §3 的那句括号描述对非冻结路径成立、对冻结路径不成立（实现当时是 `self`）。决定本身不变，因此在 ADR 里加一条**注明日期的更正**，不改决定、不改方向。

## 4. 发现 3：Player Intent 在 v10 下不是"缺样本"，是走不通

核查结论比审查描述的更具体：**Player Intent 目前无法表达一次冻结交互**，三处都写死 v9 词表。

| 位置 | 问题 |
|---|---|
| [player-intent-preparation.ts](../../../packages/application/src/player-intent-preparation.ts) | interact 选项写死 `actionVersion: 1`，且不像 move 那样先解析验证 |
| [player-submission.ts](../../../packages/contracts/src/player-submission.ts) | `PlayerIntentAffordance.actionVersion` 是字面量 `1`；`choice.actionVersion !== 1` 直接判非法；interact 参数只认 `{targetId, interactionId, arguments}`；产出的动作写死 `actionVersion: 1` |
| 同上 | `/act` 与显式 `input.action` 路径同样写死 `1` |

而冻结路径的 `affordances()` 已经正确地报出 `interact@2` 与冻结请求形状——也就是说，选项摆在面前，绑定层把它拒了。

### 4.1 修法

| 位置 | 改动 |
|---|---|
| [player-submission.ts](../../../packages/contracts/src/player-submission.ts) | `actionVersion` 放开为 `1 \| 2`；版本按动作类型判定（言语与移动只能 1，交互 1 或 2）；交互参数按版本分派——v1 仍是 `{targetId, interactionId, arguments}`，**v2 是冻结请求 `{targetRef{kind,id}, bindingId, definitionRef{id,version}, arguments}`**，逐字段校验（目标 kind 的闭集、定义版本为正安全整数、参数为对象）；产出的动作沿用选项自己的版本 |
| [player-intent-preparation.ts](../../../packages/application/src/player-intent-preparation.ts) | 交互选项沿用 affordance 的版本（`2` 保留，其余为 `1`）；显式命令路径从它所行使的 affordance 取版本，因为命令本身不带版本 |
| 夹具与用例 | 新增 `frozenIntentWorld(profile?)`（同一个 v10 世界，把玩家输入策略换成 `player-intent/v1`）；崩溃 worker 增加 `frozen` 模式 |

模型可见契约（`player-intent-candidate/v1`）没有改动——候选仍然只点名 `affordanceId` 与 key，改的是 Host 侧绑定的形状与版本。

### 4.2 四类样本

| 样本 | 断言 |
|---|---|
| 提交 | `interprets free text into a frozen interaction, with Authority 6 and one commit`：模型被提供的正是冻结请求形状（`binding:entity:cup:base:take`、`"actionVersion":2`、`definitionRef`），杯子只被拿走一次 |
| Authority 6 | 同一用例读回该回合的 Authority，`schemaVersion` 为 6，且至少一条 resolution 带 `interaction` |
| 重放 | 同一输入再提交一次返回同一结果，且 provider 只被问过一次（`calls === 1`） |
| 恢复 | `recovers an interpreted frozen interaction after hard termination at store.before-commit / store.after-commit`：租约过期重启后自行完成，provider 不再被问（`calls === 0`），转移恰好一次，Authority 仍为 6 |

另外新增两条单元用例：显式命令从 affordance 取版本（成功路径），以及**一个走不通的动作类型要澄清而不是被编造版本**（`action is not currently afforded` 的守卫）。

### 4.3 证伪与一处删掉的代码

回退逐条跑过，全部变红：R-A 产出动作钉死版本 1、R-B 绑定层恢复"只接受版本 1"、R-D 准备层把交互版本钉死 1。

还有一处**删掉**的代码：我最初在准备层给交互选项加了"先解析验证再提供"（照抄 move 分支）。回退测试显示没有任何用例变红——因为**冻结路径的 `view()` 自己已经只列出可尝试的选项**，而 v9 那边我没有用例证明它改变过行为。于是删掉：它是 v10 下的死代码，v9 下的未验证行为变化。用例里保留了"模型看不到 `binding:entity:cup:base:drop`"这条断言，但注释改成归因于世界自己的视图。
