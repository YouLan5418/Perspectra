# 随代码维护这套文档

入口是[当前架构](README.md)。入门、模块地图、代码路线帮助读者理解源码；专题页解释机制；指南说明操作；研究页保存当次证据。历史 ADR 与 archive 不承担现行行为说明。

## 1. 哪一处是主要解释

| 内容 | 维护位置 | 更新触发 |
| --- | --- | --- |
| 初学者概念与例子 | getting-started.md | 产品流程或术语发生变化 |
| 目录与模块职责 | modules.md | 新增、删除、合并包或改变职责 |
| 实际入口与调用路线 | code-walkthrough.md、runtime.md | 入口、循环或提交流程变化 |
| 交互和输出协议 | interaction.md | 决策字段、动作或受众行为变化 |
| 原生与 Core 记忆 | cognition-memory.md | 来源、窗口、召回或整理行为变化 |
| 活动与作者能力 | creator-runtime.md、controlled-interaction.md | 脚本能力、限制或调度变化 |
| 操作和发行范围 | guides 与专题说明 | 命令、配置、源码能力或发行包变化 |
| 实测记录 | studies 与 experiments | 新实验另记日期、配置和证据 |

其他页面引用主要解释，避免复制整段。新增模块有实际职责就补地图与必要说明，不为每个文件生成独立文档。

## 2. 每次改代码怎样更新

1. 确认影响读者的哪个问题：怎么启动、拿到什么信息、能做什么、怎么提交、哪里查失败。
2. 读对应章节与改过的实现，更新路径、行为和例子。
3. 区分“源码已接通”“测试验证范围”“未来计划”“发行包已包含”。包没重建不写成已发行。
4. 实质修改解释页时更新核对日期，不只刷新日期而不读代码。
5. 运行下面的检查；按代码风险选择相关测试。只改文档不用跑全仓测试。
6. 交付说明更新了哪些章节、核对了什么，哪些体验未验证。无法核对的部分明确标注，避免留下看似确定的旧叙述。

~~~powershell
node scripts/docs/check-links.mjs
~~~

## 3. 用读者问题检查可读性

每篇说明应回答：解决什么问题？输入来自哪？输出给谁？谁有权改变世界？失败后哪些结果仍成立？下一步读哪个文件？

第一次出现缩写解释意思；先写角色互动例子，再给类名。重要判断靠近源码链接。控制流程可画简图，但注明省略分支。

例如先写“角色已有更新的记忆档案，较早的后台任务不能把它覆盖回去”，再解释前缀与实现，读者更容易理解。

## 4. 自动检查的边界

[check-links.mjs](../../../scripts/docs/check-links.mjs)检查当前架构目录、根 README 和 docs/README 中本地链接目标，并核对模块地图涵盖 packages 的直接子目录。它不访问外网、不读取角色数据、不调用模型。

它能发现文件移动后的断链，以及新增包后遗漏地图；不核对标题锚点、函数语义或自然语言准确性，也不能保证新功能都被写进文档。修改者仍需核对正文。

根 AGENTS.md 的同步要求让后续 Agent 沿用此流程。采用 Markdown、源码链接、一个轻量脚本和改动时核对的约定，不增加文档平台或模型审查层。
