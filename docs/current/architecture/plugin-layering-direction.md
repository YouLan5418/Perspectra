# 插件分层方向与暂缓需求

日期：2026-11-04。用户在阶段 11 后明确的方向与暂缓需求。随后用户依据核心边界截图确认：目标是玩法可组合，内部机制使用 Cordis，外部玩法可通过脚本等形式组合。正式约束见[核心与插件统一规范](plugin-standard.md)，本文继续保留两个暂停需求及其讨论来源。规范不表示代码已全部完成分层。

例如制作一场料理比赛：内部机制提供活动流程、合法操作、状态、观察和裁定入口；外部玩法插件组合食材、计分、角色参与和结束条件；世界包提供人物、场景、美术及具体比赛内容。宿主负责将合法结果保存并交付给有权看到的人。新玩法不应要求作者读懂 WorldHostCore 的内部调用关系。

## 1. 已确认的方向

优先把现有功能的分层、职责和接口规范整理清楚，再增加功能。后续目标是：**主干负责世界运行与事实边界，内部插件开放可组合的机制，外部插件通过这些机制接口组织不同玩法，世界包提供具体内容与配置。**

此前按需求逐个抽取的接缝是已有成果，但“实现已经搬到包里”不等于功能分层和规范已经统一。不能把阶段编号或可替换模块数量当作架构整理完成的证据。

| 层 | 负责什么 | 依赖边界 |
| --- | --- | --- |
| 主干与宿主 | 世界／分支生命周期、授权读取与投递、写入边界、原子提交、存档恢复、插件装载与诊断；连接模型、脚本和前端 | 通过公开契约连接插件，不逐个认识某种玩法的业务规则 |
| 内部插件／机制模块 | 提供职责明确的通用机制及默认实现，例如活动流程、状态操作、交互、调度、角色执行、记忆和模型适配 | 面向主干契约与明确声明的机制接口，不反向依赖外部玩法或特定世界包 |
| 外部插件／玩法模块 | 声明需要的机制与状态，组合操作、条件、流程和规则，形成不同玩法 | 使用公开机制接口；支持的路径不导入宿主私有实现、不直接写世界数据库 |
| 世界包／内容 | 人物、地点、物品、事件池、剧情内容、美术、玩法选配及配置；必要的包内脚本 | 使用已声明的玩法与机制，不复制一套引擎才能运行 |

内部机制使用 Cordis，外部玩法可以使用声明、脚本和配置；第三方原生 Cordis 扩展作为单独的适配入口保留。“内部／外部”不自动构成安全沙箱。现有第三方仍是受信任代码；官方接口应统一维护权限与事实边界。内部插件的默认玩法也应消费公开机制，不为官方实现留下只有宿主能用的业务捷径。

既有调度、模型等底层替换能力暂时保留。用户本次没有要求立即移除它们或把所有外部插件强制改成玩法插件；后续按统一分层核对，而不是重建另一套平行接口。

## 2. 目录要表达职责

优先沿用现有位置，不为目录整齐先做大规模迁移：

- `packages/official-*`：现有官方内部实现的主要位置；后续核对哪些是真正的通用机制，哪些应是消费机制的默认玩法。
- `packages/plugin-sdk`：外部可依赖的契约入口，不能只是把宿主内部方法原样导出。
- `desktop/host`：宿主装配、运行和边界桥接；逐步识别仍混在其中的玩法职责，不能继续作为所有新功能的归宿。
- `examples/host-plugins`：外部插件开发示例，不代表已安装插件的运行目录。
- 外部插件实际代码：继续由用户配置路径装载；具体安装布局后续单独统一，不自动下载、不新增市场。
- `examples/world-packs`：具体内容与玩法使用示例，不承载宿主公共实现。

目前活动、状态、通信、知识和自主配置仍有实现留在宿主。目录整理需要先列出实际消费者、依赖和数据归属，再决定拆分；本次不把这些目标写成已经完成的迁移。

## 3. 后续统一规范应回答的问题

每项机制先说明用途、输入／输出、状态归属、谁能读写、如何裁定、何时调用、失败如何反馈，以及 open／close、回合、保存／分叉／重新生成时如何处理。外部玩法组合机制时应能从这份契约得到答案，而不是查内部源码补齐隐含顺序。

跨模块调用用明确的公开接口与依赖声明，不依赖导入顺序、临时回调或共享可变对象。继续区分包的插件依赖、Cordis 服务就绪、机制执行顺序；不把三者混成一个万能依赖系统。

统一规范与初步实现差距清单现已写入[正式规范](plugin-standard.md)，后续按实际模块和消费者确定需要修改的接口与目录。不能把“统一规范”直接展开成一次全仓重写，也不为已经可用的简单组合增加无必要的协议层。

## 4. 曾经暂缓的两个需求

### A. 剧情导演：扰动器与节拍器

**2026-11-05 已实施为起伏器：** 由 official-pacing 解释世界包的 scripts/pacing.js，还能按条件改数值、给角色一次察觉或念头。决策全部从已提交事件推导，不需要 B。作者用法见[剧情节奏](../guides/story-pacing.md)，真实对照见[记录](../studies/2026-11-story-pacing.md)。下面是当时的需求记录。

- 扰动器按作者声明的关键内容与实质进展条件检测停滞，提高介入倾向，从高／中／低矛盾事件池选择合适事件。
- 节拍器按正弦节奏调整不同强度事件的投放权重与冷却，结合高强度后的恢复期，避免持续紧绷。目标是调节供应，不能宣称波形保证玩家实际体验。
- 保留角色自主选择；事件必须满足当前世界条件并通过正常启动／裁定路径，不能用旁白伪造状态变化。
- 此前讨论过以活动自动开始的候选选择作为最小接入点，监测指标、时钟、冷却、随机回放及调试说明仍待在统一架构下细化。

### B. 插件声明宿主管理的持久化世界状态

- 插件声明状态的类型／Schema、初值、作用范围、可见性，以及操作与规则；提出变更后由宿主校验、裁定并原子提交。
- 状态按稳定插件身份区分命名空间；归属、读权限、写权限分开定义；跨插件通过公开机制协作，不能任意写另一个插件的状态。
- 必要世界状态随节点、分叉、重新生成和恢复保持一致，区别于插件自己写的文件、缓存和诊断记录。
- 复用既有状态与事件存储作为优先调研方向，不预先承诺新的数据库或事件协议。具体注册接口、生命周期及版本不兼容处理均未定案。
- 起伏器已不依赖它：相位和冷却从已提交事件推导，作者自己的长期数值存进已声明的状态。
- **状态：仅记录需求和讨论方向，暂停实现。** 当前没有通用的外部插件状态声明接口；现有插件目录和记忆快照不能冒充这项能力。

这两个需求后续应落在统一分层与契约内，不继续各自给宿主加一条特殊路径。
