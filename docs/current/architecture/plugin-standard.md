# 核心与插件统一规范

2026-11-11 定稿。用户已确认[可组合游戏引擎架构](composable-engine.md)用于指导施工，本文作为现行规范入口。实现差距见第 8 节，批次与进度见[实施计划](../../superpowers/plans/2026-11-11-composable-engine-refactor.md)。

例如搜证玩法，作者用一个定义模块声明精力、搜查裁定、NPC 用途、目击观察和线索面板，游戏包显式启用，工具链通过短剧本检验扣精力、线索与受众。角色自行决定行动，正式效果经过核心验证和原子提交。

## 1. 永久保留的核心边界

核心维护实体身份、权威事件、授权视图、认知来源、状态与效果验证、短事务原子提交、分支一致性，以及正式执行的资格和硬预算。

玩法提供具体业务规则，核心绑定真实主体并执行相应规则。状态、位置、物品和观察通过核心认识的效果提交，自然语言负责自由表达。程序隔离与叙事一致性分别验证。

稳定能力定义、具体 Provider 和调用方分别组织。模块可以共处一个包，包结构根据实际依赖与消费者收敛。

## 2. 四层与宿主适配

| 层 | 负责内容 | 公开边界 |
| --- | --- | --- |
| 核心 | 事实、权限、提交、分支、执行资格和实际硬预算 | 窄的授权读取与受控执行接口 |
| 能力服务 | scheduler、decision、memory、llm、state、activity、communication 等契约和可替换实现 | 明确输入、结果、生命周期与失败语义 |
| 玩法与策略 | 战斗、骰子、节奏、自主、跑团及具体交互 | 状态、操作、限制、活动与展示定义 |
| 游戏包 | 组合玩法、参数、内容和轻量脚本 | 显式插件选择和必要能力要求 |

Host 与 Launcher 提供运行、装配、HTTP、管理、凭证与端侧适配。核心调用能力契约，官方和第三方玩法使用同一公开注册入口。

## 3. 内部机制插件与实例生命周期

使用现有 Cordis Service、inject、effect 和插件 Fiber。进程登记工厂与可共享定义，每个世界、Lens 和重生候选持有独立服务绑定、注册表与任务。

Context 的 isolate／extend 组织服务解析范围。实例根插件 Fiber 拥有其插件、监听器、effect 与清理责任，关闭时释放保存的实例 Fiber。实例事件分发和可变缓存同样明确归属。

调度器安排机会和提出有界执行周期，核心原子检查激活、并发和期限。预算属于宿主执行请求或持续会话，周期换界继续使用剩余额度。模型发送与重试在真实调用边界计量。

普通调用处理授权投影，可信裁定取得声明需要的真值。数据所有权通过窄投影、适当复制和冻结保护，异步取消主动结束等待并收回执行资格，资源按拥有者与依赖顺序清理。

## 4. 外部玩法与自描述定义

原生模块和包内脚本使用共同作者契约，定义共享状态、操作参数 Schema、授权 offer、唯一处理器、NPC 用途和结果说明、玩家展示及所需钩子。作者接口具有明确返回类型，外部输入与输出继续运行校验。

默认规则采用限制合取和命名空间操作 ID 的唯一处理器。计算修正在所属操作确定主结果前完成，afterAction 消费共同候选快照，单层派生与主结果一起验证并原子提交。

原生插件属于可信代码。宿主先核对安装和用户允许状态再导入入口，配置校验模块采用同一授权。包内脚本使用其执行环境公开的能力。

原生注册及共同脚本定义属于本轮施工范围，现行作者格式与新契约的对应见[共同契约](mechanism-contracts.md)，实际迁移对象在相应批次登记。

## 5. 状态、周期、兼容与失败

| 方面 | 定稿要求 |
| --- | --- |
| 插件状态 | 复用已有状态、事件与分支能力，所属模块公开操作负责合法变更，核心检查结构、转换和效果 |
| 执行周期 | 玩家或系统入口可启动，核心持有周期资格和结果，玩法轮次与世界时间分别表达 |
| 周期末 | 正常完成且具备资格时运行 onCycleEnd，各钩子至多一次并独立结算 |
| 恢复范围 | 保留已提交事实和必要插件状态，未提交计划、反应与剩余结算允许丢弃 |
| 存档兼容 | 插件 ID 和数据兼容声明覆盖持久结构及语义，摘要按诊断或重生可比性用途处理 |
| 装载失败 | 显式玩法、显式 Provider 和选定必要能力采用 Fail-Closed，纯外围扩展可跳过并告警 |
| 运行故障 | 结构化返回业务拒绝，插件异常和非法返回值按故障处理，影响范围按调用位置确定 |

单个 LLM 能力可以按角色路由多个模型和连接。记忆来源保持角色与分支范围，已安装且可交付的归档决定安全覆盖边界。perform 成功后的表达失败分别反馈，已提交行动保留。

## 6. 目录和命名规范

参考布局为 sdk、core、providers、memory-core、plugins、world-pack、frontend 以及 Host／Launcher 应用端。实际拆合根据依赖与独立导入成本决定，模块地图在每次真实迁移后更新。

当前目录继续见[模块地图](modules.md)。详细包职责见[定稿第 14 节](composable-engine.md#14-软件包参考布局应用端与默认展示)。SDK 保持轻量，核心通过契约使用能力，静态校验入口可独立于模型、Python 和游戏 Host 工作。

## 7. 每个机制统一写清的契约

每项机制按以下顺序说明。

1. 一个玩家互动例子，以及机制解决的问题。
2. 提供者、调用方、公开入口和必要依赖。
3. 输入、结果、身份、真值与授权投影范围。
4. 状态、业务不变量、规则与原子提交边界。
5. 执行时机、周期、预算、同步或异步及取消。
6. 业务拒绝、插件故障、部分成功与端侧反馈。
7. 实例 Fiber、资源清理、存档兼容及有限恢复。
8. 源码、自动化、真实体验与发行分别验证的范围。

工具链以 configSchema 和注入的纯校验函数描述配置。默认舞台消费通用动作、控件与只读面板，无头推演复用正式执行路径和隔离 SQLite。

| 玩法规则 | B4 限制合取、唯一处理器、公开计算方法、同快照单层派生和最终不变量已接通并通过独立审查 | B5／B6 官方业务迁移 |

| 游戏包与存档 | B6 数据兼容声明区分持久结构与候选摘要，读档／分享只读预检实际值与阶段 | B6 独立复审通过；显式组合和共同脚本留 B7 |

## 10. 范围调整与历史约定

| 历史约定 | 现行结论 |
| --- | --- |
| 第三方调度预算只作建议 | 所有正式执行使用核心硬预算，运行时差距在相应批次处理 |

剧情节奏已有实现并进入公开机制迁移。范围沿革与现有证据见[分层与范围记录](plugin-layering-direction.md)。
