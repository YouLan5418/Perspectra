# 核心与插件统一规范

日期：2026-11-04。状态：用户确认的架构目标与后续开发规范；现有代码的差距见第 8 节。本文规定分层目标；实际迁移进度见第 8 节，不表示两项暂缓功能已经实现。

例如料理比赛：核心保存实体、事件和授权状态；Cordis 内部插件提供活动、交互及状态操作机制；外部脚本组合选材、烹饪、评分和结束条件；世界包提供角色、场景、食材与文案。角色自己决定如何参与，重要效果经裁定后才成为世界事实。

**目标是玩法可组合，而不是把全部代码插件化。** 移除非必要官方能力后，核心仍应能管理世界实体、事件、权限、状态与原子提交；日常 RP、狼人杀、RPG 等作为能力组合运行。这是后续验收标准，当前运行入口尚未达到这个状态。

## 1. 永久保留的核心边界

| 保留在核心 | 插件可做什么 | 不授予插件的提交权力 |
| --- | --- | --- |
| 世界事件记录 | 声明玩法事实的含义与合法产出；使用核心认可的事件表达结果 | 自行追加未经验证的权威事件、改写历史 |
| 事实原子提交 | 提出经规则裁定的状态与效果变化 | 绕过校验写库、把部分效果当成完整成功 |
| 角色认知隔离 | 提供记忆、召回、认知或上下文算法 | 通过普通角色接口读取他人的私密材料 |
| 授权视图 | 根据授权数据生成候选和玩法判断 | 用全量真值代替模型／玩家的授权视图 |
| 存档与分支一致性 | 声明必要持久状态及保存／恢复含义 | 用插件外部文件偷偷改变已保存分支的事实 |
| 插件生命周期与权限 | 注册具体机制、适配器或玩法能力 | 让关闭／取消后失效的调用继续提交 |

核心还保留世界实体身份、通用状态基础、调用者身份和提交来源。核心检查结构与权限、执行注册规则并验证产出；玩法规则定义动作的业务合法性。规则来自插件，不表示核心自动证明任意第三方规则正确。

“插件可定义新玩法事件和状态”是扩展方向，不是现在就接受任意 eventType。当前只能产出核心认识的事件，新的事实表达必须先有明确声明和核心验证支持，不能由模型输出或自由旁白直接生成。

## 2. 四层与宿主适配

| 层 | 职责 | 允许依赖 | 典型归属 |
| --- | --- | --- | --- |
| 核心 | 实体、事件、授权、状态基础、提交、分支与生命周期边界 | 基础契约与通用基础设施 | contracts、kernel／application／store-sqlite 中对应职责；这些包仍需按职责核对，不因包名整体认定为纯核心 |
| 内部机制插件 | 提供通用机制、可替换算法与公开服务 | 核心契约和明确声明的机制服务 | `packages/official-*`；使用 Cordis |
| 外部玩法扩展 | 组合机制、定义规则和流程，形成玩法 | 公开机制契约、授权输入和声明的扩展依赖 | 包内／可复用脚本与配置；不要求作者使用 Cordis |
| 内容 | 人物、场景、初始物品、事件内容、资源、玩法选配 | 所选玩法的公开内容格式 | 世界包 |

宿主与 Launcher 是运行和交付适配：装载、装配、HTTP／桌面／前端连接、凭证接入和诊断。它们连接上述层，不能继续累积料理、战斗或具体剧情的规则。默认组合可以选择安装哪些机制，但不属于不可替换的核心事实边界。

官方制作的玩法也应使用机制接口，不因“官方”而放进核心。“内部机制”和“外部玩法”主要描述架构职责；官方玩法可以和社区玩法遵守同一份契约。

## 3. 内部机制插件：统一使用 Cordis

- 使用现有 Context、Service、inject、effect 和 Provider，不新增服务容器。注册与清理由所属 Cordis 生命周期负责。
- 跨机制依赖用公开服务声明；不导入另一个模块的私有文件，不依赖共享可变对象或偶然的装载顺序。
- 区分进程注册与世界实例：注册机制不等于打开某个世界。每个世界、分支重开和重生候选应有独立的实例状态，关闭前取消或完成在途工作。
- 对外提供窄的机制契约：输入、授权范围、操作、结果、错误和生命周期。不能把整个 WorldHostCore、数据库或 commitRound 作为方便参数传给玩法。
- 实现与默认选择分开。机制包实现能力，默认组合声明选配与执行顺序，宿主提供世界能力并执行提交。
- 模型凭证、文件和外部进程等原生资源留在适配层；普通玩法脚本不因调用一个机制而获得这些资源。

机制可以提供可替换策略；替换机制实现仍遵守核心边界。调度顺序、记忆算法和表现策略不是核心永久规则，也不要求每个函数都单独成为插件。

## 4. 外部玩法：通过脚本等形式消费机制

首选已有声明＋脚本入口，逐步统一共同约定，不立即发明新的脚本格式。当前 `plugins.json`／`plugins/*.js` 与活动、状态脚本的实际格式见[双入口指南](../guides/dual-plugin-entrypoints.md)及[活动与状态](../guides/activity-and-variables.md)。

共同契约应遵循：

1. **声明。** 稳定标识、所需机制、配置、操作参数、必要状态及可见性；资源文件与入口可验证。
2. **装载。** 校验声明与依赖，再打开世界实例；注册成功、依赖就绪和实际生效分别报告。
3. **观察与候选。** 模型／玩家侧的 policy、输入准备和表现只获得其有权看到的数据。可信裁定函数可获得声明需要的真值，但不能把它整体返回给角色。
4. **提案与裁定。** 模型、玩家和自动机制提出操作，宿主绑定真实调用者；规则在最新状态上判断条件并返回结果。候选不等于执行授权。
5. **验证与提交。** 核心检查效果与权限，原子保存本次逻辑上不可分割的事实。外部能力计算和模型请求不跨越数据库长事务。
6. **投递与结束。** 按提交时的实际权限生成观察；失败明确区分条件拒绝、计算失败、外部结果未完成和已提交后的后续失败。

返回结果不应混淆“完成”“排队”和“失败”。此前已提交的合法结果，不因后续脚本或模型失败被假装撤销。

脚本运行环境、支持的语言、限额与同步／异步调用方式，由相应机制接口明确说明。现有包内同步 hook 不会因为本规范自动获得异步、Node 导入或模型调用能力。

第三方确有原生接入需求时，现有 `.mjs` Cordis 宿主扩展继续作为原生适配入口；它和作者编写的玩法脚本要分别说明，不能把“扩展玩法”默认等同于“给 Node 插件整个宿主权限”。这不改变当前可信插件、无恶意代码沙箱的事实。

## 5. 状态与生命周期的一致约定

| 类别 | 归属与处理 |
| --- | --- |
| 世界事实与必要玩法状态 | 宿主管理，必须说明初始化、裁定、权限、存档、分叉、重生与恢复含义 |
| 可重建投影与缓存 | 从对应分支重建，不成为另一份事实来源 |
| 临时模型输出、候选与计算 | 可丢弃；取消、关闭和世界失效后不能晚到提交 |
| 插件配置与凭证 | 配置与世界事实分开；凭证不进入世界快照、公开 identity 或角色上下文 |
| 诊断与外部副作用 | 诊断不证明效果成功；外部副作用的完成与不确定性必须明确，不能承诺靠读档撤销现实世界效果 |

角色归属、可见性和写入资格分别定义。命名空间只解决身份冲突，不自动授予跨插件读取或写入权。停用、缺失、版本不兼容时应说明是否允许继续，不能把缺失数据静默当成初始状态。

已有包内模块能声明状态并走当前状态裁定；这与“任意外部 Cordis 插件可独立注册宿主管理状态”是两项不同能力，后者仍为暂缓需求。普通插件文件目录目前也不能替代统一的分支状态支持。

## 6. 目录和命名规范

以下约定优先利用现有目录；已完成的机制迁移见第 8 节：

| 位置 | 应承载什么 | 不应承载什么 |
| --- | --- | --- |
| `packages/contracts` 与 `packages/plugin-sdk` | 基础数据契约、公开插件／机制类型；SDK 可按机制组织导出 | 私有宿主实现和某个玩法的隐含捷径 |
| `packages/official-*` | Cordis 内部机制实现及清楚命名的默认组合能力 | 未声明依赖地反向引用具体世界包 |
| `desktop/host` | 世界运行、授权桥接、装配与交付适配 | 所有新机制和业务规则的默认落点 |
| `examples/host-plugins` | 原生宿主扩展示例 | 对所有外部玩法扩展形式的唯一示范 |
| 世界包的 `plugins/`、`scripts/` | 按公开格式消费机制的玩法与内容脚本 | 核心数据库写入和复制的宿主实现 |
| 外部插件安装位置 | 当前仍按用户配置路径装载原生扩展；可复用脚本的分发位置后续随实际装载方案确定 | 本轮没有新建安装目录、市场或自动下载 |

“机制插件”“玩法扩展”“内容包”“原生适配”要在说明中区分。一个实现即使暂时仍在旧目录，也应登记其职责与依赖；移动文件本身不算分层完成。

## 7. 每个机制统一写清的契约

机制文档按同一顺序回答：

1. 一个玩家互动例子，以及机制解决的具体问题。
2. 由谁提供、由谁调用，公开入口和必要依赖。
3. 输入／输出、调用者身份、真值和授权视图边界。
4. 操作规则、状态及事件效果，谁负责验证和提交。
5. 调用时机与顺序、同步／异步、预算与取消。
6. 拒绝、异常、部分流程已经成功和外部结果不确定时的行为。
7. 实例初始化／关闭，保存、重生、分支和恢复。
8. 源码接通、自动测试、真实体验和发行包各自验证到哪里。

包依赖声明、Cordis inject、机制执行顺序保持各自语义；统一规范不等于建设一个万能依赖协议。规则定义方式可以按机制有所不同，但权限、事实提交和生命周期边界不能靠各个玩法自行约定。

既有 SDK 对可信原生插件暴露了跨角色读取等特权；这是当前信任模型，不等于普通脚本应获得同样的输入。接口整理需逐项核对，不能仅在文档里宣称已经收紧。

## 9. 后续整理与验收顺序

源码探查结果与具体批次见[迁移计划](../../superpowers/plans/2026-11-04-core-mechanisms-migration.md)。M0／M1 已实施，其他批次仍为目标，不能据此认定对应包和接口已经存在。

先按模块列出职责、消费者、状态和依赖，再逐项确定“核心／内部机制／玩法／内容／适配”的归属；依据本规范补齐契约，发现公开能力缺口后才做对应拆分。每一项以一个实际玩法消费者验证，避免为追求目录完整一次性公开大量宿主方法。

验收需要逐步达到：

- 核心不依赖具体官方日常 RP、狼人杀或 RPG 内容。
- 去掉非必要官方能力后，可在无模型、无具体玩法的最小运行测试中管理实体、事件、授权与通用状态；仍能拒绝非法事实并保持原子提交和分支一致。
- 两个不同玩法能消费同一个机制，组合时不复制宿主代码；官方和外部消费者都走公开接口。
- 关闭、取消、切换候选、保存和恢复遵守机制契约，不能串世界或串分支。
- 保留角色主体性，依据真实模型试玩单独评估体验，不能用目录数、接口数或测试数量替代。

以上仍是整体验收目标。当前 M0／M1 完成知识机制试点和启动探针，尚未达到完整最小核心；实际测试与构建范围见[M0／M1 记录](../studies/2026-11-core-migration-m01.md)，未发布发行包。
