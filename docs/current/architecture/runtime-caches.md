# 运行时缓存：设计与维护注意事项

核对日期：2026-10-30。说明源码已接通的组件复用与读取缓存；实测配置、历史对照和验收限制保存在文末研究记录中。

例如玩家在序章点击“继续”，活动先提交结果，NPC 接着表达，状态脚本结算，最后刷新玩家画面。阶段之间需要交还写权限，但无需销毁所有服务；这些阶段读取相同历史时，也无需反复解析 JSON。当前设计分别处理资源寿命、事件读取和角色投影，不把缓存变成权威事实来源。

需要先记住：保留连接不代表持有写权限，复用事件不代表已经验证了完整 Hash 链，复用视图也不授予新的读取权限。新事实仍通过规则裁定和 WorldStore 原子提交。

## 1. 哪些数据保留多久

| 对象 | 所有者与寿命 | 失效／释放 | 代价 |
| --- | --- | --- | --- |
| Store、收件箱、投递、记忆等分支组件 | WorldApplication 挂载的同地址 Cordis 分支，可跨阶段、跨步保留 | 正式 release、关闭或恢复失败后 dispose | 连接句柄与服务对象驻留更久；空闲不自动淘汰 |
| 完整事件前缀 | WorldStore.withEventReadCache 的一次操作等待链 | 操作完成或失败时停用并清空 | 首次读取仍为 O(n)，前缀驻留到步末，增加冻结和筛选 |
| 已构建的角色视图 | CharacterViewBuilder 的弱键缓存，依附不可变事件对象 | 事件对象不再持有后可回收；不按地址长期保存“最新视图” | 缓存投影及返回副本占用内存；仍要核对事件身份和复制结果 |
| 各活动最新状态 | PackActivities 当前实例，只保留每个活动最近的完整更新 | 追加时补读；头回退或同序号 Hash 改变时重读，目录关闭时清空 | 保留活动状态；首次恢复仍需读历史 |

这几项复用现有 Store、投影和 Cordis 生命周期，没有增加连接池、数据库字段或持久化投影。WorldStore 审计连接仍按实际审计操作惰性打开，常规读取不附带审计库初始化。

## 2. 交还写权限时怎样保留组件

入口见 [WorldApplication](../../../packages/application/src/world-application.ts)、[RoundCoordinator](../../../packages/application/src/round-coordinator.ts)，宿主调用见 [WorldHostCore](../../../desktop/host/world-runtime.ts)。

1. 宿主在玩家提交、活动操作、自动开始、状态结算、NPC 激活及末端结算的常规交接处调用 `yieldWriter(address)`。
2. 未挂载该分支时不额外创建组件；已挂载时只归还本协调器的写租约，并标记已归还。重复归还不重复处理，不影响其他写入方的租约。
3. 交还后再次访问应用分支，`#branch` 对原实例调用 `resumeWriter()`。只有已归还时才重新 acquire；由现有租约服务检查当前运行状态、竞争写入方和 fencingToken（防止旧写入方继续提交的令牌）。
4. 恢复后处理待完成的授权记忆任务，保留原先重新挂载时提供的同步边界。例如 NPC 在交接期间提交的私密观察，仍只能进入该 NPC 的记忆命名空间。
5. 恢复租约或同步失败时，完整 release／dispose 原分支并向上报错。清理不得抢占或释放竞争方的租约，也不得把同步失败当作成功。

手动存档、逃生、恢复、维护与关闭等需要完整清理的路径继续使用正式 release／dispose，不能机械地把所有 release 都替换成 yieldWriter。已关闭协调器不能恢复。保留组件期间没有跨阶段保持 SQLite 写事务；下一阶段仍需取得自己的写权限。

交还后的应用访问可能写租约、补处理记忆任务，不能把它当作无副作用的轮询。游戏状态轮询应沿用宿主已刷新的投影，不要为每帧显示反复调用底层应用读取接口。

## 3. 一步内怎样共享事件前缀

源码见 [WorldStore](../../../packages/store-sqlite/src/world-store.ts)。`WorldHostCore.turn`、`activityAction`、`requestCharacter` 用 `withEventReadCache` 包住自身等待链，包括各自的收尾刷新。它覆盖 Core 操作；[TailRoundRuntime](../../../desktop/host/tail-runtime.ts)在其外侧执行的结算、备份、候选安装和恢复，不因此进入这个读取范围。

AsyncLocalStorage 按调用上下文传递范围，服务不必在构造时接收缓存参数。同一步新开的 Store 连接也能复用；各 Store 仍独立拥有和关闭自己的 SQLite 连接。嵌套启用时复用当前活动范围，独立并发操作各自创建范围，不共享前缀表。

文件库按 `resolve(path)` 得到的绝对路径，再按完整分支地址分组；`:memory:` 按连接对象区分。路径别名、符号链接或大小写差异不额外做文件系统去重，可能导致重复读取，不会据此合并不同路径的数据。

每个条目分别保存最近观察的世界头、已读取的最大序号及事件数组。看到最新世界头不等于已经读到该头：读取旧目标前缀时，已读上界可以小于当前头。

| 情况 | 处理 |
| --- | --- |
| 首次请求某个前缀 | 从零读取到目标序号与当前头的较小者，解析／规范化 JSON，深冻结事件对象后保存 |
| 头相同，目标已经读过 | 返回目标序号以内的新数组，共享其中不可变事件对象 |
| 普通提交追加，目标超出已读上界 | 只查询已读上界之后的尾部，追加到缓存 |
| 当前头序号回退 | 丢弃该分支条目，重新读取 |
| 当前头与上次观察序号相同，但 eventHash 或 tick 改变 | 丢弃条目，重新读取 |
| 补读首条事件的 previousHash 不能衔接缓存末端 | 丢弃条目，重新读取；不把它拼成同一份历史 |
| 操作成功或抛错 | 在 finally 中停用范围并清空表；后台任务之后再读会走正常数据库读取 |

范围内每次读取仍查询世界头。`readEventsRange` 保留参数校验，再按序号和事件类型筛选共享前缀；独立调用且未启用范围时，继续用原 SQL 范围与类型过滤。因此首次只需少量类型的读取，在范围内也可能加载完整前缀：这里只用于后续本来就要全史的完整宿主操作，不要为了单个稀疏查询启用它。

返回的事件数组可以单独筛选、排序，但事件及嵌套数据是深冻结的。需要制作可变草稿时先复制，不能修改返回事件来更新缓存或世界。

## 4. 授权视图怎样避免重复投影

源码见 [CharacterViewBuilder](../../../packages/store-sqlite/src/character-view.ts)。例如 A 看过自己的私密观察，后续记忆追赶与画面刷新又请求同一前缀，可以复用投影；B 仍必须取得自己的视图。

缓存以最后一条相关事件对象作为 WeakMap 的弱键，内部按地址、角色 ID 和目标序号区分。命中还要求相关事件数量、顺序和每个对象身份完全相同，不只比较最后一条事件或序号。每次入口仍检查目标序号不晚于当前世界头。

`rebuildAt` 从 Store 取得不可变事件时才建立条目。`rebuildFromEvents` 可以命中已有的相同条目，但不会为任意调用者提供的草稿建立缓存；未命中时仍复制相关事件再投影。独立读取产生的新对象不会因为地址和序号相同就复用旧结果。

首次缓存与命中都返回 `structuredClone` 副本，调用者修改自己的视图不会污染缓存。观察、认识、目标、场景可见性及删除事件沿用原过滤逻辑。WorldApplication 的 principal 与角色绑定检查仍在构建视图之前执行，不能用缓存绕过授权，也不能把原始全局历史直接放进模型上下文。

弱键缓存不等于操作结束立刻回收所有对象；已有代码仍持有相关事件时，其派生条目也可能继续存活。不要在其他长寿命对象里无期限持有整份事件数组来“保活”缓存。

## 5. 完整性、恢复与维护注意事项

`#integrityGuard` 负责捕获完整性错误并隔离分支，并非每次全量校验器。`verifyBranchIntegrity` 明确绕过缓存，直接读取事件、核对 Hash 链、头与提交记录；已提交回合的验证也保留原数据库读取。JSON 只解析一次不等于证明整条事件链正确，尾部衔接检查也不能替代显式完整性验证。

同一步内，相同头的已提交旧行视为不可变快照。手工改写旧行、但不改变头，不会刷新这一步已读内容；显式完整性检查仍读取当前存储。历史修复和文件替换应关闭旧运行实例及连接，按现有恢复入口重新打开，不能把读取缓存当作数据库热替换接口。

维护时保留以下约束：

- 新宿主入口若需要复用，范围要包住一次会结束的操作及其等待链；不能包住整个服务寿命，也不能替代现有 busy、取消与写权限控制。
- 重要状态仍通过 Action／Rulebook／Event 提交；缓存、角色视图或模型输出都不能直接成为世界事实。
- 不因缓存命中跳过提交前世界头／权限校验、stale 拒绝、关键投递结算或备份要求。
- 节点切换、候选重演和恢复沿用独立实例及正式清理，不能在旧范围内直接换底层数据库文件。
- 峰值内存、句柄增量和多分支长时间运行尚未量化；遇到长时间等待，应同时观察缓存驻留与未结束的后台任务。

| [45 步实测](../studies/2026-10-30_event-prefix-reuse-report.md) | 同一新包离线状态、转录、头、事件类型及完整授权视图一致 | 按同包、同配置复测，计数与无插桩耗时分别记录 |

分支交接轮 139 项相关回归通过，含五项强制中断恢复；单步前缀轮 192 项通过，五项强制中断测试未重跑。文档合并不把这些既有结果表述为新执行的测试。真实模型、GUI、Tauri 与发行包仍未据本次优化验收。

**尚未实现与历史长度无关的稳定 300ms。** 每步首次读取与 JSON 校验仍为 O(n)，角色投影、原候选前缀 Hash、Core 材料及完整备份还有增长成本。候选哈希增量试验未测出收益，最终未保留；没有更改 Hash 算法或持久化协议。

后续若要跨步增量，先测剩余热点，再明确旧前缀与删除事件、分支／候选切换、外部提交、损坏与修复的失效边界；不能直接延长当前 AsyncLocalStorage 范围来宣称已解决。

详细计数、耗时分布和复现条件见[分支组件复用记录](../studies/2026-10-30_branch-runtime-reuse-report.md)与[单步前缀记录](../studies/2026-10-30_event-prefix-reuse-report.md)。早两轮活动连接与读取优化见[第一轮](../studies/2026-10-30_sqlite-activity-performance-report.md)、[第二轮](../studies/2026-10-30_sqlite-activity-performance-round2-report.md)；不同样本的提速比例不能连乘。
