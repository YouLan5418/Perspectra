# 妹居物语：哪些设计值得 Perspectra 借鉴

日期：2026-10-18。范围与授权见[调研范围](meiju-design-20261018-scope.md)。

例如玩家堵住 Yuki 的五子棋攻势，程序先确定棋盘上的真实结果，再让角色对此回应；结束后把这段互动写成日记。值得借鉴的是角色与玩家共同做事、回应具体结果、随后还能回忆这段经历的连续体验。

本次判断：优先借鉴共同活动、主观回顾、主动互动节奏和声音表现。Perspectra 已有长期记忆、角色处理机会与包内活动，先用现有能力做出一段完整内容，不因参考项目有某个类就增加同名框架。

## 1. 来源与判断边界

目标是 `urban-friendship-story` 2.2.1 的解包与可读化产物，目录中已有[逆向报告](../../../../782330-decompile/REPORT.md)。本次使用 `readable/` 为主要阅读入口，结合 `merged/` 和 `extracted/assets/` 核对资源与接线。

原报告已更正过“完整恢复”的错误结论，说明曾遗漏文件，目前仍可能遗漏未被引用且未在内存中完整出现的条目。`readable/` 与 `merged/` 文件集合也不完全一致。因此下面的结论限于可见代码，不宣称拿到了完整开发工程；原生记忆库内部、远端服务、实际效果和发行运行情况均未验证。既有 REA 图仅作背景线索，其 HTML 内联脚本与动态关系覆盖限制保留，未重新执行全量分析。

Perspectra 对照的是当天当前工作树，含既有未提交修改。当前角色态度由人设、经历和模型决定，关系数值与门槛已撤销，见[世界设定指南](../guides/world-knowledge.md)。本次未改动这些文件。

## 2. 优先借鉴的体验

### 2.1 用现有活动机制呈现具体玩法细节

**玩家例子：**一起下棋时，她能注意到你刚堵住了她的进攻；你赢后，她可以不服气、恭喜你或要求再来一局。反应由角色决定，胜负由规则决定。

五子棋的合法落子会更新棋盘、检查棋型，再为活三、活四、成功堵截、悔棋、长时间思考和胜负生成不同刺激。部分刺激按每局类别只触发一次。刺激进入角色聊天队列，回复显示在游戏旁；结束后的队列还会请求生成日记。证据 E-02，静态结论 F-01。

**当前能力核对与表述更正：**Perspectra 已支持角色直接参与活动过程，不限于开场和结尾。每次获调度时，`PackActivity.projectContext/scoped` 注入最新 `context.activity`：活动 ID、版本、参与者、阶段、轮次、当前行动者，以及参与者共享的 `game.public` 和该角色自己的 `game.private`；不注入 `internal` 或他人的私有状态。玩家操作的 `description` 按结果受众提交为授权观察，随后进入角色近期经历与记忆路径，最终模型文本中的经历字段为 `context.history`。角色自己操作后的下一次续写还会收到 `result`。活动脚本可以自行把棋盘、当前局势或最近若干步记录放进 public，并不需要新增机制。

允许表达与获得处理机会是两件事：`policy.speech='free'` 允许发言，但实际调用由 `schedule/onOutcome` 选择，受活动预算限制。例如现有猜数字在玩家行动时返回 wait，即使玩家说话合法，也不保证 NPC 马上插话。主循环以最近 8 条授权观察作为活动刺激，同时提供按当前记忆模式保留的近期历史；这不是全量活动存档或全部历史状态快照。作者显式维护的 `game.public.history` 与宿主授权经历是两条不同的信息来源。

源码核对位置：`tests/experiments/pack-activity.ts:254,311,479,510,610`、`tests/experiments/playtest-frozen-runtime.ts:854,877`、`packages/application/src/prototype-character-turn.ts:248`、`packages/provider-chat/src/character-context-text.ts:45`。现有主持猜数字已把待裁决猜测放进 public.pending，并保存最近 12 次裁决到 public.history，答案仅放主持人的 private。因此此处的借鉴应理解为具体内容与反应节奏的参考，不能说我们还缺少“中途参与、状态交付、操作结果和历史进入上下文”的基础能力。本次核对源码和已有测试断言，没有重新跑真实模型。

**我们怎么用：**复用[现有包内活动](../architecture/creator-runtime.md)的规则、参与者、结果投递及 `schedule/onOutcome`。选一个简单活动，把关键结果写成角色有权观察的具体信息，让角色自行决定是否回应、怎样回应。不要每个鼠标操作都调用模型，也不预先指定“她现在必须生气”。

**收益与成本：**同一活动能因角色不同而呈现不同互动，且无需重建活动框架。需要作者挑选值得回应的节点，并验证调用开销、重复反应及旁观者权限。

### 2.2 用角色自己的口吻回顾共同经历

**玩家例子：**她后来提起的不是“完成了一次棋类活动”，而是“你那次故意停了很久，我还以为你没发现我在设陷阱”。这属于角色对经历的理解，不能凭这句话认定玩家确实故意放水。

`DiaryPromptBuilder` 要求第一人称、符合角色语气，记录印象深刻的细节与感受，不写成总结报告，也不能给玩家添加没说过的事。主聊天结束会生成并保存日记，界面提示玩家阅读；日记页面按时间组织条目。约会、旅行和五子棋也有结束后生成日记的路径。证据 E-03，静态结论 F-02。

**我们怎么用：**先用角色在后续对话中自然回提共同经历来验收记忆收益；如果要做可见回顾，可把它做成作者允许、角色实际发表给玩家的回顾。不要直接把角色私有 Core 档案、内心或其他角色经历开放成玩家日记页面。

我们已有 [Core 的 Source、Atom、Episode、Observation](../architecture/cognition-memory.md)，不需要另建日记数据库和第二套事实来源。主观回顾可以有误解和感受，但不得覆盖已裁定的位置、归属和活动结果。展示层也不应把记忆系统的整理文本自动当作角色已发表的台词。

**接受的限制：**本次没有证明目标游戏的日记生成忠实，也没有证明 Perspectra 现有记忆已达到这种自然回提效果；这应成为连续试玩验收项。

### 2.3 活动需要明确情境，不能只堆玩法入口

**玩家例子：**第二次去同一个地方，可以从上次发生的事开始聊；角色对活动的理解应来自真实邀请、当前地点和自己的经历。

约会代码以地点、时段和约会次数组织开场，随后允许自由对话，结束生成日记；旅行按景点和时段选择组织小段互动；自动 Story 会读取近期日记作为叙事输入。它们体现了“进入情境—互动—回顾”的内容组织方法。证据 E-04，静态结论 F-03。

**我们怎么用：**做一份短活动样例，把邀请、可参与条件、开场线索、少数关键结果和结束后的记忆连续性做完整。角色接受或拒绝邀请仍走现有能力。若活动实际涉及移动、物品消耗和归属，就经过现有规则；不能仅把“我们已经到海边了”写进提示词。

任务卡的作者、标签、时长、角色提示和素材目录可作组织参考，但我们已有 World Pack、活动脚本和自定义前端，不为此新增任务卡协议或独立 UGC 框架。没有证据表明目标提供了完整的创建、编辑、上传和发布工具。

### 2.4 主动开口要有节奏，避开正在进行的互动

**玩家例子：**玩家停在主界面时，角色偶尔说一句应景的话；正在读剧情或操作活动时，不再叠一个抢话弹窗。

目标的 `TimeSystem` 在整点或半点检查，聊天、日记或其他对话界面打开时跳过；`MainScene` 按时间槽去重，使用临时聊天历史，并以 `skipMemory: true` 调用问候。半小时定时路径与另一条带好感门槛的启动问候不同，不能把两者混为一条。其“闲置”判断主要看 UI 容器，不能证明玩家真的离开。证据 E-09，静态结论 F-06。

**我们怎么用：**借鉴“避开当前互动、限制频率”的节奏原则。先在现有自主机会与具体活动中验证；当前 `PackAutonomy` 按已提交玩家行为计数，并非墙钟定时器，若要在玩家完全不输入时开口，需要另外明确需求和成本。不能把已有自主调度说成已经支持常驻陪伴。

角色仍能选择沉默。若问候作为正式角色发言，继续经过表达提交、观察与记忆路径；不照搬一律跳过记忆，否则会出现玩家听见了、角色后续却无法依据自身发表接续的问题。

### 2.5 用真实播放状态驱动立绘表现

**玩家例子：**角色说话时嘴部随声音动，暂停或跳过后立即停止，下一句能接上，而不是对白已经翻页、上一句还在说。

目标的 `GenieTTSManager` 按句生成、排队播放音频，并通过 Web Audio 分析正在播放的音频振幅，驱动 Live2D 嘴部参数；结束或停止时清理嘴型同步。独立 `Live2DManager` 和桌宠脚本另有按点击部位调用动作的入口，但当前模型没有登记动作和命中区域，不能把此接口直接视为已可用的点击动作。后续核对细节见第 7 节。证据 E-10，静态结论 F-07。

**我们怎么用：**先补一个可用的合成器和模板播放器，把现有阅读游标、发言者 ID 与音频的开始、停止、结束事件连起来。口型可以从实际声音得到，不必先增加一个模型预测嘴型；更复杂的表情与动作等有素材和体验证据后再做。

目标这些模块在 `readable/` 可见，但 `merged/` 没包含全部对应文件；这里只确认静态代码中的设计与接线，没有验证音质、同步误差或各设备播放行为。我们当前也只有可选语音合成宿主接口，不能称为默认已可播音。

### 2.6 降低玩家接话负担，但保持玩家自己表达

目标会在角色回复后另行生成两个短回复建议，点击后填入输入框，玩家仍可编辑；生成任务使用低优先级、缓存和重复请求抑制。证据 E-07，静态结论 F-04。

**我们怎么用：**可作为后续可选体验：玩家不知道说什么时再提供建议，选择后仍能编辑和决定发送。它与当前“执行合法动作”的按钮职责不同，不能把自然语言建议变成已获准的移动、送礼或替 NPC 决定的结果。

**优先级较低：**会增加模型调用，而且目标建议器要求固定“温柔/幽默”两类回复，不宜照搬为所有题材的玩家人格。先做好自由输入与具体活动，出现真实接话困难后再做。

## 3. 不应照搬的设计

| 目标中的做法 | 可见实现与问题 | Perspectra 的取舍 |
| --- | --- | --- |
| 用模型文本标签直接更新好感、信任、害羞 | `cleanAIResponse` 解析标签后调用 `CharacterSystem.applyEffects`；角色设定还按好感档位切换。不是独立可信的世界裁定 | 不恢复关系分数与阈值人格切换；态度依据人设、经历和互动形成 |
| 约会结束固定奖励关系数值 | `DateSystem` 在结束路径增加固定好感、快乐、信任，不能反映具体互动是否愉快 | 借鉴场景和共同经历，不把参加活动等同于角色必然喜欢玩家 |
| 日记写成“真实经历”，冲突时日记优先 | 主聊天从最近条目往前累计，达到至少约 6000 字符后停止；这不是严格 6000 字符上限。随后要求把生成日记当真实记忆，与上文冲突时以日记为准 | 主观回顾不覆盖权威事实、人设和信息权限；避免把生成错误反复固化 |
| 随机指定心情，再让模型编造原因 | `ChatPromptBuilder` 大约每四小时随机换心情，并要求构思导致心情的事件 | 提供有来源的经历和情境，由角色决定感受；不把编造的过去当已发生事件 |
| 模型返回 `state_changes` 后直接应用任务状态 | `TRPGSystem` 把解析结果交给 `GameController.applyStateChanges`，修改资源、解锁、物品及任务状态 | 沿 Action / Rulebook / Event 或现有活动裁定，不移植任意状态写回 |
| 将旧模块名或未执行分支当成功能 | `recognizeIntent()` 第 26 行直接返回 `null`；`MemoryIndexedDB` 虽仍加载，可见主记忆路径已转移 | 聊天意图跳转目前停用；不能因文件存在就宣称支持或据此增加模块 |

桌宠屏幕陪伴属于另一个产品范围：可见代码包含全模态会话自动启动、屏幕画面传递和静默约 25 秒后的主动发言。它不等于本节较稀疏的主界面问候，也不是虚拟世界角色主体性的实现。当前无需为借鉴陪伴体验而接入真实桌面感知或周期催话。

这些是源码行为与设计取舍，不是本次实测出的漏洞利用或玩家体验结论。证据 E-05、E-06、E-08。

## 4. 与当前 Perspectra 的差异

| 方向 | 当前我们已有的基础 | 这次真正值得补的部分 |
| --- | --- | --- |
| 长期互动 | 按角色授权来源整理与召回；后台 Core 整理 | 玩家能感知的自然回提、对共同经历形成不同理解 |
| 自主互动 | `PackAutonomy` 与动态角色调度；处理机会不等于强制行动 | 在具体内容中安排合理机会，验证是否自然开口；当前不是墙钟常驻陪伴 |
| 一起做事 | 包内活动、动态参与者、邀请接受拒绝、结果受众 | 有意义的活动内容与关键局面的角色回应 |
| 声音与舞台 | 已提交表达的阅读游标、稳定发言者 ID、可选宿主语音接口 | 实际合成器、播放器及阅读/跳过/切换后的播放控制；默认尚未安装这些实现 |
| 创作者内容 | World Pack、人设文档、权限与关键词设定交付、活动脚本 | 可直接修改的短活动样例，减少作者从零拼装的工作 |

对照读取了 `packages/application/src/prototype-character-turn.ts`、`tests/experiments/pack-autonomy.ts`、`pack-knowledge.ts`、`pack-activities.ts`、`playtest-memory-core.ts`、`packages/frontend/src/speech.ts`、`reading-playback.ts` 及 `tests/experiments/playtest-server.ts`。当前能力与未验收边界仍以[架构入口](../architecture/README.md)和[表现能力核查](frontend-plugin-capability-boundary.md)为准，未将文档中的旧实测数字作为本次重新验证结果。

## 5. 建议先做的最小验证

先用现有包和活动做一个短局：玩家邀请一名角色参加一个小活动，规则给出一个值得回应的具体结果，角色自主回应；再切回普通聊天、经过其他话题后，检查她能否自然记起这件事。可以先选现有猜数字或料理内容，不必先开发五子棋。

验收关注四点：角色反应是否贴合自己和刚才的结果；玩家能否自由接话；非参与者是否只知道自己观察到的内容；之后回忆是否保留事实、又体现角色自己的理解。把端到端等待和模型调用数一起记录，避免每个小动作都插入一次生成。

声音表现可作为随后独立的一次小验证：复用现有 `synthesizeSpeech` 宿主回调和阅读游标，只给已授权、已提交的对白配音，检查跳过、切换候选、离开页面后的停止与迟到音频丢弃。无需先新增情绪分类模型、通用动画协议或插件管理层。

这些是建议，尚未实现或跑真实模型；本次不以目标的模块数量作为开发清单。

## 7. Live2D 专项：模型怎样加载与动起来

本节为同日追加的只读源码核对，回答“这个游戏的 Live2D 如何运行”。例如玩家移动鼠标时，运行库可以改变眼珠和头部朝向；播放角色语音时，音频幅度另外驱动嘴部张开。两者都操作预先绑定好的模型参数。

### 7.1 加载与渲染

Electron 主页面先加载 `live2dcubismcore.min.js`、PIXI 和 `pixi-live2d-display` 的 Cubism 4 构建。解包依赖的版本是 `pixi-live2d-display v0.5.0-beta`。

主场景实际入口位于 `readable/src/js/scenes/MainScene.js:831`。若全局没有管理器，它会在函数内定义一个 `window.Live2DManager`；因此不能只读独立的同名文件就认定完整运行路径。加载调用为 `Live2DModel.from(modelPath, {autoUpdate:true, autoInteract:true, motionPreload:'ALL'})`。页面创建透明 Canvas 与 `PIXI.Application`，将模型放入 `app.stage`，再设置位置、缩放、锚点和当前模型。失败路径会尝试静态立绘。

当前默认模型是 `extracted/assets/L2D/high/棕发1.model3.json`：

| 资源 | 当前文件 | 作用 |
| --- | --- | --- |
| 入口清单 | `棕发1.model3.json` | 引用下列模型、贴图、物理配置，以及自动眨眼参数组 |
| 已绑定模型 | `棕发1.moc3` | 供 Cubism Core 使用的模型数据；本次未反编译该二进制 |
| 贴图 | `棕发1.8192/texture_00.png` | 模型使用的图像 |
| 物理配置 | `棕发1.physics3.json` | 运行库计算参数联动和物理摆动 |
| 参数显示信息 | `棕发1.cdi3.json` | 将参数 ID 对应到角度、眼睛、嘴、脸红等可读名称 |

### 7.2 自动更新来自运行库

解包后的 `extracted/node_modules/pixi-live2d-display/dist/cubism4.js:9643` 把 `autoInteract` 映射到自动命中检测与鼠标追踪，`autoUpdate` 注册到 PIXI Ticker。其 `Cubism4InternalModel.update`（约 10291 行）按帧推进动作、表情、眨眼、注视、自然呼吸、物理和模型更新。

`updateFocus` 把目标方向写入眼珠、头部角度和身体角度；`updateNaturalMovements` 调用呼吸更新。所以即使没有配置动作文件，运行库仍有基础自动运动路径。具体是否自然取决于模型绑定与配置，本次没有实测画面质量。

### 7.3 嘴型由声音幅度驱动

`GenieTTSManager.speak`（约 180 行）把文本拆句后合成、排队播放；`playAudio`（约 297 行）创建音频元素，再接到 Web Audio `AnalyserNode`。`startMouthSync`（约 354 行）每帧取频谱，计算约 80–500 Hz 范围的平均幅度，经过阈值与平滑映射，调用 `setMouthOpen` 写入模型参数，通常为 `ParamMouthOpenY`。停止或播放结束时归零。这是随声音强弱开合的口型，不是按每个汉字或音素生成嘴形。

实时语音另有对应通道：`RealtimeVoiceManager` 分析播放音频，`DesktopPetVoiceManager` 从 RTC 客户端取得音频幅度，最终仍写嘴部参数。

桌宠运行在单独的透明、无边框、置顶 Electron 窗口，加载同一模型。桌宠 HTML 也内联定义简化管理器，不能假定它和主窗口始终使用同一个管理器实例或完整同一套代码。

### 7.4 表情素材存在，不等于 AI 表情联动已实现

当前目录确实包含三份表情：`expression1/2/3.exp3.json`，分别对 `Param5/6/7` 加值。`cdi3.json` 将这三个参数标成“脸黑”“脸红”“星星眼”。但实际 `model3.json` 没有 `Expressions`、`Motions` 或 `HitAreas`；可见游戏 JS 中也未找到角色输出到这些表情的映射调用。

独立管理器虽然定义了 `playExpression` 和 `tap_head/tap_body` 动作调用，主场景内联管理器的点击逻辑则主要转到 `onCharacterClick`。不能仅由 helper 方法或素材文件存在，推出“AI 会自动做对应表情”或“点击头身体会成功播放动作”。当前清单的 `LipSync` 参数组还重复使用眼睛参数；现有嘴型代码是直接写嘴部参数，未依赖该组，本次不据此宣称嘴型一定正常或一定失效。
