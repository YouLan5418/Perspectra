# 插件优先运行时：阶段 1 记录

日期：2026-11-02。分支：`feat/plugin-first`。设计见[插件优先运行时](../../superpowers/specs/2026-11-02-plugin-first-runtime-design.md)。

例如开发者写一个插件，让急性子的角色总是抢先回应，玩家启用后它就取代官方调度器。这次把这条路走通了：[示例插件](../../../examples/host-plugins/impulsive-scheduler.mjs)只用公开接口，放在任意路径都能加载；移除后同一存档回到官方调度。

## 改了什么

| 项目 | 结果 |
| --- | --- |
| 调度算法 | 从 `application` 移到 [official-scheduler](../../../packages/official-scheduler/src/index.ts)，运行时不依赖 `store-sqlite` 和 `application` |
| 回合接口 | [createSchedulerRound](../../../packages/application/src/scheduler-round.ts) 替调度器读事件；调度器按序号指定观察，序号不属于该角色时拒绝 |
| 宿主 | `WorldHostCore` 每个实例打开一个调度器，不再直接 import 调度实现，只有 [official-bundle.ts](../../../desktop/official-bundle.ts) 能引用官方包，边界脚本检查这一点 |
| 第三方异常 | 抛错、非法结果、打开和关闭失败都有处理；调度器忘记等待的角色回合会被取消并等待结束；已提交内容保留 |
| 插件写法 | 与 DSH 一致，可以 `import { Service } from '@deepseek-ai/cordis'`；解析钩子把它指向宿主这一份 |

## 接口够用吗

够用，但比设计初稿复杂。动态调度要跟踪已消费的观察、接续已提交的行动，所以 `round.turn` 保留了 `onCommitted` 和 `continuationOf`。第三方示例约 50 行逻辑，没有用到这两个，说明简单的调度器仍然好写。

## 成本

- 生产代码（`desktop`、`packages`、`apps`、`scripts`，不含测试）净增约 410 行。
- `world-runtime.ts` 从 2,255 行变为 2,319 行。**这个接缝让调度可替换了，但总装配文件没有变小**：调度算法本来就不在它里面，它反而多了打开实例和处理异常的逻辑。
- 原有调度测试只替换了函数名，断言都没改。

## 后续判断

- **记忆（阶段 2）：** 接口已知，最大的未知是拆分 `packages/memory` 时来源捕获对召回表的依赖。
- **决策管道（阶段 3）：** `#decide` 边界清楚，拆它才会明显减少 `world-runtime.ts` 的行数。
- **规则与玩法（阶段 4）：** 仍是最难的。本阶段没有碰它，工作量判断没有变化，仍要先摸底。

要让总装配真正变小，阶段 3、4 才是关键。调度器这种“已经是独立函数”的接缝，成本低，收益主要是开放能力。

## 真实模型短试玩（2026-11-02）

本机 8045 网关，`gemini-3.8-flash`，思考强度 low，原生记忆。世界包 `dynamic-scheduling`，玩家走进前室后说 3 句话。三种配置各跑一次。

| 配置 | 第一轮 | 后三轮 | 每轮最先被调用 |
| --- | --- | --- | --- |
| `main`（`c274d64`）官方调度 | 8 次调用，34 秒，到达预算上限 | 各 1 次，4～5 秒 | 目击者 |
| 本分支官方调度 | 8 次调用，35 秒，到达预算上限 | 各 1 次，4～8 秒 | 目击者 |
| 本分支急性子示例 | 6 次调用，37 秒，正常结束 | 6、1、2 次，5～23 秒 | 目击者 |

- **官方调度：** 分支和 `main` 的第一轮调用形态相同，前台和后室同时开始，后续调用次数和结束提示也一致；对白内容因模型随机而不同，没有看到明显退化。
- **示例插件：** 指定角色每轮都最先回应，改为逐个调用后第二轮明显变慢，符合它的写法。
- **角色表现：** 玩家叫已离开的同行者时，目击者都能说明对方已经走了。后室角色的话没有出现在玩家转录里。
- **模型表现问题：** 示例那次，目击者把同行者捡钥匙说成了自己的事，并且对白里出现“ta”。样本太少，无法归因于调度。
- **已有问题：** 三次都向玩家显示了 `entity:brass-key 已交由同行者保管。`，`main` 上同样存在，与本次改动无关。

这只是一个世界包、每种配置一次的样本，能说明接缝在真实模型下跑得通，不能代替完整体验验收。

## 独立审查

整支评审没有发现严重问题，官方路径逐行比对没有发现实际行为变化。发现的 4 个重要问题都只在第三方插件出错时出现，已各自先写失败测试再修复：

- 调度器返回后仍有未结束的角色回合，存储关闭时会产生未处理的拒绝。
- 插件 `close()` 同步抛错时，世界没有关闭。
- 有自主角色的世界包里，插件故障和未知结束原因被显示成“预算上限”，而且插件出错后自主机会仍会运行。
- 活动结果为 `null` 时，这一轮请求会失败。

现有接缝测试原来只用没有自主角色的世界包，这正是第三个问题没被发现的原因，现在已补上。
