# 插件优先运行时：阶段 2 记录

日期：2026-11-02。分支：`feat/plugin-first`。设计见[插件优先运行时](../../superpowers/specs/2026-11-02-plugin-first-runtime-design.md)，计划见[阶段 2 计划](../../superpowers/plans/2026-11-02-plugin-first-phase-2-memory.md)。

例如玩家说过妹妹怕黑，隔了几轮再问，角色还能答上来。这条路现在全程走插件接缝：官方 Core 是一个普通的记忆插件，开发者可以用自己的实现替换它，原生召回已经删除。

## 改了什么

| 项目 | 结果 |
| --- | --- |
| 记忆接缝 | 新增 `ctx.memory`，宿主 API 升到 `1.2`。每个世界实例打开一次，只有 `project` 必需 |
| 原生召回 | 删除。`--memory-native` 改为 `--memory-none`，只用于离线开发和测试，角色没有长期记忆 |
| `packages/memory` | 只保留授权来源捕获，属于主干，不可替换 |
| Core | 移到 [official-memory-core](../../../packages/official-memory-core/README.md)，只依赖公开接口。模型配置由入口组装时带入，插件拿不到 |
| 模型提示 | 删除“可以使用 recall”的说明和 `canRecall` 字段。旧提示这样写，工具却不提供，这是唯一有意的请求变化 |
| 存档 | 已有 `memory.sqlite` 经 v9 迁移丢弃原生表，来源行和哈希不变 |
| 随机端口 | 本机动态端口从 1024 开始，可能落到浏览器禁用的端口。服务和测试现在都会避开，见 [safe-port.ts](../../../desktop/safe-port.ts) |

## 接口够用吗

Core 走公开接口就能运行，但 `MemoryInstance` 有 15 个可选方法。它们是 Core 的后台整理、节点档案和调试视图带来的。第三方只写 `project` 也能跑，代价是这些功能不可用，这和预期一致。

档案只交还给写入它的同一插件。节点记录了写入者，别的实现收到空档案，分享导入时也只有 Core 写的档案才走 Core 校验。

## 真实模型试玩（2026-11-02）

本机 8045 网关，`gemini-3.8-flash`，思考强度 low。世界包 `dynamic-scheduling`，玩家说 8 轮话，中间手动整理一次，之后问“我妹妹怕什么”“我不擅长什么”。

| 指标 | `main` | 本分支 |
| --- | --- | --- |
| 整理结果 | 完成 3，失败 0 | 完成 3，失败 0 |
| 决策请求 | 24 次，全部 200 | 24 次，全部 200 |
| 尝试 recall | 0 | 0 |
| 请求提及 recall | 全部 | 0 |
| 各轮耗时（秒） | 25、16、13、19、7、8、20、9 | 24、13、11、11、6、9、20、9 |
| 整理后两轮的记忆条数 | 2、3、0 / 2、3 | 2、2、0 / 1、2 |

- **角色表现：** 两边都能答出“怕黑”和“不会游泳”。删掉 recall 说明后，模型没有去尝试 recall。
- **记忆条数的差异：** 分支略少，但整理由模型完成，每次结果本来就不同。一次样本不能判断是否退化。
- **局限：** 只有一次样本和一个小世界包，耗时差异也不能归因。这能说明 Core 经接缝跑得通，不能代替完整体验验收。
- **已有问题：** 玩家转录里的 `entity:brass-key` 仍未修复，与本次改动无关。

## 环境发现

这两项都不是代码问题，但下次在这台机器上运行 Core 会遇到：

- **`D:\Temp` 的权限：** 它的访问列表里没有当前用户，只有一个陌生 SID。Python 写不了，Node 可以写，表现是整理任务 `failed:3`。把数据目录和 `TEMP`、`TMP` 指到仓库的 `.tmp` 下即可。Node 能写的原因只是推测。
- **`.tmp/hindsight-vector-venv` 已失效：** 它的基础 Python 不在了。这次用的是发行候选包里的 Python，通过 `HCW_HINDSIGHT_PYTHON`、`HCW_HINDSIGHT_ONNX_DIR` 指定。

## 独立审查

审查由 Opus 完成（Fable 额度不足，未能使用）。官方 Core 路径、迁移、隔离和凭据边界都没有发现问题，审查者还用真实旧存档的副本核对了迁移。发现的 3 个重要问题都在第三方记忆接缝上，已各自先写失败测试再修复：

- 第三方记忆的数据目录没有进入回合快照，重新生成后，插件的数据丢失，玩家也不会收到提示。现在 `plugins/` 随回合快照复制。
- 没实现 `restoreArchives` 的记忆，从节点开的新故事线打不开，与接口注释和文档相反。现在正常打开，角色只有近期经历。
- Core 写的档案会原样交给第三方记忆。现在节点记录写入者，只交还给同一插件。

审查还指出“`SeamProvider.identity` 保持旧指纹”的裁定理由不成立：这次改动本身就让旧的末端回合失效。环境指纹现在包含记忆实现的 ID 和版本，换插件或升级后上一轮不能再重新生成。

修复没有经过第二次审查，靠新增的回归测试和全量检查验证。真实的第三方插件仍未试过，这些问题正是假实现测试原本覆盖不到的地方。

## 后续判断

- **决策管道（阶段 3）：** 判断没有变：`#decide` 边界清楚，拆它才会明显减少 `world-runtime.ts` 的行数。这次验证了“插件拿不到模型凭据”的做法，`ctx.llm` 要在这个前提下设计。
- **规则与玩法（阶段 4）：** 没有碰，仍要先摸底。
- **先验证再继续：** 两个接缝都还没有被外部开发者用过。进入阶段 3 之前，值得先用完整世界包试玩一次，再写一个真实的第三方记忆插件，看接口是否好用。
