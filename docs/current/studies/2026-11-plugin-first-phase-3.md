# 插件优先运行时：阶段 3 记录

日期：2026-11-03。分支：`feat/plugin-first-phase-3`。计划见[阶段 3 计划](../../superpowers/plans/2026-11-03-plugin-first-phase-3-decision.md)。

例如开发者想让角色走自己的本地模型，只写一个 `send` 就够了。[simple-llm](../../../examples/host-plugins/simple-llm.mjs) 这样做了，在 8045 上和角色正常对话。又如想在角色开口前加一段“今天的天气”，注册一个决策实现，给请求加一个字段。

## 改了什么

| 项目 | 结果 |
| --- | --- |
| `ctx.llm` | 新增，只要求 `send`，宿主 API 升到 `1.3`。官方实现移到 [official-llm](../../../packages/official-llm/src/index.ts)，带预设、按角色选模型和请求记录 |
| `ctx.decisions` | 新增，可叠加多个，能给请求加内容或包住整个决策。公共流程移到 [character-decision.ts](../../../desktop/host/character-decision.ts) |
| JEV 审计 | 移到 [official-jev-audit](../../../packages/official-jev-audit/src/index.ts)，作为两个决策实现接入。宿主不再有 `publicationAudit`、`shadowAudit` 选项 |
| `WorldServices` | 增加 `cast`（玩家、角色和地点的名字）和 `candidate`（是否为重新生成的候选） |
| 环境指纹 | 包含模型通道和决策实现的 ID 与版本 |
| `OPENROUTER_JEV_KEY` | 启动时从环境中取走，插件读不到（阶段 2 审查提出的问题） |

**与设计不同的一处：** 决策接缝没有用 Cordis 事件。`next()` 不接受参数，事件也没有按世界实例打开和关闭的时机。这一点已在计划里说明并经用户确认，设计文档已加注。

## 成本

| 项目 | 变化 |
| --- | --- |
| `world-runtime.ts` | 2,267 → 2,254 行，只减少 13 行，比计划预计的约 2,100 行少很多 |
| 生产代码（`desktop`、`packages`、`apps`、`scripts`，不含测试） | 增加 717 行，删除 220 行（文件移动不计）；新增的主要是接缝和接口 |

**总装配文件几乎没有变小。** `#decide` 里移走的部分，被打开、关闭和叠加决策实现的新代码抵消了大半。计划和阶段 1 记录的估计都偏乐观。这一阶段的收益是开放能力，不是简化。要让它明显变小，只能靠阶段 4。

## 真实模型试玩（2026-11-03）

本机 8045，`gemini-3.8-flash`，思考强度 low。`main`（`fdb629e`）和本分支同时跑。

| 场景 | `main` | 本分支 |
| --- | --- | --- |
| `dynamic-scheduling` Core，8 轮加一次整理 | 整理完成 3，失败 0；决策请求 14 次，全部成功；记得“怕黑”和“不会游泳” | 整理完成 3，失败 0；决策请求 22 次，全部成功；同样记得 |
| 该场景整理后的记忆条数 | 3 / 3 | 2 / 2 |
| `model-girls-werewolf` 一局，Core 关闭 | 打完，好人胜，共 36 次决策 | 打完，狼人胜，共 29 次决策 |
| `model-girls-sweet-days` Core，第一句 | 三位女主都回应，各有性格 | 同样 |
| `simple-llm` 示例，`dynamic-scheduling` 4 轮 | 不适用 | 正常对话，能说出钥匙在谁手里 |

- **决策次数的差异：** 本分支 Core 那局多了一些，集中在中间几轮（角色之间互相回应）。请求逐字相同，调度也没改，这更像是模型回答不同带来的差异，但一次样本不能证明。
- **狼人杀：** 身份随机分配，两局的胜负不能比较。两边都没有出错或卡住，角色会跳身份、互相质疑。这是阶段 1、2 都没验证过的包。
- **甜蜜日程的样本很小：** 第一句之后，玩家再说话都被拒绝（“当前表达不在创作者许可内”），`main` 上完全一样，所以只比较到一轮。这条提示来自 `pack-activity.ts` 的表达策略，我没有确认是这个包的设计还是缺陷，如果玩家在普通流程里也会遇到，值得单独看。
- **局限：** 每个场景只有一次样本，不能代替完整体验验收。

这些试玩都在修复审查发现的问题之前完成。修复只碰第三方路径和启动器文案，基线探针修复后仍逐字相同；`simple-llm` 修复后重跑了一次短局，见下节。

## 独立审查

由 Opus 审查（Fable 额度不足）。官方请求路径、凭据边界和五项重点都没发现问题。发现 1 个严重、5 个重要问题，都在第三方路径和启动器上，已各自先看到失败再修复：

- **启动器类型检查失败：** 新增的两个服务没有文案，发行构建会被挡住。`pnpm check` 不查 `.vue`，所以之前的检查都没发现。现在阶段验收要包括 `launcher:check`。
- **`world.candidate` 判断错误：** 选中候选后，世界一直留在候选目录，这个值就一直为真，重启也一样。现在只有作为候选打开时才为真。这推翻了我原来的裁定。
- **示例遇到散文直接失败：** `simple-llm` 现在原样返回文本，让宿主重试。
- **插件出错时查不到原因：** 提示说“模型服务未完成请求”，日志里什么都没有。现在提示里有插件 ID，错误写到标准错误。第三方 `prepare` 失败也不再提示检查预设。
- **`send` 不理信号会卡死世界：** 现在信号触发后宿主不再等待。
- **第三方通道被跳过时悄悄改用官方模型：** 这和指南的承诺相反，玩家的故事可能发到远程。现在清单声明了 `llm` 的插件被跳过时，世界不打开。没有清单的插件仍无法判断。

## 接受的限制

- 换掉 LLM 后没有预设，创作者页也看不到请求详情。
- Core 的整理不走 `ctx.llm`。
- 只装第三方 LLM 也要配一个模型连接。
- `official-jev-audit` 在运行时依赖 `kernel`，边界脚本为它开了例外。
- 活动脚本的 100 毫秒超时没有改，机器很忙时可能触发。

## 后续判断

- **阶段 4 是真正的难点。** `#activity`、`#status` 仍占总装配的大部分。按计划，先摸底，再和用户确认切法。
- **自主预算** `#modelCallBudget` 还在宿主里，它和自主调度一起到阶段 4 处理。
- **先用一下这些接缝。** 调度器、记忆、模型通道和决策四个接缝，只有模型通道有真实示例跑过。进入阶段 4 之前，写一个真实的记忆插件能验证更多。
