# 插件优先运行时：阶段 4 摸底

日期：2026-11-03。分支：`feat/plugin-first-phase-4`，基于 `main`（`bf5370c`）。这份记录只读代码，没有改动。[设计](../../superpowers/specs/2026-11-02-plugin-first-runtime-design.md)第 6.5 节要求阶段 4 先摸底，再和用户确认切法。

例如开发者想加一条全局规则：“角色进不了上锁的房间”，插件能做到吗？又如开发者想整个换掉活动系统，要实现多少东西，世界包还能不能用？这份记录回答这两个问题。

## 现状

| 项目 | 数字 |
| --- | --- |
| `world-runtime.ts` | 2,254 行 |
| 玩法模块（`pack-activities`、`pack-activity`、`pack-status`、`pack-autonomy`、`pack-communication`、`pack-knowledge`、`pack-modules`） | 约 4,300 行 |
| 总装配里引用玩法模块的行 | 约 100 行，分散在下面 8 处 |
| 直接引用这些模块的测试文件 | 约 20 个 |

玩法在总装配里的 8 个接触点：

| 接触点 | 位置 | 做什么 |
| --- | --- | --- |
| 打开 | `create`（135 行） | 按世界包加载，模块之间互相绑定 |
| 玩家输入 | `#commitInput`（125 行） | 状态命令、活动动作、短信 |
| 活动操作 | `#activityAction`、`#autoStartActivity`、`#endStatusRound` | 开始活动、推进、结束回合 |
| 规则链 | `#rulebooks`（15 行） | 核心 → 短信 → 状态 → 活动 |
| 角色回合 | `#turnFactory`（84 行） | 上下文投影、决策校验、执行结果、外部动作 |
| 决策内容 | `#decide`（约 35 行） | 已知状态、知识、活动脚本模拟 |
| 调度 | `#runActivityChain`、`#activateAutonomous`（132 行） | 活动轮次、自主行动和它的调用预算 |
| 投影 | `#refresh`、`#projectCommitted`（169 行） | 状态栏、活动视图、可用操作、短信 |

## 发现

**规则链容易开放。** `#rulebooks` 只有 15 行，已经是一层包一层，`CharacterTurn` 和 `WorldApplication` 都接受注入。规则的结果仍交给主干提交，只能产出主干认识的事件。

**整个玩法很难作为一个接缝开放。**

- **接口会很大：** 上面的接触点至少需要约 20 个方法，其中不少带着调校过的时序，比如活动进行时要关闭并发和发布后继续。
- **它们不是公开接口能写出来的：** `pack-activity` 和 `pack-status` 直接用 `store-sqlite` 和 `application` 读写（约 50 处），`pack-status` 和 `pack-activity`、`pack-modules` 之间还互相依赖。移成官方包，要么给边界脚本开大口子，要么先把存储访问收进 SDK，后者本身就是一次大改。
- **替换者很难受益：** 世界包的 `scripts/activity.js`、`status.js` 是写给这套实现的。换掉玩法，现有世界包的活动和状态就不能用了，第三方等于要自己重写狼人杀、甜蜜日程这些包依赖的全部能力。
- **创作者已经有更好的入口：** 想要新玩法的人，今天可以写包内脚本、`plugins.json` 和异步能力，不需要替换宿主。

**总装配变小不需要公开接缝。** 这些代码可以按职责移出 `world-runtime.ts`，不增加任何对外承诺：

| 移出的内容 | 大约行数 |
| --- | --- |
| 创作者查询（`creatorInspection`、`creatorHistory`） | 175 |
| 自主行动（含预算和提示） | 100 |
| 玩家输入分发 | 90 |
| 玩法投影 | 70 |
| 打开时的玩法装配 | 60 |
| 角色回合的玩法选项 | 50 |
| 活动轮次 | 45 |
| 决策内容（状态和知识改成内部决策实现） | 35 |
| 各种结束提示 | 100 |

合计约 700 行，`world-runtime.ts` 预计减到约 1,500 行。这是读代码的估计，前几个阶段的估计都偏乐观，实际可能少一些。

## 方案

| | A：照设计做 `ctx.gameplay` | B：只开 `ctx.rules`，内部拆分（建议） | C：先做阶段 5 |
| --- | --- | --- | --- |
| 做什么 | 约 4,300 行移到 `official-gameplay`，约 20 个方法的接缝 | 规则可由插件包一层或替换；玩法留在宿主内，按职责拆文件 | 跳过阶段 4，先做世界包依赖和 Launcher 选配 |
| 开发者得到 | 理论上能换整个玩法，但世界包会失效 | 能加全局规则 | 玩家能在 Launcher 里看到并选择模块 |
| 总装配 | 变小，约 1,500 行以下 | 变小，约 1,500 行 | 不变 |
| 风险 | 高，时序调校多，全部测试要调整 | 中，行为不变，靠现有场景回归 | 低 |
| 新增对外承诺 | 很多，以后难改 | 一个小接缝 | 清单和存档记录 |

**我的建议是 B，然后做阶段 5。** A 要付出最大的代价，换来的是一个没有实际使用者、还会让现有世界包失效的能力。按 `AGENTS.md`，没有实际需求的抽象不该先做。之后如果真有人要换整个玩法，那时已经拆好的内部模块也会让这件事更容易。

B 和设计不同：不做 `ctx.gameplay`，也不新建 `official-gameplay`。阶段 5 的计划不受影响。

## B 的验收

- 模型请求与基线逐字相同，沿用阶段 3 的探针。
- 狼人杀、甜蜜日程、状态市场的场景回归通过，真实模型试玩不退化，并用自动序章的正常流程玩甜蜜日程。
- 写一个真实的规则插件示例，比如上锁的房间。
- `pnpm check` 和 `launcher:check` 都通过。
