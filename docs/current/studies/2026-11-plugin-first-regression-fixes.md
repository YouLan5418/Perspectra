# 插件接缝复核修复

日期：2026-11-04。基线提交 864c353，分支 codex/plugin-first-next-seams。对应用户指出的六项问题。

例如 Core 已经归档了一段约定，插件替换了记忆扩充却没有交付档案，原宿主仍按 Core 的前缀截断上下文。现在历史窗口属于实际交付的决策步骤；没有声明窗口时保留近期观察并明确提示，自定义步骤不能因 Core 还开着就静默裁掉近期材料。

## 六项处理

| 问题 | 修复 |
| --- | --- |
| official-bundle 格式门禁失败 | 使用 Prettier 恢复工作区 LF，最终完整 check 重新执行。该文件的工作区换行被 Git 归一化后与原提交一致，不能单凭 git diff 为空判断格式检查一定通过 |
| memory.project 抛错指向 official-context-memory | 在记忆来源记录真实 Provider；同一异常经过外层包装时不覆盖源头，外层捕获后另抛的新异常仍归外层 |
| 自主后续反应回落到 30 秒 | 宿主传齐自主时限，官方分段策略也以自主声明的总时限为缺省；明确指定的更短时限仍保留，外层总预算仍有效 |
| 存档提示罗列内部步骤 | 玩家提示合并为上下文扩充组合；原始 plugin-set.json 继续保留全部 ID/版本，步骤版本或顺序变化仍会提示 |
| 调度器不处理活动 phase，活动静默不动 | 仍有合法参与者、实际未启动 turn 时提示活动停留；返回 undefined 等无效结果时报告调度错误，不自动补跑官方实现 |
| 替换记忆扩充仍使用 Core 截断 | 窗口声明移到 DecisionInstance；默认步骤配对交付与窗口，自定义步骤须明确接管。无声明时使用近期窗口并在需要时提示 |

新增 API 为 2.2，使用 `DecisionInstance.shortTermAfterSeq` 与 `contextSources.memoryAfterSeq`；旧 2.0、2.1 插件仍可加载。旧的自定义记忆步骤若要继续保留 Core 归档后的完整窗口，需要明确转接这两个能力。不是按插件 ID 猜交付，也没有强制恢复被停用的步骤；写法见[指南](../guides/host-plugin-authoring.md#替换记忆步骤时配对交付与窗口22)。只允许一个交付实例声明窗口；无交付方法或重复声明会拒绝打开，并先清理新开的实例资源。

## 验证

冻结最终生产源码后，`corepack pnpm@11.7.0 check` 完整运行通过：176 个测试文件、1700 项测试全部通过，包含类型、Lint、格式和原有 Windows 硬中断回归。Lint 的历史警告保留。虚拟时钟验证自主后的合法反应在第 35 秒完成，未被第 30 秒取消；不是等待慢模型来猜时限。

12 组默认请求、转录与行动结果和原基线一致。后端构建及构建模式的 desktop-launch 回归（1 项）通过。本轮真实模型使用 8045 的 gemini-3.8-flash：分段自主 3 次请求、约 20.1 秒；甜蜜日程完整固定序章后对话 3 次请求、约 33.2 秒，均没有处理错误。固定序章仍未调用模型。

记忆回归使用归档边界替身检查模型实际收到的 history：省略或替换投影后仍收到近期暗号；显式配对的替代实现交付归档暗号并执行它声明的边界；记忆交付每次只调用一次。另验证源头错误不会被外层覆盖、外层的新错误仍归外层，以及冲突窗口的实例被关闭。这些验证不代表真实 Core 长会话整理和召回质量已验收。

文档链接检查仍有历史断链，按主工作树对照不新增本轮断链。日志在本工作树 `.tmp/plugin-first-next/review-*.log`，真实短试玩在 `.tmp/plugin-first-next/live/review-*.json`；没有记录凭证或请求头。没有改动历史试玩数据或完整发行包。

## 明确限制

停用长期记忆交付后，近期窗口不等于完整长期记忆；这是明确选择和提示的功能限制。第三方声明截断后是否实际交付档案，仍由受信任插件作者负责。宿主没有语义证明器或沙箱。阶段 7 的单次晨间无请求观察本轮未复现，仍不能声称已定位其原因。
