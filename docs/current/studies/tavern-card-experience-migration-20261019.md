### 1.6 条件与触发机制

按用户要求分三类，不把推断说成已实现。

**第一类：原始文件确实包含的机制**

- 常驻 / 关键词子串触发；注入位置 `before_char` / `after_char`；`depth`（创世回廊 719 条 depth=4）。
- `probability` 与 `useProbability`：四张卡全为 100% / true，**实际不生效**。
- `selectiveLogic`、`prevent_recursion` / `exclude_recursion`：大量为 true，但配合的是 EJS 自渲染，不是真正的递归触发。
- **正则改写输入输出**：`placement`（1=用户输入、2=AI 输出）、`markdownOnly`、`promptOnly`、`minDepth` / `maxDepth`、`runOnEdit`。魔法少女用 8 字符的占位符替换出 7.2 万字符的 HTML 创角表单（含 28 个 input、1 个 select、内联 JS）。
- **词条内 EJS 在渲染期执行**：可调 `getvar`、`_.get`、`_.random`；创世回廊的一条主线控制器还调用了取词条接口，在渲染期取另一条词条并按章节切片。
- **MVU 变量读写**：模型每轮输出一段变量更新块（分析文本 + JSON Patch 数组），`op` 限定 `replace / delta / insert / remove`；脚本侧用 Zod 校验、自动建型、按阈值结算等级。
- **阶段机与枚举**：魔法少女有八个阶段（创角阶段、幕间休息、战斗准备、战斗回合、终结回合、战斗胜利、战斗败北、战后处理）与五种姿态（非战斗、战斗中、劣势、力尽待辱、战后虚弱）。
- **多开局**：鸣潮 16 条 `alternate_greetings` 加一个索引跳转脚本（改 `swipe_id` 换开局）。
- **骰子**：创世回廊用酒馆宏 `{{roll:1d20}}` 预生成骰池（D20×10、D12/D10/D8/D6 各 20、D4×10），规则要求从左到右顺序消耗、不继承；魔法少女则在 EJS 里真的掷骰并生成强制变量补丁。

**第二类：可合理推断的设计意图**（有数据支撑，但原文没有写死）

- 创世回廊的模块化是有意的：562 条停用词条 + 36 组分段标记 + Mod 区块，说明作者预期玩家按需开关而非全量加载。
- 鸣潮对每个核心角色提供 Pro / Lite 两份人设，`creator_notes` 明确写“需要深度互动的核心角色，需开启 Pro 版本词条并关闭对应 Lite 版本”——作者自己在做上下文预算管理。
- 魔法少女把裁定权从模型手里拿走交给脚本是刻意的：战斗规则词条直接写“胜负判定由后台脚本根据 HP 和韧性自动判决，严禁手动修改阶段”。

**第三类：可能依赖外部配置、但无证据**

- 创世回廊的 5 个 CDN 存根（辅助计算、外置状态栏、小手机、格式修复）逻辑完全不在卡内，无法从卡本身判断它们做了什么。
- `odysseia_trace` 的用途与是否有配套服务端，无证据。
- 三张卡的状态栏与开局 HTML 依赖 Google Fonts、cdnjs、jsdelivr 等外链；渲染效果、可用性、版本漂移均无证据。
- 鸣潮是否有配套预设分发（启动预设为空）无法从卡判断。

### 1.7 必须单列的安全事实

鸣潮的变量结构脚本（卡内 49,160 字符）中包含一段**针对特定第三方平台的防盗版载荷**：它嗅探若干宿主环境标志与本地存储键；命中后接管页面、注入全屏图像、通过 WebAudio 播放随机变速音效、写入访问标记，并在后续触发跳脸帧。在未命中的环境下静默退出。

本页不复述其实现。记录这一点的原因是：**这张卡的脚本不是中性的“游戏代码”**，它包含宿主环境嗅探、DOM 与音频接管、以及外部资源加载。任何“原样搬脚本逻辑”的迁移方案都不成立；本轮“不执行卡内脚本”的要求是必要的，而非形式主义。这也是“只加载可信来源的整个游戏包”这条规则的现实例证。

## 第二部分：原卡设计意图

### 2.1 四张卡分别在卖什么

| 卡 | 玩家买到的体验 | 一句话 |
| --- | --- | --- |
| Ark·Endfield | 世界模拟器 / 旁白 GM：你不扮演谁，你是“管理员”，一张会自己运转的星球 | 把我当成一个世界，不是一个人 |
| 鸣潮 | 长篇剧本 + 关系养成 + 手机生态：跟着主线节点走，同时私聊、解锁 CG，NPC 有独立人格与自主行为 | 把原作剧情做成可以住进去的日常 |
| 魔法少女 | 规则化养成 Roguelike：确定性战斗引擎 + 数值成长 + 事件队列 + 双路线 + 声望与状态面板 | 我要玩一个系统，不是聊一场戏 |
| 创世回廊 | 可拼装的开放世界沙盒：D20 检定 + 属性/技能/装备/生产/经营 + 长主线 + 满地可选模块 | 给我一套规则，我自己造世界 |

### 2.2 Ark·Endfield：把“人设”换成“世界”

- **角色体验**：`{{char}}` 是**场外讲述者**，不出场、不扮演。角色由 41 条 `[角色]:` 词条承载，每条 1–8.4K 字，格式统一为“基本信息 / 外貌 / 经历”——是可被讲述的**对象**而不是对话者。
- **剧情体验**：没有主线。四个开局是四个切片，之后玩家去哪就是哪。
- **玩法体验**：几乎没有机制，只有“世界会按自己的逻辑运转”的承诺（`[强调]:备注` 仅 297 字）。
- **信息体验**：靠 38 条 `[种族]:`、4 条 `[组织]:`、4 条 `[地点]:` 的关键词触发，制造“提到才展开”的深度感。
- **动态体验**：无。世界状态完全在模型嘴里。
- **表现体验**：叙述文学性（开局正文是标准轻小说笔法）。

**体验契约（丢失就会变味）**

1. 讲述者视角：不出现“我”作为角色，只出现“我”作为叙述者。
2. 客观、不评判、不升华。
3. 悲剧照写，不避讳。
4. 专有名词触发式展开。
5. 角色词条是“档案”而非“性格标签”——重点是经历。

### 2.3 鸣潮：四层体验叠在一起

**第一层·剧本。** `剧情权重`（数字、AI 只读、由逻辑控制器计算）充当全局进度条。人设词条用条件分支逐段解锁身份与能力（称号、新武器、新元素属性）。主线大纲配合“当前演绎事件节点 / 即将进行的下一个事件节点”决定每轮推进位置。

**第二层·扮演。** 角色扮演逻辑核心词条里有一整套**反全知铁律**：NPC 不得默认玩家知道自己个人经历里的事，不得替玩家回忆，只有玩家主动提及或 NPC 自己讲出；带“身份保密”“伪装陌生”标注的 NPC 必须一路伪装到揭秘节点。此外还有“玩家在场审计”“原著形象转化审计”“身份隔离强制执行”等检查项。**这是四张卡中最接近 Perspectra 独立认知机制的部分。**

**第三层·关系。** 女性角色是一个按角色名索引的记录结构，每人含好感度数值、只读的态度派生字段、内心想法、私密资料与日志。数值不直接进提示词，而是由控制器换算成态度文本。

**第四层·生态。**

- **飞讯**（367 KB 脚本）：内嵌即时通讯应用，含联系人、群聊、未读、头像缓存、时间线校验、消息摘要、成员清洗，以及**主动发消息**——它会自己调用模型给玩家发私信，带亲和度选取与触发判定。
- **CG 图鉴**（87 KB）：图片缓存、解锁状态、好感联动、全屏查看器。
- **世界书控制**（207 KB）：运行时按剧情开关词条、繁简切换、精简模式、批量管理。
- **剧情逻辑**（110 KB）：按变量计算下一个节点并回写，另含悬浮 UI。

**体验契约**

1. **进度可见**：玩家随时知道“我在哪一章、下一步是什么”。
2. **身份会解锁**：能力与称号随剧情增加，不是一开始全给。
3. **NPC 不比自己知道得多**：反全知是硬约束，不是风格建议。
4. **NPC 有自己的生活**：会主动发消息、有目标与记忆。
5. **手机是第二现场**：正片之外还有私聊与群聊的信息流。
6. **玩家在场**：主角必须是视点，缺席要被补足。
7. **不被打断**：玩家不想推进时，危机只能以暗示形式出现。

### 2.4 魔法少女：一张伪装成角色卡的桌游

- **玩法循环**：创角 → 幕间休息 → 幕间计数到阈值触发 BOSS 生成 → 战斗准备 → 战斗回合（每回合选战术）→ 战斗胜利 / 败北 → 战后处理 → 回到幕间。
- **战斗引擎是确定的**：双方各掷 1d20 并叠加由基础强度换算的修正，再计入未变身惩罚、撤退累积惩罚、发情修正与威胁等级修正，比较后落入五档结果（极大成功 / 成功 / 纠缠拉扯 / 失败 / 极大失败），每档对应固定的伤害、充能、反伤与快感区间，**由脚本生成变量补丁**，模型只按给定的叙述指引把结果写成小说。必杀、撤退、投降、危机、推进各有专门分支。
- **两条路线**：人格状态在“善良”与“堕落”之间切换，会连带改变必杀技名称、威胁等级语义、叙事人格与整套数值方向。
- **成长系统**：性癖经验与等级阈值、淫纹经验与等级、永久性身体改造表、快感值与高潮计数、污染度、名声（知名度 / 风评 / 风评标签）、道具栏、世界观备注表。
- **事件队列**：待处理事件由脚本推送、模型消费并出队，用于避免事件死循环。
- **创角**：正则把占位符替换成一份 HTML 表单（28 个输入项）。
- **表现层**：PC 与手机两套状态面板、行动方式控制台、快速选项模块、变量更新美化与未更新警告。

**体验契约**

1. **规则可信**：战斗结果由骰子决定，玩家不能靠嘴赢。
2. **状态可见**：HP / MP / 充能 / 快感 / 名声随时可查。
3. **成长可量化**：经验、等级、改造条目会累积且不可逆。
4. **阶段推进有节奏**：幕间计数到阈值必出 BOSS，不能无限躲避。
5. **失败有后果也有内容**：战败不是结束，而是进入被俘 / 改造分支。
6. **双路线**：堕落不是惩罚，是另一套完整体验。
7. **创角是仪式**：先填表，再开局。

### 2.5 创世回廊：把“世界”当软件包

- **玩法循环**：骰池 → 属性检定 → 战斗 / 装备生成 / 敌人设定 → 经验与熟练度 → 自学技能 → 生产制作 → 经营与资产（规模分级 + 建设序列 + 收件箱式待办事件）→ 委托生成 → 篇章推进。
- **主线**：主线控制器内含 **101 个篇章**的名单，用“当前事件 → 副本 → 篇名 = 进行中 / 已完成”记录进度；每轮只加载当前篇章大纲，并支持按篇章登记“剧情修正”（人物 / 物品 / 事件的偏差），即**玩家的蝴蝶效应会被写回主线**。
- **模块化**：多个既有 IP 分区并存，各自有开始 / 结束标记。
- **创作工具**：创意工坊脚本在 iframe 中开外部工坊页，能读写词条、加 Mod 边界条目、按名称分组重排。

**体验契约**

1. **一切有数**：属性、技能、装备品级、金钱、经验都有数值。
2. **检定无情**：失败就描写失败后果，不许为剧情跳取骰子。
3. **世界有价目表**：物价、势力、地理都有明确设定。
4. **主线不因玩家改向而消失**：偏移登记为剧情修正后仍收敛。
5. **模块可插拔**：玩家自己决定这一局是世界哪个角落。
6. **经营会自己长**：资产规模、建设序列、周产、待办持续推进。

## 第四部分：推荐迁移方案

### 4.1 总原则

1. **一条体验走一条通道**：客观数值走状态；秘密与误会走认知；设定展开走知识；玩法裁定走活动与状态的裁定函数；角色主动走自主行动；表现走预设与前端。不要用提示词模拟已经有机制的层。
2. **不为单卡动宿主**：资源登记与作者脚本已足够覆盖本轮全部 A / B 级目标。
3. **秘密分开写**：反全知与角色秘密要翻译成认知结构，不能只留在一条人人可见的词条里。
4. **不要复刻情感数值**：把“好感度到某值才答应”改写成“角色依据记忆自己决定”；只在玩法确有客观门槛时用状态。
5. **不要用叙事冒充裁定**：战斗必须走裁定路径，否则“骰子决定胜负”这条契约立刻失效。
6. **不要搬实现**：只搬玩法语义，不搬 MVU 协议、不搬 EJS、不搬卡内脚本。

### 4.2 组织方式（按卡）

| 卡 | 角色 | 地点与物品 | 状态 | 活动 | 自主 | 前端 |
| --- | --- | --- | --- | --- | --- | --- |
| Ark·Endfield | 精选 8–12 条角色词条作为 NPC，其余保留为知识 | 2–3 个地点，物品可选 | 无，或只有地点与日期 | 无 | 不需要 | 默认舞台 |
| 鸣潮 | 守岸人、椿、NPC 漂泊者 3 人；其余降级为知识 | 花房 + 庭院（可扩展） | 剧情阶段、时间、金钱、委托 | 主线推进活动（含行动选项、暂停继续） | 1–2 人开启 | 可选：状态栏与行动按钮 |
| 魔法少女 | 玩家 + 若干敌人模板 | 据点 + 巢穴 | HP / MP / 充能 / 快感 / 纹等级 / 名声 / 改造表 / 阶段 | 战斗活动 + 幕间活动 | 不需要 | 可选状态面板 |
| 创世回廊 | 选一个模块，8–10 个 NPC 词条 | 该模块地点分批落地 | 属性 / 技能 / 品级 / 金钱 / 篇章进度 / 剧情修正 | 篇章推进活动 + 委托活动 | 可选 | 状态栏显示属性与资产 |

### 4.3 字段落地（全部来自现有源码与示例，未编造字段）

- **角色**：`characters.json` → `characterId / displayName / controllerClass / pronouns / initialLocationId / portrayal（summary, speakingStyle, backgroundTextRef, drives, principles）/ interactionBindings`
- **秘密与误会**：`cognition.json` → 观察（key, content, epistemicKind, saliencePermille, basisKeys）、主张（key, proposition, stance, confidencePermille 等）、目标（key, objective{kind, value}, priorityPermille, targetKeys, basisKeys），以及关系、情感、内在张力、承诺、未结环
- **记忆关注**：`memory.json` → `characterId / profile / attentionTopics[]`
- **设定展开**：`knowledge.json` → `maximumCharacters` 与条目数组（`documentId / keywords / constant / priority / when?`），正文各自一个 Markdown，登记用途与受众；`portrayal` 与 `memory_seed` 只能私有。2026-10-19 起 `when` 可读授权处境（位置、场景人物、当前／旧物品、本人活动、本次刺激、已知状态与 `current`），但正文仍是静态文本，不做插值
- **客观状态**：作者状态脚本 → 状态定义（`key / label / type / owner / schema? / alwaysKnown? / activities? / playerTruth?`）、操作定义，以及 `initialize / resolve / policy? / onRoundEnd?`
- **玩法流程**：作者活动脚本 → 定义（`title / operations / npcIds 或 participants`）与 `initialize / policy / resolve / schedule? / onOutcome? / simulate? / resume?`
- **角色主动**：`autonomy.json` → `characters[]`，每项含 `characterId / triggers[{actionType, definitionId?}] / everyPlayerTurns / opportunities / interactions / locationIds`
- **显示名**：实体的可选 `name` 字段
- **开场**：没有开局字段；用活动加固定演出（官方序章模式），或用认知初始观察加首个玩家输入驱动

### 5.3 十个设计问题的回答

1. **创建哪些角色**：玩家（manual）、守岸人（scripted）、椿（scripted）；可选第三位 NPC 漂泊者，用来复刻“双漂泊者身份隔离”这条最有特色的规则。不要一次搬全部角色。
2. **场景、地点、物品**：花房与庭院（即原卡开局本身的空间）；2–4 件关键物品，每件绑定拿取 / 放下 / 给予。
3. **公开与私有**：公开的是地理与制度类短条目（走公开设定的文档）；私有的是各角色对玩家的观察、暗号认知、在危机中的角色（走各自认知与私有文档）。规则：秘密写进认知，不写进公共知识；`portrayal` 只能私有。
4. **初始化哪些状态**：剧情阶段（数字、公共、始终已知）、游戏时间（字符串、公共、始终已知）、金钱（数字、按角色）、委托（对象，带 Schema，含阶段与备注，并配条件知识）。**不要做好感度。**
5. **哪些需要活动与交互**：交互直接用内建的物品与关系定义，不新写交互包；活动做“主线节点推进”与“委托接取 / 完成 / 领取”两场，用暂停 / 继续切换；领取与加钱必须同一次提交，防重复领取。
6. **提示词保留 / 改写 / 删除**：保留反全知铁律（改写成认知加一句预设说明）、叙事风格、称呼规则；改写好感度为态度；“权重阈值解锁”改成按条件分发的知识——阈值做成公共状态键（`alwaysKnown`）或活动阶段，人设段落拆成互斥文档各自设条件；删除变量更新协议、JSON Patch 语法、骰池宏、隐藏变量与 UI 相关正则、重复人设中的一份。
7. **是否需要自定义前端**：第一版不需要。默认舞台已能显示状态栏（分组、变化后标“上次确认”）。确有需要时只做状态分组与行动按钮。
8. **如何实现开场**：不用多开局机制。把原卡那条花房开局压缩成三人的初始观察；需要固定演出时用活动加固定演出逐句提交，末句后交还自由输入；不替玩家做承诺或选择。
9. **如何推进关键剧情而不剥夺自由**：主线节点做成玩家主动点击的操作；危机用条件知识与自主行动以暗示形式出现；玩家偏离大纲时把偏差登记进状态，后一轮由角色按新处境行动，不把结果拉回原纲。注意两点：条件关闭只停止后续交付，**不会撤回**她已经说过或记住的内容，所以“保密撤回”不能用条件实现；没有本次刺激的自主机会不会满足要求 `stimulus` 的条件，所以“她主动开口时也要拿到某条知识”不能写成刺激条件。
10. **只能近似实现的效果**：16 个开局变 1 个；飞讯 IM 变带媒介的私聊；CG 与立绘缺失；状态栏只能做 SDK 投影；变量面板与悬浮球缺失；每轮变量更新的即时反馈变成“点操作才有变化”。

### 5.4 迁移优先顺序

**核心人物（守岸人 + 玩家 + 认知隔离）→ 开场场景（花房 + 2 地点 + 3 物品）→ 最重要的玩法循环（委托：接取 → 完成 → 领奖，串起状态、许可与条件知识）→ 关键状态变化（剧情阶段与条件解锁）→ 事件分支（主线活动暂停 / 继续）→ 其他细节（第二角色、自主行动、前端）。**

一条能玩通的最短路径：进花房 → 与守岸人聊到关键词（知识交付）→ 接到委托 → 完成 → 领奖（状态变化加条件知识出现）→ 切到庭院遇见椿（信息差）→ 回花房核对（记忆与认知边界）。

## 第六部分：实验计划

> **基准声明。** 以下预期全部来自静态元数据推断与宿主源码阅读。**没有在酒馆里运行过这些卡，也没有做过同模型 A/B。** 任何“体验等价”的结论都只能来自真实试玩，不能由本页证明。

### 实验 1：开场体验（人设、氛围、自由度）

| 项 | 内容 |
| --- | --- |
| 初始条件 | 新实例，花房场景，玩家与守岸人同场；她有三条观察与一个目标 |
| 玩家操作 | 先只写“（我环顾四周）”；再说一句带关键词的话；最后说一句完全不相关的话 |
| 预期系统变化 | 第二次输入触发对应知识条目进入她的请求；第三次不触发 |
| 预期角色表现 | 先描述环境而不是自我介绍；提到关键词时能说出对应设定；跑题时不硬拉回大纲 |
| 失败判据 | 开口即报设定；或关键词无法触发；或每轮都被强行推主线 |
| 观察点 | 创作者调试页面的实际模型请求；知识条目是否进入角色上下文 |

### 实验 2：关键交互（状态是否真的改变）

| 项 | 内容 |
| --- | --- |
| 初始条件 | 玩家与守岸人各有金钱；委托处于进行中；状态栏可见 |
| 玩家操作 | 先尝试领奖（条件未满足）→ 完成委托 → 再次领奖 → 重复一次 |
| 预期系统变化 | 第一次被拒绝且什么都不提交；完成后一次提交加钱与阶段变更；重复执行被拒 |
| 预期角色表现 | 玩家说“我领到钱了”时，守岸人不该凭空知道自己未被告知的余额 |
| 失败判据 | 只加钱没改阶段；重复领奖成功；守岸人报出玩家余额 |
| 观察点 | 只读事件查询中的状态更新记录与策略错误字段 |

### 实验 3：条件剧情（授权处境四类条件）

| 项 | 内容 |
| --- | --- |
| 初始条件 | 同实验 2。给三条材料分别加条件：①委托阶段已完成（`knownStatus` / `self`）；②她人在花房且玩家在场（`locationId` + `scene.people`）；③钥匙当前可确认在她手里（`items.current` 含 `holderId`） |
| 玩家操作 | 阶段未满足时让她处理一次 → 完成后再次处理 → 把钥匙交给另一个人 → 移动到庭院再让她处理 |
| 预期系统变化 | ①未满足不交付、满足后交付；②离开花房后停止交付；③钥匙易手后“持有”条件不再命中，只剩“可见”条件命中 |
| 预期角色表现 | 未满足时她不知道领奖这件事；离开花房后不再引用花房限定材料；钥匙易手后不会说成自己还拿着 |
| 失败判据 | 条件失效（未满足仍交付）；条件过紧（满足后仍不交付）；把 `lastObserved` 的旧归属当成当前持有；离开后仍交付新条目 |
| 观察点 | 逐次请求中的知识清单；**离开后是否停止交付，但此前说过的话仍被记住**（这是已记录的设计：关闭条件只停止后续交付，不撤回记忆） |

### 实验 4：长期互动（记忆与经历）

| 项 | 内容 |
| --- | --- |
| 初始条件 | 与守岸人约定一个暗号（仅自己可见的发言），随后移动到庭院与椿对话（不给椿暗号），再回花房 |
| 玩家操作 | 回花房后问“刚才我们说了什么” |
| 预期系统变化 | 暗号的观察主体只有玩家与守岸人（用只读查询核对） |
| 预期角色表现 | 守岸人准确复述；椿被问到时明确表示不知道 |
| 失败判据 | 椿复述出暗号；或守岸人跨场景后忘记 |
| 观察点 | 事件观察主体清单；各角色实际请求中的私有文档 ID |
| 已知风险 | 上一轮真实试玩在后半段出现明显表达重复（同一句眼部描写出现多次）——把重复也列为观察项 |

### 实验 5（原卡含秘密，必加）：多角色信息差

| 项 | 内容 |
| --- | --- |
| 初始条件 | 守岸人与椿各有至少一条主观推断（误会）与一条直接观察（事实） |
| 玩家操作 | 分别问两人“你觉得自己知道什么”；再当众说一句只有守岸人知道的事 |
| 预期系统变化 | 无状态变化；两条私有认知应分别出现在各自请求里 |
| 预期角色表现 | 两人对同一事件的描述不一致且都自洽；不当众说漏私语 |
| 失败判据 | 两人说法被拉平；或椿说出只有守岸人知道的内容 |
| 参照 | [赔罪晚宴第一次试玩](../../../examples/world-packs/model-girls-dinner/README.md)中角色认领了不属于自己的行为——说明“在认知里写清我没做过”很关键 |

### 实验 6（原卡含自主行动，必加）：角色主动找玩家

| 项 | 内容 |
| --- | --- |
| 初始条件 | 守岸人配置为每次玩家提交给一个自主机会，触发条件为发言与移动；她有一个自己的目标 |
| 玩家操作 | 连续三轮只做普通对话，不移动、不提问 |
| 预期系统变化 | 每轮按配置给她一次机会；预算与时限按运行参数 |
| 预期角色表现 | 她可能主动开口、移动，或什么都不做——允许弃权 |
| 失败判据 | 玩家不说话时系统仍在后台计时调用；自主机会绕过观察权限；或被强制完成目标 |
| 观察点 | 运行参数中的自主预算；每轮调用主体计数 |

若要把“好感度到态度”这条也验证一遍，可加一组对照：让守岸人在“记忆中已有被帮助”与“没有”两条分支下面对同一情境，看她是否自己做出不同判断——这验证不经数值也能改变态度。

## 第七部分：建议与优先级

### 7.1 现在就能做（零宿主改动）

1. **Ark·Endfield 整卡迁移**：纯声明式，91 条启用词条与 4 个开局。挑十余条角色词条做 NPC，其余做知识；把词条前缀翻译成关键词。这是验证关键词知识通道的最佳第一战。
2. **鸣潮花房 2.0**：在[花房切片 v3](tavern-card-slice-20261018.md) 基础上加状态、条件知识与自主行动。
3. **把反全知铁律翻译成认知**：这是四张卡里与宿主最同构的一条，直接写进各角色观察与目标，不需要任何新机制。
4. **把行动选项做成活动操作**（含一键操作）：原卡体验最显眼、迁移成本最低。

### 7.2 需要小幅适配

1. **魔法少女战斗引擎 → 状态裁定 + 战斗活动**：要把八个阶段、五种战术、五档结果与必杀 / 撤退 / 投降分支逐个改写成裁定分支。这不是配置，是一个中等规模的作者脚本；且该卡内容分级需单独判断。
2. **创世回廊篇章控制器 → 用活动暂停 / 继续切换篇章**：需要设计“当前篇章”状态键与每篇的活动状态；原卡的渲染期取词条做不到，要把大纲拆成多份 Markdown 按条件分发。
3. **飞讯 → 跨场景通信示例模式**：只保留私聊与观察媒介。
4. **文本规则**：只先迁移短规则。

### 7.3 值得未来加入的通用能力（按收益排序）

> 2026-10-20：原第 2 项“条件知识分发的增强”已随 `62666b9` 落地（授权处境视图），下列按剩余缺口重排。

1. **多开局 / 开局选择**：玩家槽恰好 1 个是硬限制，这是四张卡里唯一普遍缺失的体验契约，也是酒馆卡的常见形态。条件扩展后，“开场活动写入公开标记 + 按标记分发开场材料”这条变通更完整，但初始场景与首发消息仍只有一个。
2. **条目内的条件文本与计算**：扩展解决了“是否交付”，没有解决“交付什么”。原卡用词条内脚本按状态生成措辞（按人格切换整段叙述、把数值插入句子、掷骰决定文案），现在只能拆成多份文档分别设条件。需要模板插值或作者脚本生成正文。
3. **状态可见性的默认前端**：先用默认舞台；若试玩证明“看不到数值就没有反馈回路”，再做。
4. **活动内的随机仪式支持**：作者脚本自己掷骰已够用，但“骰池顺序消耗”这类仪式感无法表达。优先级低。

### 7.4 不值得为单张卡复刻的酒馆特有机制

| 机制 | 理由 |
| --- | --- |
| MVU / 变量树 / 变量更新协议 | 与“模型不写权威状态”的边界直接冲突；迁移目标是玩法语义而不是协议 |
| 词条内执行脚本与渲染期取词条 | 等于在提示词里跑任意代码；应改为作者脚本 |
| 酒馆宏 | 已被作者脚本与角色显示名取代 |
| latest 标签的 CDN 存根与外部 iframe 工坊 | 不可复现、不可审计，[清单文档](tavern-card-inventory-20261018.md)已列为限制 |
| 正则渲染巨型 HTML 面板 | 与“后端脚本可信、前端只做展示”的信任模型冲突 |
| 多开局索引跳转 | 用多包替代更干净 |
| 好感度数值与门槛 | 项目方向已撤销；用记忆与认知替代 |
| 卡内防盗版载荷 | 不迁移；并作为“只加载可信来源的整个游戏包”这条规则的现实例证 |

## 结论

**能还原得很好的部分是结构性的，不是勉强替代：**

- **独立认知与信息差。** 四张卡里只有鸣潮认真做了“NPC 不比自己知道得多”；宿主把它做成一等公民（每角色独立认知 + 来源校验 + 观察范围裁定），且比酒馆更严格：秘密写进世界包不会自动人人皆知。这一条上“重新创作”可以比原卡更好。
- **角色自主行动。** 原卡靠数百 KB 脚本轮询加额外模型调用硬做主动发消息；宿主有受预算约束、复用同一套观察权限与提交路径的一等机制，并已有真实试玩证据（角色自己进厨房、来汇报、追究玩家的挑拨）。
- **规则化裁定。** 骰子、装备、经营、委托可以变成作者裁定分支加原子提交，并做到“机制在跑但信息分层”——集市钱袋样例证明了失主只知道“有变化”、不知道数值与来源，原卡做不到。
- **长期记忆。** 原卡靠往上下文反复塞提醒；宿主有分层整理与跨压缩召回的真实验证样例。

**会明显变味的部分：**

- **开场仪式**：四张卡里三张开场是 HTML 界面，宿主只有文本或简单前端。
- **状态栏的即时感**：原卡每轮变量更新加面板重绘，玩家看到数值跳动；宿主是“点操作才有变化”。
- **手机生态与 CG**：飞讯与图鉴只能近似成跨场景私聊。
- **多开局与模块拼装**：单包单开局，创世回廊的拼装玩法要拆成多个包。
- **长篇主线的自动化推进**：原卡有 101 章控制器与逐轮节点比对；宿主需要作者把每章写成活动状态。

**一句话结论。** Ark·Endfield 可以接近完整迁移；鸣潮可以迁移出“认知 + 自主 + 剧本 + 关系”的骨干，会丢掉手机生态与视觉表现；魔法少女可以迁移出“规则化战斗与成长”的骨干，会丢掉界面与即时变量反馈；创世回廊只能迁移其中一个模块的局部循环。真正值得投入的不是“把卡搬进来”，而是**用宿主的认知隔离、长期记忆、规则化交互与角色自主，把原卡想做、但因工具限制只能用提示词与脚本硬凑的那几件事做成系统能力**——尤其是鸣潮的“NPC 反全知 + 会自己行动”，那正是这张卡最贵、也最容易在酒馆里崩掉的部分。

**2026-10-20 补充。** 条件知识扩展之后，上表里最依赖“按进展解锁”的两处——鸣潮的人设逐段解锁与创世回廊的篇章限定设定——从“只能拆包或提前全给”变成“按阶段条件交付”，魔法少女的大规则集也可以只在对应活动阶段生效。但这只解决了“给不给”，没有解决“给什么”：原卡在词条里按状态生成句子与数值的能力仍然缺失，所以界面化的、计算型的表现依旧只能近似。换句话说，**体验保真度的短板已经从“内容到不了”移到了“内容不会算”**。
