# Launcher 模型连接与角色模型分配设计

日期：2026-10-17 · 状态：待用户审阅

## 1. 为什么做

用户在真实使用中反馈 Launcher 的模型配置“很卡手”：

- 模型标识只能手打，需要从别处复制模型名。
- 同一个接口要在左下角「模型设置」和实例「模型配置」各填一遍协议、地址；实例里换接口后还要回全局补 Key。
- API Key 只保留在本次会话，每次启动 Launcher 都要重填。
- 想给不同角色用不同模型：重要角色用推理强、文笔好的模型，次要角色用快而便宜的模型。不同模型文笔差异也是角色质感的一部分。这些模型往往来自不同服务商。

目标：**连接只配一次，模型从列表里选，按角色分配。**

## 2. 目标 / 非目标 / 反目标

目标：

1. 全局维护多条“连接”（协议 + 接口地址 + Key），每条可一键列出可用模型；所有连接的模型汇总显示，相当于 Launcher 内置的聚合网关。
2. 实例里不再填协议、地址、Key，只从汇总列表选择模型。
3. 实例可设置“所有角色”的默认模型，并按角色单独覆盖。
4. Key 持久保存在 Windows 凭据管理器中，不再每次重填。

非目标：

- 不给玩家输入解析配模型（该功能尚未接入）。
- 不起本地代理进程。“聚合网关”只是 Launcher 记住多条连接，游戏运行时直接请求对应服务商。
- 不做按角色组分配模型（现有预设映射有角色组，模型分配本次只做“默认 + 单个角色”）。
- 不做模型能力、价格等元数据展示，列表只显示模型 ID。

反目标（做成这样就算失败）：

- 选模型仍然需要手打或复制，或者列表拉取失败时完全无法手动填写。
- Key 被写入项目、数据目录、实例索引、日志、请求检查器或游戏前端可见的任何输出。
- 某个角色的私有记忆整理请求被发到不属于该角色的配置之外（见第 5 节“记忆整理”）。

## 3. 用户可见行为

### 3.1 全局「模型设置」→ 连接管理

- 一个连接列表。每条连接：名称（用户起，如“本地 8046 网关”“DeepSeek 官方”）、协议（OpenAI 兼容 / Anthropic Messages / Google Gemini）、完整接口地址（沿用现有校验规则，见 `desktop/launcher-core.ts` 的 `localModel`）、API Key。
- 可新增、编辑、删除连接。删除仍被实例或角色引用的连接时，提示有哪些实例在用，确认后删除；被引用处在实例配置里显示“连接已删除，请重新选择”，启动游戏前必须修好。
- 每条连接有「获取模型列表」按钮，结果显示在该连接下（只看不选）。保留现有「测试模型连接」能力（发一次小请求），因为能列出模型不代表能对话。
- 去掉“新实例默认模型标识”字段。

列模型的请求（由桌面端发出，Key 不进网页）：

| 协议 | 由完整地址推导 | 认证 |
|---|---|---|
| OpenAI 兼容 | 把路径末尾 `/chat/completions` 换成 `/models`，GET | `Authorization: Bearer <key>` |
| Anthropic | 把路径末尾 `/messages` 换成 `/models`，GET（需要分页时跟随 `has_more`/`after_id`） | `x-api-key` + `anthropic-version` |
| Google | 取地址 `.../models/` 之前的部分加 `/models`，GET（跟随 `nextPageToken`），只保留支持 `generateContent` 的模型；返回名去掉 `models/` 前缀 | 与现有 Google 调用相同的 Key 传递方式 |

失败时显示服务商返回的错误摘要（不含 Key），不阻止保存连接。

### 3.2 实例「模型配置」→ 角色模型分配

- **默认（所有角色）**：选一个“连接 + 模型”，以及思考强度。
- **按角色覆盖**：列出该包可调用的角色（与现有预设映射使用的角色集合一致）。每个角色可选“跟随默认”，或单独设置：
  - 角色决策：连接 + 模型 + 思考强度；
  - 记忆整理：连接 + 模型（默认跟随该角色的决策模型）。
- 默认层也有记忆整理模型，默认跟随默认决策模型。
- 模型选择器：可搜索的下拉框，按连接分组；**也允许直接输入**模型 ID（针对不提供 `/models` 的网关）。打开对话框时若某连接还没拉过列表，自动拉一次；结果在本次 Launcher 运行期间缓存，可手动刷新。
- 现有思考强度的约束保留（Gemini 部分型号不能关闭等），按每个选择各自判断。
- 实例卡片上的模型摘要显示默认模型，若有覆盖再显示“另有 N 个角色单独配置”。

### 3.3 新建实例

默认值取“上一次在任何实例中保存的默认选择”；如果没有，就用第一条连接的第一个模型；没有任何连接时，提示先去全局添加连接。

## 4. Key 存储

- 用户已同意：Key 存入 Windows 凭据管理器（加密，按 Windows 用户隔离）。
- 每条连接用一个稳定 ID（UUID）作为凭据条目名的一部分，例如 `Perspectra/model-connection/<id>`。连接元数据（名称、协议、地址）照常存放在 Launcher 索引中，**不含 Key**。
- 删除连接时同时删除对应凭据条目。
- 启动游戏时，由 Launcher 读取所需连接的 Key，只通过子进程环境或 IPC 传给运行时，与现在的 `HCW_LOCAL_API_KEY` 传递方式同级。不写盘，不进日志或请求检查器。
- 浏览器 Mock 模式下不接凭据管理器，Key 仅存于内存。
- 这替代了当前“Key 只保留于本次会话、绑定协议与地址”的机制（`apps/launcher/src/stores/launcher.ts` 中的 `providers` 和启动时的匹配逻辑）。

## 5. 运行时接线

现状（2026-10-17 核对）：

- Launcher 启动游戏时只通过环境变量 `HCW_LOCAL_MODEL / HCW_LOCAL_ENDPOINT / HCW_MODEL_PROTOCOL / HCW_THINKING_LEVEL / HCW_LOCAL_API_KEY` 传**一个**模型（`desktop/launcher-core.ts` 约 458 行）。
- 运行时已为每个角色单独创建 provider：`tests/experiments/playtest-frozen-runtime.ts` 中的 `roleProviders`（约 315 行），目前只有预设随角色变化，模型、地址、Key 都共用。
- 记忆整理走 Python Core worker（`experiments/activity-memory/core_bridge.py`），从环境变量读取单一模型配置，所有角色共用。

需要的改动：

1. **决策模型按角色**：把每个角色的生效配置（协议、地址、模型、思考强度、Key）传入运行时，在构建 `roleProviders` 时按角色使用各自配置。角色 ID 校验沿用预设映射已有的“引用了此包之外或不可调用的角色”检查。
2. **记忆整理按角色**：Core worker 的请求要能按角色携带模型配置，而不是只读进程环境变量。具体方式（每次请求带配置，或按配置分组启动 worker）由实现者决定，但必须满足：
   - 某角色的记忆整理只用该角色生效的记忆整理配置；
   - Key 不写入 Core 的任何落盘文件（包括 `utility-attempts.jsonl`）。
3. 无覆盖的角色行为与现在完全一致（使用默认配置）。

## 6. 数据迁移（本人判断，可调整）

现有索引里有 `defaults: LocalModel` 和每个实例的 `model: LocalModel`。首次加载新版本时一次性迁移：

- 收集 `defaults` 与所有实例 `model` 中不同的“协议 + 地址”组合，各自建一条连接，名称取地址的 host:port。Key 为空，需用户在全局补填一次。
- 每个实例的 `model` 变为默认选择（指向对应连接 + 原模型名 + 原思考强度），无角色覆盖。
- 不保留旧字段的兼容读取分支。迁移前把旧索引文件备份为同目录下的带时间戳副本。

## 7. 验收

- 自动化：列模型的地址推导（三种协议，含分页）、迁移、角色覆盖解析（覆盖 / 跟随默认 / 引用已删连接）、Key 不出现在索引和日志中。
- 真实试玩：至少两条不同服务商的连接，一个角色单独配置为另一服务商的模型，跑一局确认请求检查器里该角色的调用确实走了对应模型，记忆整理也走对应配置；其他角色仍走默认。
- 体验：从零配置到开局，全程不需要复制模型名。

## 8. 交付顺序（本人判断）

分两步交付，每步都可单独试用：

1. **连接与选择**：全局连接列表、列出模型、凭据管理器、实例默认选择（连接 + 模型 + 思考强度）、迁移。运行时仍只接收一个模型，记忆整理跟随默认。
2. **角色覆盖**：实例按角色覆盖决策模型和记忆整理模型，以及运行时与 Core worker 的按角色接线。记忆投影与构建已按角色（`characterId`）进行（`tests/experiments/playtest-memory-core.ts`），所以按角色选择配置有现成的切入点。

## 9. 交给实现者决定的事

- 列表 UI 的具体样式和组件选型（沿用现有 `components/ui` 风格）。
- 凭据管理器的接入方式（Tauri 侧 Rust `keyring` crate 或其他方案），以及 Key 从 Tauri 到 `launcher-core` 的传递路径。
- 记忆整理按角色配置的具体实现方式（第 5 节约束内）。
- 模型列表缓存细节。
- 需要同步的当前文档：`docs/current/model-protocols.md`、`docs/current/architecture/` 下涉及 Launcher 与运行时模型配置的章节。
