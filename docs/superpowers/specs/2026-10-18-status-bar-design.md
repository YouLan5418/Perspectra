# 状态栏：经裁定的常驻世界状态（设计）

日期：2026-10-18。状态：待用户确认。本文是设计，不表示已经实现。

## 1. 为什么做

很多酒馆角色卡依赖 MVU 变量：HP、金钱、时间、剧情阶段等每回合变化，并显示在状态栏上。Perspectra 现在没有能承接它的机制：

- **包变量**（`scripts/variables.js` → `pack-variables.json`）只有宿主调试命令 `/vars` 能写，玩法中没有任何写入路径；存在独立文件里，不走世界事件事务；只要启用，就会关闭动态调度、发表后续写和行动前表达。现有 4 个示例包的变量脚本都是同一份演示副本，只存一个从未改动的 `剧情.阶段 = '初见'`。
- **活动状态**有作者代码裁定、原子提交和按范围通知，但只在活动运行中、对参与者、按轮次生效，同一时间只能运行一个活动，不适合常驻状态。
- **宿主交互包**（`packages/interactions-basic`）的规则代码写死在宿主里，作者不能在世界包里新增"购买""偷窃"这类交互；现有 `base:take` 只能拿没人保管的物品，观察范围也只有现场公开。

用户希望：创作者用代码定义客观状态和改变它们的操作，所有变化都经过裁定；每个角色（包括玩家）只知道自己观察到的值。

一个例子：玩家钱袋有 100 金币。扒手阿七执行"偷窃"，作者脚本裁定成功，真实值变为 70，结果只通知阿七。玩家的状态栏和上下文仍显示"金钱 100（上次确认）"；直到玩家付账时作者脚本判定余额不足（这是一个被接受、但没有扣钱的结果，见 6.1），或执行"查看钱袋"，才看到 70。

## 2. 目标

1. 作者在世界包里用一个 JS 脚本声明状态和操作，宿主负责校验、提交和分发。
2. 状态的真实值是权威世界事实，以世界事件提交，和对话、行动在同一次事务里；故事节点、分叉、末端重新生成自动随事件回滚。
3. 所有变化只能来自已声明操作的裁定结果。模型和玩家只能提出执行某个操作，不能直接写值；叙事文本不改变任何状态。
4. 认知按用户确认的方案 B：每个观察者（NPC 和玩家相同）只知道自己被告知过的值，以及值是什么时候确认的。作者可以让角色观察到别人的值。
5. 玩家状态栏显示玩家已知的值；默认舞台提供简单面板，自定义前端通过 SDK 拿到同样的数据。
6. 作者可以按需收窄状态的适用范围：默认任何已声明操作都能改（经过裁定），也可以限定只在某些活动里改。例如 HP 只在战斗活动中变化，战斗外保持"上次确认"的值，模型的候选行动里也看不到攻击、治疗等操作（见 6.3.1）。
7. 状态可以随回合自动变化，例如每轮推进游戏时间、中毒每轮掉血（见 6.3.2）。
8. 退役包变量：删除 `PackVariables`、`pack-variables.json`、`/vars` 命令，以及因包变量而关闭的调度路径；示例包迁移或删除无用的演示变量。

## 3. 非目标（这一版不做）

- 模型直接写变量，或从叙述文本中解析变量更新（例如 MVU 的 `<UpdateVariable>` 块）。
- 自动导入 MVU 卡的变量脚本。可以以后单独做 schema 和初始值导入，更新规则仍由作者重写。（我的选择）
- 世界书按状态条件激活条目。（我的选择）
- 多开局及每个开局各自的初始状态。（我的选择）
- 任意嵌套 JSON 值。（我的选择）
- 把地点或物品归属复制成状态。地点和物品继续走现有规则，状态脚本只能读取，不能改写。

## 4. 反目标（即使能跑，也算失败）

- 一个角色读到了自己无权知道的真实值，例如失主在没有任何观察的情况下，上下文里就出现了被偷后的余额。
- 对话已提交，但状态变化没有提交，或者反过来。
- 叙述里写"他挨了一刀"，HP 就变了。
- 新机制重新引入串行调度，或单独再存一个状态文件。
- 作者为了一个简单的金钱数值，要写一大段样板代码。
- 被限定在战斗里的 HP，在战斗外被任何操作改动。

## 5. 约束

- 遵守 AGENTS.md：ESM、TypeScript strict、显式 `.ts` 本地导入；SQLite 提交保持短事务和原子性。
- 作者脚本沿用活动脚本的执行方式（`node:vm`、同步 JSON 输入输出、执行时间和数据大小有界）。和活动脚本一样，它是可信作者的后端扩展，不是对恶意包的安全沙箱。
- 脚本必须作为编译资产登记，加载时核对内容哈希和包内路径（复用 `pack-activity.ts` / `pack-json-asset.ts` 的做法）。
- 新事件类型要在 kernel 的事件清单里登记，就像 `activity.updated` 登记在 `characterInteractionManifestRegistries`（[world-spec.ts:505](../../../packages/kernel/src/world-spec.ts)）里一样。
- 不得新增数据库或独立存储文件。

## 6. 已经决定的设计

### 6.1 作者写什么

入口文件 `scripts/status.js`，在 `assetFiles` 里登记后才会启用，全局入口为 `globalThis.statusScript`：

- **definition**：声明状态和操作。
  - 每个状态有：键名、显示名称、值类型（数值 / 字符串 / 布尔）、归属（公共一份，或每个角色各一份）、是否"所有人始终知道"。
  - 每个操作有：ID、标签、参数 schema（形式和活动操作相同，封闭字段）、谁能执行（例如只有玩家，或任何角色）。
- **initialize**：返回所有状态的初始真实值。建世界时以一个初始 `status.updated` 事件提交。默认告知规则：每个角色的私有状态告知其归属者，公共状态如果不是"所有人始终知道"，默认不告知任何人。作者可以在 `initialize` 里额外返回 reveals，覆盖默认规则。
- **resolve(statusView, actorId, operationId, parameters, world)**：裁定一次操作，返回以下两种之一：
  - `{ rejectReason }`：拒绝，什么都不提交，和活动的拒绝方式相同；
  - `{ changes, reveals, description, audience }`：
    - `changes`：真实值的变化；
    - `reveals`：要让哪些观察者看到哪些状态的当前值；
    - `description` 和 `audience`：结果描述及其接收者，接收者可以是行动者本人、指定角色，或现场所有人。
  - **自动告知**：如果一次操作改变了行动者本人拥有的状态，这个新值自动告知行动者，作者不用写 reveal。其他人引起的变化（例如被偷）不会自动告知归属者。
  - **"失败"不等于"拒绝"**：`rejectReason` 表示操作根本不成立，例如参数非法或目标不在场，这时什么都不提交，也不告知任何值。玩法上的失败，例如余额不足、偷窃被发现，应当作为被接受的结果返回：`changes` 为空或只包含部分变化，`reveals` 和 `description` 照常带上。这样角色才能通过失败得知真实值。

`resolve` 拿到的 `statusView` 是**真实值**，因为裁定必须按事实来，例如余额不足要拒绝。它只在宿主内运行，不会进入任何角色视图。`world` 和活动 `resolve` 的第五个参数相同，是行动者当前有权看到的事实（地点、在场角色、物品）。

### 6.1.1 操作参数与目标

- 参数 schema 在活动操作已有类型的基础上增加"角色引用"类型，例如偷窃的目标。宿主在调用 `resolve` 之前先校验：被引用的角色存在，并且处在行动者当前的授权场景里。（活动操作的 `targetRef` 固定是行动者本人，这里不能照搬。）
- "每个角色各一份"指包里声明的全部角色，包括玩家，也包括尚未登场的角色。
- `reveals` 和 `audience` 只能指向行动者本人，或行动者当前授权场景里的角色。跨场景告知（例如短信、银行通知）这一版不支持，否则会绕开现有的场景观察范围。

### 6.2 提交

操作被包装成一种交互，模型通过 perform 提出，玩家通过行动菜单或表单提出，走现有的 Rulebook 和原子事件提交路径；参考活动操作的包装方式（[pack-activity.ts](../../../tests/experiments/pack-activity.ts) 的 rulebook 包装）。接受之后，一次提交里写入一个 `status.updated` 事件，内容包括真实值的变化，以及这次的 reveals。真实值等于按事件顺序累加的结果，不需要另存快照。

### 6.3 认知（方案 B）

某个观察者对某个状态的已知值，是在读取时从事件日志推导出来的，方式和物品的 `current` / `lastObserved`（[character-visible-items.ts](../../../packages/application/src/character-visible-items.ts)）相同：

- 标成"所有人始终知道"的状态：每个人都直接拿到真实值。
- 其他状态：取最近一次指向该观察者的 reveal 中的值，并附上确认时的世界序号。之后真实值如果又变了，观察者那里仍保持旧值，并标成"上次确认"。
- 从来没有被告知过的状态，观察者那里完全没有这一项，而不是显示为空值。

**角色看到什么**：角色上下文里新增一项（例如 `context.status`），只包含该角色已知的值，并附一句提示：这是上次确认的值，不一定等于现在。模型最终看到的文本由 `characterRequestText` 呈现。

**玩家看到什么**：玩家与 NPC 同样处理。

### 6.3.1 适用范围（按需收窄）

用户的原则是：状态默认在整个游戏里都能被已声明操作改动，作者可以按需把它收窄。这一版用活动作为收窄的单位。

- **状态声明**可以加 `activities: [活动标识, ...]`，表示只有这些活动在运行时、由这些活动的裁定才能改这个状态。不写这一项，表示 `status.js` 里的操作都能改它。
- **活动的 `resolve` 可以附带状态变化和告知**，和 `activity.updated` 在同一次提交里写入。宿主校验：这个活动必须在被改状态的 `activities` 清单里；没有写 `activities` 的状态，活动也可以改。告知规则和 6.1.1 相同。
- **`status.js` 的操作**也可以加 `activities: [...]`：只在其中某个活动运行、并且行动者是参与者时，才出现在候选行动里，也才能执行；其他时候既不出现，也会被拒绝。
- **宿主统一在提交前检查**：任何改动只要来自不被允许的地方（例如 `status.js` 的普通操作去改一个限定在战斗里的 HP），整次操作都会被拒绝，什么都不提交。
- 读取不受范围限制：战斗外，角色和玩家仍然看到 HP 的"上次确认"值；状态栏照常显示。
- 位置、剧情阶段等其他条件这一版不做成声明，作者可以在 `resolve` 里自己检查，用 `rejectReason` 拒绝。（我的选择）

### 6.3.2 每轮结束钩子

用户确认要加。`status.js` 可以提供可选的 `onRoundEnd(statusView, round)`：

- **什么时候调用**：每次玩家输入被受理、本轮所有角色反应结束之后调用一次。玩家输入被拒绝时不调用。末端回合重新生成时，会随这一轮一起重新执行。（我的选择）
- **输入**：真实值，以及轮次信息（例如第几轮）。拿不到任何角色的上下文，也拿不到模型输出。
- **输出**：`null`（什么都不变），或 `{ changes, reveals }`。作为本轮最后一个 `status.updated` 事件提交，所以分叉和重新生成时会一起回滚。
- **能改什么**：只能改没有被限定在活动里的状态。限定在活动里的状态（例如战斗中的 HP）由活动自己管理。（我的选择）
- **能告知谁**：钩子没有行动者，所以没有"当前场景"。`reveals` 只能告知被改状态的归属者本人，例如中毒掉血只告诉中毒的人。"所有人始终知道"的状态，例如游戏时间，本来就人人可见，不需要告知。（我的选择）
- **不产生对白或叙述**，也不会额外调度任何角色。如果作者想让"天黑了"出现在场景里，仍需走活动或角色的表达。（我的选择）
- 钩子失败或超时：本轮已提交的内容保留，状态不变，宿主在调试信息里记录失败，不重试。（我的选择）

例子：游戏时间是一个公共的、所有人始终知道的状态。`onRoundEnd` 每轮把它加 10 分钟；"购买"操作在 `resolve` 里读这个时间，18:00 以后给出"店已关门"的结果。

### 6.4 显示

- PlayerView 新增一个白名单字段，内容是玩家已知的值、显示名称，以及是否为"上次确认"的旧值。
- 默认舞台增加一个简单的状态栏面板；自定义前端通过 SDK 读取同一字段。
- 创作者调试接口（已有创作者令牌鉴权）显示全部真实值，用来替代原来的 `variables.debugSnapshot()`。PlayerView 和公共 SDK 永远不包含真实值。

### 6.4.1 存档

初始事件是在建世界时提交的。`status.js` 是编译资产，增加或修改它都会改变包哈希，已有存档会被现有的"包与存档不一致"检查拒绝。所以不存在"读取时现算初始值、作者改脚本后悄悄改写历史"的问题，也不需要额外的存档校验。

### 6.5 退役包变量

- 删除 `tests/experiments/pack-variables.ts`、运行时里对它的接线、`/vars` 命令、`context.packVariables`，以及 `this.#variables===undefined` 这类调度门槛。
- 故事节点、分享和末端存储的文件清单里去掉 `pack-variables.json`。
- 4 个示例包里只有演示用的 `variables.js`，直接删掉；如果某个包确实需要剧情阶段，改写成一个"所有人始终知道"的公共状态。
- 不保留兼容旧存档的分支：旧存档如果带有 `pack-variables.json`，按"包与存档不一致"处理并提示用户新建存档。这条依据 AGENTS.md 第 6 节，具体做法见第 9 节。

## 7. 验证要求

- **单元和集成测试**
  - 拒绝操作时什么都不提交；
  - 操作接受时，状态和事件在同一次提交里写入；
  - 偷窃场景下失主的上下文里没有新值；
  - reveal 之后观察者拿到新值，之后真实值再变化时，观察者那里显示"上次确认"；
  - "所有人始终知道"的状态对所有人一致；
  - 分叉和末端重新生成后状态回到当时的值；
  - 用模拟 HTTP 服务，在 Ollama 和本地 OpenAI 两条协议下各跑一遍，确认私有值不会进入其他角色的请求。
  - 每轮钩子：只在玩家输入被受理后调用一次；结果在重新生成和分叉时回滚；不能改限定在活动里的状态；只能告知归属者本人；失败时状态不变。
  - 适用范围：限定在战斗里的状态，在战斗外被普通操作改动时整次拒绝；限定在战斗里的操作，在战斗外不出现在候选行动里；战斗活动的裁定改状态时，状态变化和活动进度在同一次提交里写入。
- **真实试玩**：用一个小样例包（金钱、购买、偷窃、查看钱袋），走 Core 记忆做一次真实模型试玩。人工检查失主是否在没有观察的情况下"察觉"失窃，以及角色是否把叙述当成了数值变化。
- 运行 `check` 和文档链接检查，并更新当前架构文档和作者指南。

## 8. 交给实现者决定的部分

- 事件数据的具体字段名和结构、上下文字段名、提示的措辞。
- 状态操作怎样出现在模型的候选行动里、玩家怎样填写操作参数（可以参考活动操作的现有做法）。
- 状态数量、操作数量、字符串长度、脚本执行时间这些上限，取值应当足够承载一张中等规模的 MVU 卡。
- 默认舞台状态栏的视觉样式。

## 9. 我替用户做的决定（请确认）

以下 6 条来自审阅者提出的问题：

- 开局时，私有状态默认告知其归属者，`initialize` 可以用 reveals 覆盖。
- 行动者自己的状态被改变时自动告知本人，其他人引起的变化不自动告知。
- 玩法失败（例如余额不足）按"被接受、无变化、带告知"返回；`rejectReason` 仅用于操作不成立的情况，什么都不提交。
- 新增"角色引用"参数类型，由宿主校验目标在场。
- 告知和结果的接收者限于行动者本人和其当前授权场景内的角色，这一版不做跨场景告知。
- 创作者调试接口显示全部真实值，玩家侧永远只拿到已知值。

以下为最初列出的决定：


1. 值只支持数值、字符串、布尔，不支持嵌套 JSON。
2. ~~活动脚本的 `resolve` 这一版不能修改状态。~~ 已按用户要求推翻：活动可以改状态，作者可以把状态收窄到指定活动（见 6.3.1）。
3. 带 `pack-variables.json` 的旧存档不做迁移，直接提示新建存档。
4. 活动运行期间，状态操作是否可用由活动的 `policy` 决定，和其他交互一样需要被列入允许清单。
5. 默认舞台的状态栏只显示玩家已知的值，不提供隐藏或折叠设置。
