# 活动按条件自动开始（设计）

日期：2026-10-20。状态：设计已确认（第 9 节），2026-10-21 已在源码实现并通过自动测试，并做过一次 8 回合 DeepSeek 短试玩（结果见当前作者指南）。现行行为以[当前作者指南](../../current/guides/activity-and-variables.md#按条件自动开始2026-10-21当前源码)为准，本文保留为设计记录。与草案的差异：`notice` 不再另加一条提示，而是替换玩家看到的固定开场行“〈标题〉开始。”，避免两条系统行连着出现（参与者仍收到固定行）；条件不满足、返回 null 均不提交；平局随机与活动初始化随机合并为同一条按轮记录的序列，重新生成按记录回放（第 5 节第 2 条原写“可能选中另一场”，已不成立）。

## 1. 为什么做

例如终末地包里，玩家去四号谷地看过矿脉、回来向佩丽卡回报巡查。作者希望回报之后，弭弗来找管理员谈巡查名单的事：这一幕在剧情上必须发生，不能指望玩家刚好想到去点“开始”，也不能指望某个角色恰好自己提起。

现在活动只能由玩家手动开始。作者已有的条件手段各管一段：

| 手段 | 能做到 | 做不到 |
| --- | --- | --- |
| 状态 + `policy` | 按任务阶段决定哪些操作出现 | 让一段剧情自己开始 |
| 知识条目 `when` | 阶段推进后，角色知道新消息，可能自然提起 | 保证某一幕一定发生 |
| 活动内的条件入口（如“找一找草莓蛋糕”） | 条件满足时出现在菜单 | 仍须玩家手选 |
| `onRoundEnd` | 每轮按真实值改状态 | 不产生对白，不调度角色，不开始活动 |

只是**引导剧情方向**，状态加知识条件已经够用，不需要本功能。本功能只解决“**某一幕必须在条件满足后发生**”。

## 2. 目标

1. 作者在活动脚本里声明一个开始条件；每个玩家回合结束时，宿主检查一次，满足就自动开始这场活动。
2. 自动开始与玩家点“开始”走**同一条路径**：参与者校验、初始化、投递、调度、逃生和退出全部不变。
3. 条件只读状态真实值和玩家当前的授权事实，与状态脚本已有的输入一致，不新增数据来源。
4. 执行有界：每轮最多自动开始一场，不形成同一轮内的连锁。

## 3. 非目标

- **同一轮内的事件链。** 自动开始的活动在本轮产生的变化，最早到下一轮才参与检查。
- **打断或自动暂停正在运行的活动。** 有活动运行时不检查，等它结束或暂停后的下一轮再检查。
- **召唤角色或移动角色。** 活动 `resolve` 现在只能返回剧情状态、描述、受众、玩家表达和状态变化，不能移动任何人。参与者必须已在玩家当前场景；“某人突然出现”只能等角色自己经移动规则过来，或者把条件写成“玩家走到了那个人身边”。
- **场外剧情。** 参与者不在玩家场景时不开始，玩家不在场的地方不演出。
- **条件读取事件日志。** “执行了某种交互”由作者在那个交互的 `resolve` 里写一个状态标记，条件只看状态。
- **NPC 行动触发检查。** 只在玩家回合结束时检查；NPC 回合结束不触发。
- **宿主记录“已触发”。** 是否只发生一次由作者用 `previous` 或状态标记控制，宿主不保存触发队列或标记。

## 4. 作者写什么

活动脚本新增一个可选 hook：

```js
// 回报巡查后，弭弗在玩家身边时，开始“名单”这段剧情；只发生一次。
autoStart(truth, world, previous) {
  const stage = truth?.public.patrol?.valley?.stage
  return {
    when: [
      previous === null,                                  // 以前没开始过
      stage === 'done' || stage === 'claimed',            // 已经回报巡查
      world.characterIds.includes('character:c11'),       // 弭弗在玩家身边
    ],
    notice: '弭弗朝你走了过来。',                          // 可选：只给玩家的提示
  }
}
```

| 参数 | 内容 |
| --- | --- |
| `truth` | 状态真实值（没有状态脚本时为 null），与活动 `resolve` 第六个参数相同；只在宿主内使用，不进入任何角色视图 |
| `world` | **玩家**当前授权事实：locationId、characterIds、items，与 `resolve` 第五个参数的格式相同 |
| `previous` | 这场活动上次的玩家视图，从未开始过时为 null，与 `initialize` 的 `previous` 相同 |

返回值为 `null`（这个活动没有自动开始条件可查），或一个对象：

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `when` | 是 | 条件数组，元素必须是布尔值，至少 1 个。**全部为 true 才算满足**；数组长度就是这场活动的**条件数目**，用于优先级比较（第 5 节） |
| `npcIds` | 玩家选人模式必填 | 这次的参与者；宿主照常校验人数、白名单和场景授权。固定参与者（definition 声明了 `npcIds`）时不能填写 |
| `notice` | 否 | 开始成功后只给玩家的一句提示，例如“弭弗朝你走了过来。”。不写就不提示，活动卡片照常出现。按暂停／继续提示的方式只投递给玩家，不进入任何角色的上下文 |

条件数目由作者列出的条目决定：一个条目写成复合表达式（`a && b`），就只算一条。作者想让某段剧情比另一段更优先，应当把它的条件写得更具体，而不是随意拆分条目。

`autoStart` 只做判断，不修改任何状态。要“只发生一次”，就像上例那样把 `previous === null` 列为一个条件，或检查作者自己写的状态标记。

## 5. 宿主怎样检查

现在一个玩家回合的顺序是：玩家输入提交 → 在场角色反应 → `onRoundEnd`（[frozen runtime](../../../tests/experiments/playtest-frozen-runtime.ts) 的 `#endStatusRound`）。自动开始接在后面：

1. **前提：** 本轮确实提交了新的玩家输入（幂等重试没有提交新内容时，不结束回合，也不检查）；当前不在逃生、关闭或暂停 NPC 的状态；**没有活动正在运行**。
2. **选择：** 对所有未在暂停中的活动调用 `autoStart`（暂停中的活动由玩家决定是否继续），收集 `when` 全部为 true 的候选。**条件数目最多的候选胜出；数目相同时随机选一个。** 本轮只开始这一场，其余候选不开始，下一轮条件仍满足时再参与比较。
   - 随机选择的结果随开始事件提交，提交后就是这一轮的事实。末端重新生成会重新检查，可能选中另一场，这与模型输出在重新生成时会变化性质相同。
   - 如果胜出的候选被宿主校验拒绝（例如参与者已经不在场），本轮不再改试其他候选，见第 5 条。
3. **开始：** 以宿主身份发出与玩家相同的 `start` 请求，独立提交。requestId 由本轮输入派生，保证重试幂等。开始后像手动开始一样给参与者一次处理机会，让他们对开场做出反应。
4. **回合数：** 自动开始不计入玩家回合，`回合` 不额外递增。实现时需要让 `endRound` 的回合计数识别这类开始，与快捷活动的开始与执行合算一轮同理。
5. **失败：**
   - `autoStart` 抛错、超时或返回值不合格：什么都不提交，错误记到调试信息（与 `debug.statusRoundError` 同处），本轮不重试，下一轮照常检查。
   - 宿主校验拒绝开始（例如参与者不在场）：视为“这轮不开始”，不提交，记调试信息。条件下一轮仍满足时再试，不需要队列。
6. **重新生成与分叉：** 自动开始属于这一轮的提交，末端重新生成会连同它一起重演；节点和分叉随事件回滚，与现有活动一致。

## 6. 边界与不变量

1. **有界执行：** 每轮最多一次检查、最多开始一场；本轮自动开始产生的变化不触发本轮再检查。
2. **不绕过世界规则：** 开始校验与手动开始相同，参与者必须在玩家当前场景；活动不能移动角色或改变物品归属（物品仍走普通交互）。
3. **认知隔离：** 条件可以读真相，但内容不能泄露真相。开场的 description、`game.public`、开场旁白按活动现有的投递规则只给参与者；条件用到的真实值不会因为“剧情开始了”就进入任何角色视图。作者不能在开场文字里替角色说出他们不该知道的答案。
4. **角色主体性：** 推荐**情境式**开场：用开场描述或 `game.public` 给出情境（“弭弗找到你，手里拿着那份名单”），参与者自己决定怎么说、怎么做。必须保证台词的关键节点可以用已有的 `simulate` **演出式**写死，但只用于少数关键剧情点。
5. **玩家能离开：** 逃生和退出照常可用；自动开始的活动没有特殊的“不可退出”状态。

## 7. 替代与删除

- 本功能不新增事件类型或状态机，复用活动的 `start` 操作和 `activity.updated` 事件，只给开始请求加上来源标记（例如 `source: 'auto'`），供回合计数和调试区分。
- 撤销活动指南第 3 节“不引入自动事件链”这句话中关于活动的部分：现在允许“玩家回合结束 → 按条件开始一场活动”这**一步**，仍然不允许递归链条，也不从叙事解析状态变化。实现时同步改写该句和[已验证与已知限制](../../current/guides/activity-and-variables.md#已验证与已知限制)第 7 条。

## 8. 验收

自动测试（最小集）：

- 返回 null 或 `when` 含 false → 什么都不提交；全部为 true → 恰好一次 `start` 提交，参与者获得一次处理机会。
- 两个候选同时满足：条件数目多的开始；数目相同时只开始其中一场（固定随机源下结果确定）。
- `when` 为空数组、含非布尔值，或固定参与者活动填写了 `npcIds` → 按作者错误处理，不提交。
- 有 `notice` 时只有玩家收到提示，任何角色上下文里都没有它；没有 `notice` 时不出现额外提示。
- 有活动运行时不检查；同一轮自动开始后，另一个条件已满足的活动不在本轮开始。
- `autoStart` 抛错 → 不提交、记录调试信息，下一轮可正常开始。
- 参与者不在玩家场景 → 不提交，下一轮条件满足且人在场时开始。
- 幂等重试的玩家输入 → 不检查；自动开始不增加 `回合`。
- 条件中读取的私有真值不出现在任何角色上下文里。

真实试玩：在终末地包里加“名单”剧情（第 4 节示例）。回报巡查后，分别验证弭弗在场和不在场两种情况：在场时剧情开始，参与者的开场反应自然，不像在念剧本；不在场时剧情不开始，等玩家去找她或她自己过来。

## 9. 已确认（2026-10-20）

1. 多个候选同时满足时，条件数目多的优先，数目相同随机选（第 5 节第 2 条）。条件数目由 `autoStart` 返回的 `when` 数组长度决定，因为函数式条件无法由宿主自行计数；不改成声明式 Schema，以免为“玩家身边有谁”这类条件另造描述语言。
2. 是否给玩家提示由作者决定：可选的 `notice` 字段，只投递给玩家（第 4 节）。
