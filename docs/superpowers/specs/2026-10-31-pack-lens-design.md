# 包透视：不开游戏看清世界包（设计）

日期：2026-10-31。状态：**已实现**（`feat/pack-lens` 分支，Task 1–9；用户通读与真实桌面验收待完成），与设计的差异见文末第 11 节。验收对象：[甜蜜日程包](../../../examples/world-packs/model-girls-sweet-days/)。

## 1. 为什么做

例如作者对 AI 说“深夜冰箱事件改成傍晚也能触发，DeepSeek 不该能发短信”。AI 改完后，作者手里只有两样东西：

- **AI 自己写的总结**：作者无法判断它准不准、全不全；
- **亲自试玩**：要载入包、开新实例、走到深夜、走进厨房，几分钟才验证一处，而且只能碰到恰好玩到的部分。

即使有 skill 和模板，创作仍然复杂，原因不在写不出 JSON，而在三件事：

1. 改完一处，不知道实际效果；
2. 看不出 AI 为了满足要求具体改了哪些地方；
3. 想看懂一个包，要先理解认知、活动、自主唤醒、状态、回合钩子等很多概念，而这些设置分散在十几个 JSON 和几千行脚本里，甜蜜日程包就有 17 个 JSON 和约 2600 行脚本。

用户的结论是：**改包仍然交给 AI，人不需要了解字段和规则；人需要的是看得见。**

## 2. 目标

验收标准（用户原话）：**用甜蜜日程包，在不开启游戏的情况下知道所有包作者设置的东西。**

1. **只读透视**：包校验通过后，在 Launcher 里打开，不启动游戏实例，用游戏里的话展示包的全部作者设置。
2. **三种看法**（用户全部需要）：
   - 按角色看：她什么时候会自己动、能做什么、能去哪、和哪些事件有关；
   - 按事件看：什么条件下触发、触发后玩家能选什么、选完改了什么、告诉了谁；
   - 按回合看：玩家行动后依次发生了什么（推演）。
3. **改动标记**：和对比基准相比，有变化的地方在视图里标出来，让作者不用读 AI 的总结也能核对改动。
4. **桩模型推演**：不调用真实模型，把规则、事件检查、角色唤醒和回合钩子跑一遍；可以一步步点选，也可以跑 AI 写好的推演脚本。
5. **圈选给 AI**：作者在视图里选中想改的东西并留一句话，AI 自己通过 CLI 读到选了什么、在哪个文件哪个位置、当前值是什么。

## 3. 非目标与反目标

- **不在工具里编辑包。** 不做表单编辑。唯一的写入是作者自己的圈选清单、对比点和查看记录（见第 6、7 节），不写世界包内容。用户明确表示字段和规则不适合由人类直接修改。
- **不判断角色演得好不好。** 桩推演只证明规则、触发和状态变化是对的；对白自然度、角色主体性仍然要靠真实模型试玩。工具界面上要明确这一点，不能让“推演通过”看起来等于“体验验收通过”（AGENTS.md 第 1、7 节）。
- **不翻译 JS 代码。** 不对脚本做静态分析来生成“时段是深夜”这类说明。条件写复杂一点（比如先 filter 再数长度）就翻不准，而且会让作者以为工具已经全看懂了。说明文字只来自作者写的标签和运行时实际算出的结果（第 5 节）。
- **暂不做 MCP。** 先走 skill 已经在用的 `worldpack.cmd` CLI；MCP 是一套新协议，每种客户端都要单独配置。CLI 用顺之后再考虑。
- **不依赖 git。** 发行包作者一般没有仓库。
- **第一阶段不自动试跑活动选项**（见第 4.3 节）。
- **不支持旧格式包。** 只支持当前 `worldpack-source/v5`。
- **反目标**：如果作者用了这个工具，仍然要去读 JSON 才能确认 AI 改对了，那就算失败；如果推演为了跑起来另写了一套简化规则，导致和真实游戏结果不一致，同样算失败。

## 4. 作者看到什么

### 4.1 入口

在 Launcher 中，校验通过的包旁边有“透视”入口，打开后的页面风格和现有[创作者控制台](../../../apps/launcher/src/creator/)一致（左侧导航、主视图、右侧详情）。不需要选存档或开始游戏。包校验失败时入口不可用，并显示校验错误。

### 4.2 设置范围（“所有设置”的整理）

下面的分类是设计方的整理，用户认可了这份清单：

| 分类 | 展示内容 | 主要来源 |
| --- | --- | --- |
| 角色 | 人设与外观摘要、立绘、初始位置、自主唤醒（频率、机会次数、哪些事件会叫醒她）、主动时可用的交互、可去的地点、相关事件 | characters、autonomy、scenes、frontend |
| 谁知道什么 | 每个角色及玩家的初始观察、目标、知识条目和受众，用矩阵显示 | cognition、知识／文档文件 |
| 地点与场景 | 有哪些地方、开场时谁在哪 | locations、scenes |
| 物品与状态 | 状态键、初始值、可见范围（alwaysKnown／谁能看）、物品与归属 | entities、status 脚本的 definition 与 initialize |
| 事件与活动 | 标题、开场、参与者、玩家操作选项、自动触发条件、触发次数控制 | activities 脚本的 definition、autoStart |
| 规则与钩子 | 每个交互的名称和适用对象，以及 `onRoundEnd` 每轮做了什么 | interactions、status 脚本 |
| 预设与记忆 | 只显示摘要和使用了哪个，不展开全文 | model-preset、role-presets、memory |

能从 JSON 或脚本 `definition` 直接得到的都静态展示；只能运行脚本才知道的内容（条件真假、`initialize` 返回的初始状态、`onRoundEnd` 的效果），通过第 5 节的推演沙箱得到。

### 4.3 三种视图

示意稿保存在 `.superpowers/brainstorm/3965-1793434408/content/views.html`（本地，未提交）。

- 角色的“能做什么”分两层显示（设计方的选择）：静态显示 autonomy 白名单；在推演中，再按当前时刻状态脚本 `policy` 的实际结果，标出哪些此刻能用、哪些不能用。
- **角色视图**：例如 DeepSeek 一栏写着“每 1 个玩家回合给她 1 次主动机会；日程推进、有人睡到第二天、有人去打工时也会叫醒她；能做简单料理，不能泡茶；相关事件：深夜冰箱、醋意视线……”。
- **事件视图**：例如“深夜冰箱的偷吃抓包，同时满足以下条件时触发：✔ 时段是深夜 ✘ 玩家在厨房 ✔ DeepSeek 在厨房 ✔ 还没发生过”。条件真假按当前推演时刻计算，没有推演时按开场状态计算。下面列出玩家可选操作的名称。选项效果写在脚本的 `resolve` 里，工具不翻译代码，所以**第一阶段只在推演中实际选过某个选项后**，才在该选项下显示它改了哪个状态、告诉了谁（用户已确认）。“自动从当前状态分叉、试跑每个选项”记为第二阶段，不在本设计范围内。
- **回合推演**：逐步列出“① 玩家移动到厨房，规则判定成功 → ② 检查自动事件：深夜冰箱触发，醋意视线未触发（在场少女不足 2 人）→ ③ DeepSeek 获得机会 → ④ 回合结束钩子：游戏时间变化……”。

## 5. 推演

### 5.1 原则：用真实运行时，不写第二套规则

推演必须和真实游戏一致，否则就是反目标。因此推演复用真实的宿主运行时（状态脚本、活动桥、自主调度、规则裁定、事件提交），只做两处替换：

- 数据目录换成临时目录，推演结束即丢弃，不碰任何存档或 `D:/worlds`；
- 模型换成桩：角色获得机会时，不调用真实模型。

这里是建议方向。具体是起一个无界面的宿主进程，还是直接在 Launcher 的 Node 桥里组装 `WorldApplication`，由实现者根据现有 `desktop/host/world-runtime.ts` 的结构决定。约束只有一条：不能另写一份简化规则。

### 5.2 桩模型的行为

- 活动脚本声明了 `simulate` 的，按 `simulate` 走，这和真实游戏一样；
- 其他情况下，角色默认弃权；
- 一步步推演时，作者可以为某个角色指定这一步的行为：弃权、说一句指定的话，或尝试某个交互（照样经过规则裁定，可能被拒绝）。

### 5.3 起点：作为另一种开场直接设定（用户已确认）

推演可以直接设定起点，例如“时段=白天，DeepSeek 在厨房，序章活动不运行”，不必从开场一步步合法走到那里。做法是：

- 起点被当作**另一种开场**：在推演运行时启动之前，用它覆盖包的初始数据（场景参与者与位置、状态初始值、物品归属等），再按正常开场初始化世界。不在运行中途写入事实，也不绕开 Action／Rulebook；起点之后的每一步都走真实规则；
- 起点只存在于临时推演目录，不写回包文件，也不是游戏事实；
- 起点能覆盖哪些字段由实现者决定，至少要能覆盖时段等状态值、角色所在场景，以及是否跳过自动开场活动；
- 起点不合法时（例如引用了不存在的地点），推演按包校验的规则直接报错，不尝试修正。

不设定起点时，从包的正常开场开始。

### 5.4 两种推演方式

1. **点选推演**：选起点（开场，或推演脚本里定义的某个中间状态），然后像玩游戏一样点玩家可用的行动（移动、交互、活动操作、静观）。每点一步，回合推演视图追加这一步的完整经过，事件视图里的条件真假随之更新。
2. **脚本推演**：AI 写一份推演脚本（JSON，包括起点、玩家行动序列、各角色的桩行为、可选的期望），工具或 CLI 一口气跑完，显示同样的逐步经过；写了期望的，标出是否满足。之后在 skill 里补充写法。

推演脚本放在包源目录之外，或者放在包内不参与编译的位置（见第 7 节），不进入发行内容。

### 5.5 条件标签

`autoStart` 返回的 `when` 现在是一串没有名字的布尔值。新增一种写法，每项可以是 `[标签, 布尔值]`：

```js
when: [
  ['还没发生过', previous === null],
  ['时段是深夜', truth?.public?.slot === '深夜'],
  ['玩家在厨房', world.locationId === 'location:kitchen'],
]
```

- 宿主把两种写法同等对待：全部为真才触发，触发语义不变；
- 透视和推演用标签显示“✔/✘ 时段是深夜”；没有标签的项显示为“条件 2：✘”，并附上源码位置；
- 更新 skill 和作者指南，要求 AI 写标签；甜蜜日程包的 autoStart 补上标签，作为示范。

这是本设计对包格式唯一的改动，也是可选写法，旧包不受影响。

## 6. 改动标记

- 工具把每次查看时的“透视结果”（第 4.2 节那些条目的规范化内容，而不是原始 JSON 文本）存成一份快照；
- **默认基准**：作者上次查看时的快照。打开时只标出这之后的变化。“查看过”以作者在界面上点“已看过”为准：打开、关闭页面都不会让基准前移，AI 通过 CLI 读取透视结果也不会（设计方的选择，避免 AI 一读标记就消失，或者作者没看完就丢了标记）；
- **对比点**：作者可以手动存一个命名对比点，需要时选它做基准，用来一起检查攒了几轮的改动；
- 标记以条目为单位：新增、删除，以及字段变化（例如“唤醒频率 2 → 1”“条件新增：时段是傍晚”）；
- 比较的是透视结果，所以 AI 只调整格式或缩进时不会出现标记。

## 7. 圈选给 AI（待改清单）

### 7.1 作者这边

在任意视图里选中一个条目（一个条件、一项能力、一条知识、一个状态初始值……），写一句话，例如“改成傍晚”，它就进入**待改清单**。每条记录自动包含：

- 作者原话；
- 条目在游戏里的叫法，例如“事件『深夜冰箱』的条件『时段是深夜』”；
- 精确位置：文件加 JSON Pointer，或者脚本文件、hook 名和条件标签；
- 创建时的当前值。

AI 改完后，如果条目在透视结果中发生了变化，清单上会显示“已改动，待确认”，作者在视图里核对后自己关闭。AI 不能关闭或修改清单条目。

### 7.2 AI 这边

用户要求 AI **自己去读**，不需要作者复制粘贴。在 `worldpack.cmd`（[creator-cli.ts](../../../packages/world-pack/src/creator-cli.ts)）新增只读命令，命令名由实现者定：

- 读透视结果：输出与界面同源的 JSON，让 AI 看到作者看到的内容；
- 读待改清单：输出未关闭的条目；
- 跑推演脚本：输出逐步经过和期望结果。

skill 增加一条工作方式：作者说“按清单改”时，先读清单，改完跑 validate，再对相关条目跑推演自查，最后在交付说明里逐条对应清单。界面上另外保留一个“复制给 AI”按钮，作为备用。

### 7.3 存放位置

清单、快照、对比点和推演脚本需要满足两点：CLI 只给源目录就能找到它们；它们不会进入编译、导出或发行内容。建议放在包源目录下一个固定的隐藏子目录（例如 `.perspectra-lens/`），并确认 validate、compile、导出和发行打包都忽略它。这一点是设计方的选择，实现者如果发现现有打包流程更适合放在别处，可以调整，但必须保持“CLI 只凭源目录就能找到”。

## 8. 约束

- 只读：不修改世界包内容文件，不写历史数据目录，不调用真实模型，不需要凭证；
- 推演复用真实运行时（第 5.1 节）；脚本仍在现有的 `node:vm` 沙箱和超时限制内执行；
- 透视展示的是作者设置，作者本人可以看到全部私有内容（角色私有观察、internal 状态等），这和创作者控制台的定位一致；这些内容不能进入玩家页面或游戏前端；
- 沿用 ESM、TypeScript strict、显式 `.ts` 导入，以及 Launcher 现有的 Vue 和创作者控制台组件风格；
- 修改后同步作者指南（[activity-and-variables.md](../../current/guides/activity-and-variables.md) 中的条件标签）、[代码技术文档](../../current/architecture/README.md)相关章节，以及 skill 的 [SKILL.md](../../../skills/perspectra-creator/SKILL.md) 和 [gameplay.md](../../../skills/perspectra-creator/references/gameplay.md)。

## 9. 交给实现者决定

- 推演运行时的具体组装方式和进程边界（第 5.1 节）；
- 透视结果的数据结构和规范化方式；
- CLI 子命令名、推演脚本的 JSON 字段；
- 视图布局细节和交互（沿用创作者控制台风格即可）；
- 实施顺序。建议先做静态透视，再做推演和条件标签，最后做改动标记和待改清单，每一步都能单独用甜蜜日程包验收。

## 10. 验收

- 用甜蜜日程包，不开游戏，逐类核对第 4.2 节的设置都能看到，并且和包文件一致；
- 推演“深夜，玩家走进厨房，DeepSeek 在厨房”：深夜冰箱触发；同一场景换成白天时不触发，并显示是哪个条件不满足；
- 推演结果与真实宿主在同一输入下的状态变化一致（用自动化测试对比，至少覆盖一个活动和 `onRoundEnd`）；
- 让 AI 按清单改一处，例如把触发时段改成傍晚：AI 通过 CLI 读到清单并完成修改；工具标出这处改动，清单显示“已改动”；推演确认傍晚触发；
- 推演不写任何存档或包内容文件（可以只检查文件修改时间）；
- 明确不覆盖：角色对白和表现的质量，仍需真实模型试玩。

## 11. 实现与设计的差异（2026-10-31）

- 实现位置：`desktop/lens/`（推演、视图、比较、存储、脚本、CLI、会话）、`desktop/launcher-core.ts` 的 `lens-*` 操作、`apps/launcher/src/lens/`。作者指南见[包透视](../../current/guides/pack-lens.md)，代码说明见[创作者运行时](../../current/architecture/creator-runtime.md)。
- CLI 命令名为 `worldpack.cmd lens view|requests|simulate`。`lens` 不走 `packages/world-pack` 的 CLI 进程，而是独立打包成 `runtime/lens.mjs`，由 `worldpack.cmd` 转发，因为它需要完整的宿主运行时。
- 第 7.2 节的“复制给 AI”备用按钮在待改清单页，复制待改与已改动条目的可读文本（含“AI 不能关闭条目”的说明）。
- 待改清单条目的状态为 open / changed / removed / closed；CLI 只列出 open 与 changed。
- 推演脚本的 `start` 支持 `status`、`scenes`、`skipAutoStart`；步骤为 `say`、`move`、`interact`（可加 `target`、`arguments`）、`activity`、`wait`；期望为 `started`、`notStarted`、`status`。窗口里点选推演还可以给角色指定一次行为，并显示她此刻被运行时提供的选项（`npcOptions`）。
- 脚本和对比点的存放位置是 `<包源目录>/.perspectra-lens/`，已加入仓库 `.gitignore`；编译只读取清单列出的文件，没有为该目录另写忽略逻辑，打包时是否带走未专门验证。
- 仍待验收：真实桌面窗口与真实包、发行包中的 `lens.mjs`、真实 AI 按清单改、NPC 按选项实际执行。
