# 角色调用的缓存前缀：方案

日期：2026-11-07。状态：第一步及其补充（工具定义固定、认识移到经历之后）已在 feat/stable-call-prefix 分支实施，见文末；第二步未实施。依据：2026-11-07 甜蜜日程包试玩的 54 次请求记录（Go 直连 `deepseek-v4.1-flash`）。

例如 Claude 说完"来得正好，蛋炒饭刚起锅"，4 秒后宿主再给她一次续写机会。这两次请求的角色设定、三万多字的经历、物品和可用操作几乎相同，但第二次只读到 0～4000 token 缓存。整局 54 次调用约 104 万输入 token，缓存只命中 13.9%；续写占 25 次，平均读取比例不到 10%。

## 1. 问题出在哪里

coding agent 能让多轮调用很便宜，是因为每次请求都以上一次请求的全文为前缀，新内容只接在末尾。Perspectra 的每次角色调用都重新拼装，而且开头就不稳定：

| 位置 | 实际情况 |
| --- | --- |
| 工具定义（约 2900 字符） | 续写前后完全相同 |
| 第一条 system：角色决策契约（约 2200 字符） | 这局出现了 4 个版本。其中五类句子随步骤或回合变化："本次首次 publish 后……"与"publish 会结束……"二选一、续写专用的"你刚才已经正式发表了表达……"、只在有执行证据时出现的 recentExecutionEvidence 说明、活动玩法说明、行动前表达说明。去掉这五类后只剩 1 个版本 |
| 预设 system 节点 | 不变 |
| 角色上下文 JSON（平均约 4 万字符） | 经历 history 平均 3.2 万字符，在前；位置、状态、物品、场景、可用操作、操作说明、刺激在后。续写时只在 history 末尾多一条自己的发言 |

续写请求在第一条 system 就和上一次分叉，所以后面再相似也读不到缓存。

用这局记录离线核算（只比较请求文本，不调用模型）：

| 情况 | 续写（25 对） | 下一回合（26 对） |
| --- | --- | --- |
| 现在的公共前缀 | 7.9% | 14.2% |
| 实际缓存读取 | 9.8% | 17.6% |
| 把五类变化句移到末尾后的公共前缀 | 56.6% | 34.0% |
| 续写改为追加式后（估计） | 接近整段 | 不变 |

公共前缀是理论上限，实际命中还受上游路由与驻留影响：之前直连 Go 原样重复时约 77%。

## 2. 方案

### 第一步：把会变的说明移到末尾（推荐先做）

- 角色决策契约只保留不随步骤、回合变化的部分。
- 五类变化句按原文移到请求最后，作为"本次处理说明"，放在预设后置节点之后。文字不改，只改位置。
- 工具定义保持现状。
- 改动集中在 [character-turn-call.ts](../../../packages/provider-chat/src/character-turn-call.ts)；[gateway-turn-call.ts](../../../packages/official-llm/src/gateway-turn-call.ts) 复用同一份消息，需要核对。不改上下文内容、授权、调度、插件接口。

收益：续写和下一回合都受益，因为执行证据说明的出现与否也不再打断前缀。

风险：同样的说明从开头挪到最后，模型的遵守程度可能变化。一般来说放在最后更显眼，但"续写时无需重复对白""执行证据不等于目标完成"这类说明需要真实试玩复核。

需要核对：放在末尾的 system 消息在三种协议上的位置。预设后置 system 节点已经是这种用法，OpenAI 兼容会保留原位；Anthropic 和 Google 的 SDK 转换需要逐一确认，不合适时改为追加到 user 消息末尾。

### 第二步：续写改为追加式（视第一步结果再定）

续写请求 = 第一次请求的完整消息 + 一条 assistant（第一次的决定）+ 一条 user（发生了什么、这一步能做什么）。这样第二次请求以第一次的全文为前缀，基本整段命中。

追加内容只能来自同一角色在新世界位置上的授权视图：

- 第一次之后新增的 history 条目（自己的发言、他人此间的行动）；
- 与第一次相比有变化的处境字段（位置、物品、场景、可用操作），按字段整体给出新值；
- 执行结果与本步说明。

满足以下任一条件时退回完整重建，不尝试拼接：

- 第一次的 history 不是第二次 history 的前缀，例如记忆归档或窗口滑动；
- 预设、模型或协议在两步之间变了；
- 角色被搬到别的场景导致授权范围改变。

需要改的接缝：[LlmInstance](../../../packages/plugin-sdk/src/llm.ts) 的 `prepare` 现在是无状态的。需要由 [CharacterTurn](../../../packages/application/src/character-turn.ts) 在续写时把上一步已发送的调用和决定作为可选字段传入，官方模型通道据此拼接；第三方模型插件不认识这个字段时照旧收到完整上下文。

风险：比第一步大得多，涉及授权视图的差量、预设宏与正则对新增内容的处理、检查器展示、第三方通道兼容。只有第一步之后续写仍明显偏贵时才值得做。

### 不在这次范围

- 减少续写次数本身：例如续写只允许执行动作，或用"行动前表达"把"说话加行动"合成一次调用。这属于玩法设计，另行决定。
- 把稳定资料与动态处境拆成两条消息。之前 Go/GLM 与 DeepSeek 官方实测结论不一致，而且会改变模型看到的排布。
- 跨启动保持缓存会话。

## 3. 验证

1. 自动测试：同一角色续写前后、有无执行证据、有无活动时，第一条 system 与工具定义逐字相同；变化句仍完整出现在请求末尾；授权上下文内容不变。
2. 离线核算：用本局请求记录重算公共前缀，确认续写达到约 55% 以上。
3. 真实对照：同一个包、同一条 Go 直连连接、新存档，跑与这局相近的几轮。对比缓存读取比例、每回合输入 token、平均延迟。
4. 体验检查：续写时是否重复刚才的对白、是否把执行证据当成目标完成、活动玩法规则是否仍被遵守。测试通过不等于体验验收。

## 4. 接受的限制

- 前缀稳定不保证命中，上游仍可能因路由、驻留或过期而未命中。
- 下一回合的处境字段每轮都会变，第一步之后这部分仍然按全价计算。
- 第一步改变了提示词顺序，会让旧存档第一次请求的缓存失效一次。

## 5. 第一步实施记录

- 变化句移入 user 消息 JSON 的最后一个字段 `turnInstructions`，而不是新增一条末尾消息。原因：多处测试和插件（如 JEV 审计）按"最后一条消息就是角色上下文 JSON"读取，新增消息会打破它们；放在 JSON 内也避开了各协议对后置 system 消息的不同处理。说明仍在预设后置节点之前，作者放在最后的风格要求保持最后。
- 契约中加一句："用户消息末尾的 turnInstructions 是本次处理适用的规则，与这里的说明同样有效。"
- 回归测试 [stable-call-prefix.test.ts](../../../tests/host/stable-call-prefix.test.ts) 覆盖两种调用格式：五种步骤或回合组合下第一条消息逐字相同，每条规则都出现在授权上下文之后，且 `turnInstructions` 是最后一个字段。
- 已运行 provider-chat、official-llm、host、scenarios、integration 共 134 个测试文件 1210 项，全部通过。未做真实模型复测，真实对照与体验检查待做。

## 6. 补充：工具定义固定、认识移到经历之后

原则：会话历史是请求的大头（2026-11-07 晚的 GLM 试玩中约占角色上下文 85%），游玩中可能变化的内容都排在它之后，不变的内容排在它之前。

当晚第二局试玩开了 22 次采集，确认第一步生效：22 次请求的第一条 system 都是 2156 字符、逐字相同；工具定义没变时，相邻请求一直相同到经历末尾（约 86%）。同时发现两处仍在经历之前变化：

| 位置 | 变化来源 | 处理 |
| --- | --- | --- |
| 工具定义（最前） | 续写第二步去掉 perform；无人在场时去掉 direct/private；按场景列出目的地、交互目标、接收者、参数 | gateway 工具只给固定结构，选项留在 context，本步不能执行写进 turnInstructions；活动期间保留作者参数 schema |
| `cognition`、`claims`、`goals` | 目标、关系、情绪更新 | 移到 `history` 之后 |

宿主校验不变；被放宽的只是模型侧的引导。20 对相邻请求中有 7 对曾因工具变化只剩约 1% 公共前缀，[stable-call-prefix.test.ts](../../../tests/host/stable-call-prefix.test.ts) 覆盖了在场的人、目的地、交互、能否执行和行动前表达各种组合下工具逐字相同。

真实模型复测（同日，用户授权用其 DeepSeek Key）：[stable-prefix-live.ts](../../../tests/experiments/stable-prefix-live.ts) 直连 `deepseek-flash`，缓存策略自动（被动），甜蜜日程包从第一天清晨起 16 轮固定台词，开局即开启采集。75 次调用全部成功，输入 604144 token，缓存读取 194688（32.2%），续写 36.1%、下一回合 30.0%，平均 1.66 秒。72 对相邻请求全部只在上一份经历末尾分叉，工具定义与 system 一次都没变。角色 21 次移动或交互全部被规则接受，没有格式重试或失败。这局经历只从约 1000 增长到 8800 字符，其后的处境（可用操作与说明约 7500 字符）仍占一半，所以公共前缀平均只有 29%；经历越长，可复用比例越高。新旧版本没有在同一条件下对照，不能把 32.2% 与此前长局的 13.9% 直接比较。

接着用同一脚本、按 Launcher 默认接上 Core 记忆跑 60 轮（第一次 60 轮漏接 Core，历史停在 16+8 条的滑动窗口，那局结果不代表默认配置，不采用）：201 次调用全部成功，输入 3786406 token，缓存读取 3069696（81.1%），续写 80.4%、下一回合 81.3%，平均 1.82 秒。经历从约 3000 增长到 79000 字符，期间未触发 Core 整理；198 对相邻请求全部纯追加。按经历长度分档：

| 经历字符数 | 调用 | 经历占上下文 | 缓存读取 | 公共前缀 |
| --- | --- | --- | --- | --- |
| < 1 万 | 24 | 37% | 54.6% | 52.8% |
| 1 万～2 万 | 31 | 62% | 69.7% | 67.7% |
| 2 万～4 万 | 78 | 77% | 81.1% | 79.2% |
| ≥ 4 万 | 68 | 83% | 85.5% | 84.4% |

没有格式重试、规则拒绝或失败；15 次放弃回应。整理那一次的断开本局未出现，未测。

已运行 provider-chat、official-llm、application、official-scheduler、host、scenarios、integration、desktop 共 170 个测试文件，1468 项通过；model-girls-undercover 的一项在全量并发时失败，单独运行在改动前后都通过。

接受的限制：

- 模型失去枚举引导，选错目的地或交互的次数可能增加；宿主仍按带当前选项的严格 schema 校验，选错时照旧触发格式重试，重试请求换用单个分支的工具，这一次无法复用前缀。
- Google 协议的 oneOf 工具、活动期间的工具、表达策略切换仍会让工具变化。
- 核心记忆整理后 `history` 开头改变，这一次无法复用。
