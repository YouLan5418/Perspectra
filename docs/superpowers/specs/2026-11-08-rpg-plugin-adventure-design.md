# RPG 插件与小型冒险包设计

2026-11-08，分支 `feat/rpg-plugin`。本文是设计，不表示已实现。

## 1. 一个例子

玩家和澄住在山脚的小屋。家里的日子照常：聊天、做饭、睡觉，状态栏上没有血量和魔力。某天两人决定去后山的遗迹。玩家邀请澄入队，澄自己决定答应。走进遗迹入口那一刻，状态栏多出“生命 40/40、魔力 8/8”，澄也有她的一份。第一层石廊的文字写着“潮湿的石廊，尽头有一扇铁门，门前站着一只遗迹守卫”。玩家往前走，守卫开口说“擅入者，止步”，战斗开始：玩家选技能和目标，澄自己决定用火球还是治疗，守卫按规则出手。打赢后掉落一把铁钥匙，铁门可以打开了，第二层还有一个宝箱。玩家受了伤回家，状态栏收起战斗数值，但伤势记着；睡一觉之后，作者声明的“休息回血”把生命补满。

作者写的只有数据：角色和敌人的数值、技能、装备、背包初始物品、每张地图的文字、敌人和宝箱、进门条件，以及可选的固定台词。他不写战斗公式，也不写移动规则。

## 2. 为什么做

一次从零创作走查（2026-11-07）表明，新手在“写玩法规则代码”上耗步最多：消耗品、时段推进、目击者都要自己拼。RPG 是最常见的需求，之前的 [RPG Core 原型](../../current/studies/2026-10-26_cordis-rpg-core-prototype.md)证明“作者只写战斗数据”可行，但它只覆盖单场战斗，没有跨场景数值、装备、背包、队伍和副本。用户希望把这类常见玩法做成插件：包声明需要，作者只写配置。

## 3. 目标、非目标与反目标

目标：

1. 作者在包里声明使用 RPG，用 JSON 配置：每个角色的数值（生命、魔力和作者自定义数值）、技能槽与模板技能、装备槽、初始背包、敌人，以及副本地图。
2. 战斗：回合制，队友是真实角色，自己选择技能和目标；敌人是纯规则单位，不调用模型，可以有作者写的固定台词。
3. 数值整局存在，存档、分支、回看与其他状态一致。作者可声明某些数值只在副本启用。
4. 战斗外可选操作：休息回血、使用道具、装备与卸下。作者声明了才出现。
5. 队伍：角色自己决定是否入队；入队后玩家移动时队员随行；可以离队；作者可规定某些场合（如战斗中）不能离队。
6. 副本：文字地图链。每张地图有剧情文字、敌人、宝箱、通往下一张地图的条件。
7. 作者可以写死队友在战斗或地图事件中的回应，包括出手回合的台词和技能；没写的地方角色自由发言。
8. 战败时，全队传送到作者配置的地点。
9. 一个新的小型冒险包作为验收：有家和至少两层的副本。

非目标（第一版不做）：等级与经验、格子地图、RPG Maker 桥接、商店系统（可由作者用现有状态操作写）、多支队伍、PvP、敌人调用模型。

原则（用户 2026-11-08 确认）：程序尊重角色自主，但更要尊重创作者对故事的控制。作者没写的地方，角色自己决定；作者明确写下的演出（指定台词、指定技能、战败去向），程序照作者的意思执行，并且照常经过规则裁定和事件提交。

反目标（做出来也算失败）：

- 程序替角色做主：调度器或插件在作者没有写明的地方替她选技能、规定她必须入队，或阻止她自主离队（作者明确声明的场合除外）。
- 战斗或移动结果没经过规则裁定就成了事实，或某角色看到了不在场时发生的战斗细节。
- 背包与物品归属出现两份记录，叙事里“谁拿着什么”与数值对不上。
- 没声明 RPG 的包行为发生任何变化。
- 作者仍需要写 JS 才能做出例子里的那段体验。

## 4. 约束

- 遵守 [AGENTS.md](../../../AGENTS.md) 与[核心与插件统一规范](../../current/architecture/plugin-standard.md)：插件不能自行写入未经验证的事件，只产出核心认识的事件；状态通过现有状态机制；物品归属通过现有物品事件。
- “插件声明宿主管理的持久化状态”仍是暂缓需求。RPG 的数值不另建存储，借现有状态机制保存。
- 10-26 删除过“插件注册活动规则、包按名字引用”的设计，原因之一是“插件没装对，世界就打不开”。用户这次接受“声明了就必须有”。必需插件缺失时，世界打开前就失败，并写明缺什么，沿用 `plugins.json` 必需能力缺失时的报错方式。
- 存档一致性：同一个世界以后用更新过的插件打开，规则可能变了。插件的标识、版本和生成内容摘要要记进世界，打开时不一致就明确失败，不静默换规则。
- 现有脚本限制照旧：单次 hook 100 ms、源码 256 KiB、状态定义 64 个、操作 32 个、状态值合计 512 KiB。配置超出时在校验阶段报错。
- 修改在 `feat/rpg-plugin` 分支上进行。

## 5. 已经决定的做法

**插件是什么。** 官方 RPG 插件随程序分发。包用一个配置文件（暂名 `rpg.json`，登记在 `assetFiles`）声明使用它并给出全部数据。世界打开时，插件校验配置，再把配置与随插件分发的共享规则合成为现有机制能直接加载的内容：

- 一个状态模块：数值、装备、战斗外操作；
- 战斗活动：沿用 [battle-runtime.js](../../../examples/rpg-core/battle-runtime.js) 的思路和代码；
- 副本的移动与地图规则。

宿主照常经过状态、活动和规则裁定提交事件。之所以选这种“载入时生成”的方式，是因为现有活动源本来就是脚本源码，状态模块也已经能拼进状态脚本，不需要新的提交路径。“进入战斗时载入”落实为：战斗活动在遇敌时才开始，其余时间不参与回合。

**数值。** 每项数值是一条角色状态，例如 `rpg-hp`、`rpg-mp`、作者自定义的 `rpg-stamina`，并记录最大值。

- 作者可标注某项数值只在副本内启用：在家里不进状态栏和角色上下文，相关操作不出现，数值本身保留不清零。现有状态机制没有按地点控制显示的字段，需要为此给状态声明加一个可选的地点范围。这是本设计对状态机制唯一的扩展；对活动机制的扩展见“战斗”。
- 战斗中谁看到谁的数值，沿用活动的可见性规则：敌人的生命对在场者公开，不在场的角色拿不到战斗细节。

**背包与装备。** 背包就是角色手里拿着的物品，用现有物品归属。消耗品用掉后用物品外观（`kind`）标为已用，或移到一个“已耗尽”位置；第一版选哪一种由实现决定，选定后写进文档。装备是一条角色状态，记录“哪个槽位装着哪件物品”。被装备的物品必须在该角色手里；交出或丢下时自动从槽位卸下，这条规则由插件的物品规则检查。装备提供的加成在战斗结算时读取。

**战斗。**

- 回合顺序与原型一致，按速度排序。队友通过正常的角色行动入口，以活动操作“使用技能（技能、目标）”出手。
- 敌人行动由规则推进，策略取自作者配置的简单选项，例如打生命最低的、随机、固定目标。
- 胜利时掉落作者配置的物品，并改变作者声明的状态。掉落物落在这张地图的地上，由玩家或队友自己用现有的“拿起”拾取（实现时的决定）。物品要先在包里登记，放在一个不可到达的存放地点，战斗胜利时移到地图上。
- 失败时，全队传送到作者配置的地点（用户选择）。撤退由作者配置：原地脱战，或同样传送。这需要扩展活动机制：让活动结果能移动角色，并且能一次移动多件物品（掉落也用这条路）。这是本设计对活动机制的扩展，必须与战斗结果原子提交。被移动的角色、留下的人、到达地点的人各自看到什么，要像随行一样单独测试。
- 敌人台词是作者在敌人配置里写的固定文字，按时机显示：遇敌、受伤、倒下。它是规则结果的说明文字，不是角色发言。

**队伍。** 新增入队、离队两个交互和一条“随行”规则。入队需要被邀请者自己同意：NPC 通过自己的回合接受，不能由邀请者单方面完成。随行发生在队长（玩家）移动且移动被接受之后，队员在同一次提交里随之移动。作者可以声明在战斗活动进行中不能离队。现有的牵手关系在移动后自动解除，不能复用来随行，需要新做；可以参照牵手“关系 + 移动后的生命周期规则”的写法。

**副本地图。** 每张地图是一个现有地点。地图配置给出：

- 剧情文字：进入时显示，第一次进入与再次进入可以不同；
- 敌人组：走进来就遇敌，或可见、可以选择开战；
- 宝箱：一个物品，打开后里面的物品归开箱者；
- 去往下一张地图的条件：例如击败某敌人组、持有某物品、某状态为真。

条件不满足时，移动被拒绝并给出作者写的理由，例如“铁门锁着，需要钥匙”。进入时的剧情文字用玩家可见的旁白呈现；需要让同场角色也读到时，用场景旁白。

**固定演出（用户选择宽口径）。** 作者可以写死队友在某个时机的回应。实现上沿用活动的 `simulate` 钩子：替换这一次决定，之后照常走规则裁定和提交。不写的地方，由模型自己决定。

- 战斗中，任何时机都可以写死，包括她的出手回合。在出手回合，作者可以同时指定台词和技能、目标；技能不可用时（例如魔力不足），按规则拒绝，并把理由告诉作者。
- 地图事件中，也可以写死队友台词，例如“进入第二层时澄说一句话”。现有 `simulate` 只在活动里生效，所以地图事件要包装成一段很短的活动（自动开始、播完即结束）。它与战斗不能同时运行：同一张地图上既有固定台词又遇敌时，先播台词再开战。

**队伍补充（实现时的决定）。** 入队的队员自己移动到别处，就自动离队，不阻止她移动。

**物品规则归属（实现时的决定）。** 拿、放、给仍由作者用现有物品模板写在 `scripts/status.js` 里，RPG 插件不接管。“作者不写 JS”指 RPG 部分。装备采用结算时检查：战斗结算时，装备物品不在她手里，该槽位就视为空；物品转移的那一刻不去改槽位。所以不需要在别人的“交给”操作里插入卸装逻辑。

**作者工具链。**

- 校验：`worldpack validate` 至少要报出 `rpg.json` 的结构错误；完整的配置校验在宿主载入时进行，包透视能显示错误。
- 包透视：要能显示 RPG 的角色数值、敌人和地图，推演要能跑一场战斗。
- 创作 Skill：新增一节“RPG 配置”，给出完整示例。

## 6. 验收包

新建 `examples/world-packs/<名称>`（名称由实现决定）。至少包含：

- 地点与人物：家（至少两个地点）、副本两层、玩家和一名队友；
- 敌人与地图内容：两种敌人、一个宝箱、一扇需要钥匙的门；
- 战斗外操作：休息回血、使用药水；
- 固定演出：一段战斗中写死的队友台词加技能，一段进入地图时写死的队友台词，其余自由；
- 战败：战败后传送回家。

验收分三层，交付时分别说明：

1. 自动测试：配置校验、数值只在副本显示、战斗胜负、掉落到地上并能拾取、战败传送与各方认知、固定演出指定技能与技能不可用时的拒绝、装备加成、入队需要同意、随行移动与离队、锁门拒绝、存档分支回滚、未声明 RPG 的包不受影响。
2. 包透视推演：用 `knows` 检查不在场的角色不知道战斗细节。
3. 真实模型试玩：至少一局从家到副本再回家。重点看队友是否自然地选技能、是否有自己的态度，以及随行是否让人觉得她被拖着走。

## 7. 留给实现决定的

- `rpg.json` 的具体字段名与结构。原型的 `battle.config.json` 可作起点。
- 插件以哪种形态装进宿主：随程序的 Cordis 机制包 `packages/official-rpg`，或复用 `plugins.json` 包模块入口加一份官方共享代码。两者都要满足第 4 节的存档一致性约束。实现前先写一页取舍记录。
- 随行规则用哪个接缝实现：交互生命周期，或规则层中间件 `ctx.rules`。须保证随行与队长移动原子提交，并给出场景转换。
- 状态地点范围字段的名字和语义细节：只影响显示，还是同时禁止改动。
- 敌人策略的具体选项、伤害公式。可沿用原型，不追求平衡。
- 消耗品用后的表示方式。
- 每张地图剧情文字的呈现通道：插件自己在移动结果里给出，或交给剧情节奏的节拍。

做出这些决定时，在实现说明里写明理由。凡是新增概念，写明它替代了什么。

## 8. 已知风险

- 战败传送与随行一样，是“规则移动别人”，而且需要扩展活动结果。这是本设计里最大的一处核心改动，要先单独做完并测试，再做其他部分。
- 宽口径的固定演出会让作者能替队友选技能。这是用户有意的选择；但作者写下的演出有可能和她当下的认知矛盾，比如让她喊出她不可能知道的事。程序不检查这一点，靠创作指南提醒，靠试玩发现。
- 随行会让一个角色在自己没有行动时改变位置。这是新的“规则替别人移动”的情形，必须严格限定在她已同意入队的范围内，并单独测试认知：留下的人看到谁离开，新地点的人看到谁到来。
- 插件生成的脚本仍受 100 ms 和体积限制。配置很大时可能超限，要在校验阶段给出明确报错。
- 装备、背包和战斗交织后，模型可能在叙事里声称装备了不在手里的东西。权威状态由规则保证，叙事越权按现有原则处理，不新增分类器。
