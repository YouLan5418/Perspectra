# 跑团活动与骰子机制设计

2026-11-08。本文是设计，不表示已经实现。基于 `feat/rpg-plugin` 分支的 `ctx.content` 接缝。

## 1. 一个例子

客厅里有玩家、澄和阿茹。玩家打开“跑团”，从在场的 AI 角色中选阿茹当主持人，澄和玩家做参与者，选作者写好的剧本《雨夜古宅》。阿茹念出开场：“雨夜，你们的车坏在一座古宅门口……”。

玩家说：“我想撬开书房的门。”阿茹判断需要检定，宣布这是“敏捷检定，难度 12”。程序掷出 d20 = 9，加上玩家的敏捷 +2，结果是 11。这组点数只有玩家和阿茹看得到。阿茹随后宣布：“门锁卡住了，撬棍发出一声刺耳的响动。”这句结算澄也能看到。澄出于自己的性格说：“你小声点！”接着她主动提出去查看楼梯。阿茹又掷了一个只有她自己知道的暗骰，判断宅子里的“管家”有没有听到响动，并把结果记进自己的私密笔记。

一局结束后回到客厅，三人都记得“我们玩了一局跑团，玩家在古宅里撬门时出了声”。没有人会以为主世界里真有一座古宅。只有玩家和阿茹记得那次撬门掷的点数。

## 2. 为什么做

用户提出把跑团做成一种可选的活动玩法：主持人由 AI 角色担任，其他角色保留各自的性格，自主参与。它和 RPG 有共同的需求：随机和检定必须可信、可回看，并且不能由模型说了算。现有活动只在 `initialize` 时由宿主提供随机数，并记进每轮的随机记录（`ActivitiesRuntime` 的 `beginRoundRandom`，重新生成时按原样重放）；`resolve` 时脚本拿不到这份记录（[official-activities](../../../packages/official-activities/src/index.ts)、[activity-runtime](../../../desktop/host/activity-runtime.ts)）。RPG 敌人的 `random` 策略没有用随机数，而是用回合与版本号算出来的，本来就能重放，所以第一版不改它。

## 3. 目标、非目标、反目标

目标：

1. 新增内部机制插件 `official-dice`（`ctx.dice`），提供：
   - 宿主提供的随机数，结果写进提交的事件；
   - “骰子 + 修正 对比 难度”的检定；
   - 每次掷骰都带告知范围。

   跑团和 RPG 都用它。
2. 新增玩法插件 `official-trpg`。它通过 `ctx.content` 读世界包登记的 `trpg.json`，生成一个跑团活动。没有登记这个文件的世界里没有跑团。
3. 玩家手动开局：从当前场景在场的 AI 角色里勾选参与者（默认全选），再从参与者里选一名主持人。主持人用自己的回合接受或拒绝。
4. 故事来源二选一：作者写的剧本，或一个题目（作者预设，或玩家开局时填写）。两者落到同一套局内状态。
5. 局内状态只属于这一局，包括：
   - 公开笔记；
   - 主持人的私密笔记；
   - 局内地点、物品、NPC；
   - 每名参与者一张小角色卡（几项数值和几项技能）。

   局内状态不影响主世界。
6. 参与者提出行动的方式：自由说话，或用“提出行动”操作。主持人决定是否检定，以及用哪项技能、难度多少。程序掷骰，点数只告诉提出者和主持人。主持人宣布的结算，全体参与者都能看到。主持人还可以掷只有自己知道的暗骰。
7. 主持人用有类型的专属操作维护局内状态，主持人身份不改变他的人设。
8. 主持人宣布结局或玩家主动结束，都会结束这一局。结束后主持人的权限随活动一起结束。
9. 记忆沿用狼人杀的路径：结算描述和对白按告知范围进入参与者记忆，并且标明是哪个活动。
10. 一个验收用的世界包，以及作者文档。

非目标（第一版不做）：
- 完整规则书，例如整张 COC 或 D&D 角色卡、职业、成长、法术表；
- 战斗回合、先攻、距离；
- 让主持人直接修改主世界的状态或物品；
- 多局之间延续的角色卡；
- 局内 NPC 由独立的模型扮演（局内 NPC 由主持人代言）；
- 玩家当主持人；
- 在没有声明 `trpg.json` 的世界里开跑团。

反目标（做出来也算失败）：
- 点数由主持人的模型说出来，或者点数不在提交的事件里；
- 没参与掷骰的参与者、不在场的角色，看到了点数或主持人的私密笔记；
- 主持人的操作改到了主世界状态，或者跳过了规则检查；
- 局内事件进入记忆时没有标明是游戏，角色把它当成主世界的事实；
- 宿主出现跑团或 RPG 的专有代码。

## 4. 约束

- 遵守 [AGENTS.md](../../../AGENTS.md) 和[核心与插件统一规范](../../current/architecture/plugin-standard.md)：
  - 只产出核心认识的事件；
  - 模型输出只能提出操作，由脚本检查后提交；
  - 宿主不出现具体玩法的代码。
- 用户 2026-11-08 确认的原则：作者明确写下的演出照做；作者没写的地方，由角色自己决定。主持人的裁定属于角色行为，不是作者写死的演出。
- 活动现有限制照旧：
  - 单次钩子 100 ms；
  - 脚本输出 64 KiB；
  - 活动参与者在开局时确定，之后不增减；
  - 操作参数最外层必须是封闭对象。
- 告知范围：
  - `public` 给全体参与者；
  - `private[角色]` 只给该角色；
  - `internal` 只有脚本能看到；
  - 活动结果的 `audience` 只有 `participants` 和 `self` 两种。

## 5. 已经决定的做法

### 5.1 official-dice

骰子插件是一个内部 Cordis 机制插件，入口为 `ctx.dice`，由 `official-bundle` 默认注册。它对活动脚本提供的能力，按掷骰的时机分两类：

- **初始化时**：沿用现有的随机来源，不变。
- **处理操作时**：脚本声明“这次处理需要掷骰”，宿主掷出点数，作为输入交给脚本。点数随这次活动结果一起提交，写在 `activity.updated` 里。点数应当如何告知，交给第 5.3 节的告知规则处理。

具体接口留给实现决定，可选的做法有两种：

- 两段式：先由 `resolve` 返回“需要掷 1d20”，宿主掷完后带着点数再调用一次；
- 由宿主为本次调用预先准备一串记录下来的随机数。

无论选哪种，都要满足：

1. 点数写进提交的事件；
2. 掷骰复用现有的每轮随机记录（`ActivitiesRuntime` 的 `beginRoundRandom`）：回看、分支、末端重新生成都按原样重放，不重掷。这样玩家不能靠重新生成刷检定，语义也和初始化随机数一致；
3. 只对活动脚本开放，不暴露给角色模型。

检定的计算放在插件提供的纯函数里：骰子表达式（第一版支持 `d20`、`d100`、`NdM+K`）、加修正、对比难度，得出成功或失败，并给出差值。RPG 第一版不改（见第 2 节）；所有现有 RPG 测试照常通过。

### 5.2 official-trpg 与 `trpg.json`

跑团是一个通过 `ctx.content` 注册的内容生成器，配置文件为 `trpg.json`，必须带 `plugin: { id: "official-trpg", version: "1" }`。它生成一个活动，键名由实现决定，例如 `trpg`。`trpg.json` 包含：

- 角色卡模板：数值项（例如生命、理智，各带上限）和技能项（例如敏捷、观察、交涉，给出默认修正）。还可以为某些角色预设不同的数值。
- 可选的剧本：开场文字，以及地点、物品、NPC 列表，每项标“公开”或“只有主持人知道”；还有真相和可能的结局，只有主持人知道。
- 可选的预设题目，可以有多个。没有剧本时，玩家开局可以从预设题目里选一个，或者自己填一个。
- 可选的主持人候选名单。不填时，在场的所有 AI 角色都可以当主持人。

**开局分两步，不扩展核心的开局参数。** 现有开局请求只认 `npcIds`（[activity-runtime](../../../desktop/host/activity-runtime.ts) 处理 start 的位置）。

1. **玩家开局，选参与者。** 沿用现有的“玩家选人”：玩家从在场的 AI 角色里勾选参与者，界面默认全选。没被选上的在场角色留在局外，听不到局内的定向对白。主持人也要在这次勾选的名单里。
2. **筹备阶段。** 活动以“筹备”阶段开始，玩家用局内操作“筹备”指定三件事：
   - 主持人，从参与名单里选一名 AI 角色；
   - 剧本，或预设题目，或自己填写的题目；
   - 是否开始。

   之后进入邀请阶段：被选为主持人的角色用自己的回合接受或拒绝。拒绝后，玩家可以另选一人，或者结束这一局。这沿用约会邀请的做法，因为项目原则要求不替角色做主。

这样开局流程完全落在活动脚本里，不改核心的开局参数。

### 5.3 一次行动与检定的流程

1. **参与者提出行动。** 参与者可以直接说话，也可以用“提出行动”操作附上一句描述。这句描述进入公开笔记的“待处理”队列，不改变任何东西。
2. **主持人得到机会。** 主持人是 NPC，按活动调度得到一次处理机会。可用的操作如下：
   - 要求检定：说明对象、技能、难度，是否为暗骰。
   - 直接宣布结算：不掷骰。
   - 维护局内状态：写公开笔记、写私密笔记、改某人角色卡的某项数值、新建或修改地点、物品、NPC。
   - 结束本局：给出结局描述。
3. **要求检定之后**，由脚本按第 5.1 节掷骰并计算。
   - 点数、修正、总值写进提出者和主持人各自的 `private`。暗骰只写进主持人的 `private`。
   - 公开部分只出现“某人进行了一次敏捷检定”；暗骰在公开部分不出现。
   - **点数要进记忆，所以扩展核心的活动结果约定。** 现在活动结果的 `audience` 只有 `participants` 和 `self` 两种，`private` 也不进入观察和记忆（`activityOutcomeObservations` 只用描述）。为了做到第 1 节的“只有玩家和阿茹记得点数”，活动结果新增一个可选的 `privateNotes: { [characterId]: 文字 }`：每条只作为这个角色的观察提交，接收者必须是活动参与者，并和本次结果原子提交。点数描述就放在这里，同时给提出者和主持人。暗骰只给主持人。

     这是对核心活动结果的扩展，需要单独测试：只有指定参与者收到；其他参与者和局外角色收不到；没有这个字段的现有活动行为不变。
4. **主持人宣布结算。** 结算文字作为公开描述，全体参与者都能看到。主持人宣布结算时，可以顺手改角色卡、写笔记，这些改动和结算一起提交。
5. **点数和结算之间的关系不由程序检查。** 程序只保证点数可信、对谁可见。主持人如果宣布的结算和点数不符，比如检定失败却宣布成功，属于角色表现问题，要靠试玩发现。这和“叙事越权按现有原则处理”一致。

### 5.4 主持人的操作

主持人的专属操作都要满足下面几条：

- 在 `policy` 里只开放给主持人；
- `requiresTurn: false`；
- 操作参数各自有类型。

第一版的操作如下：

| 操作 | 参数 | 效果 |
| --- | --- | --- |
| 要求检定 | 对象、技能、难度、是否暗骰 | 第 5.3 节第 3 步 |
| 宣布 | 文字 | 公开描述 |
| 写笔记 | 公开或私密、文字（追加或替换整段由实现决定） | 写进 `public` 或主持人的 `private` |
| 改数值 | 对象、数值项、新值 | 只能改角色卡模板里有的项，并限制在上下限之内 |
| 局内内容 | 新建或修改：类型（地点、物品、NPC）、名字、描述、所在地点、是否公开 | 写进 `public` 或主持人的 `private` |
| 结束 | 结局文字 | 活动结束 |

不提供通用的“任意键、任意值”操作。若试玩表明主持人确实需要改别的内容，再加一个受限的通用操作，比如只能改 `public.vars` 下面的键。

### 5.5 参与者能看到什么

- 每名参与者能看到的局内状态：
  - 公开笔记；
  - 公开的局内内容；
  - 所有人的角色卡（第一版公开）；
  - 自己的检定点数。
- 主持人额外能看到：
  - 自己的私密笔记；
  - 只有主持人知道的剧本内容；
  - 所有检定的点数和暗骰。
- 没参加这一局的角色，什么都看不到。
- 角色模型通过现有的活动视图读取这些内容，不另开通道。

### 5.6 记忆

不新增记忆机制。结算描述和对白已经按告知范围进入参与者的观察，观察里带着活动标识。所以角色记得“在跑团里”发生了什么，不会把它当成主世界的事实。验收时要真实试玩确认：回到主世界后，角色对局内事件的说法是“游戏里”。

### 5.7 验收包

新建 `examples/world-packs/<名称>`，名称由实现决定。内容要求：

- 地点：至少一个地点。
- 角色：玩家，加三名 AI 角色。
- `trpg.json`：一份角色卡模板、一份短剧本，以及两个预设题目。

## 6. 验收

1. **自动测试：**
   - 点数写进事件；回看和分支不重掷。
   - 点数只出现在提出者和主持人的视图里；暗骰只出现在主持人的视图里。
   - 主持人的操作对别人不开放。
   - 改数值时检查上下限。
   - 改动不碰主世界。
   - 结束后主持人的操作全部失效。
   - 没有 `trpg.json` 的包不受影响。
   - 现有 RPG 测试照常通过。
   - 末端重新生成后点数不变。
   - `privateNotes` 只进指定参与者的观察和记忆。
2. **包透视推演：** 用 `knows` / `doesNotKnow` 检查点数和私密笔记的可见范围。
3. **真实模型试玩：** 至少一局有剧本、一局用题目。重点看三件事：
   - 主持人的裁定是否和点数一致；
   - 澄等参与者是否自主提出行动；
   - 回到主世界后，角色是否把局内事件说成“游戏里”。

## 7. 留给实现决定的

- `ctx.dice` 的具体接口，以及处理操作时掷骰的方式（第 5.1 节的两种做法，或其他做法）。要先写一页取舍记录，说明它替代了什么。这会改动 `ActivityInstance.resolve` 的输入（plugin-sdk）和活动脚本的调用方式，属于机制接口的扩展，不改提交和事件。
- `trpg.json` 的具体字段名。
- 笔记的长度上限。长局里笔记会变长，需要在 64 KiB 的限制内裁剪或分段。
- 活动调度里主持人的机会节奏：每次有人提出行动后给主持人一次机会，还是另有安排。由试玩决定。

## 8. 已知风险

- 主持人是模型。他可能忘了掷骰，可能宣布和点数不符的结果，也可能不按操作而只在对白里“裁定”。程序只保证点数可信、可见范围正确，裁定质量要靠提示和试玩改进。
- 笔记和局内内容会随长局增长，触到脚本的大小限制。
- 参与者人数多时，主持人一次机会可能处理不过来所有待处理的行动，需要看调度节奏。
- 在处理操作时掷骰，这一能力碰到核心的重放语义。实现时要单独测试回看、分支和重新生成三种情况。
