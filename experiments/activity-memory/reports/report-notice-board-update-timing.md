# 行动提交后、即时表达前的认知更新实验

日期：2026-10-05。沿用双牌场景与现有 Gemini 网关。**在这个固定场景中，先交付更新后的冲突认识，确实改变了即时续写；仅把两份原始 Atom 一起交付没有复现这一效果。** 结论只覆盖本轮阅读干预，不表示完整自动认知更新已上线，也不表示角色已经执行核实。

## 1. 问题与最小实现

前轮角色实际看到了二楼203和一楼105，但读完第二块牌后，三次都只建议去105。旧认识和新结果当时已经同时在输入中，因此不能只归因于没找回旧记忆。

本轮没有修改核心或模型提示词，而是复用已有两个入口：

1. `maxCalls: 1`：角色自主提出查看第二块牌，Rulebook 接受并原子提交观察、裁定及 tick。暂不调用表达模型。
2. `continuationOf`：从同一已提交行动恢复一次只允许表达的续写。既有执行结果适配器仍从真实提交历史读取牌面。

三个全新种子各用真实模型完成第一块牌的查看和发言，以及第二块牌的自主查看，共9次调用。每个种子读取完成后关闭数据库，冻结此时尚未回复的状态。准备阶段的 `budget_exhausted` 是明确使用一调用预算的结果：行动已成功，当前阶段已用完调用额度；不是模型失败、主动 pass 或查看被拒绝。

牌面和玩家刺激沿用前轮：大厅牌为“登记处：二楼203”，窗口指示牌为“登记处：一楼105”。第二块牌的搬入仍是实验布景，通过既有提交路径改变可达性；模型没被告知它的文字，也没有被强制指定查看。两个对象的文字都只是来源内容，不裁定登记处实际在哪。

## 2. 更新与对照

仍使用 `notice_board_conflict.py → cognition_lineage.update`，只导出该角色两份已经提交的直接阅读证据；没有提供预期关系标签、其他角色来源或隐藏世界状态。三次调用均得到 `unresolved_conflict`，各保留两条当前分支，旧认识在历史中保留。

认识正文没有命令角色“必须问人”或“必须先核实”，只表述两个待核实线索的冲突。两份证据发生于 tick 2 和 tick 6；研究者初始认识记录于 tick 3，修订记录于 tick 6。更新发生在第二次查看成功后、其表达模型调用前。初始局部认识仍由研究者依据第一份实际 Source 写入，不能拿来证明模型自动形成了它。

每个种子复制到三个条件，各采样两次，顺序轮换：

| 条件 | 交付 |
| --- | --- |
| baseline | 原来的“大厅牌写203，尚未实地核实”认识，1项 |
| updated | 更新器生成的两个当前冲突分支，2项 |
| raw-evidence | 两份实际查看的原始 Atom，2项 |

三组都继续同一实际行动，用同一原玩家刺激，不追加问路问题。保留原生近期观察、自身观察和查看结果，不人为清空它们。禁用另一次 recall，额外执行也由原生结果续写契约禁止。

同一种子下所有六份请求去掉 `context.memories` 后完全相同，包含相同 `result.action`、`result.evidence.actionId`、执行说明、近期经历和当前刺激。新认识和原证据各两项，所以两者区别不能归因于多一个条目；但正文结构、来源时间、家族冲突标记等阅读元数据仍不同。这不是只变一段文本或单一元数据的消融。

## 3. 真实返回

全轮30次真实调用：种子9次、认识更新3次、结果续写18次。27次 Character 返回的标签均为 `gemini-3.7-flash-high`；更新日志只记录请求名 `gemini-3.7-flash`。没有 JEV 调用，也没有因返回不合预期而重试或替换样本。

| 条件 | 续写样本 | 明确表达两份信息冲突 |
| --- | ---: | ---: |
| baseline | 6 | 0 |
| updated | 6 | 6 |
| raw-evidence | 6 | 0 |

六份 baseline 和六份 raw 都只根据第二块牌建议去105。updated 中五份明确提出“核实／问问／弄清楚”；另一份保留两处线索，选择先去105、不行再去203：

> 大厅原本的牌子上写着二楼203，不过刚搬过来的这块指示牌上写的是一楼105。两边信息不太一致，要不先顺路去一楼105看看，不行再去二楼？

另一份 updated 回答：

> 我刚才看了下新搬过来的指示牌，上面写着登记处在一楼105，但大厅原先的牌子写的是二楼203……两边写的不一致，恐怕得先弄清楚哪个才是准的。

同一种子的 raw 回答：

> 我刚才看了下新搬过来的指示牌，上面写着登记处在一楼105，我们去一楼105吧。

五份显式核实和一份探索两处方案要分开计数，不能写成六次都问人。baseline 中“去看看”本身也是探索，不应写成没有任何核实意图；区别在于没有呈现两份信息的分歧。

一份 baseline 说“免得白跑一趟二楼”，暗示二楼可能已没必要去，实际尚无现场核实。三份 updated 问“哪个是最新的”，只是提出时效性问题，没有证明牌子书写或更新日期，也没有默认后一块一定正确。本轮不是自由文本绝不越权的证明。

以上判断由主代理阅读所有原生对白后给出，非盲评，没有额外评价模型或关键词自动标签。两个采样共用一个证据种子和一次更新，**每组6份回答不是6份独立经历**。样本只覆盖三个同类短场景，不能把6/6当作普遍成功率。

## 4. 判断：本轮证明了什么

1. **认识交付的及时性与呈现方式值得继续做。** 当表达模型调用前已经读到带冲突关系的当前认识，角色即时表达能保留分歧，并自行选择核实或探索方案。
2. **原始证据存在，不等于即时表达一定整合它。** 原始 Atom 和原生近期经历已经包含两份牌面，raw 组仍只谈最新执行结果。这与前轮“另起一次普通问路时 raw 也能正确说明冲突”的结果不同，说明执行续写的结果不能简单由独立问路结果代替。
3. **没有隔离出“必须调用一次认识更新模型”的收益。** 干预同时改变了自然语言组织、显式分歧关系和元数据。本轮只排除了“原始 Atom 各自多交付一次就同样有效”，没有测试把原证据变成清楚的并列自然语言、单条冲突摘要、移除冲突元数据或其他低成本交付。
4. **尚未证明角色会实际自主核实。** 所有续写原样 `publish`；此阶段不能 `perform`，玩家之后也尚未推进到核实动作。说“先问问”仍是计划，不是已执行行为。
5. **不是正式自动更新系统。** 本轮用已有拆分入口安排离线更新，再恢复表达。没有在正式运行时加每次行动都调用认识模型的钩子、预算、取消或失败回退，也没有测试它们。

## 5. 成本与验证

Character 网关 usage：prompt 85616、completion 2155、total 102348。三次更新 usage：prompt 8395、completion 893、total 14366。全轮网关 total 116714。total 可能计入隐藏推理，不按 prompt + completion 重算，也没有价格换算。

Character 调用延迟中位数4359 ms；三次更新中位数约8350 ms。若串行放到实际回复前，会多出一次模型等待，但本轮阶段分开运行，**没有测玩家端到端等待时间**。更新只做三次并在采样中复用，不是每份更新认识回答都新增一次更新调用。

通过的检查：

- 类型检查、两个新 TS 文件的 oxlint；
- 查看能力、双牌场景、原生结果续写及本轮恢复测试，共36项 TS 测试；修改 lint 表达后本轮单项又通过；
- 既有认识谱系6项单元测试；
- SQLite 只读完整性、来源角色／哈希／文字、原子接受与 tick、查看内容只在提交后可见；
- 更新原生返回可重现、旧认识和两份 Source / Atom / Episode 不变；
- 原生 Character 回答原样验证和提交；对照没有重做查看；
- 三个种子的冻结数据库不变、复制的历史事件完全一致、同种子非记忆请求一致。

审计351行 Source，其中包含对照复制的历史，不是351次新经历。真实新查看操作只有6次，对照续写新增查看0次。其他角色没有获得对应直接阅读 Source；角色把内容说给玩家后，来源仍是 `reported_speech`。

未运行全库 check、UI验收、长期试玩、自然召回、自动家族发现、认识更新失败的生产调度回退或真正核实登记处的玩法。没有修改 `packages/`、正式 Memory schema、核心世界状态／日志／规则实现、JEV或原更新提示词。只新增实验驱动、只读审计和一项恢复集成测试。

## 6. 下一步建议

保留“重要新证据提交后，让当前认识参与随后的表达”这个候选方向，但不要立即规定每次交互都调用认识模型。更新调用的额外等待不小，当前实验也没有证明推理一定必须由独立模型完成。

在生产接入前，最小的下一项对照可以是清楚、保留来源的自然语言并列证据交付，与本轮更新认识比较，检查是否能同样促成冲突表达。此对照不应写入“必须核实”的行为命令。若希望直接验角色行动，则需要在后续正常可执行 Turn 中提供真实核实途径，让她自己决定用不用；不能将本轮 `publish` 计划计作行动成功。

本轮没有实现这些下一步，也没有因此扩展生命周期或插件框架。
