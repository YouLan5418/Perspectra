# Perspectra 创作

按任务交付完整 v5 源目录、原生预设或迁移评估：人物能自由回应，需要追踪的状态通过规则改变，另附实际校验结果。比如“同行者知道信件内容，玩家尚不知情；钥匙只有拿到手后才能交给别人”，先明确各自知道什么、可以尝试什么，再选择文件与脚本；预设负责如何表达，不代替这些事实与权限。

## 选择本次工作

- 原创或修改世界包：按下文创建或编辑；读[源包与人物](references/world-pack.md)，有玩法需求再读[玩法扩展](references/gameplay.md)。
- 酒馆角色卡分析／转换：读[酒馆卡迁移](references/tavern.md)。本 Skill 已收录旧 tavern-to-perspectra 的提取器、容量分析与迁移／验收方法，不依赖另装旧 Skill。只评估时不建包；明确转换时继续完成源包与所需规则。
- 预设创作／修改：读[原生预设](references/presets.md)，按包推荐或命名交换格式输出。仅做预设时不生成游戏包；同时迁移卡和创作预设时共用本次选定人物及风格。

用户已经指定卡、作品、模型或限制时沿用。改进本 Skill 不代表允许批量转换本机卡片；本次制作 Skill 仅使用合成样本验证。

## 找到目标程序

先确定用户的 Perspectra 解压目录，读取 `build-info.json`、`创作校验.md`，实际执行 `worldpack.cmd --version` 和 `--help`。本 Skill 的脚手架核对目标是 Perspectra 0.3.1、`worldpack-source/v5`、`worldpack/v5`、编译器 0.5.0。版本号不一致时比较格式与编译器，再用目标 CLI 检查；格式不兼容时保留设计工作，明确需要对应版本的创作资源，不猜旧字段。

程序用户不必有仓库、pnpm 或全局 Node／Python。JS 脚手架使用 `<程序目录>/runtime/node.exe`；酒馆卡提取使用 `<程序目录>/runtime/python/python.exe`。以下路径占位符均替换成实际路径，相对源路径以终端工作目录为准。程序尚未定位时可以继续设计与编辑已有文件，不能声称已验证兼容。

本次玩法说明核对到 2026-10-29 main 的 `ea4e3ea`；完整活动状态调度、玩家自己的活动 private 和匿名等待提示对应 2026-10-28 的宿主／舞台修复。产品、格式和编译器版本相同，不表示这些宿主能力相同；10-24 的 candidate4 验收不覆盖它们。优先使用目标程序随附的 Skill，对照 build-info 的 sourceCommit、sourceDirty、buildTime 与该包的验收记录；sourceDirty 为 true 时提交号不是完整构建快照。无法确认时先完成设计，在目标 Launcher 新实例中检查实际 hook 输入和玩家视图，再报告兼容范围。复制新版 Skill 不会升级旧程序。

预设校验还需实际确认 `--help` 中有 `preset validate`；旧程序即使也报 0.3.1，未必带此新增入口。缺少时可在 Launcher 导入／载入验证或使用更新的程序工具，不把未知命令失败写成预设有效。

## 创作或修改

先给一段玩家与角色的互动例子，明确核心角色、开场、信息差和当前确实要追踪的玩法。普通文案与目录选择可自行决定；只有答案会实质改变作品时才询问。用户要求完整作品时，脚手架只是起点，继续实现内容和必要规则，不能以空模板代替交付。

世界包新作品用脚手架创建**不存在的新目录**，随后把人物、地点和认知改成用户的内容：

```powershell
& '<程序目录>/runtime/node.exe' '<skill目录>/scripts/create-world.mjs' '<作品目录>' 'pack:my-world' '我的世界'
& '<程序目录>/worldpack.cmd' validate '<作品目录>'
& '<程序目录>/worldpack.cmd' test '<作品目录>'
```

脚手架仅生成一个玩家、一个 NPC、一个地点的文件结构，不含剧情、玩法脚本或固定结局。编辑已有作品时先读清单与相关文件，不运行脚手架覆盖它。独立作品使用新 packId，发布内容更新时提升 packVersion；不要改旧存档或强行修改摘要来续玩新内容。

读 [源包与人物](references/world-pack.md) 了解文件引用、初始认知和知识。涉及物品、客观状态、活动（含多场、自动开始和隐藏回合）、角色自主、短信、插件或界面时再读 [玩法扩展](references/gameplay.md)，有物品规则需求才使用 `assets/status-items.js`；只想换官方舞台的配色、字体或卡片样式时，复制 `assets/theme.css` 到作品的 `frontend/theme.css` 再改。

- 角色的情绪、好感、信任等主观态度默认写进人设、预设、记忆与对白；只有用户明确要追踪这项机制时才设计数值。
- 不将秘密塞入公开描述、公共前端或全员初始观察。背景设定与亲身经历分开；知识条件只检查接收者授权的材料，不能靠条件扩大文档受众。
- 重要位置、物品归属与明确追踪的状态由 Action／规则／事件路径裁定。普通姿态和语气保留自由，不扩成闭合动作码；拒绝后不靠台词或旁白补成成功。
- 调度给角色机会，不能代替它决定态度与行为；固定脚本演出只用于用户确实需要的片段。
- 酒馆原卡、HTML、EJS 和第三方脚本先当数据静态阅读，所需逻辑另写包内代码，不直接执行原卡。复杂迁移单独列出待核查内容，不把本 Skill 当自动兼容层。

## 按清单改，并用推演自查

作者用 Launcher 的“包透视”圈选了想改的地方，再说“按清单改”时：

1. 运行 `worldpack.cmd lens requests '<源目录>'`，读出未关闭条目：作者原话、条目在游戏里的叫法、文件与位置（JSON Pointer，或脚本 hook 与条件标签）、创建时的值。清单为空就如实告诉作者。
2. 逐条修改源目录，不改作者没圈的东西；条件写 `[标签, 布尔值]`，让透视能逐条显示。
3. 运行 `validate`，再为相关条目写或复用推演脚本（格式见[玩法扩展](references/gameplay.md#包透视与推演脚本)，存进 `<源目录>/.perspectra-lens/scenarios/`），运行 `lens simulate '<源目录>' '<脚本>'`，核对 `expectations` 和各步 `error`。
4. 交付说明逐条对应清单 id：改了什么、在哪个文件、哪个推演脚本验证了什么、哪里没验证。
5. **清单条目由作者在 Launcher 里关闭，你不关闭也无法关闭。** 改完的条目会显示“已改动，待确认”。`lens` 命令全部只读，不会移动作者的“已看过”基准。

推演用真实宿主运行时加桩模型，只证明规则、触发和状态变化；不证明角色演得自然，不替代真实模型试玩，交付时不要把“推演通过”写成体验通过。`lens` 随目标程序的 `worldpack.cmd` 提供；`lens` 命令不可用时说明程序版本过旧，改用 `validate` 并标出未做推演。

## 校验与实际运行

用目标程序的 `validate` 修正文件、引用和资产错误，再运行 `test`。读取退出码及 JSON；非零失败不得当成功。包契约诊断通常有 `details.diagnostics[].file/jsonPointer/message`，命令错误使用 `INVALID_REQUEST`。

世界包 `validate` 不执行玩法脚本，也不加载状态、活动、知识、前端与预设的完整宿主扩展。`test` 只编译适配，`assertionsExecuted: 0`；`compile` 的 JSON 制品不替代 Launcher 所需的完整源目录。预设另用 `preset validate <file>` 或包推荐的 `preset validate <file> --pack`，它们复用原生校验器，只检查字段／宏／正则语法，不证明风格效果。不要使用 `activate` 冒充完整游戏启动或断言执行。

把完成的源目录载入本版本 Launcher，在**新实例**中检查启动与扩展配置，然后按作品核心循环检查自然回应、信息差、可见选项、规则拒绝和成功后状态；需要续玩时再验证停止与重新启动。后台记忆整理、模型调用、外部服务沿用用户已有授权，未授权或缺少配置时完成其余工作并明确未验证项，不索取或记录明文凭证。

游戏源文件和程序运行环境分开保存；不改程序 runtime，不写历史数据目录，不把原始角色卡、凭证、数据库、模型请求和私人日志装进公开作品。后端玩法脚本是可信代码，前端沙箱不意味着任意游戏包都安全。

交付说明玩家能做什么、源目录位置、所需程序版本、校验结果、宿主启动和真实模型试玩各自的范围，以及已接受的限制。没有实际运行的步骤写成待验收步骤，不标成通过。用户没要求时不发布、推送或安装额外插件。
