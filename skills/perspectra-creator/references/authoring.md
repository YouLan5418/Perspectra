# 逐幕创作与接手

## 从作者给的地方开始

一句构想就可以开工。已有角色卡或大纲时，先从中找出玩家是谁、与哪些角色在哪里碰面、玩家能先做什么。例如作者写了「你和阿林在门廊发现一封信」，就可以直接讨论「玩家是随时能拆信，还是先得找到开信刀？」前者影响叙事节奏，后者让拿取物品成为有后果的选择。地点只补到足以让这一幕发生。已有包或工作区时先接手现状，再谈下一幕。

把角色、世界、玩法、剧情、美术和测试当作随时能回访的话题。已有材料足够时直接做，遇到取舍时每轮只问一两个答案会改变体验的问题。作者决定世界观、角色动机、各人可知的信息和剧情边界。把「希望阿林显得迟疑」记作试玩时观察的软目标，把「拿到开信刀才出现「展开便笺」选项」记作可验的硬规则，把「阿林是否解释来信」留给她自己选择。只有作者指定的固定演出才按固定结果制作和检查。

动手前，用一句话说清这轮要让玩家多做什么，记下要守住的边界和怎么算完成。自行用目标构建的帮助、当前包启用的规则和候选查询选择实现。若工具缺少某能力，先找能达到相同体验的做法；只有需要改变体验或已确认边界时才请作者取舍。

## 留下一份可接手的作品记录

多轮作品在作者控制的工程目录使用 [AUTHORING.md 模板](../assets/AUTHORING.md)，已有记录可就地补足。记录放在玩家源包和导出目录之外。工程可沿用原布局；只记相对位置和稳定 ID，让下位创作者能找到实际对象、清单、剧本和报告。包内定义仍由源文件维护。

1. 接手先读目标、已否决的方向、最近完成的步骤和待办。对照改动基线查看当前包、编辑器草稿和作者手改。基线可用已有提交加未提交差异，或上次保留的相关文件副本及摘要。导出摘要用于识别受测成品，不能用来推断草稿没有变化。
2. 对照稳定 ID 和实际内容，确认上次修改是否已经落地。已完成就接着做下一项；只完成一半就补差。保留作者改过的文案、选项和布局。用编辑器时，以最新读取的 `base` 合并涉及字段。直接写文件时，重读相关文件并保留改前版本或可恢复的差异。冲突若涉及作者意图，只问冲突的那一点。[编辑器协作](editor-handoff.md#与编辑器协作)
3. 每做完一个可独立核对的步骤，就更新「现在能玩什么」、相关 ID 和证据。中断后可从此处恢复。重跑用同一用例 ID、新的导出位置和报告，保留上一版证据。把本轮可玩的同一份导出交给作者，告诉作者从哪里开始、试哪个动作。作者的反馈直接开下一轮。咨询和试玩反馈中没有明确授权的扩改或发布，留作提议。

## 交接时怎样记证据

把作者确认的规则对应到清单里的稳定用例 ID，具体步骤和桩留在剧本里。先查目标程序 `worldpack.cmd --help`，需要导出或专项试玩时再查 `editor --help`。从当前作品正式导出到新目录，验收和交给作者试玩使用同一目录。作者记录、私有诊断和凭证留在玩家交付物之外。

| 实际运行 | 在作品记录里写什么 |
| --- | --- |
| `test` 或 `simulate` | `test` 只编译，包内断言声明仍待执行。单剧本 `simulate` 记该剧本验证了哪些行为、哪里失败或没验。 |
| `accept … --only <用例ID>` | 记所选 ID、各项结果和报告位置。即使退出 0，这也是筛选运行。 |
| `accept <导出目录> <清单.json>` | 保存程序生成的 JSON。核对 `scope: all`、`deliveryPassed: true` 和报告对应的导出目录摘要、编译包、前端（如有）、清单、各剧本和引擎构建身份。失败、未执行、证据不足分别照录原因。有一项输入变了，就把旧结果保留为历史，对要交付的版本重新全跑。 |
| 目标构建没有 `accept` | 记录缺少全量入口，依该构建帮助使用已提供的正式 `simulate` 或专项试玩，列出实际覆盖及仍待验内容。 |

验收记录可直接链接原报告，无须抄录全部摘要。工作笔记只表达意图、进度和指向证据的线索；运行事实以该版本的程序输出为准。桩推演验证规则，真实模型的角色表现和作者亲自试玩的感受分别记录，尚未进行就写「没验」。每轮交给作者一个可玩的变化及其试玩入口，或一个确实需要作者决定的问题。[清单与断言示例](gameplay.md#交付验收)
